Rework native review lane draft submission around generic Pi tool-call structured output

Plan artifact: docs/plans/LIV-218-rework-review-lane-pi-tool-submissions-generic-primitives.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

This plan supersedes docs/plans/LIV-204-pi-tool-enforced-review-lane-drafts.html. It treats the LIV-207 / PR #133 implementation direction as a rejected approach because that approach coupled native review-lane semantics into Scherzo core. The replacement direction is to consume the generic Pi-tool-call structured-output source primitive delivered by LIV-217 / PR #139, then keep all review-specific behavior in workflow, prompt, Pi extension, script, fixture, and smoke-test surfaces.

Purpose / Big Picture

Native Scherzo review lanes should finish by submitting their review_lane_draft artifact through a terminating Pi tool call named submit_review_lane_draft, not by printing final assistant JSON. An operator running the native review workflow should be able to inspect retained run artifacts and see that each specialist lane produced its structured draft from the generic Scherzo source type pi_tool_call, with the generic tool name recorded as provenance, and that review-domain checks were performed by the workflow-local review tooling.

After this change, malformed or missing review-lane drafts are easier to diagnose. If a lane merely prints a JSON-looking final response, Scherzo rejects that lane because the configured generic source requires a successful Pi tool call. If a lane calls the tool with JSON arguments that are syntactically valid but violate review-domain rules, scripts/scherzo-review rejects or normalizes the lane through the existing review validation path. The visible product goal is unchanged from the older plan: native review lanes submit drafts through an enforced terminating Pi tool call before synthesis consumes them.

Problem Framing and Constraints

Today, .scherzo/workflows/review-native.yml defines four native specialist agent lanes: lane_correctness, lane_test_quality, lane_idioms_maintainability, and lane_security_performance. Each lane has a structured_output block with JSON format, a lane-specific artifact name, required: true, validator: review_lane_draft, and a required-key schema. Because the current blocks do not set structured_output.source, they use Scherzo's default final-assistant-response source. The corresponding prompts under .scherzo/workflows/prompts/review-native-*.md also instruct the agent to return JSON only. That shape is too weak for the desired workflow contract: an agent can satisfy the lane by printing JSON as its final response instead of making the tool submission that operators want to enforce.

The important architectural constraint is that native review is a workflow domain, not a Scherzo core domain. Scherzo core should know how to retain structured output from a generic Pi tool call; it should not know what a review lane is, which lane ids are valid, or how to validate draft findings. Therefore this plan must not add a core tool_submission DSL, a core lane field, a production module such as src/scherzo/review_lane_draft_validator.gleam, review-lane-specific structured-output failure codes, or native-review-specific retry prompts. The only Scherzo core behavior this plan may rely on is the already-implemented generic LIV-217 primitive.

The word lane appears in two very different places, and this plan keeps them separate. A lane field inside a review_lane_draft JSON artifact is review-domain data and remains valid. A lane field in core workflow parsing, core step metadata, StructuredOutputSpec, or structured_output.source would be review-specific Scherzo core metadata and is out of scope.

Strategy Overview

Use the generic source configuration already available in Scherzo:

structured_output:
  format: json
  artifact_name: correctness_draft
  required: true
  source:
    type: pi_tool_call
    tool_name: submit_review_lane_draft
    require_single: true
    reject_sibling_tool_calls: true
  validator: review_lane_draft
  schema:
    type: object
    required:
      - schema_version
      - artifact_type
      - generated_at_utc
      - producer
      - lane
      - input_refs
      - draft_findings
      - review_notes
      - evidence_requests
      - self_check
      - remote_mutations

Apply the same source block to each review-native specialist lane while preserving the lane-specific artifact_name values and the review-domain schema. Add a workflow-local Pi extension under .pi/extensions/scherzo-review-lane-draft/ that exposes exactly one tool, submit_review_lane_draft. Pi auto-discovers project-local extensions from .pi/extensions/*/index.ts when it starts from the repository root, so no global installation is required. The native review workflow does not need a Scherzo core extension DSL; it relies on the normal project-local Pi extension load path used by review-native agent sessions.

The extension takes the review draft object as the tool's JSON arguments and terminates successfully without mutating files, posting comments, pushing branches, updating Linear, or contacting remote services. The tool name remains a workflow-local Pi extension name, not a Scherzo core concept. The extension must include prompt metadata (promptSnippet and promptGuidelines) so Pi advertises the tool to the model as an available terminating structured-output action.

Update the review-native prompts so each lane knows to call submit_review_lane_draft exactly once with object-valued JSON arguments. The prompts should stop telling lanes to end with final JSON. They may still describe the required artifact keys and the lane-specific focus, but the last instruction should be to use the tool call and not to submit final assistant JSON instead.

Keep deep review-domain validation in scripts/scherzo-review. The generic Scherzo primitive should only decide whether the configured tool call exists, whether it is a successful single call without sibling tool calls, whether its arguments are JSON object data, and whether the configured generic structured-output schema passes. The Pi extension performs only shallow transport and defense-in-depth checks listed later in this plan. Review-specific validation such as evidence references, repository-relative evidence paths, severity/category rules, finding-to-evidence linkage, final synthesis readiness, and historical manifest compatibility stays in scripts/scherzo-review and review-local tests.

This approach is proportionate because the reusable primitive already exists. The implementation can be a small reconfiguration and review-local extension/testing change rather than a new core feature. It also provides a falsifiable contract: a lane that prints a complete review_lane_draft final response but never calls submit_review_lane_draft must fail the lane's structured-output validation.

Alternatives Considered

Continuing LIV-207 / PR #133 as-is is rejected. The architecture problem is that PR #133 followed the old LIV-204 plan by adding review-specific concepts to Scherzo core. That makes one workflow's domain rules part of the generic workflow runtime, increases maintenance risk for unrelated workflows, and creates a precedent for adding more domain-specific branches to core. Do not merge, rebase, or continue PR #133 as the implementation path for this work.

Keeping final assistant JSON with stronger prompts is also rejected. Better wording might reduce accidental wrong submissions, but it does not enforce the operator-visible contract. The plan needs Scherzo to reject final JSON when the lane is configured to require a Pi tool call, and prompts alone cannot provide that guarantee.

Adding a new core tool_submission DSL or a core lane field is rejected. The already-available structured_output.source.type: pi_tool_call configuration expresses the generic behavior without naming review. A second DSL would duplicate the primitive and invite review-specific behavior to leak into parsing, metadata, retry, and error handling.

Putting all validation into the Pi extension is insufficient. The extension provides a workflow-local tool surface and shallow guardrails, but scripts/scherzo-review already owns review artifact validation, evidence verification, normalization, preflight, and legacy PR smoke behavior. Keeping those checks in the script avoids duplicating review-domain rules in the extension and keeps Scherzo core generic.

Risks and Countermeasures

The first risk is that the review-native workflow may appear to use the tool while Scherzo still accepts final assistant JSON. Counter this by writing the parsed-workflow source assertion and final-response-only rejection test before editing .scherzo/workflows/review-native.yml. In the unmodified workflow the test must fail because the parsed source is FinalResponseSource and final-response-only JSON is still accepted. After the YAML change, the same test must pass because the parsed source is PiToolCallSource and the final-response-only artifact fails with a generic missing-tool-call error mentioning submit_review_lane_draft.

The second risk is that agents are told to call submit_review_lane_draft, yet Pi never loads or advertises that tool. Counter this with a deterministic advertisement check in scripts/scherzo-review extension-schema-smoke --verify-pi-advertisement. The check must run from the repository root, prove that .pi/extensions/scherzo-review-lane-draft/index.ts is in Pi's project-local auto-discovery path, invoke the extension's /review-lane-draft-tool-info validation command in print mode, and fail before any prompt changes if the tool is missing from pi.getAllTools(). The expected missing-tool diagnostic is REVIEW_LANE_DRAFT_TOOL_ADVERTISED={"status":"missing","tool_name":"submit_review_lane_draft"} followed by a nonzero smoke exit.

The third risk is that prompt wording, extension shallow checks, and scripts/scherzo-review deep validation drift apart. Counter this by making .pi/extensions/scherzo-review-lane-draft/tool-contract.v1.json the shared review-local extension contract for the tool name, required top-level keys, allowed lane ids, and explicitly duplicated defense-in-depth constants. The smoke command must use the same checked-in fixture directory to exercise both the extension shallow phase and the script deep-validation phase, so a fixture such as absolute-path.arguments.json can intentionally pass the extension phase but fail the script phase.

The fourth risk is accidentally reintroducing review-specific Scherzo core changes while making tests pass. Counter this by making the implementation checklist explicitly exclude production files under src/scherzo/ except for consuming existing generic configuration in tests. If a stale implementation branch contains src/scherzo/review_lane_draft_validator.gleam, review-lane-specific error codes, native-review retry prompt code, or a core workflow lane field, delete those branch changes instead of forward-porting them.

The fifth risk is losing useful provenance in preflight and smoke manifests. Counter this by reading the generic step metadata Scherzo already emits, especially source_type, source_tool_name, structured_output_status, artifact_name, and the structured artifact path, and copying that into review-local manifests. Do not add review-specific fields to Scherzo attempt metadata. Put review-specific validation results in script-owned fields such as review_local_validation, evidence_verdicts, or existing lane result fields.

The sixth risk is that the native review contract spike and curated legacy PR smoke still exercise the old final-response path. Counter this by updating .scherzo/workflows/review-native-contract-spike.yml, its review-native-contract-*.md prompts, and the native preflight/legacy smoke assertions so at least one positive and one negative scenario prove the Pi-tool-call source path.

Context and Orientation

Scherzo workflows are checked in under .scherzo/workflows/. The native review workflow is .scherzo/workflows/review-native.yml. It prepares a review brief, runs four specialist agent lanes in parallel, verifies each lane's evidence, normalizes each lane result, synthesizes a final review, applies feedback, validates final artifacts, and publishes in dry-run mode.

The four lane prompts are .scherzo/workflows/prompts/review-native-correctness.md, .scherzo/workflows/prompts/review-native-test-quality.md, .scherzo/workflows/prompts/review-native-idioms-maintainability.md, and .scherzo/workflows/prompts/review-native-security-performance.md. The current lane prompts tell agents to return JSON only; this plan changes that instruction to a Pi tool call.

The review artifact helper is scripts/scherzo-review. It is intentionally outside the Scherzo runtime. It prepares native review inputs, validates review artifacts, verifies lane evidence, normalizes lane results, runs native preflight scenarios, and runs curated legacy PR smoke checks. Domain-specific validation such as review_lane_draft shape and evidence rules belongs here.

The generic structured-output primitive lives in Scherzo core and is already a prerequisite, not part of this plan's implementation. The relevant files observed in the current tree are src/scherzo/structured_output_source.gleam, which parses FinalResponseSource and PiToolCallSource; src/scherzo/structured_output.gleam, which validates final-response or Pi-tool-call sources; and tests such as test/workflow_dag_test.gleam, test/structured_output_test.gleam, and test/workflow_run_test.gleam, which exercise the generic behavior. Those files are context for the prerequisite and for test assertions; this plan does not require production edits in src/scherzo/.

A Pi extension is project-local TypeScript code that exposes tools to the Pi agent runtime. Pi auto-discovers .pi/extensions/*.ts and .pi/extensions/*/index.ts when it starts from the repository root, and extensions register tools with pi.registerTool(). This plan creates .pi/extensions/scherzo-review-lane-draft/index.ts for the review lane draft submission tool plus .pi/extensions/scherzo-review-lane-draft/tool-contract.v1.json for the shared review-local contract. The extension is allowed to know about the review draft's shallow shape because it is checked into the workflow repository, not into Scherzo core.

import { defineTool, type ExtensionAPI } from "@mariozechner/pi-coding-agent";
import { StringEnum } from "@mariozechner/pi-ai";
import { Type, type Static } from "typebox";

export const SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME = "submit_review_lane_draft";
const allowedLaneIds = ["correctness", "test-quality", "idioms-maintainability", "security-performance"] as const;

export const submitReviewLaneDraftParameters = Type.Object({
  schema_version: Type.Number({ description: "Must be 1." }),
  artifact_type: Type.String({ description: "Must be review_lane_draft." }),
  generated_at_utc: Type.String(),
  producer: Type.Object({}, { additionalProperties: true }),
  lane: Type.Object({
    id: StringEnum(allowedLaneIds),
    name: Type.String(),
    category: Type.String(),
    version: Type.String(),
  }, { additionalProperties: true }),
  input_refs: Type.Array(Type.Unknown()),
  draft_findings: Type.Array(Type.Unknown()),
  review_notes: Type.Array(Type.Unknown()),
  evidence_requests: Type.Array(Type.Unknown()),
  self_check: Type.Object({}, { additionalProperties: true }),
  remote_mutations: StringEnum(["none"] as const),
}, { additionalProperties: true });

export type SubmitReviewLaneDraftInput = Static<typeof submitReviewLaneDraftParameters>;

export function shallowValidateReviewLaneDraft(params: SubmitReviewLaneDraftInput): string[] {
  const errors: string[] = [];
  if (params.schema_version !== 1) errors.push("schema_version must be 1");
  if (params.artifact_type !== "review_lane_draft") errors.push("artifact_type must be review_lane_draft");
  if (params.remote_mutations !== "none") errors.push("remote_mutations must be none");
  if (!params.lane || !allowedLaneIds.includes(params.lane.id as typeof allowedLaneIds[number])) {
    errors.push("lane.id must be one of the native review lane ids");
  }
  return errors;
}

const submitReviewLaneDraftTool = defineTool({
  name: SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME,
  label: "Submit Review Lane Draft",
  description: "Submit the final review_lane_draft object for a native Scherzo review lane. This tool has no side effects.",
  promptSnippet: "Submit a native review_lane_draft object as the final terminating review-lane artifact",
  promptGuidelines: [
    "Use submit_review_lane_draft exactly once as the final action for native Scherzo review lanes.",
    "Do not print review_lane_draft as final assistant JSON; pass the object as submit_review_lane_draft arguments instead.",
    "Do not call sibling tools in the same tool-call batch as submit_review_lane_draft.",
  ],
  parameters: submitReviewLaneDraftParameters,
  async execute(_toolCallId, params) {
    const errors = shallowValidateReviewLaneDraft(params);
    if (errors.length > 0) {
      throw new Error(`invalid review_lane_draft: ${errors.join("; ")}`);
    }
    return {
      content: [{ type: "text", text: `Accepted review_lane_draft for ${params.lane.id}` }],
      details: {
        artifact_type: "review_lane_draft_tool_receipt",
        tool_name: SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME,
        lane_id: params.lane.id,
        remote_mutations: "none",
      },
