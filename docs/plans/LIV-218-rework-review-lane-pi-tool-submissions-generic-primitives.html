Rework native review lane draft submission around generic Pi tool-call structured output

Plan artifact: docs/plans/LIV-218-rework-review-lane-pi-tool-submissions-generic-primitives.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

This plan supersedes docs/plans/LIV-204-pi-tool-enforced-review-lane-drafts.html. It treats the LIV-207 / PR #133 implementation direction as a rejected approach because that approach coupled native review-lane semantics into Scherzo core. The replacement direction is to consume the generic Pi-tool-call structured-output source primitive delivered by LIV-217 / PR #139, then keep all review-specific behavior in workflow, prompt, Pi extension, script, fixture, and smoke-test surfaces.

Purpose / Big Picture

Native Scherzo review lanes should finish by submitting their review_lane_draft artifact through a terminating Pi tool call named submit_review_lane_draft, not by printing final assistant JSON. An operator running the native review workflow should be able to inspect retained run artifacts and see that each specialist lane produced its structured draft from the generic Scherzo source type pi_tool_call, with the generic tool name recorded as provenance, and that review-domain checks were performed by the workflow-local review tooling.

After this change, malformed or missing review-lane drafts are easier to diagnose. If a lane merely prints a JSON-looking final response, Scherzo rejects that lane because the configured generic source requires a successful Pi tool call. If a lane calls the tool with JSON arguments that are syntactically valid but violate review-domain rules, scripts/scherzo-review rejects or normalizes the lane through the existing review validation path. The visible product goal is unchanged from the older plan: native review lanes submit drafts through an enforced terminating Pi tool call before synthesis consumes them.

Problem Framing and Constraints

Today, .scherzo/workflows/review-native.yml defines four native specialist agent lanes: lane_correctness, lane_test_quality, lane_idioms_maintainability, and lane_security_performance. Each lane has a structured_output block with JSON format, a lane-specific artifact name, required: true, validator: review_lane_draft, and a required-key schema. Because the current blocks do not set structured_output.source, they use Scherzo's default final-assistant-response source. The corresponding prompts under .scherzo/workflows/prompts/review-native-*.md also instruct the agent to return JSON only. That shape is too weak for the desired workflow contract: an agent can satisfy the lane by printing JSON as its final response instead of making the tool submission that operators want to enforce.

The important architectural constraint is that native review is a workflow domain, not a Scherzo core domain. Scherzo core should know how to retain structured output from a generic Pi tool call; it should not know what a review lane is, which lane ids are valid, or how to validate draft findings. Therefore this plan must not add a core tool_submission DSL, a core lane field, a production module such as src/scherzo/review_lane_draft_validator.gleam, review-lane-specific structured-output failure codes, or native-review-specific retry prompts. The only Scherzo core behavior this plan may rely on is the already-implemented generic LIV-217 primitive.

The word lane appears in two very different places, and this plan keeps them separate. A lane field inside a review_lane_draft JSON artifact is review-domain data and remains valid. A lane field in core workflow parsing, core step metadata, StructuredOutputSpec, or structured_output.source would be review-specific Scherzo core metadata and is out of scope.

Strategy Overview

Use the generic source configuration already available in Scherzo:

structured_output:
  format: json
  artifact_name: correctness_draft
  required: true
  source:
    type: pi_tool_call
    tool_name: submit_review_lane_draft
    require_single: true
    reject_sibling_tool_calls: true
  validator: review_lane_draft
  schema:
    type: object
    required:
      - schema_version
      - artifact_type
      - generated_at_utc
      - producer
      - lane
      - input_refs
      - draft_findings
      - review_notes
      - evidence_requests
      - self_check
      - remote_mutations

Apply the same source block to each review-native specialist lane while preserving the lane-specific artifact_name values and the review-domain schema. Add a project-local Pi extension under .pi/extensions/scherzo-review-lane-draft/ for the submit_review_lane_draft tool. Pi auto-discovers project-local extensions from .pi/extensions/*/index.ts when it starts from a repository checkout, so the file can be loaded by unrelated implementation, execplan, or human Pi sessions too. To prevent accidental global tool exposure, the extension must register and advertise submit_review_lane_draft only when SCHERZO_WORKFLOW_ID is review-native or review-native-contract-spike. Outside those workflow ids the extension may expose diagnostic commands for smoke tests, but the review draft submission tool must be absent from Pi's active tool list. The native review workflow does not need a Scherzo core extension DSL; it relies on the normal project-local Pi extension load path plus workflow-scoped registration.

The extension takes the review draft object as the tool's JSON arguments and terminates successfully without mutating files, posting comments, pushing branches, updating Linear, or contacting remote services. The tool name remains a workflow-scoped Pi extension name, not a Scherzo core concept. The extension must include prompt metadata (promptSnippet and promptGuidelines) so Pi advertises the tool to the model as an available terminating structured-output action only inside the review-native workflow scope.

Update the review-native prompts so each lane knows to call submit_review_lane_draft exactly once with object-valued JSON arguments. The prompts should stop telling lanes to end with final JSON. They may still describe the required artifact keys and the lane-specific focus, but the last instruction should be to use the tool call and not to submit final assistant JSON instead.

Keep deep review-domain validation behind the existing validator: review_lane_draft path in scripts/scherzo-review. The generic Scherzo primitive should only decide whether the configured tool call exists, whether it is a successful single call without sibling tool calls, whether its arguments are JSON object data, and whether the configured generic structured-output schema passes. The Pi extension performs only shallow transport and defense-in-depth checks listed later in this plan. Review-specific validation such as evidence references, repository-relative evidence paths, severity/category rules, finding-to-evidence linkage, final synthesis readiness, and historical manifest compatibility stays in scripts/scherzo-review and review-local tests. This slice explicitly accepts the current debt that validator: review_lane_draft is still a hard-coded StructuredOutputValidator case in Scherzo core that shells out to scripts/scherzo-review; removing or generalizing that named-validator coupling is a follow-up and not part of this plan.

This approach is proportionate because the reusable primitive already exists. The implementation can be a small reconfiguration and review-local extension/testing change rather than a new core feature. It also provides a falsifiable contract: a lane that prints a complete review_lane_draft final response but never calls submit_review_lane_draft must fail the lane's structured-output validation.

Alternatives Considered

Continuing LIV-207 / PR #133 as-is is rejected. The architecture problem is that PR #133 followed the old LIV-204 plan by adding review-specific concepts to Scherzo core. That makes one workflow's domain rules part of the generic workflow runtime, increases maintenance risk for unrelated workflows, and creates a precedent for adding more domain-specific branches to core. Do not merge, rebase, or continue PR #133 as the implementation path for this work.

Keeping final assistant JSON with stronger prompts is also rejected. Better wording might reduce accidental wrong submissions, but it does not enforce the operator-visible contract. The plan needs Scherzo to reject final JSON when the lane is configured to require a Pi tool call, and prompts alone cannot provide that guarantee.

Adding a new core tool_submission DSL or a core lane field is rejected. The already-available structured_output.source.type: pi_tool_call configuration expresses the generic behavior without naming review. A second DSL would duplicate the primitive and invite review-specific behavior to leak into parsing, metadata, retry, and error handling.

Putting all validation into the Pi extension is insufficient. The extension provides a workflow-scoped tool surface and shallow guardrails, but scripts/scherzo-review already owns review artifact validation, evidence verification, normalization, preflight, and legacy PR smoke behavior. Keeping those checks in the script avoids duplicating review-domain rules in the extension and keeps Scherzo core generic.

Risks and Countermeasures

The first risk is that the review-native workflow may appear to use the tool while Scherzo still accepts final assistant JSON. Counter this by writing the parsed-workflow source assertion and final-response-only rejection test before editing .scherzo/workflows/review-native.yml. In the unmodified workflow the test must fail because the parsed source is FinalResponseSource and final-response-only JSON is still accepted. After the YAML change, the same test must pass because the parsed source is PiToolCallSource and the final-response-only artifact fails with a generic missing-tool-call error mentioning submit_review_lane_draft.

The second risk is that agents are told to call submit_review_lane_draft, yet Pi never loads, activates, or correctly scopes that tool. Counter this with a deterministic advertisement check in scripts/scherzo-review extension-schema-smoke --verify-pi-advertisement. The check must run from the repository root using the same cwd, environment shape, and Pi launch path that a Scherzo-managed workflow agent step uses; the positive path must set SCHERZO_WORKFLOW_ID=review-native-contract-spike or review-native, and a negative path must run with an unrelated or absent workflow id. It must invoke the extension's /review-lane-draft-tool-info validation command in print mode and prove the tool is present in pi.getActiveTools() for the review workflow scope, not merely present in pi.getAllTools(). It must also fail if submit_review_lane_draft is active outside the review workflow ids. The expected missing-tool diagnostic is REVIEW_LANE_DRAFT_TOOL_ADVERTISED={"status":"inactive","tool_name":"submit_review_lane_draft"} followed by a nonzero smoke exit.

The third risk is that prompt wording, the JSON contract file, the TypeScript TypeBox schema, shallowValidateReviewLaneDraft, the tool execute result, and scripts/scherzo-review deep validation drift apart. Counter this by making .pi/extensions/scherzo-review-lane-draft/tool-contract.v1.json the shared review-local extension contract for the tool name, required top-level keys, allowed lane ids, and explicitly duplicated defense-in-depth constants, and by adding an extension-runtime fixture phase that imports or invokes the real registered TypeScript tool. The smoke command must use the same checked-in fixture directory to exercise the TypeBox parameter schema, shallowValidateReviewLaneDraft, successful execute results with terminate: true, and the script deep-validation phase, so a fixture such as absolute-path.arguments.json can intentionally pass the extension runtime phase but fail the script phase.

The fourth risk is accidentally reintroducing review-specific Scherzo core changes while making tests pass. Counter this by making the implementation checklist explicitly exclude production files under src/scherzo/ except for consuming existing generic configuration in tests and the existing local native preflight fixture runner's result-shape adaptation in src/scherzo/local_workflow_run.gleam. If a stale implementation branch contains src/scherzo/review_lane_draft_validator.gleam, review-lane-specific error codes, native-review retry prompt code, or a core workflow lane field, delete those branch changes instead of forward-porting them.

The fifth risk is losing useful provenance in preflight and smoke manifests. Counter this by reading the generic step metadata Scherzo already emits, especially source_type, source_tool_name, structured_output_status, artifact_name, and the structured artifact path, and copying that into review-local manifests. Do not add review-specific fields to Scherzo attempt metadata. Put review-specific validation results in script-owned fields such as review_local_validation, evidence_verdicts, or existing lane result fields.

The sixth risk is that the native review contract spike and curated legacy PR smoke still exercise the old final-response path. Counter this by updating .scherzo/workflows/review-native-contract-spike.yml, its review-native-contract-*.md prompts, and the native preflight/legacy smoke assertions so at least one positive and one negative scenario prove the Pi-tool-call source path.

Context and Orientation

Scherzo workflows are checked in under .scherzo/workflows/. The native review workflow is .scherzo/workflows/review-native.yml. It prepares a review brief, runs four specialist agent lanes in parallel, verifies each lane's evidence, normalizes each lane result, synthesizes a final review, applies feedback, validates final artifacts, and publishes in dry-run mode.

The four lane prompts are .scherzo/workflows/prompts/review-native-correctness.md, .scherzo/workflows/prompts/review-native-test-quality.md, .scherzo/workflows/prompts/review-native-idioms-maintainability.md, and .scherzo/workflows/prompts/review-native-security-performance.md. The contract-spike prompts are .scherzo/workflows/prompts/review-native-contract-valid.md, .scherzo/workflows/prompts/review-native-contract-malformed.md, and .scherzo/workflows/prompts/review-native-contract-failed.md. The current lane prompts tell agents to return JSON only; this plan changes that instruction to a Pi tool call.

The review artifact helper is scripts/scherzo-review. It is intentionally outside the Scherzo runtime. It prepares native review inputs, validates review artifacts, verifies lane evidence, normalizes lane results, runs native preflight scenarios, and runs curated legacy PR smoke checks. Domain-specific validation such as review_lane_draft shape and evidence rules belongs here.

The generic structured-output primitive lives in Scherzo core and is already a prerequisite, not part of this plan's implementation. The relevant files observed in the current tree are src/scherzo/structured_output_source.gleam, which parses FinalResponseSource and PiToolCallSource; src/scherzo/structured_output.gleam, which validates final-response or Pi-tool-call sources; and tests such as test/workflow_dag_test.gleam, test/structured_output_test.gleam, and test/workflow_run_test.gleam, which exercise the generic behavior. Those files are context for the prerequisite and for test assertions; this plan does not change the generic primitive. The only src/scherzo/ implementation edit discovered as necessary is in src/scherzo/local_workflow_run.gleam, where existing local native preflight fixture agents must emit tool-call submissions so fixture runs exercise the configured generic source.

A Pi extension is project-local TypeScript code that can expose tools to the Pi agent runtime. Pi auto-discovers .pi/extensions/*.ts and .pi/extensions/*/index.ts when it starts from the repository root, and extensions register tools with pi.registerTool(). This plan creates .pi/extensions/scherzo-review-lane-draft/index.ts for the review lane draft submission tool plus .pi/extensions/scherzo-review-lane-draft/tool-contract.v1.json for the shared review-local contract. Because project-local auto-discovery is broader than one workflow, the extension must gate the actual tool registration on SCHERZO_WORKFLOW_ID. The extension is allowed to know about the review draft's shallow shape because it is checked into the workflow repository, not into Scherzo core.

Preconditions and Verified Facts

The implementation must start from a branch where LIV-217 / PR #139 is merged. The required generic interface is a structured_output.source map with type: pi_tool_call, a tool_name string, require_single: true, and reject_sibling_tool_calls: true. The generic parser rejects unsupported source types and invalid tool names. The generic validator validates the arguments JSON from the matching Pi tool call as the structured artifact payload and records source metadata such as source_type: "pi_tool_call" and source_tool_name in retained step artifacts.

The existing native review workflow path is .scherzo/workflows/review-native.yml. The current lane artifact names are correctness_draft, test_quality_draft, idioms_maintainability_draft, and security_performance_draft. Keep those names so downstream verify_*_evidence and normalize_* command steps can continue reading from their lane-specific structured artifact paths.

The review helper path is scripts/scherzo-review. It already contains review-domain constants for specialist lanes and native preflight behavior, including correctness, test-quality, idioms-maintainability, and security-performance. It also validates preflight and legacy PR smoke manifests. Extend those review-local manifest checks as needed rather than adding Scherzo core fields.

The current workspace had no source-control changes before authoring this plan. The repository also had no existing .pi/extensions directory during plan discovery, so the extension path in this plan is new.

import { defineTool, type ExtensionAPI } from "@mariozechner/pi-coding-agent";
import { StringEnum } from "@mariozechner/pi-ai";
import { Type, type Static } from "typebox";

export const SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME = "submit_review_lane_draft";
export const REVIEW_LANE_DRAFT_WORKFLOW_IDS = ["review-native", "review-native-contract-spike"] as const;
const allowedLaneIds = ["correctness", "test-quality", "idioms-maintainability", "security-performance"] as const;

export function shouldRegisterReviewLaneDraftTool(workflowId = process.env.SCHERZO_WORKFLOW_ID || ""): boolean {
  return REVIEW_LANE_DRAFT_WORKFLOW_IDS.includes(workflowId as typeof REVIEW_LANE_DRAFT_WORKFLOW_IDS[number]);
}

export const submitReviewLaneDraftParameters = Type.Object({
  schema_version: Type.Number({ description: "Must be 1." }),
  artifact_type: Type.String({ description: "Must be review_lane_draft." }),
  generated_at_utc: Type.String(),
  producer: Type.Object({}, { additionalProperties: true }),
  lane: Type.Object({
    id: StringEnum(allowedLaneIds),
    name: Type.String(),
    category: Type.String(),
    version: Type.String(),
  }, { additionalProperties: true }),
  input_refs: Type.Array(Type.Unknown()),
  draft_findings: Type.Array(Type.Unknown()),
  review_notes: Type.Array(Type.Unknown()),
  evidence_requests: Type.Array(Type.Unknown()),
  self_check: Type.Object({}, { additionalProperties: true }),
  remote_mutations: StringEnum(["none"] as const),
}, { additionalProperties: true });

export type SubmitReviewLaneDraftInput = Static<typeof submitReviewLaneDraftParameters>;

export function shallowValidateReviewLaneDraft(params: SubmitReviewLaneDraftInput): string[] {
  const errors: string[] = [];
  if (params.schema_version !== 1) errors.push("schema_version must be 1");
  if (params.artifact_type !== "review_lane_draft") errors.push("artifact_type must be review_lane_draft");
  if (params.remote_mutations !== "none") errors.push("remote_mutations must be none");
  if (!params.lane || !allowedLaneIds.includes(params.lane.id as typeof allowedLaneIds[number])) {
    errors.push("lane.id must be one of the native review lane ids");
  }
  return errors;
}

export const submitReviewLaneDraftTool = defineTool({
  name: SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME,
  label: "Submit Review Lane Draft",
  description: "Submit the final review_lane_draft object for a native Scherzo review lane. This tool has no side effects.",
  promptSnippet: "Submit a native review_lane_draft object as the final terminating review-lane artifact",
  promptGuidelines: [
    "Use submit_review_lane_draft exactly once as the final action for native Scherzo review lanes.",
    "Do not print review_lane_draft as final assistant JSON; pass the object as submit_review_lane_draft arguments instead.",
    "Do not call sibling tools in the same tool-call batch as submit_review_lane_draft.",
  ],
  parameters: submitReviewLaneDraftParameters,
  async execute(_toolCallId, params) {
    const errors = shallowValidateReviewLaneDraft(params);
    if (errors.length > 0) {
      throw new Error(`invalid review_lane_draft: ${errors.join("; ")}`);
    }
    return {
      content: [{ type: "text", text: `Accepted review_lane_draft for ${params.lane.id}` }],
      details: {
        artifact_type: "review_lane_draft_tool_receipt",
        tool_name: SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME,
        lane_id: params.lane.id,
        remote_mutations: "none",
      },
      terminate: true,
    };
  },
});

export default function scherzoReviewLaneDraftExtension(pi: ExtensionAPI) {
  const workflowId = process.env.SCHERZO_WORKFLOW_ID || "";
  const enabledForWorkflow = shouldRegisterReviewLaneDraftTool(workflowId);
  if (enabledForWorkflow) {
    pi.registerTool(submitReviewLaneDraftTool);
  }

  pi.registerCommand("review-lane-draft-tool-info", {
    description: "Print whether submit_review_lane_draft is active in this Pi session.",
    handler: async () => {
      const activeToolNames = new Set(pi.getActiveTools());
      const tool = pi.getAllTools().find((candidate) => candidate.name === SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME);
      const active = activeToolNames.has(SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME);
      const status = active ? "active" : enabledForWorkflow ? "inactive" : "disabled_workflow_scope";
      console.log(`REVIEW_LANE_DRAFT_TOOL_ADVERTISED=${JSON.stringify({
        status,
        tool_name: SUBMIT_REVIEW_LANE_DRAFT_TOOL_NAME,
        workflow_id: workflowId || null,
        source: tool?.sourceInfo?.source || null,
        path: tool?.sourceInfo?.path || null,
      })}`);
      if (enabledForWorkflow && !active) {
        throw new Error("submit_review_lane_draft was registered for this workflow scope but is not active");
      }
      if (!enabledForWorkflow && active) {
        throw new Error("submit_review_lane_draft is active outside review-native workflow scopes");
      }
    },
  });
}

Testing and Falsifiability

The main falsifying test is final-response-only rejection. The test should use a syntactically valid review_lane_draft JSON object as the final assistant response and no tool calls. If validation succeeds after .scherzo/workflows/review-native.yml has been edited, this plan is wrong because the workflow did not actually enforce the Pi tool-call source. The expected result is a generic structured-output tool-call error, not a review-specific error code.

The red phase is mandatory. Before workflow edits, test/review_native_workflow_test.gleam must fail because the existing workflow still parses as FinalResponseSource and accepts final-response-only JSON. After adding the source maps, the same test must pass. This sequence proves that the test detected the old behavior rather than merely confirming a hand-built spec.

The source-configuration test should parse the checked-in .scherzo/workflows/review-native.yml rather than constructing a spec by hand. It should fail if any specialist lane falls back to FinalResponseSource, uses a tool name other than submit_review_lane_draft, allows multiple matching calls, allows sibling tool calls, or drops required: true.

The successful-tool-call test should create a ToolCallSubmission named submit_review_lane_draft with object-valued JSON arguments, status success, and sibling count 1. It should validate through the parsed lane spec and return StructuredOutputPresent. This proves the workflow consumes the generic primitive rather than relying on final response text.

The extension schema smoke tests should run valid and invalid fixture files through the checked-in extension contract, the real TypeScript extension runtime, and the script-owned deep validator. Valid fixtures must pass the TypeBox parameter schema, shallowValidateReviewLaneDraft, the tool execute path with terminate: true, and script deep validation. missing-lane.arguments.json and wrong-artifact-type.arguments.json must fail the extension runtime and script deep validation. absolute-path.arguments.json must pass the extension runtime phase and fail the script deep phase. That split is falsifying: if the extension rejects absolute paths, validation boundary drift has reappeared; if the script accepts absolute paths, review-domain path validation has regressed; if Python-only contract checks pass while the TypeScript runtime fails, the contract and implementation have drifted.

The Pi advertisement check is falsifying for the rollout path. If .pi/extensions/scherzo-review-lane-draft/index.ts is not auto-discovered from the repository root, if the tool is missing from pi.getActiveTools() under SCHERZO_WORKFLOW_ID=review-native-contract-spike or review-native, or if it is active under an unrelated or absent workflow id, scripts/scherzo-review extension-schema-smoke --verify-pi-advertisement must fail before prompt changes. The implementation must not weaken prompts back to final JSON to paper over a missing or incorrectly scoped tool.

The native preflight tests should exercise at least a no-finding success scenario and a malformed-output containment scenario. The manifest must fail readiness if lane provenance says final_response, if the tool name is missing or wrong, if review-local validation did not run, or if any lane result is synthesized from a missing draft without recording the failure.

Curated legacy PR smoke should be run where practical because it exercises the real native workflow against prior pull-request shapes. It is acceptable to run a small curated subset during implementation, such as PR 116 for a small clean change, then run the broader curated set before declaring the work ready. The smoke is falsifying if it passes while provenance still shows final-response sources; update assertions so that cannot happen.

Rollout, Recovery, and Idempotence

This change is local to the checked-in native review workflow and review helper surfaces. It should be rolled out as one implementation branch after LIV-217 / PR #139 is present. Because the workflow is used by dogfood review automation, keep all changes dry-run and no-mutation by default. Rollback is straightforward. Reverting the implementation commit returns review-native lanes to final-response structured output and removes the extension path. No persisted production data migration is involved. Retained run artifacts from old and new runs may differ in source provenance; scripts that read retained artifacts should tolerate both during the transition only when reading historical runs. Most implementation steps are idempotent. Re-running extension smoke, Gleam tests, native preflight, and legacy smoke overwrites or recreates files under tmp/.
