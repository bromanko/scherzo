Add interactive feedback capture to ExecPlan PR review previews

Plan artifact: docs/plans/LIV-193-interactive-execplan-pr-review-feedback-ui.html 22 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Reviewers currently can run scripts/scherzo-execplan-review 123 to download the single ExecPlan artifact changed by a GitHub pull request and open a local preview, but any review feedback still has to be translated manually back into GitHub's PR review UI. After this change, a reviewer can run an explicit interactive review command for an HTML ExecPlan, click the rendered block they want to discuss, draft comments in a local side panel, edit or delete those drafts, and then deliberately submit the feedback to GitHub from the local tool.

The visible success case is a reviewer opening a locally served ExecPlan PR artifact, clicking an element with class commentable, entering a comment, seeing that draft persist in the review drawer, and pressing a Submit button that creates GitHub PR review feedback against docs/plans/<plan>.html. No GitHub comments are created before that Submit action.

Problem Framing and Constraints

The operator problem is review friction. ExecPlans are intended to be reviewed in their rendered HTML form, where headings, prose blocks, and checklist items are easier to scan than a raw diff. GitHub review comments, however, must be anchored to file paths and line numbers in the PR diff. Today the reviewer has to inspect the rendered HTML, find the matching source line manually, and re-enter feedback in GitHub. That discourages precise feedback on the plan's actual visible structure.

The first interactive version is intentionally limited to docs/plans/*.html artifacts. Markdown plans may still be downloaded and previewed, but Markdown comment capture is out of scope because the rendered Markdown line numbers do not directly identify the PR artifact line that GitHub can comment on. Non-ExecPlan PRs and PRs that change zero or multiple plan artifacts remain rejected by the existing single-plan validation behavior.

The implementation must keep remote mutation explicit and safe. Browser JavaScript must never receive a GitHub token or run gh; the Python localhost server performs all GitHub operations by invoking gh api on the reviewer's machine. The server must bind only to loopback, require a random per-session token for every API endpoint, retain local draft artifacts under tmp/scherzo-execplan-review/, and make submission a deliberate browser action.

Strategy Overview

The right-sized approach is to extend the existing Python helper instead of introducing a web framework or a separate service. The current script already knows how to infer the repository, fetch PR metadata, enumerate changed files, download the plan artifact, render Markdown for preview, open a browser, and store local files under tmp/scherzo-execplan-review/. The implementation should extract the script into an importable Python module for tests, keep the wrapper command name, and add a small standard-library http.server based review server for HTML plans.

Before the browser UI depends on any GitHub line-coordinate shape, the implementation must prove the GitHub create-review contract in a controlled scratch PR. The expected contract is GitHub's REST endpoint POST repos/{owner}/{repo}/pulls/{pull_number}/reviews with commit_id, event: "COMMENT", and a comments array whose entries contain path, body, side: "RIGHT", and line. The fake-gh tests and the final submit code must use those exact field names only after the scratch-PR probe proves GitHub accepts them. If GitHub rejects that shape, implementation must stop, update this ExecPlan's Decision Log with the accepted coordinate model, and change the mapping helpers before any browser capture or submission work continues.

The interactive path serves a sanitized copy of the downloaded HTML through http://127.0.0.1:<port>/ and injects local CSS and JavaScript. The injected JavaScript listens for clicks on .commentable elements, reads data-comment-id and related DOM metadata, writes drafts to server-side drafts.json, and renders a side drawer for pending comments. At submit time the server maps each data-comment-id back to the line in the original downloaded HTML source, filters those lines through the PR diff so only GitHub-commentable lines are sent inline, and submits one GitHub review containing all eligible inline comments using the contract verified in the first milestone. Drafts whose source line cannot be mapped, or whose line is not present on the right side of the PR diff, are included in the review body as a fallback summary rather than being silently dropped.

This avoids a larger application architecture. There is no persistent daemon, no database, no OAuth flow, and no dependency beyond Python's standard library and the existing gh CLI. The tradeoff is that the browser UI is deliberately simple: click a block, type plain text, manage a list of drafts, and submit.

Alternatives Considered

The simplest alternative is to keep the existing file:// preview and ask reviewers to copy line references into GitHub manually. That has almost no implementation risk, but it does not solve the concrete review friction and does not produce structured, line-anchored PR feedback.

Another option is a browser extension or GitHub App that overlays comments directly on GitHub's rendered files. That would be much larger, would require a distribution and authentication story, and would not fit the local helper workflow that already exists in this repository.

A third option is to create one PR issue comment containing all feedback and never attempt inline comments. That would avoid GitHub's diff-line restrictions, but it would lose the most useful review affordance: comments attached to the relevant plan source locations. The chosen design attempts inline comments when the mapping is valid and falls back to a summary only for locations GitHub cannot accept.

A fourth option is to use GitHub's older diff position coordinate if line and side are rejected. That option is deliberately deferred rather than silently chosen because the create-review API now documents line-based comments for current clients, and building around a deprecated or incorrect coordinate would make the local UI appear to work while posting fails. The first milestone is the gate that proves whether line and side are valid for this repository's workflow.

Risks and Countermeasures

The main usability risk is incorrect line mapping. The countermeasure is to treat data-comment-id as the stable key, scan the original downloaded HTML source for the exact attribute, and unit test the mapping with fixture HTML. Browser-provided data-source-line is useful context but not authoritative.

The main GitHub API risk is that the inline review payload contract differs from the expected line and side shape, or that inline comments can only target lines that exist in the PR diff. The countermeasure is an explicit API-contract milestone before UI work: use a controlled scratch PR to submit one test review to POST repos/{owner}/{repo}/pulls/{pull_number}/reviews with commit_id, event: "COMMENT", and one comment containing path, body, side: "RIGHT", and line. Only after GitHub accepts that payload may the implementation keep right_side_commentable_lines as the source-line eligibility helper. The diff parser still filters to right-side source line numbers that appear in added or context lines. Comments outside those lines go into the review body fallback. If GitHub rejects the review request later, the tool writes submit-error.json, keeps drafts.json, and asks the reviewer to explicitly confirm a summary-only retry before making a different remote mutation.

The main security risk is serving PR-supplied HTML locally with injected JavaScript. The countermeasure is defense in depth and must be implemented exactly, not as a regex-only best effort. The server binds only to 127.0.0.1; every JSON endpoint requires a random session token; browser JavaScript never receives GitHub credentials; the sanitizer removes active and remote-loading PR content; and the HTML response includes these headers: Content-Security-Policy: default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; object-src 'none'; media-src 'none'; font-src 'none'; script-src 'nonce-<nonce>'; connect-src 'self'; img-src 'self' data:; style-src 'unsafe-inline', Referrer-Policy: no-referrer, Cache-Control: no-store, and X-Content-Type-Options: nosniff. This policy intentionally blocks external images, styles, frames, forms, media, objects, and non-nonce scripts. It reduces risk but does not claim to make arbitrary hostile HTML fully safe.

The main token-leak risk is that the review URL contains the random session token as a query parameter for initial page load. The countermeasure is to remove or rewrite PR-supplied external links and resources before serving, use Referrer-Policy: no-referrer, prefer the X-Scherzo-Review-Token header for JSON API calls after bootstrapping, and test with hostile fixtures that contain <base>, external img and link tags, iframe srcdoc, forms, meta refresh, and ping or javascript: URLs.

The main remote-mutation risk is accidental submission. The countermeasure is that preview mode remains read-only, review mode prints that remote mutations are only available after browser submit, the browser shows a confirmation before invoking /api/submit, and tests assert that fake gh receives no review submission before the submit endpoint is called.

Context and Orientation

scripts/scherzo-execplan-review is the existing local helper. It is an executable Python script. It accepts a GitHub PR number, uses gh to find the repository and PR, enumerates changed PR files, requires exactly one changed file matching docs/plans/*.html or docs/plans/*.md, downloads that file from the PR head repository and SHA, stores it below tmp/scherzo-execplan-review/, renders Markdown plans to HTML with scripts/scherzo-execplan-html, opens a browser preview, and prints key-value metadata such as PR_NUMBER, PLAN_PR_PATH, PLAN_SOURCE_PATH, PLAN_PREVIEW_PATH, PLAN_PREVIEW_URL, and PLAN_REMOTE_MUTATIONS=none.

docs/plans/ is the repository directory where ExecPlan artifacts are checked in. The current workflow validates Carbon HTML artifacts with scripts/scherzo-execplan validate. A Carbon HTML artifact is a complete HTML document generated by scripts/scherzo-execplan-html; it includes sidebar navigation, stable DOM targets, and rendered plan content.

A commentable element is any rendered HTML block that can be selected for review feedback. The important metadata is data-comment-id, a stable string identifier emitted into the HTML. Some generated elements also carry data-source-line, but for PR review submission the authoritative line must come from the downloaded HTML file's source line, not from the browser DOM.

A GitHub PR review comment is an inline comment attached to a file path and a line in a pull request diff. The planned endpoint is the GitHub REST create-review endpoint, addressed through gh api --method POST repos/{owner}/{repo}/pulls/{pull_number}/reviews --input <payload>. The expected inline comment object contains path, body, side: "RIGHT", and line; the whole review payload also contains commit_id and event: "COMMENT". GitHub generally accepts comments only on lines that are present in the diff. For newly added plan HTML files, most or all lines should be commentable. For revised plan HTML files, unchanged lines outside the displayed diff hunks may be rejected. This exact payload contract must be validated against a scratch PR before the implementation builds browser UI or submit code around it.

Preconditions and Verified Facts

The implementation starts from the current repository root. The file scripts/scherzo-execplan-review exists and currently imports argparse, base64, json, re, shutil, subprocess, sys, urllib.parse, webbrowser, Path, PurePosixPath, and Any. It defines PLAN_RE as a regular expression for docs/plans/*.html and docs/plans/*.md, DEFAULT_OUTPUT_DIR as tmp/scherzo-execplan-review, and helper functions including run_gh, gh_json, infer_current_repo, validate_repo, parse_pr_number, paginated_pr_files, find_plan_file, pr_metadata, head_repo_and_sha, repo_file_bytes, safe_local_path, render_markdown, browser_open, parse_args, preview_pr, and main.

The current helper writes downloaded files under tmp/scherzo-execplan-review/<owner>__<repo>/pr-<number>/ while preserving the repository path of the plan artifact below that directory. The repository .gitignore ignores tmp/, so draft JSON files and retained submit artifacts under that directory are not tracked.

The renderer scripts/scherzo-execplan-html is a Python script that renders Markdown plans to a complete Carbon-style HTML artifact. Its commentable_attrs helper emits id, class="commentable ...", data-comment-id, and optionally data-source-line. The validation helper scripts/scherzo-execplan validate requires checked-in plan artifacts to be complete Carbon HTML documents under docs/plans/ and rejects literal local absolute path prefixes in the artifact.

At plan authoring time, no existing Python test_*.py tests were found. The implementation should introduce a standard-library unittest test file rather than adding a new test dependency.

Scope Boundaries

In scopean explicit interactive review mode for a single changed docs/plans/*.html PR artifact; a loopback-only localhost server; local JavaScript and CSS injection; click-to-comment behavior for .commentable elements; draft persistence under tmp/scherzo-execplan-review/; edit and delete operations in a side drawer; source-line mapping using data-comment-id; a pre-UI GitHub create-review contract probe; diff eligibility detection from GitHub PR file patches; one server-side gh api submission path using the verified payload shape; retained submit payload and result artifacts; exact response-security headers; sanitizer tests for active and remote-loading HTML; and tests using fake gh calls and fixture HTML.

Out of scopeinteractive Markdown review; reviewing arbitrary non-ExecPlan files; supporting PRs with zero or multiple changed plan artifacts; multi-user collaboration on drafts; rich text formatting beyond plain-text comment bodies; OAuth or browser-side GitHub authentication; long-running background daemons; public network serving; and automatic posting of any fallback summary after a failed inline review without a second explicit reviewer confirmation.

Existing preview behavior remains in scope and must continue to work. Bare invocation, open, and preview continue to mean read-only preview with PLAN_REMOTE_MUTATIONS=none. The new interactive capability is reached through scripts/scherzo-execplan-review review PR_NUMBER.

Plan of Work

Create a new importable module scripts/scherzo_execplan_review.py and move the current implementation from scripts/scherzo-execplan-review into it. Leave scripts/scherzo-execplan-review as a thin executable wrapper that imports main from scherzo_execplan_review and exits with its return code. Keep function names stable where practical so the diff is easy to review, but introduce dataclasses for session and draft state once the module exists.

Extend argument parsing to recognize explicit subcommands. The default mode and the existing open and preview aliases call the preserved preview-only path. The new review subcommand accepts the same PR_NUMBER, --repo, --output-dir, and --no-open options, plus an optional --port defaulting to 0 for an available ephemeral port. Do not add a general --host; the server must bind to 127.0.0.1 only.

Add the API-contract probe before browser UI work. The probe can be a documented manual step plus a testable payload builder rather than a permanent user-facing command, but it must write api-contract-probe-payload.json and either api-contract-probe-result.json or api-contract-probe-error.json under tmp/scherzo-execplan-review/<owner>__<repo>/pr-<number>/. The payload must use the expected REST create-review shape: commit_id, event: "COMMENT", body, and comments with one object containing path, body, side: "RIGHT", and line. The scratch PR must target a disposable changed line in a docs/plans/*.html file. If GitHub accepts the review and shows the inline comment on that line, continue. If GitHub rejects it, do not implement the browser capture path until this plan is revised with the accepted coordinate fields.

Add a PlanSession dataclass that records repository, PR number, PR URL, plan path, head repository, head SHA, session root, source path, preview path, drafts path, submit payload path, submit result path, submit error path, PR files JSON path, API-contract probe artifact paths, and review mode. Write a non-secret session.json for observability. The random server token may appear in the printed URL and injected runtime configuration, but it must not be mistaken for a GitHub credential and should not be needed after the server exits.

Add server code using http.server.ThreadingHTTPServer and a small BaseHTTPRequestHandler subclass. The handler should serve exactly the generated preview document and JSON API endpoints. It must not expose arbitrary filesystem paths. Every API endpoint must validate the session token from an X-Scherzo-Review-Token header or a token query parameter. The preview HTML response must include the exact CSP, referrer, cache, and nosniff headers named in Risks and Countermeasures. JSON responses should include Cache-Control: no-store and X-Content-Type-Options: nosniff.

Add a sanitizer and injector for HTML review previews. Implement the sanitizer with an HTML parser or a conservative tokenizing approach, not with only regular expressions. Remove entire PR-supplied <script>, <iframe>, <frame>, <frameset>, <object>, <embed>, <portal>, <svg>, <math>, <template>, and <noscript> elements and their contents. Remove <base> and <link> elements. Remove any <meta http-equiv=...> element, especially refresh or content-security-policy. Strip every attribute whose lower-case name starts with on, and strip srcdoc, srcset, ping, autofocus, action, formaction, poster, background, and xlink:href. For href attributes, keep only same-page fragment links that start with #; rewrite all other values to # and store no fetchable URL. For src attributes, keep only data:image/... values; remove all other src values. Preserve data-comment-id, data-source-line, IDs, classes, and plain text content. Inject only the local review CSS and a nonce-bearing local review script. The script may be inline in the generated preview copy to keep the feature self-contained.

Add browser UI behavior in the injected script. Use event delegation on document to find the closest .commentable element. On click, prevent the selection action only when the review UI is active, read data-comment-id, data-source-line, tag name, and a short text excerpt, then display a popover near the clicked element. Saving a draft sends JSON to the server with X-Scherzo-Review-Token rather than relying on the query string. The side drawer fetches the server draft list, shows the block identifier, line if known, excerpt, and comment body, and provides Edit and Delete buttons. The Submit button is disabled when no drafts exist and shows a confirmation dialog before calling /api/submit.

Add draft persistence. Store drafts.json atomically by writing to a temporary sibling file and replacing the original. Use a schema with version, repo, pr_number, plan_path, head_sha, updated_at, and a comments array. Each comment has id, data_comment_id, dom_tag, dom_source_line, text_excerpt, body, created_at, updated_at, source_line, diff_eligible, and submitted_at. Validate that comment bodies are non-empty after trimming, limit each body to a reasonable maximum such as 16000 characters, and cap draft count at a practical limit such as 200 comments.

Add mapping helpers. line_for_comment_id(source_text, comment_id) scans the original downloaded HTML source line by line for an exact data-comment-id attribute match and returns a one-based line number only when exactly one match is found. right_side_commentable_lines(patch_text) parses unified diff hunks from GitHub's PR files response and returns the set of new-file line numbers represented by context or added lines. For a file whose GitHub response has no patch, classify all drafts as fallback-only rather than guessing. Because Milestone 0 verifies line and side, the first implementation can map an eligible source line directly to InlineCommentCoordinate(path=session.plan_path, side="RIGHT", line=source_line).

Add submit helpers. build_review_submission(session, drafts, pr_file_record) returns inline comments and fallback summary entries. Inline comments use path: session.plan_path, side: "RIGHT", line: source_line, and a plain-text body that includes the reviewer comment plus a short footer with data-comment-id. Fallback entries include the same comment body plus the best available source line, DOM source line, and excerpt. submit_review(session, submission) writes the JSON payload to submit-payload.json and invokes gh api --method POST repos/{repo}/pulls/{pr_number}/reviews --input <payload>. Use commit_id: session.head_sha and event: "COMMENT". If there are inline comments and fallback entries, put fallback entries in the review body. If there are no inline comments, require the browser to confirm a summary-only submit and use gh api --method POST repos/{repo}/issues/{pr_number}/comments --input <payload>.

Handle GitHub failures conservatively. If the review request fails, write submit-error.json with exit code, stdout, stderr, endpoint, and payload path, return a non-success JSON response to the browser, and do not mark drafts submitted. If the failure appears to be a line validation problem, the browser may offer a second explicit Submit summary instead button that posts all drafts to the PR issue comment endpoint. That second endpoint is still a remote mutation and must require confirmation in the browser.

Update the CLI output. Preview-only mode continues to print PLAN_REMOTE_MUTATIONS=none. Review mode prints the existing metadata plus PLAN_REVIEW_MODE=interactive-html, PLAN_REVIEW_DRAFTS_PATH=<absolute-local-path>, PLAN_REVIEW_SERVER=http://127.0.0.1:<port>/, PLAN_PREVIEW_URL=http://127.0.0.1:<port>/?token=<session-token>, and PLAN_REMOTE_MUTATIONS=available-after-browser-submit. Use placeholders in tests for absolute paths; do not write absolute paths into checked-in docs.

Rollout, Recovery, and Idempotence

Rollout is additive. Keep the existing preview-only command path as the default and add review as an opt-in subcommand. If the interactive server has a defect, reviewers can immediately fall back to scripts/scherzo-execplan-review preview PR_NUMBER and no existing workflow is blocked.

Local artifacts are safe to regenerate. Re-running the command for the same PR rewrites the downloaded source and injected preview for the current PR head. Existing drafts.json may be preserved only when the stored head_sha, plan_path, and source content hash match the current session; otherwise the tool should move the old draft file aside with a timestamp suffix or start a fresh draft file to avoid submitting comments against stale lines.

Remote mutation is not idempotent after a successful submit because GitHub will create real PR feedback. To reduce accidental duplicates, record successful submission metadata in submit-result.json, mark local drafts with submitted_at, and make the UI warn before re-submitting already submitted drafts. If a submit fails, leave drafts unchanged so the reviewer can retry after fixing credentials, network access, or stale PR data. The API-contract probe and the final real-GitHub smoke test must run only against disposable PRs where a retained test review is acceptable.

Recovery from bad local state is simple: stop the server with Ctrl-C and remove the relevant directory under tmp/scherzo-execplan-review/. Recovery from an unwanted GitHub comment is manual through GitHub's PR UI or API, which is why the implementation must keep confirmation and retained payload artifacts. For scratch validation, closing or deleting the disposable PR or repository is an acceptable cleanup path if the individual test review cannot be deleted.
