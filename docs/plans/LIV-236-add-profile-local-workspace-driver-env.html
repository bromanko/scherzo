Add profile-local workspace driver environment

Plan artifact: docs/plans/LIV-236-add-profile-local-workspace-driver-env.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Operators can already select a trusted workspace driver command in an orchestrator config profile, but they cannot configure reusable packaged drivers without changing the whole Scherzo process environment or writing wrapper scripts. After this change, an operator can put driver-specific environment variables next to the selected profile, for example workspace.profiles.isolated.driver.env.SCHERZO_JJ_WORKSPACE_BASE: "@", and Scherzo will pass those values when it discovers the driver, invokes lifecycle operations, runs workflow command steps, and launches agent steps for that profile.

The observable result is that a config like this works without a wrapper executable:

workspace:
  default_profile: isolated
  profiles:
    isolated:
      driver:
        command: scherzo-workspace-jj
        lifecycle: [create, before-step, after-step, remove]
        timeout_ms: 60000
        env:
          SCHERZO_JJ_WORKSPACE_BASE: "@"
          SCHERZO_JJ_WORKSPACE_REMOTE: upstream
          SCHERZO_JJ_WORKSPACE_BASE_BRANCH: trunk

driver.command remains one executable token. Scherzo still invokes drivers through argv, not by evaluating shell. driver.env supplies OS environment variables for trusted operator-selected driver processes and for workflow subprocesses that may call SCHERZO_WORKSPACE_DRIVER with the same profile policy. It is not a secret store, because command steps, agent subprocesses, and external tools can read these values.

Problem Framing and Constraints

Workspace profiles are trusted operator policy. Workflow YAML may select a profile and require capabilities, but workflow YAML must not define the driver command or mutate the profile-owned driver configuration. Today the driver schema under workspace.profiles.<name>.driver supports command, lifecycle, and timeout_ms; capabilities are discovered by running <driver> describe --json. The command field intentionally rejects inline shell fragments and inline assignments such as FOO=bar scherzo-workspace-jj.

That safety boundary creates friction for packaged drivers. A reusable driver such as scherzo-workspace-jj often needs per-profile policy knobs, for example which jj base revision, remote, or base branch to use. The current choices are to set process-wide environment before starting Scherzo or to create a repo-local wrapper that exports variables and then execs the packaged driver. Both choices are awkward because they move profile-specific policy away from the profile and make otherwise reusable configs less portable.

The change is constrained by four safety requirements. First, driver.env is trusted operator config only; workflow YAML must not be able to configure it. Second, the feature must not make driver.command shell-like. Values are passed through process environment APIs and are never concatenated into driver command strings by Scherzo. Third, because this plan intentionally exposes profile driver.env to command-step shells and agent-step processes, driver.env is not a safe secret store. Fourth, Scherzo-owned outputs should avoid accidental disclosure of likely sensitive profile values, but redaction must not corrupt normal diagnostics by replacing short or common values such as @, trunk, or upstream.

Strategy Overview

Add an optional env map to WorkspaceDriverConfig, validate it while reading orchestrator config, and carry the normalized key/value pairs anywhere Scherzo already carries driver context. The new schema is additive: old profiles continue to parse exactly as before with an empty profile driver environment. The implementation should use one small helper module for environment validation, merge precedence, redaction value extraction, and fingerprint serialization so discovery, lifecycle, command steps, agent steps, and tests all share the same behavior.

The selected behavior is deliberately literal and conservative. driver.env values are strings only, including the empty string, and are preserved exactly as YAML strings. Scherzo does not perform $NAME interpolation for driver.env; a value written as "$LINEAR_API_KEY" is passed to the driver as the literal string $LINEAR_API_KEY. This avoids reintroducing shell semantics, avoids accidental process-secret capture, and keeps workflow fingerprints deterministic.

Profile driver.env is passed to driver discovery, lifecycle invocations, workflow command-step environments, and agent-step environments. It is not added to prompt-template locals such as {{ workspace.driver }}, because templates and prompts are durable, visible text surfaces and should not gain another way to reveal driver configuration. If a workflow calls SCHERZO_WORKSPACE_DRIVER from a command step or agent tool, that child process sees the same profile-owned driver configuration that Scherzo used for discovery and lifecycle.

The merge rule is: base process or pi argv environment first, profile driver.env second, Scherzo-generated step and driver context last. In practical terms, a key from driver.env overrides the same key inherited from the Scherzo daemon process or from pi.argv.env, but Scherzo-generated keys such as SCHERZO_WORKSPACE_DRIVER, SCHERZO_WORKSPACE_PATH, and SCHERZO_REPO_ROOT cannot be overridden by profile config. Exact generated keys are rejected during config parsing, and the runtime merge helper still lets generated values win as defense in depth.

PATH is supported as a profile driver.env key. This is intentional because some packaged drivers or helper tools may need a profile-specific search path. The value is literal and complete: PATH: "<computed-path>:$PATH" does not append the inherited path, it passes the literal string containing $PATH. A profile-provided PATH affects driver discovery, lifecycle hooks, workflow command steps, and agent launches for that profile. Operators who configure PATH must provide the full search path they want those subprocesses to see; rollback is to remove PATH from driver.env or return to a wrapper.

Redaction is intentionally narrower than "redact every driver env value." workspace_driver_env.values_for_redaction(profile_env) must return only unique, non-empty values whose string length is at least 8 and whose key name is sensitive-looking. A key is sensitive-looking when its uppercase underscore-separated segments include SECRET, TOKEN, PASSWORD, PASS, CREDENTIAL, CREDENTIALS, or AUTH, or when adjacent final segments form API_KEY, ACCESS_KEY, PRIVATE_KEY, or SESSION_KEY. Values under normal policy keys such as SCHERZO_JJ_WORKSPACE_BASE, SCHERZO_JJ_WORKSPACE_REMOTE, SCHERZO_JJ_WORKSPACE_BASE_BRANCH, and PATH are not redacted automatically. This keeps driver-env-redaction-token redacted when it is configured as DRIVER_SECRET_TOKEN, while ensuring @, trunk, upstream, and empty values do not mangle operator-visible output.

Alternatives Considered

The simplest alternative is to keep requiring wrapper scripts. That preserves the current code but does not solve the operator problem: profile-specific policy remains hidden in extra executables or in process-manager global environment, and packaged driver reuse stays cumbersome.

Another option is to add shell-like command strings or inline env NAME=value command syntax to driver.command. This is rejected because it weakens the existing command safety boundary. Driver commands must remain one executable token with no shell metacharacters, and Scherzo should continue to pass operation arguments as argv.

A third option is to pass driver.env only to lifecycle invocations and not to workflow command or agent steps. That would reduce agent exposure, but it would make workflow-facing capabilities unreliable: a command step that invokes SCHERZO_WORKSPACE_DRIVER changed-files would not receive the same jj base policy that Scherzo used elsewhere. This plan chooses consistent exposure and compensates with explicit non-secret documentation, prompt isolation, and limited Scherzo-owned redaction.

A fourth option is to implement a private secret mechanism for driver env. That is larger than the current problem. It would need separate storage, redaction, prompt isolation, process-launch rules, and operator UI. This plan does not build that mechanism; it documents that driver.env is not safe for secrets.

A fifth option is to reject PATH in driver.env. That would reduce the chance of breaking command and agent subprocess tool lookup, but it would also prevent operators from using a profile to select a packaged driver toolchain. This plan supports PATH with explicit documentation and tests because it is trusted operator config and the behavior is reversible.

Risks and Countermeasures

The biggest risk is accidental secret leakage. The countermeasure is to state that driver.env is not a secret facility, to avoid prompt-template locals, to avoid logging env maps, to redact only likely-sensitive configured values on Scherzo-owned surfaces, and to fingerprint values by digest instead of literal text. This reduces accidental leakage in Scherzo's own artifacts but does not change the fact that command steps and agents can read their environments.

A second risk is corrupting useful diagnostics through over-broad redaction. The countermeasure is the precise redaction policy above: empty values, short values, and normal policy values such as @, trunk, upstream, and PATH are not redaction secrets. Tests must prove those values remain visible where they are expected and that a value such as driver-env-redaction-token is redacted only when configured under a sensitive key such as DRIVER_SECRET_TOKEN.

A third risk is overriding core Scherzo variables. The countermeasure is to validate exact reserved generated names during config parsing and to use a single merge helper where Scherzo-generated variables win even if a collision reaches runtime through a bug or future refactor.

A fourth risk is nondeterministic or secret-bearing workflow fingerprints. The countermeasure is to canonicalize driver.env by sorting entries by key and to serialize each entry as the key plus a SHA-256 digest of the value. Changing a value changes the execution fingerprint, but the canonical fingerprint input does not contain the raw value.

A fifth risk is inconsistent behavior between discovery, lifecycle, command steps, shell-mode pi launches, and argv-mode pi launches. The countermeasure is to add tests for each invocation surface and to route env construction through the same helper functions.

A sixth risk is PATH breaking expected tools in command or agent subprocesses. The countermeasure is to document that profile PATH is a complete literal replacement for that profile's subprocesses and to add tests that both shell-mode and argv-mode pi launches receive the configured PATH while generated Scherzo keys remain authoritative.

A seventh risk is breaking old configs or wrappers. The countermeasure is that env is optional, wrappers keep working, and rollback is to remove the env block or restore a wrapper command. Invalid env fails config loading before dispatch instead of failing halfway through workspace cleanup.

Context and Orientation

The orchestrator config is parsed in src/scherzo/config.gleam. The config types live in src/scherzo/config/types.gleam. The current WorkspaceDriverConfig contains the driver executable token, supported lifecycle operation list, discovered capabilities, and timeout. Config parsing currently rejects the removed driver.capabilities key and reads command, lifecycle, and timeout_ms in read_workspace_driver.

Driver discovery lives in src/scherzo/workspace_driver_discovery.gleam. It enriches parsed profiles by running each configured driver as <driver> describe --json and storing the discovered capabilities back into WorkspaceDriverConfig. Discovery currently uses a minimal environment and must continue not to pass workspace-specific variables such as SCHERZO_WORKSPACE_PATH.

Driver lifecycle invocation lives in src/scherzo/workspace_driver_lifecycle.gleam. It invokes lifecycle create, lifecycle before-step, lifecycle after-step, and lifecycle remove through argv using hooks.run_argv_with_env. It receives the run and workspace env from src/scherzo/workspace_run.gleam, then adds driver context such as SCHERZO_WORKSPACE_DRIVER, SCHERZO_WORKSPACE_CAPABILITIES, and SCHERZO_REPO_ROOT.

Workflow command-step environment construction lives in src/scherzo/workflow_run.gleam in step_command_env. Command execution itself lives in src/scherzo/command_step.gleam. Agent steps are launched from src/scherzo/workflow_run.gleam in default_dependencies().agent_step, which calls run_attempt.run_prompt_mode_in_workspace with config_types.with_pi_env(effective, step_command_env(context)). The pi env helper lives in src/scherzo/config/types.gleam: with_pi_env prepends shell export lines for pi.command mode through shell_command_with_env, and merges env into PiArgvCommand.env for argv mode through argv_command_with_env.

The current workspace template locals come from src/scherzo/workspace_driver_context.gleam and expose workspace.profile, workspace.driver, and workspace.capabilities; this plan intentionally does not add env values to those locals.

Execution fingerprints live in src/scherzo/workflow_fingerprint.gleam. The execution fingerprint is the right place for profile driver.env because it includes operator-selected workspace profile details that can change how a workflow behaves at runtime. The plain DAG fingerprint should remain based only on workflow YAML.

The normative driver contract is docs/specs/WORKSPACE_DRIVER_SPEC.md. Migration guidance is docs/runbooks/workspace-driver-migration.md. Public examples include examples/scherzo.yaml, examples/workflows/research.yaml, and README material in README.md.

Scope Boundaries

In scopeadd the driver.env schema, validation, storage, merge helper, invocation propagation, limited redaction, fingerprinting, tests, docs, and public examples. The schema exists only in orchestrator config under workspace.profiles.<name>.driver.env.

Out of scopeadding workflow YAML env overrides, changing driver.command to an argv array, adding shell interpolation, adding a private secret store, changing the driver describe --json response schema, changing capability names, or redesigning workspace profile selection.

Existing wrappers remain supported. If a wrapper only exports variables and execs the real driver, docs should show how to migrate it to driver.env. If a wrapper also supplies arguments, performs authentication, discovers tools, or contains safety checks, this plan does not require removing it.

This plan does not require changing jj driver semantics. It only makes profile-owned environment available to packaged drivers. Documentation may show jj base-policy variables such as SCHERZO_JJ_WORKSPACE_BASE, SCHERZO_JJ_WORKSPACE_REMOTE, and SCHERZO_JJ_WORKSPACE_BASE_BRANCH as driver-specific examples for the packaged jj driver.

Milestones

Milestone 1 adds parsing and validation without changing runtime behavior. At the end, configs with driver.env parse into WorkspaceDriverConfig, invalid keys and non-string values fail with clear config errors, empty values are accepted, duplicate env keys are rejected, PATH is accepted as a literal value, and old configs still parse with an empty env list. This milestone retires schema ambiguity before touching process launch code.

Milestone 2 centralizes env merge and propagates it to discovery and lifecycle invocations. At the end, fake drivers can prove that describe --json and lifecycle operations receive profile-local env values, while discovery still does not receive workspace-only variables. Discovery and lifecycle failure diagnostics redact only likely-sensitive configured values.

Milestone 3 exposes profile driver env to workflow command and agent step environments, adds Scherzo-owned redaction for all claimed workflow surfaces, and keeps prompt templates unchanged. At the end, command steps and both pi launch modes can call the selected driver with the same configuration, command artifacts and events redact configured sensitive values when printed, and templates still expose only profile, driver, and capabilities.

Milestone 4 updates execution fingerprints. At the end, changing a profile env value changes workflow_fingerprint.fingerprint_for_execution, but the canonical fingerprint input contains only env keys and value digests.

Milestone 5 updates docs, examples, and migration guidance. At the end, operators can copy a documented jj driver profile that configures base policy without a wrapper, and docs clearly warn that driver.env is not a secret mechanism, that redaction is limited, and that PATH is a complete literal replacement for profile subprocesses.

Milestone 6 runs full validation and cleanup. At the end, tests, format, production lints, and docs checks pass through direnv.

Plan of Work

In src/scherzo/config/types.gleam, add an env: List(#(String, String)) field to WorkspaceDriverConfig. The invariant is that this list contains unique keys sorted by key. Update every direct construction of WorkspaceDriverConfig in source and tests to pass env: [] until a test intentionally uses values.

Add a small module src/scherzo/workspace_driver_env.gleam. It should contain key validation, the exact reserved generated key list, canonical sorting, merge behavior, sensitive-key detection, limited redaction value extraction, and fingerprint-friendly serialization helpers. Keep this module independent of workflow execution so parser, discovery, lifecycle, command-step, agent-step, and fingerprint code can all reuse it.

The reserved generated key list must include these exact names: SCHERZO_CONFIG_DIR, SCHERZO_REPO_ROOT, SCHERZO_WORKSPACE_DRIVER, SCHERZO_WORKSPACE_CAPABILITIES, SCHERZO_RUN_KIND, SCHERZO_WORKFLOW_ID, SCHERZO_RUN_ID, SCHERZO_RUN_ROOT, SCHERZO_ISSUE_ID, SCHERZO_ISSUE_IDENTIFIER, SCHERZO_STEP_ID, SCHERZO_ATTEMPT_INDEX, SCHERZO_ATTEMPT_KEY, SCHERZO_HOOK_IDEMPOTENCY_KEY, SCHERZO_WORKSPACE_ROOT, SCHERZO_WORKSPACE_PROFILE, SCHERZO_WORKSPACE_NAME, SCHERZO_WORKSPACE_PATH, SCHERZO_SOURCE_WORKSPACE_NAME, SCHERZO_SOURCE_WORKSPACE_PATH, SCHERZO_SCHEDULED_JOB_ID, SCHERZO_SCHEDULE_DUE_AT, SCHERZO_SCHEDULE_STARTED_AT, and SCHERZO_RUN_ATTEMPT. The helper module should expose behavior equivalent to these signatures:

pub fn valid_key(name: String) -> Bool
pub fn reserved_generated_key(name: String) -> Bool
pub fn sensitive_key(name: String) -> Bool
pub fn canonicalize(entries: List(#(String, String))) -> List(#(String, String))
pub fn merge(
  profile_env: List(#(String, String)),
  generated: List(#(String, String)),
) -> List(#(String, String))
pub fn values_for_redaction(profile_env: List(#(String, String))) -> List(String)
pub fn fingerprint_entries(profile_env: List(#(String, String))) -> List(#(String, String))

merge must remove any profile entry whose key appears in generated, then return profile entries followed by generated entries, or otherwise construct a unique-key list that has the same effective precedence. The tests should assert behavior rather than list order where order is not meaningful. fingerprint_entries should return sorted pairs where the second element is hash.sha256_hex(value).

values_for_redaction must return a sorted unique list of values that meet the policy in Strategy Overview: non-empty, at least 8 characters, and under a sensitive-looking key. It must not include values for SCHERZO_JJ_WORKSPACE_BASE: "@", SCHERZO_JJ_WORKSPACE_REMOTE: upstream, SCHERZO_JJ_WORKSPACE_BASE_BRANCH: trunk, PATH, or EMPTY_VALUE: "". Rollout, Recovery, and Idempotence

This is an additive config feature. Existing configs without driver.env keep the same behavior because the parsed env list defaults to empty. Existing wrapper commands keep working because driver.command semantics do not change.

Rollout is safe because invalid driver.env fails config loading before workflow dispatch. A bad value that causes driver discovery to fail is contained to the affected profile and reports workspace_driver_discovery_failed. A bad lifecycle value fails the same lifecycle error path drivers already use. A bad PATH can break driver, command, or agent subprocess tool lookup only for the affected profile; the recovery is to provide a complete PATH, remove PATH from driver.env, or return to a wrapper.

Rollback for an operator is to remove the env block and restart or reload Scherzo, or to return to a wrapper command that exports the desired values. Rollback for code is to revert the additive schema and docs commits; configs using driver.env will then fail to load, which is explicit and safer than silently ignoring operator policy.

Steps are idempotent. Re-running tests recreates fixtures under test/tmp/.... Re-running config parsing does not mutate state. Driver lifecycle tests should create and remove only test directories under test/tmp/....
