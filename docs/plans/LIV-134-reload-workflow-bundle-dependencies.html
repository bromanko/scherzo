Reload workflow bundle when routed workflows or prompts change

Plan artifact: docs/plans/LIV-134-reload-workflow-bundle-dependencies.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Scherzo runs as a long-lived daemon, which means operators expect it to notice workflow configuration changes without requiring a restart for every edit. After this change, a daemon that was started with a valid .scherzo/scherzo.yaml will automatically reload its runtime workflow bundle when a routed workflow YAML file or a prompt file changes, not only when the top-level orchestrator config changes. A newly dispatched Linear issue will then use the updated workflow steps and prompt contents, and invalid dependent-file edits will block dispatch with operator-visible diagnostics instead of silently continuing with stale behavior.

The observable outcome is simple: edit a routed workflow such as .scherzo/workflows/execplan-implementation.yaml to add a gate step, or edit a prompt file used by that workflow, wait for the daemon reload check, and the next selected workflow should include the new step or prompt text. If the edit breaks YAML or removes a prompt file, the daemon should mark the workflow bundle invalid the same way it already does for an invalid .scherzo/scherzo.yaml edit.

Problem Framing and Constraints

The live daemon currently compares only the chosen top-level config file contents in src/scherzo/orchestrator/workflow_reloader.gleam. That top-level file can remain byte-for-byte unchanged while it points at routed workflow YAML files and prompt files whose contents have changed. In that situation the daemon reports the bundle as unchanged and keeps the old runtime_bundle.RuntimeBundle in memory. Operators can force a reload with scherzoctl reload or restart the daemon, but automatic polling does not notice the dependent-file change.

This is operator-risky because the workflow DAG, which is the directed set of workflow steps and dependencies Scherzo dispatches for an issue, is part of the daemon's safety policy. The reported stale run for LIV-127--576438025271-7 followed the older workflow:execplan-implementation path and did not execute the current checked-in plan-completion gate steps. A stale DAG can therefore publish work without the gates that reviewers believe are active.

The implementation must stay focused on local file dependencies that already affect runtime_bundle.load: the top-level YAML config, routed workflow YAML files listed under routing.workflows, and prompt files referenced by agent steps inside those workflows. It must not introduce file watchers, background OS-specific services, or a broad configuration subsystem rewrite. The existing poll-tick reload path and explicit operator reload command are the right integration points.

Strategy Overview

Extend the runtime bundle with a dependency manifest that records every local file read while constructing the bundle and the contents observed for that file. The manifest must include .scherzo/scherzo.yaml or the explicitly selected config path, every resolved routed workflow YAML path, and every resolved prompt file path. The loader remains the single source of truth for path resolution: runtime_bundle.load discovers dependencies at the same points where it already reads those files.

workflow_reloader.reload_if_changed should probe the current on-disk state of all paths in the last valid bundle manifest before deciding whether to reload. If the daemon is currently valid and every probe succeeds with the same contents, it returns Unchanged. If any file differs or cannot be read, it attempts a full runtime_bundle.load(Some(state.chosen_path)). If the daemon is already invalid because of an earlier automatic dependency reload and the newly probed dependency snapshot is byte-for-byte identical to that earlier failed snapshot, it returns Unchanged without attempting another full load; this suppresses repeated identical log noise while the bad edit remains unchanged.

A failed automatic reload must retain the last known good state.bundle and state.effective, mark state.reload_state.current_status as config.CurrentInvalid(reason), and store the failed dependency snapshot in state.last_invalid_dependency_snapshot. A later poll must attempt a full reload whenever the probed snapshot differs from that failed snapshot, even if the files have been restored to exactly the last good contents; a successful load clears last_invalid_dependency_snapshot and marks the workflow current status valid again. This defines both repeated-invalid and recovery semantics before implementation begins.

This approach is proportionate because Scherzo already rebuilds the whole bundle when the top-level config changes. The missing behavior is only change detection for the files that feed that same bundle. A manifest keeps the reload logic deterministic and testable without adding platform-specific file watching. Reloading the entire bundle after any dependency change also avoids partial-update bugs; validation remains centralized in runtime_bundle.load.

The reload path should preserve current operator semantics. scherzoctl reload should still force a full load even when no dependency changed or when the same invalid dependency snapshot has already been observed automatically. Invalid reload diagnostics should use the exact outcome shape workflow_reloader.Invalid(State, reason: String, message: String). reason is the stable machine-readable bundle error code stored in config.CurrentInvalid(reason); message is the human-readable, path-bearing diagnostic logged by the daemon and shown by operator reload responses where practical.

Alternatives Considered

The simplest plausible alternative is to keep the current top-level comparison and tell operators to run scherzoctl reload after every workflow or prompt edit. That does not solve the reported failure mode because the daemon is expected to reload automatically on poll ticks, and humans will eventually forget the manual step.

Another option is to watch the workflow directory with an operating-system file watcher. That is larger than needed, introduces platform-specific behavior, and still requires dependency discovery to know which files matter. Polling all known dependencies on the existing reload check is simpler, portable, and aligned with the current design.

A third option is to compute a recursive directory hash for .scherzo/workflows. That would notice more edits but would also reload on unrelated files, hidden editor backups, or future assets not used by any routed workflow. A manifest of actual files loaded into the bundle is more precise and easier to explain in diagnostics.

Risks and Countermeasures

The main risk is missing a file that affects workflow execution. Counter this by recording dependencies at the same points where runtime_bundle.load reads files: the top-level config read, each load_workflow_dag read, and each read_relative_prompt read. Add tests that assert the manifest contains all three categories for a small fixture bundle.

A second risk is spurious reloads due to nondeterministic manifest ordering. Counter this by normalizing dependencies by path before storing or comparing them. If the same prompt file is referenced by two steps, the final manifest should contain one entry for that path with the contents from the last read; do not add prompt-read caching for this ticket unless an existing helper already makes it trivial.

A third risk is noisy repeated invalid reload attempts. A malformed workflow file or deleted prompt differs from the last valid manifest on every poll, so a naive implementation would full-load and log workflow_reload_failed repeatedly. Counter this by adding last_invalid_dependency_snapshot to workflow_reloader.State and returning Unchanged on later automatic polls when the current failed snapshot is identical to the previous failed snapshot. Explicit operator reload must bypass this suppression so an operator can ask for the current diagnostic on demand.

A fourth risk is losing the last known good bundle when a dependent file becomes invalid. Counter this by keeping the existing config.ReloadState(last_known_good: Some(state.effective), current_status: CurrentInvalid(reason)) behavior and by verifying in tests that effective and the existing in-memory bundle remain unchanged after an invalid dependent-file reload attempt.

A fifth risk is claiming that invalid dependent files gate dispatch without proving the daemon uses the invalid reload state. Counter this with focused validation rather than a broad daemon harness: invalid dependent-file tests must assert !config.can_dispatch(next.reload_state), and the plan must keep the verified daemon adapter transition_dispatch_context using dispatch_enabled: config.can_dispatch(state.workflow.reload_state) before candidate fetch. If that adapter no longer has this exact line when implementation starts, add a compact daemon or transition-boundary test before changing reload behavior.

A sixth risk is weakening scherzoctl reload. Counter this by keeping explicit reload independent from change detection and invalid-snapshot suppression. The command should call a full load and report either workflow reloaded on success or a rejected command with the bundle error code and path-bearing message on failure.

Context and Orientation

Scherzo is a daemon-driven workflow orchestrator. A daemon is a long-running process. A workflow bundle is the in-memory runtime object that contains the resolved orchestrator config, routing rules, workflow DAGs, prompt text, secrets, and validation results used when the daemon dispatches work. A routed workflow is a workflow selected from a Linear issue label such as workflow:execplan, using the routing.workflows map in the top-level config.

The main files for this change are:

  • src/scherzo/runtime_bundle.gleam, which loads the top-level YAML config, resolves routing.workflows, parses workflow YAML files into workflow_dag.WorkflowDag values, replaces prompt-file references with inline prompt text, and returns RuntimeBundle.
  • src/scherzo/orchestrator/workflow_reloader.gleam, which stores the active bundle in reload state and decides whether an automatic or explicit reload should occur.
  • src/scherzo/orchestrator/daemon.gleam, which calls workflow_reloader.reload_if_changed on poll ticks before evaluating scheduled jobs and fetching dispatch candidates. It also calls workflow_reloader.reload_now for the operator reload command.
  • test/runtime_bundle_test.gleam, which covers loading routed workflows, resolving prompt files, selecting workflows by label, and checked-in dogfood workflow loading.
  • test/orchestrator_workflow_reloader_test.gleam, which covers automatic reloads for top-level config changes, invalid config reloads, unchanged reload checks, and explicit reloads with unchanged config contents.

The top-level config resolver in src/scherzo/config.gleam resolves routing.workflows entries relative to the config file path via resolve_relative_config_path. Prompt paths are resolved relative to their workflow YAML file by read_relative_prompt in src/scherzo/runtime_bundle.gleam, and prompt paths are required to be relative and not contain parent-directory segments.

Preconditions and Verified Facts

From the current tree, src/scherzo/orchestrator/workflow_reloader.gleam defines State with workflow_path, chosen_path, last_contents, bundle, reload_state, effective, and secrets. Its reload_if_changed function reads only state.chosen_path; when those contents equal state.last_contents, it returns Unchanged(state) without checking routed workflow or prompt files.

src/scherzo/orchestrator/workflow_reloader.gleam currently defines Outcome.Invalid(State, reason: String). This plan requires changing that to Outcome.Invalid(State, reason: String, message: String). src/scherzo/config.gleam currently defines CurrentInvalid(String) and can_dispatch returns False for that status; this plan intentionally keeps that config type shape unchanged.

src/scherzo/runtime_bundle.gleam defines RuntimeBundle with config_path, config_contents, effective, orchestrator, workflows, and secrets. It does not currently expose dependency paths or fingerprints. load_orchestrator reads the selected config, resolves the orchestrator config, loads the workflow map from orchestrator.routing.workflows, validates workspace profiles, validates model settings, validates scheduled workflows, and then returns RuntimeBundle.

src/scherzo/runtime_bundle.gleam resolves prompt files by replacing workflow_dag.PromptFile(prompt_path) with workflow_dag.PromptInline(prompt) in agent steps. That means the in-memory bundle contains prompt contents, not a live reference to the prompt file.

src/scherzo/orchestrator/daemon.gleam applies reload outcomes through apply_workflow_reload_outcome. A valid reload rebuilds tracker, handoff, Linear command, triage, scheduled failure reporter, and runtime settings derived from the new effective config. An invalid reload logs workflow_reload_failed and keeps the workflow state marked invalid. The same file builds dispatch context with dispatch_enabled: config.can_dispatch(state.workflow.reload_state), so a CurrentInvalid workflow state disables candidate dispatch through the transition layer.

test/orchestrator_workflow_reloader_test.gleam already has fixture helpers that create a top-level config, a routed workflow file, and a prompt file under test/tmp/.... Those helpers are the best starting point for dependency reload regression tests.

Scope Boundaries

In scopedependency tracking for files read by runtime_bundle.load; automatic reload detection for changed routed workflow YAML files and prompt files; preserving explicit scherzoctl reload; tests for valid dependency reloads and invalid dependency reloads; path-bearing diagnostics where the failing dependent path is known.

Out of scopeadding OS file watchers; changing the YAML workflow schema; changing Linear issue routing semantics; changing workspace profile behavior; changing how prompt templates are rendered after they are loaded; and changing retained-run history. Existing workflow execution behavior should remain the same except that the active bundle is refreshed when dependent files change.

The implementation should not change .scherzo/scherzo.yaml, checked-in workflow YAML, checked-in prompts, or Linear labels as part of this ticket unless a test fixture explicitly writes temporary files under test/tmp/... during a test.

Milestones

Milestone 1 adds a manifest to RuntimeBundle and proves that loading a bundle records the top-level config, the routed workflow YAML file, and the prompt file. At the end of this milestone, no reload behavior has changed yet, but the loader exposes enough information for reloader tests to be precise.

Milestone 2 changes automatic reload detection to compare the full manifest. At the end of this milestone, changing a routed workflow YAML file or prompt file causes workflow_reloader.reload_if_changed to return Reloaded and the selected workflow in the new bundle includes the changed steps or prompt text.

Milestone 3 hardens invalid reload behavior. At the end of this milestone, invalid dependent-file edits mark the reload state invalid while preserving the last good bundle, diagnostics mention the offending path where practical, repeated automatic polls over the same invalid file return Unchanged without another full load, and fixing the file causes a later poll to return Reloaded with CurrentValid.

Milestone 4 preserves explicit operator reload behavior and proves dispatch safety. At the end of this milestone, reload_now still forces a full load regardless of manifest equality or repeated invalid snapshots, operator responses include useful diagnostics, and invalid dependent-file states are shown to disable dispatch through config.can_dispatch and the daemon dispatch context.

Milestone 5 runs the full validation gates and records any discoveries in this plan. At the end of this milestone, the tree is formatted, tests pass, glinter passes, and scherzo_lint passes.

In src/scherzo/orchestrator/workflow_reloader.gleam, add explicit dependency probe types and extend State and Outcome as follows. The field order can follow the current file style, but the semantics must match this shape:

pub type DependencyReadStatus {
  ReadContents(String)
  ReadFailed
}

pub type DependencyRead {
  DependencyRead(path: String, status: DependencyReadStatus)
}

pub type State {
  State(
    workflow_path: Option(String),
    chosen_path: String,
    last_contents: String,
    bundle: runtime_bundle.RuntimeBundle,
    reload_state: config.ReloadState,
    effective: config_types.EffectiveConfig,
    secrets: List(String),
    last_invalid_dependency_snapshot: Option(List(DependencyRead)),
  )
}

pub type Outcome {
  Unchanged(State)
  Reloaded(State)
  Invalid(State, reason: String, message: String)
}

from_bundle must initialize last_invalid_dependency_snapshot to None. A successful reload must set it back to None. A failed automatic reload must set it to Some(snapshot), where snapshot is the normalized list of dependency probe results for the last known good manifest paths.

Replace the single simplifile.read(state.chosen_path) comparison in reload_if_changed with a helper that probes all state.bundle.dependencies. The decision order is important: if the current status is invalid and the new probe snapshot equals state.last_invalid_dependency_snapshot, return Unchanged(state); otherwise, if the current status is valid and every probe read matches state.bundle.dependencies, return Unchanged(state); otherwise attempt a full reload. This ensures fixing an invalid file back to the last good contents still performs a reload attempt and restores CurrentValid.

Refactor reload_now so it always attempts runtime_bundle.load(Some(state.chosen_path)) without consulting the manifest or invalid snapshot. This preserves the behavior covered by workflow_reloader_reload_now_reloads_when_config_contents_unchanged_test and lets operators request fresh diagnostics even when automatic polling is suppressing a repeated invalid snapshot.

Refactor apply_new_contents into apply_reload_attempt(state, attempted_snapshot: Option(List(DependencyRead))). On success, copy bundle.config_contents into last_contents, install the new bundle, refresh effective, reload_state, secrets, and clear last_invalid_dependency_snapshot. On failure, preserve the old bundle and effective config, set reload_state.current_status to config.CurrentInvalid(code), set last_invalid_dependency_snapshot to the provided snapshot when present, and return Invalid(next, code, message). If the failed snapshot includes a readable entry for state.chosen_path, set last_contents to that attempted top-level contents for compatibility; otherwise keep the previous last_contents. Do not let last_contents decide unchanged status by itself.

Improve path-bearing diagnostics in src/scherzo/runtime_bundle.gleam. When workflow YAML parsing fails, wrap the workflow_dag.DagError message with the workflow path, for example workflow <path>: <message>. When top-level YAML parsing fails, include the selected config path. When a prompt path is invalid or missing, keep or add the workflow path or resolved prompt path in the message. Keep error codes stable unless a new code is strictly necessary; tests should mostly assert message substrings rather than exact full messages.

Update src/scherzo/orchestrator/daemon.gleam for the new Outcome.Invalid shape. apply_workflow_reload_outcome should log workflow_reload_failed with both error set to reason and message set to the path-bearing message. reload_workflow_for_operator should reject with the stable reason and display workflow reload failed: followed by the message. Do not change config.CurrentInvalid; it continues to store only the stable reason code used by config.can_dispatch.

Rollout, Recovery, and Idempotence

This change is internal to bundle loading and reload detection. It does not change the checked-in config schema or require data migration. The rollout path is to merge the code with tests and restart deployed daemons once, after which future dependent-file edits will be detected on normal poll ticks.

If the change causes unexpected reload churn, operators can inspect workflow_reloaded and workflow_reload_failed logs to identify which path is changing. Identical invalid automatic polls should not churn because the daemon stores the failed dependency snapshot and returns Unchanged until the files change. Operators can still run scherzoctl reload for an on-demand diagnostic because explicit reload bypasses that suppression.

A bad workflow or prompt edit can be recovered by fixing the file and waiting for the next reload check or by running scherzoctl reload. Recovery must work when the file is fixed to new valid contents and when it is restored to the exact last known good contents. On success, last_invalid_dependency_snapshot is cleared, CurrentValid is restored, and dispatch can resume.

Implementation steps are idempotent. Re-running tests rewrites only temporary fixtures under test/tmp/.... Running reload_if_changed repeatedly with unchanged valid dependency contents should return Unchanged. Running it repeatedly with the same invalid dependency snapshot should return Invalid once and then Unchanged while preserving the invalid state.

Rollback is straightforward: revert the commits that add the manifest, invalid snapshot field, outcome-message shape, and reloader comparison. The previous behavior will return, so operators would again need scherzoctl reload or daemon restart after dependent-file edits. No persisted data requires migration back.

The desired automatic behavior is conceptually:

pub fn reload_if_changed(state: State) -> Outcome {
  let snapshot = probe_dependencies(state.bundle.dependencies)
  case should_suppress_repeated_invalid(state, snapshot) {
    True -> Unchanged(state)
    False ->
      case manifest_matches_last_good(state, snapshot)
        && config.can_dispatch(state.reload_state) {
        True -> Unchanged(state)
        False -> apply_reload_attempt(state, Some(snapshot))
      }
  }
}

Do not paste this pseudo-code blindly; adapt it to Gleam's actual result handling, but preserve the decision order. The important behavior is that a currently invalid state with a changed or fixed snapshot attempts a reload even when the fixed contents match the last good bundle.
