Scherzo ExecPlan HTML artifact

Create token-efficient ExecPlan briefs and HTML extraction

Plan artifact: docs/plans/LIV-213-token-efficient-execplan-briefs-and-html-extraction.html 22 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Scherzo operators and implementation agents need to work from checked-in ExecPlans without spending most of their context window on generated HTML shell, CSS, navigation markup, or repeated full-plan reads. After this change, an implementation workflow that receives PLAN_PATH=docs/plans/example.html can first read a compact, deterministic brief and can ask a helper for readable Markdown or a named section of the plan. The full checked-in Carbon HTML ExecPlan remains self-contained and remains the source of truth, but routine implementation, verification, and review steps can consume bounded plan context and fall back to the full plan only when the bounded context is incomplete or ambiguous.

A human can see the result by rendering any Carbon HTML plan, running scripts/scherzo-execplan-html extract-md docs/plans/example.html, running scripts/scherzo-execplan-html section docs/plans/example.html "Validation and Acceptance", and then running scripts/scherzo-implementation prepare --source execplan in a workflow fixture that references that plan. The successful helper output should include PLAN_BRIEF_STATUS=ok, PLAN_BRIEF_PATH=tmp/scherzo-execplan-brief.md, and PLAN_INDEX_PATH=tmp/scherzo-execplan-index.json, and the prompts should instruct agents to read those bounded artifacts before requesting additional sections. If the status is unavailable, agents use the full plan at PLAN_PATH.

Problem Framing and Constraints

The concrete operator problem is that ExecPlan implementation runs repeatedly ask agents and verifiers to read full plan artifacts. Current Carbon HTML artifacts are much larger than their visible plan text because they include a structured shell, CSS, navigation DOM, and commentable metadata. Older Markdown plans can also be large. Re-reading the full plan at implementation, plan-completion verification, feedback repair, and late validation wastes tokens and increases the chance that the agent skips important details because the context is noisy.

The plan must not weaken ExecPlan self-containment. A full plan must still be enough for a stateless agent or a human novice to implement the work without any generated side file. The compact brief and index are derived conveniences, not alternative plans. They must never be the only place where a milestone, acceptance criterion, validation command, scope boundary, open question, or living-document state exists.

This repository already has a Carbon HTML renderer in scripts/scherzo-execplan-html, structural validation in scripts/scherzo-execplan, and implementation workflow helpers in scripts/scherzo-implementation. The implementation workflow is configured in .scherzo/workflows/execplan-implementation.yaml and currently uses prompts under .scherzo/workflows/prompts/ that require full-plan reads. The change must be additive, must keep legacy Markdown plan support, and must avoid checking in generated Markdown copies of HTML plans.

The implementation should avoid broad workflow redesign. The right-sized solution is to add deterministic extraction and indexing helpers, generate a prepare-time brief under tmp/, update the prompts to prefer bounded context, and keep the full plan path and full-plan fallback available everywhere.

Strategy Overview

Extend scripts/scherzo-execplan-html from a render-only tool into a small plan-inspection helper with these subcommands: render, extract-text, extract-md, section, and brief. The new subcommands use only the Python standard library. For HTML input they parse the Carbon artifact, ignore style, script, navigation, and other non-plan chrome, then emit readable text or Markdown-like content from the plan article. For legacy Markdown input they pass through or normalize the Markdown directly so older plans keep working.

Generate an ExecPlanBrief at prepare time from the authoritative plan file. The brief is a deterministic extraction, not an agent-written summary. It contains the plan path, the raw source SHA-256, title, section index, required living-document sections, required milestones, acceptance and validation sections, scope boundaries, progress, open questions, and instructions for asking the section helper for more context. A companion JSON index contains the same metadata in a machine-readable shape. Both files live under tmp/ and are safe to delete and regenerate. The checked-in full plan remains the only durable source of truth.

Make the brief bounded by policy, not by hope. Define constants in scripts/scherzo-execplan-html: BRIEF_SCHEMA_VERSION = 1, MAX_BRIEF_CHARS = 30000, and MAX_BRIEF_SECTION_CHARS = 6000. The brief always includes metadata, usage instructions, a full section index, and warning blocks. It then includes critical sections in this priority order: Progress, Scope Boundaries, Acceptance Criteria when present, Testing and Falsifiability, Validation and Acceptance, Rollout, Recovery, and Idempotence, Open Questions and Clarifications Needed, Outcomes & Retrospective, Milestones, Concrete Steps, and Plan of Work. Any included section longer than MAX_BRIEF_SECTION_CHARS, or any lower-priority section that would push the brief beyond MAX_BRIEF_CHARS, is truncated with a visible Markdown warning that names the section, the original character count, the included character count, and the exact scripts/scherzo-execplan-html section <plan> "<section>" fallback command. The JSON index records the same information in truncated_sections; no section may be silently dropped.

Update scripts/scherzo-implementation prepare --source execplan to attempt brief generation and to print PLAN_BRIEF_STATUS=ok, PLAN_BRIEF_PATH, PLAN_INDEX_PATH, and PLAN_SOURCE_SHA256 in addition to the existing PLAN_PATH when generation succeeds. If the plan path is valid but brief generation fails, prepare remains non-fatal: it prints PLAN_BRIEF_STATUS=unavailable plus a bounded PLAN_BRIEF_WARNING, persists that status in metadata, exits successfully, and the prompts fall back to reading the full plan. Add scripts/scherzo-implementation plan-brief --check and scripts/scherzo-implementation plan-brief --refresh-if-stale so later prompts can detect and refresh stale briefs after living-document edits. Update execplan-implementation prompts to read the brief first when PLAN_BRIEF_STATUS=ok, use section for named bounded sections, and fall back to the full plan when the brief is unavailable, stale, missing, truncated, inconsistent with the plan hash, or too ambiguous to implement or verify safely.

Make HTML living-document edits safer by changing the workflow instructions. Agents should not hand-edit noisy generated HTML unless there is no helper available. For an HTML plan, they should run scripts/scherzo-execplan-html extract-md "$PLAN_PATH" > tmp/current-execplan.md, edit the temporary Markdown, and render it back to the same HTML path with python3 scripts/scherzo-execplan-html render tmp/current-execplan.md "$PLAN_PATH" "$PLAN_PATH". The temporary Markdown stays under ignored tmp/; the checked-in HTML remains the source of truth.

Add a tiny non-visible HTML comment near the top of newly rendered HTML artifacts that tells agents which helper to use. The comment must be less than a few hundred bytes and must not introduce visible UI text. Existing HTML artifacts without this comment remain valid.

Alternatives Considered

The simplest alternative is to only update prompts so agents read less of the full plan. That is insufficient because the current artifact format still makes bounded reads awkward: a raw HTML read contains CSS and DOM metadata, and there is no reliable way to ask for a named section without reading or manually searching a noisy file.

Another alternative is to check in both a full HTML plan and a Markdown source plan. That would make editing easier, but it would create two durable representations that can drift. It also conflicts with the current workflow contract that the final retained plan artifact under docs/plans/ is the Carbon HTML file. This plan keeps generated Markdown under tmp/ only.

Another alternative is to create an LLM-written plan summary. That would be compact, but it would introduce summary drift and could omit acceptance criteria. This plan uses deterministic extraction and explicit source hashes instead. If a future team wants model summaries, they should be layered on top of this deterministic index and must not replace it.

Another alternative is to compress or minify the Carbon HTML itself. That might reduce bytes on disk, but it would not solve agent cognition: minified HTML is harder to read, and implementation agents still need a plan-oriented interface. This plan leaves reviewable Carbon HTML intact and adds readable extraction helpers.

Risks and Countermeasures

A stale brief could mislead a verifier after an implementation agent updates the plan's Progress or Outcomes sections. To reduce this risk, every brief and index includes the raw plan SHA-256, and stale detection is executable rather than left to manual inspection. scripts/scherzo-implementation plan-brief --check reloads tmp/scherzo-implementation.json, computes the current plan hash, compares it to the metadata and index hash, prints PLAN_BRIEF_STATUS=fresh on a match, and prints PLAN_BRIEF_STATUS=stale with a non-zero exit code on mismatch. scripts/scherzo-implementation plan-brief --refresh-if-stale regenerates the brief, index, and metadata when the hash differs. Prompts tell agents to run the check before verification and after any living-document edit; if check or refresh fails, agents fall back to the full plan.

A compact brief could omit acceptance criteria or required milestones. To reduce this risk, the brief is deterministic, copies named critical sections instead of paraphrasing them, and enforces the explicit MAX_BRIEF_CHARS and MAX_BRIEF_SECTION_CHARS policy. The JSON index records which expected sections were found, which were missing, and which included sections were truncated, including original character counts and exact fallback commands. Prompts must treat missing or truncated critical sections as a reason to call section or read the full plan before implementing or verifying that part of the plan.

Readable extraction from HTML could lose formatting that matters, such as checklist state, code blocks, tables, or labeled Decision Log entries. To reduce this risk, tests must render representative Markdown to HTML and verify that extract-md preserves headings, checkboxes, fenced code blocks, ordered lists, labeled statements, and open-question text well enough to render back into a valid Carbon HTML plan.

Agents could over-trust the brief and lose autonomy. To reduce this risk, the prompts must say that the brief is an index and starting context, not a replacement for judgment. When implementation is unclear, when a section reference is not included, when the brief flags missing/truncated content, or when source hashes disagree, the agent must fetch the relevant section or read the full plan.

The helper could break old Markdown plans or older Carbon HTML artifacts that do not contain the new hint comment. To reduce this risk, every new helper subcommand accepts both docs/plans/*.html and legacy docs/plans/*.md. For Markdown input, extract-md returns the Markdown, extract-text strips only lightweight Markdown syntax, section finds Markdown headings, and brief uses the same section parser. For old HTML input, parsing must rely on the existing article.plan-document, headings, and visible content rather than the optional new hint comment. End-to-end tests must cover both a legacy Markdown plan path and an old HTML fixture without the hint comment.

Brief generation failure could otherwise turn an additive token-saving helper into a mandatory blocker. To reduce this risk, prepare --source execplan treats brief generation failure as non-fatal when the plan path itself is valid. It records PLAN_BRIEF_STATUS=unavailable, prints a bounded warning, deletes or ignores any partial brief/index files, and instructs prompts to read the full plan. This preserves the old implementation path while still making helper failures visible and debuggable.

The HTML hint comment could increase raw-read cost or become visible in browsers. To reduce this risk, it is a short HTML comment placed after the doctype, and tests assert that no visible comment-helper UI is reintroduced. The comment should name only the helper and should not include a long tutorial.

Round-tripping an extracted HTML plan back through the renderer could rewrite more DOM than a tiny manual edit. That is acceptable because Carbon HTML is generated markup. The validation and PR diff will show one plan file changed. The safety requirement is that the visible plan content remains self-contained and that the Carbon shell, commentable metadata, and required sections validate after rendering.

Context and Orientation

Scherzo is a Gleam service with repository-local shell and Python helpers for workflow automation. A workflow is a YAML-defined sequence of command and agent steps. The ExecPlan authoring workflow creates a checked-in plan under docs/plans/, validates it, opens a pull request, and creates a follow-up implementation issue. The ExecPlan implementation workflow reads a checked-in plan and changes source code according to it.

The current plan renderer is scripts/scherzo-execplan-html. It reads Markdown and writes one complete Carbon-style HTML document. The generated HTML includes a sticky top bar, a table-of-contents panel, commentable elements, and data-comment-id attributes so reviewers and operators can refer to stable DOM targets. It also stores the displayed plan artifact path in the document metadata.

The structural validator for new plan PRs is scripts/scherzo-execplan. It validates that the changed plan is exactly one newly added docs/plans/*.html file, that it is a complete HTML document, that it uses the Carbon shell, that it has commentable metadata, that it has required sections such as Progress and Open Questions, and that it does not contain local absolute path prefixes.

The implementation helper is scripts/scherzo-implementation. In prepare --source execplan, it fetches the Linear issue, extracts exactly one plan path, validates that the path exists, writes tmp/scherzo-implementation.json, and prints PLAN_PATH. Later commands analyze changed files, generate plan-completion context, validate with SelfCI, and publish a PR.

The implementation workflow is .scherzo/workflows/execplan-implementation.yaml. Important agent prompts are under .scherzo/workflows/prompts/. The initial implementation prompt is execplan-implementation-implement.md. Plan-completion verifier prompts include execplan-implementation-verify-completion.md, execplan-implementation-verify-completion-after-feedback.md, and execplan-implementation-verify-completion-before-final-validation.md. Feedback prompts include execplan-implementation-apply-plan-completion-feedback.md and execplan-implementation-apply-feedback.md. ExecPlan PR revision uses execplan-revision.md and scripts/scherzo-execplan-revision.

A Carbon HTML plan is self-contained: it contains the visible plan content and all CSS/DOM needed to review it as a standalone file. An ExecPlanBrief in this plan means an ephemeral, generated Markdown document that copies the implementation-critical pieces of the plan and points back to the full plan with a source hash. A plan index means a JSON file with section titles, slugs, character counts, source hash, and flags that help workflows decide whether the brief is fresh and complete.

Acceptance Criteria

The authoritative relationship is explicit: the checked-in full plan remains the only source of truth, while tmp/scherzo-execplan-brief.md and tmp/scherzo-execplan-index.json are derived artifacts with a source hash and can be regenerated at any time.

The helper commands preserve plan self-containedness and operator debuggability. extract-md and extract-text let an agent inspect readable content without raw HTML noise, section lets the agent fetch bounded named sections, and the full HTML plan can still be opened or read directly when needed.

The implementation workflow consumes bounded context when available and remains backward-compatible when it is not. On successful brief generation, prepare output includes PLAN_BRIEF_STATUS=ok, PLAN_BRIEF_PATH, PLAN_INDEX_PATH, and PLAN_SOURCE_SHA256. On helper failure for an otherwise valid plan, prepare output includes PLAN_BRIEF_STATUS=unavailable and a bounded warning while preserving PLAN_PATH; prompts then read the full plan. The implementation and verification prompts instruct agents to read the brief first only when it is available, use section for extra detail, and fall back to the full plan when the brief is stale, missing, truncated, unavailable, or ambiguous.

The risks around stale summaries, lost acceptance criteria, oversized sections, and reduced agent autonomy are addressed. The brief is deterministic rather than model-written, critical sections are copied or visibly truncated according to the explicit limits, hashes detect staleness through scripts/scherzo-implementation plan-brief --check, and prompts explicitly require fallback to full plan or named sections when the brief is insufficient.

Safe living-document edits for HTML plans are supported. Prompts instruct agents to extract temporary Markdown to tmp/, edit it, render it back to the same HTML plan path, validate the result, run scripts/scherzo-implementation plan-brief --refresh-if-stale when metadata exists, and avoid hand-editing generated HTML except as a last resort.

Compatibility acceptance is explicit. A legacy docs/plans/*.md plan path still prepares successfully, helper commands still work for Markdown input, and an older Carbon HTML artifact without the new hint comment still supports extract-md, section, brief, and implementation-helper prepare fallback behavior.

Plan of Work

In scripts/scherzo-execplan-html, replace the current two-branch CLI parsing with a small subcommand dispatcher. Keep the existing render PLAN OUTPUT [DISPLAY_PATH] behavior exactly compatible, including PLAN_HTML_PATH=<output>. Add usage() text for all subcommands.

In scripts/scherzo-execplan-html, add a lightweight document model. Define a PlanDocument data class with source_path, source_kind, title, raw_sha256, and a list of PlanBlock or PlanSection values. A section should record heading level, title, slug, source line when available, plain text, Markdown text, and character count. Use the existing HEADING_RE and slugify for Markdown input. For HTML input, use html.parser.HTMLParser from the standard library to walk the plan article. Keep the parser work deliberately staged: first recognize the article.plan-document boundary and title, then headings and paragraphs, then list/checklist state, then code blocks, then tables and labeled statements. Each stage should have one focused assertion in test/execplan_html_renderer_test.gleam before adding the next stage. Ignore script, style, nav, and top-bar content. Convert headings to Markdown headings, paragraphs to plain paragraphs, list items to bullets or numbered items, checklist inputs to - [x] or - [ ], code blocks to fenced code blocks, and tables to readable Markdown tables when practical.

In scripts/scherzo-execplan-html, implement extract-md PLAN. For Markdown input, print the original Markdown normalized to end with one newline. For HTML input, print reconstructed Markdown that starts with the level-one title and includes all visible plan sections. It does not need byte-for-byte equality with any original private Markdown source; it must preserve visible meaning and must be accepted by render for round-trip edits.

In scripts/scherzo-execplan-html, implement extract-text PLAN. This prints a plain-text version for agents that do not need Markdown structure. It should include headings as readable lines, preserve checklist state in text, preserve code block contents, and omit Carbon shell text such as Scherzo ExecPlan artifact / Carbon structured, CSS, JavaScript, and data-comment-id values.

In scripts/scherzo-execplan-html, implement section PLAN HEADING_OR_SLUG. It should match case-insensitive exact heading title first, then slug, then unique substring. It should print that heading and its child content until the next heading of the same or higher level. If no section matches, exit non-zero and print available headings. If multiple sections match, exit non-zero and print the ambiguous candidates. Add --format md|text if doing so keeps the implementation simple; default to Markdown because it is best for living-document edits.

In scripts/scherzo-execplan-html, implement brief PLAN --markdown OUT --json OUT. Testing and Falsifiability

The extraction tests must prove that the helper removes HTML overhead without removing plan meaning. extract_md_recovers_readable_markdown_from_html_test fails before implementation because extract-md is not a valid subcommand. It passes after implementation when the extracted Markdown contains the plan title, required headings, checklist items, code block text, and open questions, and does not contain Carbon shell or DOM metadata strings.

The section tests must prove bounded context. section_extracts_named_section_without_neighbor_sections_test fails before implementation because section is not a valid subcommand. It passes after implementation when the output includes only the requested section subtree. The missing or ambiguous section test passes only if the helper exits non-zero and prints candidate headings, because silent empty output would cause agents to miss acceptance criteria.

The text extraction test must prove token efficiency at the content boundary. It should assert absence of CSS, JavaScript, data-comment-id, and navigation words that are not part of the plan. It should assert presence of the title and purpose text. If this test passes while output still includes large style/script blocks, the implementation is wrong.

The brief tests must prove that acceptance-critical content is preserved or explicitly flagged and that the brief stays bounded. A representative plan with Validation and Acceptance, Testing and Falsifiability, Milestones, Scope Boundaries, Progress, and Open Questions should produce a brief containing those sections. The JSON index should list missing sections only when they are actually absent. An oversized-section fixture must force Concrete Steps past MAX_BRIEF_SECTION_CHARS and assert visible Markdown warning text, a truncated_sections JSON entry with original and included character counts, and the exact scripts/scherzo-execplan-html section docs/plans/sample.html "Concrete Steps" fallback command. The test should compute or parse the source SHA-256 and compare it to the current plan file hash. A stale or wrong hash falsifies the design.

The round-trip edit test must prove safe living-document edits. It fails if extract-md output cannot be rendered back into valid Carbon HTML, if the rendered plan loses required sections, or if scripts/scherzo-execplan validate docs/plans/sample.html fails after the round-trip.

The implementation-helper tests must prove workflow integration and safe fallback. prepare --source execplan should still accept HTML plan paths and should still print PLAN_PATH. Success assertions should require PLAN_BRIEF_STATUS=ok, PLAN_BRIEF_PATH, PLAN_INDEX_PATH, PLAN_SOURCE_SHA256, metadata fields, and actual brief/index files. Failure-path assertions should prove that brief helper failure for a valid plan prints PLAN_BRIEF_STATUS=unavailable, persists a warning, exits successfully, and leaves the full-plan path usable. Stale-check assertions should prove plan-brief --check reports stale state after a plan edit and that --refresh-if-stale refreshes metadata and files.

Prompt contract tests must prove behavior changes and resolve the exec-plan skill tension. They should assert that the implementation and verifier prompts no longer say to always read the full plan before deciding. They should assert that PLAN_BRIEF_STATUS, PLAN_BRIEF_PATH, PLAN_INDEX_PATH, source hash freshness, scripts/scherzo-implementation plan-brief --check, scripts/scherzo-implementation plan-brief --refresh-if-stale, scripts/scherzo-execplan-html section, and full-plan fallback are all mentioned. The compatibility tests must prove that the additive rollout is real. The non-functional claim is token efficiency. This plan does not require a fixed percentage reduction for every possible plan, but it is falsifiable for representative fixtures: extract-md and extract-text output must be materially smaller than raw rendered HTML because they omit CSS, scripts, navigation, and DOM metadata, and brief output must obey MAX_BRIEF_CHARS = 30000 except for the unavoidable length of explicit warning and metadata lines. Rollout, Recovery, and Idempotence

This change is additive. Existing checked-in HTML and Markdown plans remain valid. Existing Linear implementation issues that only include PLAN_PATH still work because PLAN_PATH output remains unchanged. New brief fields are extra stdout and metadata fields. PLAN_BRIEF_STATUS=ok means bounded artifacts are available; PLAN_BRIEF_STATUS=unavailable means the workflow should use the old full-plan path.

The brief and index are generated under tmp/, so they are safe to delete. Regenerating them is idempotent for an unchanged plan file: the source hash and section index should be identical, and generated timestamps should either be omitted from deterministic tests or stored in a way that does not affect hash comparisons. If the plan changes, scripts/scherzo-implementation plan-brief --check must report stale state and scripts/scherzo-implementation plan-brief --refresh-if-stale is the correct recovery path.

If extraction fails on an unusual old HTML artifact during prepare, the workflow must keep PLAN_PATH, print PLAN_BRIEF_STATUS=unavailable, record a bounded helper diagnostic, remove partial brief/index files, and tell the agent to fall back to the full plan. If extraction fails during manual section lookup, the agent should read the full plan. Do not silently produce an empty brief. An empty or partial brief without warnings is more dangerous than no brief.

If prompt changes confuse an agent or a helper command is unavailable, the fallback is simple: read the full plan at PLAN_PATH, because the full plan remains self-contained. This fallback should be written directly into the prompts, along with the conflict-resolution sentence that the brief and named section reads are the required first pass for this workflow when available, not a replacement for the authoritative full plan.

If round-trip editing produces an invalid plan, recover by reverting the plan file to the previous state in the working copy and either retrying the extract-edit-render flow with a smaller edit or making a careful direct HTML edit. After any recovery, run scripts/scherzo-execplan validate <plan> for plan PRs or the relevant workflow validation command for implementation runs.

No deployment migration is needed. The changed scripts and prompts take effect when the workflow bundle is run from a revision containing this implementation. There is no data migration, no external service schema change, and no Linear API behavior change.

Interfaces and Dependencies

scripts/scherzo-execplan-html must support these command shapes at the end of the implementation:

scripts/scherzo-execplan-html render PLAN OUTPUT [DISPLAY_PATH]
scripts/scherzo-execplan-html extract-md PLAN
scripts/scherzo-execplan-html extract-text PLAN
scripts/scherzo-execplan-html section PLAN HEADING_OR_SLUG
scripts/scherzo-execplan-html brief PLAN MARKDOWN_OUT JSON_OUT

render keeps its existing output contract and prints PLAN_HTML_PATH=<output>. extract-md, extract-text, and section print plan content to stdout and use stderr for diagnostics. brief writes both files and prints at least PLAN_BRIEF_PATH=<path>, PLAN_INDEX_PATH=<path>, and PLAN_SOURCE_SHA256=<hash>.

The ExecPlanBrief Markdown is a human-readable artifact. It should include sections with these headings: Metadata, How to use this brief, Limits and warnings, Section index, Scope boundaries, Progress, Required milestones, Acceptance and validation, Living-document sections, Open questions, and Missing or truncated sections. These headings can be adjusted if tests assert the final names, but the content categories must remain. The brief must print MAX_BRIEF_CHARS=30000 and MAX_BRIEF_SECTION_CHARS=6000 in the Metadata or Limits section.

scripts/scherzo-implementation must print and persist these fields for execplan sources on successful brief generation: plan_brief_status, plan_brief_path, plan_index_path, and plan_source_sha256. On helper failure for a valid plan path it must persist plan_brief_status = "unavailable" and plan_brief_warning without path/hash fields. The metadata file tmp/scherzo-implementation.json remains JSON and remains backward-compatible because existing fields are not removed.

scripts/scherzo-implementation plan-brief must support these command shapes:

scripts/scherzo-implementation plan-brief
scripts/scherzo-implementation plan-brief --check
scripts/scherzo-implementation plan-brief --refresh-if-stale

The default command regenerates the brief unconditionally. --check prints PLAN_BRIEF_STATUS=fresh, PLAN_BRIEF_STATUS=stale, or PLAN_BRIEF_STATUS=unavailable and exits non-zero for stale or unavailable states. --refresh-if-stale regenerates only when needed and prints the same success fields as prepare after refreshing.

The implementation uses only Python standard library modules already available to the scripts: hashlib, html, html.parser, json, re, sys, and pathlib. No package dependency or Gleam dependency is added.

The prompt interface is textual. Prompts should refer to PLAN_BRIEF_PATH and PLAN_INDEX_PATH from prepare output, and to PLAN_PATH as the authoritative full plan. They should name exact helper commands, but they should not depend on absolute checkout paths.
