# LIV-523 daemon decomposition v2 review

This review is a planning artifact for the next daemon decomposition wave. It recommends derivative implementation work; it does not implement an extraction.

## Purpose / Big Picture

Scherzo's daemon should remain the stable public actor for daemon mode while no longer being the place where every runtime concern accumulates. This v2 plan gives maintainers a ranked extraction sequence, the evidence behind that sequence, and guardrails that make future daemon regrowth visible before another 7k-line actor becomes normal. After this review is published, an implementation owner should be able to start the first derivative slice from this document and the retained implementation pack without inventing acceptance evidence, test obligations, or rollout timing. This ticket remains documentation-only; it does not introduce a runtime manual, browser, or dogfood check before publish because no runtime behavior changes here.

## Problem Framing and Constraints

`src/scherzo/orchestrator/daemon.gleam` is currently 7,099 lines. The prior plan, `docs/plans/daemon-decomposition.md`, started from 3,991 lines, extracted side effects, workflow reload, event publishing, worker registry, poll/retry schedulers, and command handling, and recorded a completion checkpoint at 3,490 lines. Those earlier boundaries still mostly exist as modules, and the old side-effect/event helper grep checks still return no matches in the daemon, but new concerns have regrown around them.

The current daemon now owns these responsibility clusters: public actor startup and message dispatch; control-plane file/server wiring; startup recovery from the ledger and projection store; scheduled job admission, retry, failure reporting, and scheduled-worker lifecycle; poll and remote-command phases; operator-control resolution and synchronous worker command routing; transition/effect shell callbacks; worker and YAML-step spawning, updates, and completion; side-effect completion interpretation; shutdown interruption recording; logging, redaction, and small utility mapping. The constraint is behavior preservation: this work must not change public daemon/control behavior, Linear command syntax, workflow YAML semantics, EventHub event shape, or the overall OTP/process architecture.

## Strategy Overview

Use a v2 strangler sequence that extracts the largest coherent state owners first while keeping `daemon.gleam` as the compatibility shell. The first extraction slice should be scheduled runtime state and decisions, because scheduled jobs account for a large, coherent block of regrowth, already have `schedule_core.gleam` as a pure nucleus, and touch explicit state fields in `State`. Each derivative item below should be its own implementation ticket or ExecPlan unless a reviewer intentionally combines adjacent low-risk items. Every derivative plan should begin with characterization tests for current behavior, state the exact targeted and full validation commands, and record whether any operator-visible dogfood check is required before publish or explicitly deferred to a human after implementation.

## Alternatives Considered

Updating only the old plan was rejected because it is a completed historical record whose final state no longer matches the tree. A big-bang daemon rewrite was rejected because the daemon has many public lifecycle and control surfaces, so a broad process-architecture change would hide regressions. Adding only line-count checks was rejected because size is a symptom; the useful guardrail is ownership-aware source tests plus a ratcheting size budget.

## Risks and Countermeasures

The main risk is moving lifecycle code and accidentally changing ordering. The countermeasure is to start every derivative item with characterization tests, keep public daemon messages stable, and run full daemon/control/Linear-command parity tests after each slice. Another risk is creating new god modules; the countermeasure is to require each new module to own a named state subset and to prohibit imports from extracted subsystem modules back into `scherzo/orchestrator/daemon`. A third risk is brittle source guardrails; the countermeasure is to combine targeted forbidden-declaration checks with an explicit ratchet that reviewers update only when ownership is intentionally changed. A fourth risk is that derivative implementation packs could claim parity without evidence; the countermeasure is to require each derivative item to name its targeted tests, the full `gleam test` gate, the format gate, both production lint gates, and any required or deferred manual/operator check.

## Scope Boundaries

In scope for this plan: identifying current daemon clusters, comparing them with the prior decomposition plan, ranking derivative extraction work, naming proposed module boundaries, specifying behavior-preservation tests, recommending the first slice, and proposing guardrails. Out of scope: implementing any extraction in this ticket, changing public behavior, converting to a new supervision tree, changing tracker or Linear semantics, migrating documentation/helper infrastructure, changing provider-live or cache behavior, or rewriting all runtime state at once. After the sequence, the daemon should still own public actor startup, public message receipt, compatibility types, dependency injection, top-level logging/redaction context, and handoff between subsystem outcomes.

The ranked milestones below are derivative implementation boundaries, not work already completed by this planning ticket. Each derivative implementation must first add or extend the listed behavior-preservation tests as characterization evidence, then run the targeted tests plus `direnv exec . gleam format --check src test`, `direnv exec . gleam test`, `direnv exec . gleam run -m glinter`, and `direnv exec . gleam run -m scherzo_lint` before publish. A milestone is not accepted solely because `daemon.gleam` gets shorter; it is accepted when the expected daemon ownership column is true and the named evidence has been collected. This planning ticket itself has no pre-publish manual/browser/dogfood runtime check; future derivative owners should add one only when their slice changes operator-visible daemon behavior, and otherwise state that human review of the PR is the deferred manual check.

## Rollout, Recovery, and Idempotence

This ticket rolls out only a plan document and a structured implementation pack, so recovery is to revert this document and the generated bundle if reviewers reject the sequence. Future extraction tickets should be additive and reversible: introduce tests and a new module, route daemon callbacks through it, run parity validation, then remove daemon-local code. Re-running the planning validation commands is idempotent; source guardrails should be ratcheted only in commits that intentionally move ownership. Because this ticket intentionally avoids docs/helper migration and provider-live/cache changes, rollback does not need data cleanup or cache invalidation.
