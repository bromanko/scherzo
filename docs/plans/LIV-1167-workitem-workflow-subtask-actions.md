# WorkItem workflow-subtask action metadata and controls

This ExecPlan v2 review document is the human review surface for LIV-1167. It plans a later implementation that lets Scherzo Core describe and execute Work screen actions for workflow subtasks; mechanical steps, tests, interfaces, dependencies, and artifact notes are supplied through the structured implementation-pack submission captured by Scherzo.

## Purpose / Big Picture

The Work screen should show only actions that Scherzo Core believes are valid for the current task, subtask, workflow run, retained artifact, and operator authority state. After this plan is implemented, `work_item_list` and `work_item_show` responses can include stable action metadata for running a workflow, cancelling an active workflow subtask, reviewing retained artifacts, and fixing/retrying a failed workflow subtask.

The visible outcome is not a finished browser UI. The visible outcome is a daemon-owned contract: the UI can render labels and disabled reasons from query data, send an action id back through the authenticated control plane for mutating actions, receive a normal command result, and refresh the WorkItem instead of hard-coding state rules or command payloads in the UI.

## Problem Framing and Constraints

Today Scherzo has read queries for status, metrics, tasks, and outbox records, plus a planned WorkItem hierarchy contract for parent tasks and subtasks. The current tree also has operator commands such as `retry`, `retry-step`, `abort`, `stop-after-turn`, and artifact-publication retry, but those commands are operator-centric and do not give the Work UI a safe list of available buttons. If the UI invents its own rules, it can offer stale, destructive, unsupported, or unauthorized actions.

Action availability must be read-only metadata. An action descriptor may say that a button is enabled or disabled and why, but it must not be treated as permission to mutate. Every mutating request must be authenticated by the local control token or UI server daemon credential, decoded through the daemon control plane, revalidated against fresh provider and daemon state, and reported as a command result. The metadata and result payloads must not expose credentials, local control tokens, raw provider payloads, prompts, descriptions, comments, raw artifact contents, or absolute local paths.

This plan assumes a WorkItem read-query surface named `work_item_list` and `work_item_show`. If that contract is not present when implementation starts, the implementation must first add or normalize that WorkItem contract rather than placing workflow-subtask actions on legacy `task_list` and `task_show` DTOs.

Action metadata must preserve the WorkItem provider-live behavior: each query derives from the current WorkItem provider capability plus current daemon runtime and ledger state, not from a new daemon provider cache, legacy flat task DTOs, retained artifact bodies, or helper-generated files. This issue is not a docs/helper migration; do not change `workflows/dogfood/`, workflow schema files, or ExecPlan helper scripts for this feature unless a later, separate issue explicitly expands scope.

## Strategy Overview

Extend WorkItem and WorkSubtask DTOs with an `actions` array whose entries are generated by Scherzo Core from provider-live WorkItem data, workflow configuration, daemon runtime state, the ledger projection, retained artifact metadata, and tracker capabilities. Use stable action ids `work_item.run_workflow`, `work_subtask.cancel`, `work_subtask.review_artifacts`, and `work_subtask.fix_retry`. Each descriptor should include a deterministic action instance id, a label, whether it is read-only or mutating, an enabled flag, a structured disabled reason with a stable code and safe message when disabled, and a redacted target summary.

Use a first-class control-plane command for UI-originated WorkItem actions, such as `work_item_action`, instead of asking the UI to send low-level commands directly. The daemon maps that action command to existing semantics where appropriate: `fix_retry` delegates to the existing retry-step planner, `cancel` delegates to resolved active-worker cancellation/abort semantics, `review_artifacts` stays read-only and never becomes a command, and `run_workflow` uses a new tracker workflow-subtask creation capability before dispatching or queueing the created subtask.

Action snapshots should be computed by a small, testable Core module that is pure over its inputs: provider-live WorkItem data, workflow configuration, daemon runtime/session information, ledger projection, artifact metadata, and tracker capability flags. The module must not persist descriptors, create cache files, or depend on browser state. Its output should be safe to serialize directly and should be reproducible for the same observed state.

The action executor must re-fetch or re-derive enough current state to detect stale metadata, reject disabled actions, dedupe duplicate submissions, and return `CommandResult` statuses (`applied`, `queued`, `rejected`, `not_found`, or `not_allowed`) with safe messages. The UI must refresh the WorkItem after any command result; command results are acknowledgements, not a replacement for fresh query state.

## Alternatives Considered

Hard-coding button rules in the UI is the simplest implementation, but it is unsafe because the UI cannot reliably know daemon runtime state, tracker capabilities, retry repairability, artifact retention, or command authority. It would also duplicate Scherzo policy across server and browser code.

Returning raw `OperatorCommand` payloads in WorkItem query responses was rejected because it would couple the UI to daemon internals and tempt the browser to replay commands without revalidation. Stable action ids plus a daemon action executor preserve a declarative UI contract while still reusing existing operator semantics inside Core.

Making every candidate action a separate first-class `OperatorCommand` was also rejected for the initial UI contract. Existing operator commands should remain available for `scherzoctl` and operators, but WorkItem buttons need one target-checked action envelope that can carry an observed state fingerprint and idempotency key consistently across create, cancel, retry, and future actions.

For artifact review, this plan chooses safe retained-artifact refs and availability metadata first, not raw artifact content endpoints. A later UI issue may add a read-only artifact content/query endpoint if the browser needs previews; until then the action can open or list safe refs, hashes, sizes, and display paths without exposing local filesystem paths or artifact bodies.

## Risks and Countermeasures

The main product risk is showing an enabled button that is no longer safe. Counter this by treating descriptors as hints, adding an observed action fingerprint to mutating requests, and making the daemon recompute current action availability before it mutates anything. Stale requests must return a safe `rejected` result such as `stale_action` or the current disabled reason.

A provider-live/cache regression risk is deriving action metadata from stale scheduler data or adding a new cache without invalidation rules. Counter this by making action derivation explicit about its sources, using the WorkItem provider-live capability for task hierarchy, using the ledger and runtime only for Scherzo workflow state, and adding tests that prove repeated queries and commands re-read or re-derive current state without writing provider cache artifacts.

The main data-integrity risk is duplicate workflow-subtask creation. Counter this with a UI/server idempotency key, a daemon action-command receipt keyed by action id and target, and a tracker-level dedupe check for an existing child subtask with the same parent, workflow id, and Scherzo action marker before issuing a provider create mutation. The same key with a different payload must be rejected as an idempotency conflict.

The main safety risk for cancellation is partial failure. Counter this by resolving the active run/session immediately before cancellation, recording local cancellation through existing workflow-cancelled or worker-stop semantics, and reporting tracker transition failures explicitly. If a worker was stopped but a tracker state transition failed, the command result must say that local cancellation was applied and tracker state needs refresh or repair; retrying with the same idempotency key should replay the same result rather than aborting twice.

The main privacy risk is leaking rich task, artifact, or provider data through action DTOs. Counter this with allowlisted fields, redaction tests using obvious secret markers, no descriptions/comments/raw payloads, no raw artifact contents, and no absolute local paths in WorkItem action metadata.

## Scope Boundaries

In scope are WorkItem/WorkSubtask action DTOs, action derivation, disabled reasons, action fingerprints, control-plane action execution, idempotency, stale-state handling, create-subtask tracker capability design, cancel/retry delegation, retained-artifact availability metadata, command results, redaction, tests, and rollout evidence needed before UI buttons are enabled.

Out of scope are final browser rendering, user-account authorization beyond the already authenticated local/UI server control plane, recursive workstream playbooks, raw artifact content browsing, broad provider cache design, changing legacy `task_list`/`task_show`, retiring existing `scherzoctl` commands, ExecPlan workflow helper or schema migration, and enabling destructive UI buttons without dogfood evidence.

## Milestones

Milestone 1 is the action metadata contract. Reviewers should see WorkItem and WorkSubtask DTOs with stable action ids, labels, enabled flags, disabled reason codes/messages, mutating-versus-read-only classification, deterministic action instance ids, and action fingerprints. The proof is codec and derivation tests covering every candidate action and a no-secret serialization check.

Milestone 2 is the action-state derivation engine. Reviewers should see a daemon-readable action snapshot that combines provider-live WorkItem hierarchy, workflow configuration, dispatch pause state, active/pending workers, ledger projection workflow runs, step attempts, parked issues, and artifact refs. The proof is state-matrix tests for parent terminal state, dispatch paused, unsupported provider capability, active subtask, failed/interrupted run, completed run with artifacts, missing or corrupt artifact metadata, and provider-live/no-cache behavior across repeated queries.

Milestone 3 is the authenticated action command envelope. Reviewers should see local control, remote/UI command protocol, command codec, and command result tests for `work_item_action`, including token rejection before dispatch, stale fingerprint rejection, duplicate idempotency replay, duplicate idempotency conflict, unsupported action id, target not found, and sanitized result messages.

Milestone 4 is workflow-subtask creation. Reviewers should see a tracker capability and fake/Linear implementation path that can ensure exactly one child workflow subtask for a parent and workflow id, attach the configured workflow label and Scherzo action marker, choose the configured ready state, and either start dispatch immediately when safe or return `queued` for normal dispatch. The proof is duplicate-create tests and tracker error tests without live Linear dependency.

Milestone 5 is cancel and fix/retry execution. Reviewers should see `cancel` resolve the current active workflow subtask to a run/session and reuse existing cancellation semantics, while `fix_retry` reuses the retry-step planner for failed or interrupted runs. The proof is daemon tests for active, stale, already-terminal, parked, ambiguous, tracker-transition-failed, and successful paths.

Milestone 6 is artifact review availability. Reviewers should see `review_artifacts` enabled only when retained workflow, step, structured-output, or publication artifact refs are available, disabled with stable reasons otherwise, and encoded without raw artifact contents or absolute local paths. The proof is artifact fixture tests plus a UI/server handoff note saying whether a later artifact content query is required.

Milestone 7 is validation and button-enable evidence. Reviewers should see focused tests, full repository validation, format checks, production linting, implementation-ticket handoff notes, and explicit dogfood evidence requirements. Browser buttons remain disabled or feature-gated until the deferred live/dogfood checks in Validation and Acceptance are collected; those dogfood checks are pre-button requirements, not pre-publish requirements for the Core contract.

## Surprises & Discoveries

The current production tree has no `src/scherzo/work_item*.gleam` implementation yet, although a checked-in plan already describes a future WorkItem query contract. This action plan therefore treats WorkItem as a prerequisite contract and explicitly says not to attach these actions to legacy task queries.

The existing `src/scherzo/control/command.gleam` already has reusable command/result vocabulary and retry-step/artifact-publication variants, and the local and UI control paths already transport command results. That lowers command-reporting risk, but it does not remove the need for a WorkItem action envelope because the UI should send action ids, not low-level operator internals.

The ledger projection in `src/scherzo/state/projection.gleam` already tracks workflow runs, provenance, step attempts, publication attempts, manifests, parked issues, and dispatch pause state. Action metadata should use that projection plus daemon runtime state rather than inventing a separate workflow-subtask database.

## Decision Log

- Decision: WorkItem action ids are stable strings owned by Core: `work_item.run_workflow`, `work_subtask.cancel`, `work_subtask.review_artifacts`, and `work_subtask.fix_retry`. Rationale: stable ids let UI tests and server requests remain provider-neutral while Core keeps authority over availability and execution. Date: 2026-06-16.
- Decision: Use one first-class WorkItem action command envelope for UI button clicks, and map internally to existing operator commands or shell handlers where appropriate. Rationale: this avoids exposing raw command payloads in read DTOs while preserving existing command result semantics. Date: 2026-06-16.
- Decision: `review_artifacts` is read-only metadata, not a mutating operator command. Rationale: artifact review should never require command authority and should expose only safe retained refs until a separate read-only artifact content query is justified. Date: 2026-06-16.
- Decision: `run_workflow` requires a new tracker workflow-subtask creation capability with daemon and tracker dedupe. Rationale: the current tracker adapter can list, refresh, look up, comment, transition state, and publish scheduled failures, but it does not create Linear child issues or subtasks. Date: 2026-06-16.
- Decision: UI buttons must remain feature-gated until deterministic tests pass and live dogfood evidence proves duplicate, stale, cancellation, retry, artifact, authorization, and redaction behavior. Rationale: action metadata crosses state derivation and destructive controls, so automated unit evidence alone is not enough to enable operators to click buttons in a browser. Date: 2026-06-16.
- Decision: Do not change ExecPlan workflow helpers, workflow schemas, or dogfood scripts for this WorkItem action issue. Rationale: Scherzo will materialize implementation-pack artifacts from the structured submission, and this feature's production scope is daemon/UI action behavior rather than workflow tooling. Date: 2026-06-16.
- Decision: Derive action metadata from provider-live WorkItem data and current daemon/ledger state without introducing a provider cache. Rationale: stale buttons are the central safety risk, and a cache would require separate stale indicators, invalidation rules, rollout, and recovery design. Date: 2026-06-16.

## Outcomes & Retrospective

This plan has not been implemented yet. The intended outcome is a safe Core-owned action surface for WorkItem workflow subtasks, with UI rendering driven by query metadata and mutations routed through the authenticated daemon command plane. The main intentional gaps are browser rendering and raw artifact content browsing, which should be handled by follow-up UI and artifact-query work after Core action behavior is proven.

## Validation and Acceptance

Acceptance outcome 1 is stable read-only action metadata. Evidence must include codec and derivation tests proving the four required action ids, labels, mutating/read-only classification, deterministic action instance ids, enabled flags, disabled reason codes/messages, and action fingerprints appear in WorkItem and WorkSubtask query JSON for representative parent, active subtask, failed subtask, completed subtask, and artifact scenarios.

Acceptance outcome 2 is safe redaction and artifact availability. Evidence must include tests that inject local control tokens, enrollment tokens, API keys, raw provider bodies, raw prompts, descriptions, comments, raw artifact bodies, and absolute local paths into fixtures, serialize WorkItem action responses, and assert those markers are absent while safe labels, ids, artifact refs, hashes, byte counts, and display paths remain present.

Acceptance outcome 3 is mutating command correctness. Evidence must include command codec, local control server, UI/remote command protocol, and daemon handler tests for `work_item_action`: wrong token rejected before backend dispatch, stale action rejected without side effects, duplicate idempotency key replays the same result, duplicate key with different payload returns an idempotency conflict, unsupported action id is rejected, and command results use existing `CommandResult` statuses rather than top-level protocol failures.

Acceptance outcome 4 is behavior coverage for each candidate action. Evidence must include fake tracker and daemon tests showing `run_workflow` creates or reuses exactly one child workflow subtask and handles provider errors; `cancel` resolves and cancels an active run/session and reports tracker transition failures safely; `review_artifacts` is enabled only when safe retained refs exist and never mutates; and `fix_retry` delegates to retry-step planning for failed or interrupted runs while rejecting active, terminal, parked, ambiguous, and non-repairable runs.

Acceptance outcome 5 is provider-live and helper-scope evidence. Evidence must include tests proving action derivation calls the WorkItem provider-live capability or consumes its current result for each WorkItem query, recomputes current state before mutating commands, does not read or write a new provider cache, and does not depend on retained artifact bodies. The implementation must not modify ExecPlan workflow helper scripts or workflow schema files for this feature; if such a change appears necessary, treat it as a scope change for a separate issue.

Acceptance outcome 6 is repository validation. From the repository root, run `direnv exec . gleam test`, `direnv exec . gleam format --check src test`, `direnv exec . gleam run -m glinter`, and `direnv exec . gleam run -m scherzo_lint`; each command must exit zero. If `.envrc` is blocked, inspect `.envrc`, run `direnv allow .`, and retry the same commands.

Acceptance outcome 7 is pre-button dogfood evidence. This evidence is deferred until after Core implementation but is required before enabling browser buttons for real users, not before publishing the tested Core contract: with a Linear-backed daemon and a non-production parent issue, collect command/query transcripts showing action metadata, two `run_workflow` clicks with no duplicate child issue, stale click rejection after manual state change, cancel of an active subtask, fix/retry of a failed subtask, review-artifact availability after a completed run, safe command results, and absence of secrets or raw provider/artifact bodies in daemon and server logs.

## Rollout, Recovery, and Idempotence

Rollout is additive and feature-gated. Existing task queries, existing `scherzoctl` commands, existing operator command names, and existing WorkItem read fields stay compatible. The UI server should render WorkItem buttons only when the daemon advertises the action-capable WorkItem query contract and the browser feature flag is enabled.

Recovery is to stop advertising or rendering actions while leaving WorkItem reads intact. If the action executor misbehaves, the daemon can reject `work_item_action` with `unsupported_query` or `not_allowed`, the UI server can hide buttons, and operators can continue using existing `scherzoctl retry-step`, `abort`, `stop-after-turn`, and artifact commands. Because action metadata is derived and not cached, rollback does not require cache deletion or data migration.

Idempotence is mandatory for every mutating action. The same idempotency key and payload must return the same result, the same key with a different payload must be rejected, duplicate create-subtask attempts must not create duplicate Linear children, repeated cancel after a replay must not abort twice, and stale action fingerprints must be revalidated before any provider or worker mutation occurs.

## Open Questions and Clarifications Needed

No blocking clarification is required before implementation. The task's two open questions are resolved by this plan: UI-originated buttons use one first-class WorkItem action command envelope that delegates to existing operator semantics where appropriate, and artifact review starts with safe retained artifact refs rather than raw content endpoints. Product and UI owners may still tune button copy, confirmation text, and whether artifact content previews are worth a separate read-only query before browser launch.
