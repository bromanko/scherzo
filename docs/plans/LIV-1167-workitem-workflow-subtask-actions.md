# WorkItem workflow-subtask action metadata and controls

This ExecPlan v2 review document is the human review surface for LIV-1167. It plans a later implementation that lets Scherzo Core describe and execute Work screen actions for workflow subtasks. Mechanical steps, tests, interfaces, dependencies, and artifact notes are supplied through the structured implementation-pack submission captured by Scherzo.

## Purpose / Big Picture

The Work screen should show only actions that Scherzo Core believes are valid for the current task, subtask, workflow run, retained artifact, and operator authority state. After this plan is implemented, `work_item_list` and `work_item_show` responses can include stable action metadata for running a workflow, cancelling an active workflow subtask, reviewing retained artifacts, and fixing or retrying a failed workflow subtask.

The visible outcome is not a finished browser UI. The visible outcome is a daemon-owned contract: Core publishes stable action descriptors and fingerprints, the sidecar or browser can render them and send an action id back through the authenticated control plane, Core revalidates the click against fresh state, and the sidecar refreshes the WorkItem query state after receiving the command result. Browser copy, layout, confirmations, and feature gates remain presentation responsibilities, not Core policy.

## Problem Framing and Constraints

Scherzo now has WorkItem read queries for parent tasks and subtasks, but those responses do not yet include action descriptors. The current tree also has operator commands such as `retry`, `retry-step`, `abort`, `stop-after-turn`, and artifact-publication retry, but those commands are operator-centric and do not give the Work UI a safe list of available buttons. If the UI invents its own rules, it can offer stale, destructive, unsupported, or unauthorized actions.

Action availability must be read-only metadata. An action descriptor may say that a button is enabled or disabled and why, but it must not be treated as permission to mutate. Every mutating request must be authenticated by the local control token or UI-server daemon credential, decoded through the daemon control plane, revalidated by Core against fresh provider and daemon state, deduped by idempotency key, and reported as a command result. The metadata and result payloads must not expose credentials, local control tokens, raw provider payloads, prompts, descriptions, comments, raw artifact contents, or absolute local paths.

The central seam is deliberate. Core and the daemon own stable action ids, enabled and disabled policy, disabled reason codes and safe messages, action fingerprints, stale-state revalidation, idempotency receipts, and workflow or tracker mutations. The sidecar and browser own browser/session authorization, presentation, confirmation UX, feature gates, copy and layout, click transport, and refreshing `work_item_show` or `work_item_list` after a command result. The sidecar may hide a Core action behind a feature flag or require confirmation before transport, but it must not make a disabled action enabled or synthesize provider mutations.

Action metadata must preserve provider-live WorkItem behavior: each query derives from the current WorkItem provider capability plus current daemon runtime and ledger state, not from a new daemon provider cache, legacy flat task DTOs, retained artifact bodies, or helper-generated files. This issue is not a docs/helper migration; do not change `workflows/dogfood/`, workflow schema files, or ExecPlan helper scripts for this feature unless a later, separate issue explicitly expands scope.

## Strategy Overview

Implement the feature in smaller, independently reviewable slices. The first slice is read-only: extend WorkItem and WorkSubtask DTOs with an `actions` array whose entries are generated by small Core modules from provider-live WorkItem data, workflow configuration, daemon runtime state, the ledger projection, retained artifact metadata, and tracker capability flags. Use stable action ids `work_item.run_workflow`, `work_subtask.cancel`, `work_subtask.review_artifacts`, and `work_subtask.fix_retry`. Each descriptor should include a deterministic action instance id, label, read-only or mutating classification, enabled flag, structured disabled reason with stable code and safe message when disabled, action fingerprint, and redacted target summary.

The second slice proves the authenticated action envelope without high-blast-radius mutations. Add a first-class control-plane command such as `work_item_action` that carries the action id, instance id, target, observed fingerprint, idempotency key, and only safe action parameters. Initially this envelope should authenticate, decode, sanitize, rederive current state, reject stale or disabled actions, record or replay idempotency receipts, and return normal `CommandResult` values, but it should not create tracker children or stop workers. It may return a deliberate `rejected` or `not_allowed` result for mutating actions whose executor slice has not shipped yet.

The third slice may add lower-blast-radius actions after the envelope proves reliable. `fix_retry` should delegate to the existing retry-step planning path for failed or interrupted workflow runs, and `cancel` should resolve the currently active workflow subtask and reuse existing worker/session cancellation semantics. These actions still require fresh revalidation and idempotency. They should be implemented only if the envelope slice demonstrates that stale, duplicate, unauthorized, and disabled clicks are safely contained.

The fourth slice is `run_workflow`, and it is intentionally separate because it creates tracker children. It requires a tracker capability that can ensure exactly one child workflow subtask for a parent and workflow id, attach only allowlisted labels and metadata, use a configured ready state, and dedupe by a Scherzo action marker before issuing a provider create mutation. `run_workflow` may appear as a descriptor before this slice, but Core must keep it disabled with a safe reason until the tracker capability, duplicate-create tests, and dogfood evidence exist.

The daemon actor remains a thin shell. Action derivation and execution should live in small tested Core modules outside `src/scherzo/orchestrator/daemon.gleam`, for example under `src/scherzo/work_item/`. `src/scherzo/orchestrator/daemon.gleam` may pass dependencies, route the new command to a shell or executor, and send replies, but it must not accumulate action-policy branches, disabled-reason matrices, fingerprint construction, idempotency logic, or tracker child-creation rules.

## Alternatives Considered

Hard-coding button rules in the UI is the simplest implementation, but it is unsafe because the UI cannot reliably know daemon runtime state, tracker capabilities, retry repairability, artifact retention, or command authority. It would also duplicate Scherzo policy across Core and browser code.

Returning raw `OperatorCommand` payloads in WorkItem query responses was rejected because it would couple the UI to daemon internals and tempt the browser to replay commands without revalidation. Stable action ids plus a daemon action executor preserve a declarative UI contract while still reusing existing operator semantics inside Core.

Making every candidate action a separate first-class `OperatorCommand` was also rejected for the initial UI contract. Existing operator commands should remain available for `scherzoctl` and operators, but WorkItem buttons need one target-checked action envelope that can carry an observed state fingerprint and idempotency key consistently across cancel, retry, create, and future actions.

Bundling child workflow-subtask creation into the metadata seam was rejected after review in PR #532. `run_workflow` is the highest-blast-radius action because it creates provider-side child issues and affects tracker workflow. The smaller plan proves read-only descriptors and the action envelope first, then lower-blast-radius execution, and only then the tracker child-creation capability.

For artifact review, this plan chooses safe retained-artifact refs and availability metadata first, not raw artifact content endpoints. A later UI issue may add a read-only artifact content/query endpoint if the browser needs previews; until then the action can open or list safe refs, hashes, sizes, and display paths without exposing local filesystem paths or artifact bodies.

## Risks and Countermeasures

The main product risk is showing an enabled button that is no longer safe. Counter this by treating descriptors as hints, adding an observed action fingerprint to mutating requests, and making Core recompute current action availability before it mutates anything. Stale requests must return a safe `rejected` result such as `stale_action` or the current disabled reason.

A seam-regression risk is allowing action policy to grow inside `src/scherzo/orchestrator/daemon.gleam` or the sidecar. Counter this with a module boundary: derivation, fingerprints, disabled reasons, idempotency, and action execution live in tested Core modules; the daemon actor only routes messages; the sidecar only authenticates browser sessions, renders, confirms, transports clicks, and refreshes query state. Code review should reject branches in the daemon actor or browser that replicate Core availability policy.

A provider-live/cache regression risk is deriving action metadata from stale scheduler data or adding a new cache without invalidation rules. Counter this by making action derivation explicit about its sources, using the WorkItem provider-live capability for task hierarchy, using the ledger and runtime only for Scherzo workflow state, and adding tests that prove repeated queries and commands re-read or re-derive current state without writing provider cache artifacts.

The main data-integrity risk is duplicate workflow-subtask creation. Counter this by postponing `run_workflow` until after the read-only and envelope slices, then requiring a UI/server idempotency key, a daemon action-command receipt keyed by action id and target, and a tracker-level dedupe check for an existing child subtask with the same parent, workflow id, and Scherzo action marker before issuing a provider create mutation. The same key with a different payload must be rejected as an idempotency conflict.

The main safety risk for cancellation is partial failure. Counter this by introducing cancellation only after the envelope proof, resolving the active run/session immediately before cancellation, recording local cancellation through existing workflow-cancelled or worker-stop semantics, and reporting tracker transition failures explicitly. If a worker was stopped but a tracker state transition failed, the command result must say that local cancellation was applied and tracker state needs refresh or repair; retrying with the same idempotency key should replay the same result rather than aborting twice.

The main privacy risk is leaking rich task, artifact, or provider data through action DTOs. Counter this with allowlisted fields, redaction tests using obvious secret markers, no descriptions/comments/raw payloads, no raw artifact contents, and no absolute local paths in WorkItem action metadata.

## Scope Boundaries

In scope are Core-owned WorkItem/WorkSubtask action DTOs, action derivation, disabled reasons, action fingerprints, stale-state checks, action-command decoding, idempotency receipts, safe command results, lower-blast-radius cancel and fix/retry execution after envelope proof, retained-artifact availability metadata, and the separately sequenced tracker workflow-subtask creation capability for `run_workflow`.

Out of scope for Core are final browser rendering, browser/session authorization, confirmation text, button copy and layout, click debouncing, sidecar feature-gate policy, and the sidecar's post-command query refresh implementation. Those presentation concerns are required for launch, but they are owned by the sidecar/UI slice and must not move semantic action policy out of Core.

Out of scope for this plan are recursive workstream playbooks, raw artifact content browsing, broad provider cache design, changing legacy `task_list`/`task_show`, retiring existing `scherzoctl` commands, ExecPlan workflow helper or schema migration, and enabling destructive UI buttons without dogfood evidence.

`run_workflow` child-subtask creation is in scope only as a separate tracker-capability slice after read-only metadata and the action envelope have passed. If implementation capacity is limited, it is acceptable to ship and review slices 1 and 2 first with `run_workflow` disabled, then create a follow-up implementation task for the tracker child-creation slice.

## Milestones

Milestone 1 is the read-only Core action descriptor and fingerprint contract. Reviewers should see WorkItem and WorkSubtask DTOs with stable action ids, labels, enabled flags, disabled reason codes/messages, mutating-versus-read-only classification, deterministic action instance ids, action fingerprints, and safe target/artifact summaries. The proof is codec and derivation tests covering every candidate action, no-secret serialization checks, and no mutating command path.

Milestone 2 is the provider-live action-state derivation engine. Reviewers should see a daemon-readable action snapshot that combines provider-live WorkItem hierarchy, workflow configuration, dispatch pause state, active/pending workers, ledger projection workflow runs, step attempts, parked issues, artifact refs, and tracker capability flags. The proof is state-matrix tests for parent terminal state, dispatch paused, unsupported provider capability, active subtask, failed/interrupted run, completed run with artifacts, missing or corrupt artifact metadata, and provider-live/no-cache behavior across repeated queries.

Milestone 3 is the authenticated action command envelope without high-blast-radius mutations. Reviewers should see local control, remote/UI command protocol, command codec, idempotency receipt, stale-fingerprint, disabled-action, unsupported-action, target-not-found, and sanitized result tests for `work_item_action`. At the end of this milestone, mutating actions that do not yet have an executor return safe `rejected` or `not_allowed` command results instead of mutating provider or worker state.

Milestone 4 is lower-blast-radius execution for `cancel` and `fix_retry`, if the envelope milestone proves safe. Reviewers should see `cancel` resolve the current active workflow subtask to a run/session and reuse existing cancellation semantics, while `fix_retry` reuses the retry-step planner for failed or interrupted runs. The proof is daemon/Core executor tests for active, stale, already-terminal, parked, ambiguous, tracker-transition-failed, duplicate-idempotency, and successful paths. `run_workflow` remains disabled in this milestone.

Milestone 5 is artifact review availability. Reviewers should see `work_subtask.review_artifacts` remain read-only, enabled only when retained workflow, step, structured-output, or publication artifact refs are available, disabled with stable reasons otherwise, and encoded without raw artifact contents or absolute local paths. The proof is artifact fixture tests plus a UI/server handoff note saying whether a later artifact content query is required.

Milestone 6 is the separate `run_workflow` tracker child-creation capability. Reviewers should see a tracker capability and fake/Linear implementation path that can ensure exactly one child workflow subtask for a parent and workflow id, attach the configured workflow label and Scherzo action marker, choose the configured ready state, and either start dispatch immediately when safe or return `queued` for normal dispatch. The proof is duplicate-create tests, stale-click tests, tracker error sanitization tests, and dogfood evidence before enabling the browser button.

Milestone 7 is validation and button-enable evidence. Reviewers should see focused tests, full repository validation, format checks, production linting, implementation-ticket handoff notes, and explicit dogfood evidence requirements. Browser buttons remain disabled or feature-gated until the deferred live/dogfood checks in Validation and Acceptance are collected; those dogfood checks are pre-button requirements, not pre-publish requirements for the Core contract.

## Surprises & Discoveries

The current production tree now has a WorkItem read-query contract in `src/scherzo/work_item.gleam`, `src/scherzo/control/query/work_item_dto.gleam`, and `src/scherzo/linear/work_item_query.gleam`. The action plan therefore builds on that checked-in WorkItem surface and should not attach new actions to legacy task queries.

The existing `src/scherzo/control/command.gleam` already has reusable command/result vocabulary and retry-step/artifact-publication variants, and the local and UI control paths already transport command results. That lowers command-reporting risk, but it does not remove the need for a WorkItem action envelope because the UI should send action ids, observed fingerprints, and idempotency keys, not low-level operator internals.

The ledger projection in `src/scherzo/state/projection.gleam` already tracks workflow runs, provenance, step attempts, publication attempts, manifests, parked issues, command receipts, and dispatch pause state. Action metadata should use that projection plus daemon runtime state rather than inventing a separate workflow-subtask database.

The largest implementation risk is not the descriptor DTO; it is allowing the tracker child-creation capability for `run_workflow` to ride along before the envelope has proved authentication, stale-state rejection, and idempotency. The revised plan treats `run_workflow` as a later slice and keeps it disabled until that capability is proven.

## Outcomes & Retrospective

This plan has not been implemented yet. The intended outcome is a safe Core-owned action surface for WorkItem workflow subtasks, with UI rendering driven by query metadata and mutations routed through the authenticated daemon command plane. The main intentional gaps are browser rendering, browser/session authorization, copy/layout, confirmation UX, and raw artifact content browsing, which should be handled by follow-up sidecar/UI and artifact-query work after Core action behavior is proven.

This revision narrows the implementation path. It no longer asks implementers to build metadata, command execution, and tracker child creation as one lump. It proves read-only descriptors first, then the command envelope and idempotency without high-blast-radius mutations, then lower-blast-radius actions if still justified, and finally `run_workflow` child creation as its own tracker-capability slice.

## Validation and Acceptance

Acceptance outcome 1 is a clear Core/sidecar seam. Evidence must include code review and tests showing Core owns action ids, enabled/disabled policy, disabled reason codes/messages, fingerprints, stale-state revalidation, idempotency, and workflow/tracker mutations, while the sidecar owns browser/session authorization, rendering, confirmation UX, feature gates, copy/layout, click transport, and refreshing WorkItem query state after command results. No browser or sidecar code may synthesize action availability or provider mutations.

Acceptance outcome 2 is stable read-only action metadata. Evidence must include codec and derivation tests proving the four required action ids, labels, mutating/read-only classification, deterministic action instance ids, enabled flags, disabled reason codes/messages, and action fingerprints appear in WorkItem and WorkSubtask query JSON for representative parent, active subtask, failed subtask, completed subtask, and artifact scenarios.

Acceptance outcome 3 is safe redaction and artifact availability. Evidence must include tests that inject local control tokens, enrollment tokens, API keys, raw provider bodies, raw prompts, descriptions, comments, raw artifact bodies, and absolute local paths into fixtures, serialize WorkItem action responses, and assert those markers are absent while safe labels, ids, artifact refs, hashes, byte counts, and display paths remain present.

Acceptance outcome 4 is mutating command-envelope correctness before high-blast-radius actions. Evidence must include command codec, local control server, UI/remote command protocol, and Core/daemon handler tests for `work_item_action`: wrong token rejected before backend dispatch, stale action rejected without side effects, disabled action rejected without side effects, duplicate idempotency key replays the same result, duplicate key with different payload returns an idempotency conflict, unsupported action id is rejected, and not-yet-implemented mutating actions return safe `CommandResult` values rather than provider or worker side effects.

Acceptance outcome 5 is behavior coverage for each later candidate action. Evidence must include fake tracker and daemon/Core executor tests showing `cancel` resolves and cancels an active run/session and reports tracker transition failures safely; `review_artifacts` is enabled only when safe retained refs exist and never mutates; `fix_retry` delegates to retry-step planning for failed or interrupted runs while rejecting active, terminal, parked, ambiguous, and non-repairable runs; and `run_workflow` remains disabled until the separate tracker capability can create or reuse exactly one child workflow subtask and sanitize provider errors.

Acceptance outcome 6 is provider-live, daemon-thinness, and helper-scope evidence. Evidence must include tests proving action derivation calls the WorkItem provider-live capability or consumes its current result for each WorkItem query, recomputes current state before mutating commands, does not read or write a new provider cache, and does not depend on retained artifact bodies. The implementation must keep action policy out of `src/scherzo/orchestrator/daemon.gleam` except for minimal routing/dependency wiring, and must not modify ExecPlan workflow helper scripts or workflow schema files for this feature.

Acceptance outcome 7 is repository validation. From the repository root, run `direnv exec . gleam test`, `direnv exec . gleam format --check src test`, `direnv exec . gleam run -m glinter`, and `direnv exec . gleam run -m scherzo_lint`; each command must exit zero. If `.envrc` is blocked, inspect `.envrc`, run `direnv allow .`, and retry the same commands.

Acceptance outcome 8 is pre-button dogfood evidence. This evidence is deferred until after Core implementation but is required before enabling browser buttons for real users, not before publishing the tested Core contract: with a Linear-backed daemon and a non-production parent issue, collect command/query transcripts showing action metadata, rejected stale clicks after manual state change, duplicate idempotency replay, cancel of an active subtask if that slice shipped, fix/retry of a failed subtask if that slice shipped, review-artifact availability after a completed run, two `run_workflow` clicks with no duplicate child issue only after the tracker capability slice ships, safe command results, post-command WorkItem refresh, and absence of secrets or raw provider/artifact bodies in daemon and server logs.

## Rollout, Recovery, and Idempotence

Rollout is additive, slice-by-slice, and feature-gated. Existing task queries, existing `scherzoctl` commands, existing operator command names, and existing WorkItem read fields stay compatible. Slice 1 can ship read-only action metadata with sidecar buttons hidden. Slice 2 can ship the authenticated envelope while mutating actions still return safe rejection results. Slice 3 can expose lower-blast-radius `cancel` and `fix_retry` behind Core and sidecar gates after focused evidence. Slice 4 can expose `run_workflow` only after tracker child dedupe, provider error sanitization, and dogfood transcripts are complete.

Recovery is to stop advertising or rendering actions while leaving WorkItem reads intact. Core can disable actions by returning stable disabled reasons, the daemon can reject `work_item_action` with `unsupported_action`, `not_allowed`, or `action_disabled`, and the sidecar can hide buttons through feature flags. Operators can continue using existing `scherzoctl retry-step`, `abort`, `stop-after-turn`, and artifact commands. Because action metadata is derived and not cached, rollback of the metadata slice does not require cache deletion or data migration.

Idempotence is mandatory for every mutating action and must be proven before any provider or worker side effect. The same idempotency key and payload must return the same result, the same key with a different payload must be rejected, duplicate create-subtask attempts must not create duplicate Linear children, repeated cancel after a replay must not abort twice, and stale action fingerprints must be revalidated before any provider or worker mutation occurs. The sidecar may retry transport after network failures, but Core remains responsible for replaying or rejecting by idempotency receipt.
