# LIV-751 ledger aggregate invariants and causal effects review

This is a focused ExecPlan review for LIV-751. It plans the follow-up implementation for ledger aggregate validation and typed causal continuations; it does not implement the code changes or invent a Scherzo bundle reference.

## Purpose / Big Picture

Operators should be able to trust that a retained ledger explains every durable workflow effect. After this change, Scherzo rejects new ledger batches that would create step attempts or terminal workflow records without a known parent workflow run, refuses to spawn a claimed worker unless the claim-start batch was non-empty, valid, and appended successfully, and reports any already-retained orphan step-only runs through `scherzoctl state status` with a clear read-only diagnostic.

## Problem Framing and Constraints

LIV-749 showed that a durable side effect can continue after the ledger batch meant to justify it is missing or malformed. The immediate claim-handoff mismatch is a symptom of a broader aggregate gap: projection currently tolerates child records such as `StepAttemptPrepared`, `StepAttemptStarted`, `StepAttemptContinuationStarted`, `StepAttemptPiSessionRecorded`, `StepAttemptFinished`, `StepAttemptInterrupted`, `StepAttemptSuperseded`, `WorkflowRunFinished`, and `WorkflowRunInterrupted` even when no parent `WorkflowRunStarted` or `WorkflowRunStartedWithTask` record exists. The fix must protect future appends without breaking read-only inspection of old retained ledgers that already contain corrupt or orphaned records.

## Strategy Overview

Use two layers. The authoritative layer is append-time aggregate validation against the current projection plus the proposed batch, because every writer that mutates the local ledger must pass through it before bytes are written. The transition layer should also stop constructing impossible causal effects by replacing generic `ContinueWith(LedgerContinuation)` continuations with typed causal batches, beginning with a `ClaimStartedBatch -> SpawnClaimedWorker` path and then the existing park-report-after-ledger path.

The aggregate invariants are plain: a step attempt belongs to a workflow run, so any `step_attempt_*` record must reference a workflow run that already exists or is started in the same accepted batch; a workflow terminal record finishes, interrupts, or supersedes an existing workflow run, so those records must not introduce unknown parent runs; and a durable effect may only happen after the exact ledger fact that justifies it was appended. Code-level validation points are `src/scherzo/state/ledger.gleam` for locked append validation, `src/scherzo/workflow_checkpoint.gleam` and `src/scherzo/orchestrator/daemon.gleam` for using the validated writer, `src/scherzo/orchestrator/effects/types.gleam` for typed causal append requests, `src/scherzo/orchestrator/transitions/claims.gleam` and `src/scherzo/orchestrator/transition.gleam` for claim-spawn continuation handling, and `src/scherzo/state/local_artifacts.gleam` plus `src/scherzo/ctl.gleam` for orphan status reporting.

## Alternatives Considered

Validating only in the transition layer was rejected because workflow checkpoints, startup recovery, repair commands, and future writers can append outside the claim transition path. Validating only in the raw JSONL append function was rejected because the transition API would still allow effects to be represented without a causal batch type, making future regressions easy. Rewriting old retained ledgers was rejected for this slice because it risks losing inspectability; diagnostics and separately gated repair are safer.

## Risks and Countermeasures

The main risk is blocking legitimate recovery records that intentionally repair old state. Counter this by validating only new append batches, allowing a parent run established earlier or in the same batch, and keeping read-only replay/projection permissive. A second risk is a false sense of safety if empty batches still return success; counter this by making typed causal append requests reject empty or structurally invalid claim-start batches before any worker spawn continuation can be produced. A third risk is noisy operator output for existing corruption; counter this with stable reason codes such as `orphan_step_attempts_without_workflow_run` and concise counts and run ids in status output.

## Scope Boundaries

In scope are append-time aggregate validation for workflow-run parents, transition-side typed causal append requests for claimed worker spawn and the current park-report continuation, focused tests for empty and invalid claim-start appends, focused tests for orphan step attempts and unknown terminal parents, and `state status` diagnostics for retained orphan step-only runs. The implementation must inventory every current local writer named in this review, including daemon transition appends, startup recovery appends, workflow checkpoint writes, state repair commands, and any explicit state/repair command that can add workflow-run or step-attempt records. Out of scope are automatic repair of old corrupt ledgers, wholesale ledger schema migration, changing read-only projection semantics, changing unrelated workstream ledger validation, docs/helper migration work, provider-live or cache behavior, browser UI checks, and redesigning worker lifecycle or tracker handoff behavior beyond the causal continuation boundary. Pre-publish acceptance should rely on automated fixtures and CLI evidence; a manual `scherzoctl state status --root <fixture-root>` smoke command is permitted only as a fallback if the implementer records why fixture-only CLI coverage could not be made deterministic. Real daemon dogfood on retained operator state is deferred until after implementation validation and is not a publish blocker.

## Milestones

Milestone 1 establishes the append-time validator in `src/scherzo/state/ledger.gleam`. At the end of this milestone, `append_many` rejects new workflow child records whose `run_id` is absent from the current projection and absent from the same proposed batch, while accepting a same-batch `WorkflowRunStartedWithTask` followed by step-attempt records. The expected proof is new `test/state_ledger_test.gleam` coverage for every current `step_attempt_*` ledger kind (`step_attempt_prepared`, `step_attempt_started`, `step_attempt_continuation_started`, `step_attempt_pi_session_recorded`, `step_attempt_finished`, `step_attempt_interrupted`, and `step_attempt_superseded`) plus `workflow_run_finished`, `workflow_run_interrupted`, and `workflow_run_superseded`, with clear reason strings such as `unknown_workflow_run` or `orphan_step_attempt_without_workflow_run`.

Milestone 2 routes every production ledger writer that can create workflow-run or step-attempt records through the validator. This includes daemon transition appends in `src/scherzo/orchestrator/daemon.gleam`, startup recovery append paths, checkpoint writes in `src/scherzo/workflow_checkpoint.gleam`, and explicit state or repair commands that append workflow repair/provenance records. At the end of this milestone, read-only replay still tolerates old corrupt data, but every new write goes through one locked validation path before bytes are appended.

Milestone 3 replaces generic causal continuations with typed append-success tokens for the current causal effects. The first token is for claim-start worker spawn, so `StartWorker` can only be constructed from a non-empty, structurally valid claim-start batch that has been appended successfully. The second token preserves the existing park-report-after-ledger behavior. The proof is `test/orchestrator_transition_ledger_test.gleam` coverage showing empty and invalid claim-start append paths clear or retain pending state as specified, emit a warning, and never emit `StartWorker`.

Milestone 4 adds operator diagnostics for retained orphan step-only runs without changing replay permissiveness. `src/scherzo/state/local_artifacts.gleam` should compute concise warnings from the current projection, and `src/scherzo/ctl.gleam` should print them in `state status`. The proof is automated `test/state_local_artifacts_test.gleam` or `test/ctl_test.gleam` coverage whose output contains `orphan_step_attempts_without_workflow_run`, the affected run id, an attempt count, and wording that read-only inspection is still allowed.

Milestone 5 collects the final evidence and has no remaining implementation work. From the repository root, the implementer must run `direnv exec . gleam format --check src test`, `direnv exec . gleam test`, `direnv exec . gleam test -- --suite contract` if any contract-tagged CLI or daemon coverage was touched, `direnv exec . gleam run -m glinter`, and `direnv exec . gleam run -m scherzo_lint`, and record that all commands exited zero with no new production policy errors.

## Rollout, Recovery, and Idempotence

Rollout should be additive: introduce validator types and tests, switch writers to validated append calls, then narrow transition continuation types. Existing retained ledgers remain readable because replay and projection stay permissive; only new writes are rejected. No data migration, docs/helper migration, provider-live change, or cache invalidation is part of rollout. Recovery from a bad validator rollout is to revert the writer switch or the typed continuation commit, leaving old state untouched; if a specific writer is over-rejected, revert that writer to the previous append path while retaining read-only diagnostics. Re-running validation, status checks, and tests is idempotent because rejected invalid batches do not mutate the ledger and status diagnostics are read-only. After implementation validation, an operator may dogfood by running `scherzoctl state status --root <workspace-root>` against a retained development workspace, but that deferred check is observational and must not mutate retained state.

## Open Questions and Clarifications Needed

No open question blocks implementation. The plan intentionally answers the task questions as: validation lives in both places with ledger append as authority; claim-start spawn and park-report-after-ledger are the first causal continuations; orphan repair is deferred behind a separate gate; and invariant violations surface as command or append rejection for attempted writes, daemon warnings for background append attempts, and `state status` warnings for retained historical corruption.
