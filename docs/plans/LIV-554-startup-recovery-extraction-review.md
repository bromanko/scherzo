# LIV-554 startup recovery extraction review

This is a focused ExecPlan review for Rank 2 of the daemon decomposition v2 sequence. It is documentation-only for LIV-554; the extraction itself belongs in the generated follow-up implementation task.

## Purpose / Big Picture

Scherzo should keep the daemon as the stable public actor while moving startup recovery decisions into a smaller, testable subsystem. After the follow-up implementation, maintainers should be able to reason about ledger/projection replay, recovered retry timers, cleanup work, command outbox handling, park reports, scheduled recovery reconstruction, and workflow resumption without editing the 6k-line daemon shell. Operators should see unchanged daemon startup and control behavior. This review also makes the implementation evidence explicit: characterization tests come before code movement, targeted startup-recovery tests and full validation are pre-publish requirements, and any manual/operator dogfood check is deferred unless the implementation intentionally changes operator-visible behavior.

## Problem Framing and Constraints

The source plan, `docs/plans/LIV-523-daemon-decomposition-v2.md`, ranks startup recovery planner and resumption extraction as Rank 2. In the current tree, `src/scherzo/orchestrator/daemon.gleam` is 6,719 lines and still owns the private `StartupRecovery` type, `load_startup_recovery`, issue-state fetch chunking, recovery observation mapping, scheduled recovery reconstruction, and recovered workflow launch helpers. `src/scherzo/orchestrator/scheduled_runtime.gleam` already exists, while `src/scherzo/orchestrator/startup_recovery.gleam`, `src/scherzo/orchestrator/recovered_workflow_runner.gleam`, and `test/orchestrator_startup_recovery_test.gleam` do not yet exist.

The extraction must preserve current ledger/projection semantics, fail-closed startup recovery behavior, public daemon messages, control-plane behavior, Linear command syntax, EventHub event shape, workflow YAML semantics, retry/backoff policy, provider-live behavior, cache behavior, and any docs/helper infrastructure. `test/state_recovery_test.gleam` must remain in place. This plan may rely on Rank 1 scheduled-runtime work that is already present, but it must not plan or implement Ranks 1 or 3 through 6. The follow-up implementation is not accepted merely because `daemon.gleam` gets shorter; it is accepted only when the named characterization, parity, full validation, and lint evidence exists.

## Strategy Overview

The right-sized approach is characterization first, then extraction behind the existing daemon startup path. The follow-up implementation should add tests that describe today’s behavior before moving code, introduce `src/scherzo/orchestrator/startup_recovery.gleam` as the owner of recovery planning and recovery data shaping, and leave `daemon.start` as the compatibility entry point that calls the planner and applies returned startup actions. If recovered workflow launch remains process-heavy after resumption planning is separated, that process-running code should move to `src/scherzo/orchestrator/recovered_workflow_runner.gleam`; otherwise the runner module can be omitted and that decision should be recorded.

The daemon should finish the slice as a shell that loads the runtime bundle, starts infrastructure, calls startup recovery, applies transition/effect actions, and registers any recovered workflow workers. Recovery policy and data reconstruction should no longer live in the daemon. The extracted modules must not import `src/scherzo/orchestrator/daemon.gleam`; if startup recovery needs to report startup failures, it should expose a neutral error shape that the daemon maps to its public `StartupError`, or move the shared type to a neutral module. If implementation discovers that this rank requires changing provider-live code, cache behavior, documentation helpers, workflow helper scripts, public protocol, or data formats, the owner should stop and rescope instead of silently expanding the extraction.

## Alternatives Considered

Leaving startup recovery in `daemon.gleam` was rejected because it preserves the current high-risk editing surface and makes future recovery changes hard to test in isolation. A separate startup-recovery process was rejected because this rank is behavior-preserving and does not need a new OTP boundary. Moving the logic deeper into `scherzo/state/recovery.gleam` was rejected because the daemon-level logic depends on tracker issue refresh, runtime bundles, workflow selection, session recovery metadata, and scheduled-runtime reconstruction. A source guardrail-only change was rejected because guardrails cannot replace a real ownership boundary. Requiring a pre-publish dogfood restart was rejected for the default path because this is an internal refactor with deterministic daemon startup tests; a human/operator restart check remains useful after implementation handoff if reviewers want extra operational evidence.

## Risks and Countermeasures

The main risk is changing startup ordering or losing fail-closed behavior. Characterization tests must cover both successful recovery and negative/error paths before extraction, and startup errors must continue to return `StartupError` instead of partially starting the daemon. Timer recovery can regress by losing retry generations or scheduling stale ticks, so recovered retry timer tests must assert the generation and observable follow-up behavior. Cleanup, park reports, and command outbox replay are easy to drop because they are applied as startup effects; daemon startup tests must prove those effects still happen or still fail in the same way they do today. Workflow resumption can accidentally start a drifted workflow, so identity-mismatch coverage must prove the recovered run is rejected or failed closed rather than resumed.

The extraction could create a new god module; the countermeasure is to keep `startup_recovery.gleam` focused on planning/data shaping and use `recovered_workflow_runner.gleam` only for process-heavy runner code. An import cycle or backwards dependency on `daemon.gleam` would also defeat the boundary, so the new modules must report neutral data and errors for the daemon shell to translate. Acceptance drift is another risk: a reviewer could see a shorter daemon but no evidence for startup parity. The countermeasure is to require recorded targeted test output, full `gleam test`, format, `glinter`, and `scherzo_lint` evidence before publish. Scope creep into provider-live, cache, docs/helper, public protocol, or data-format behavior would turn this into a different ticket; the countermeasure is to treat those surfaces as explicit non-goals and stop for rescoping if the extraction cannot proceed without them.

## Scope Boundaries

In scope for the follow-up implementation: moving `StartupRecovery`, ledger/projection recovery planning, issue-state fetch chunking, recovery observation mapping, scheduled recovery reconstruction, and recovered workflow resumption planning out of `src/scherzo/orchestrator/daemon.gleam`; optionally moving recovered worker launch helpers to `src/scherzo/orchestrator/recovered_workflow_runner.gleam`; keeping `test/state_recovery_test.gleam`; adding `test/orchestrator_startup_recovery_test.gleam`; and extending daemon startup coverage for interrupted runs, recovered retry timers, cleanup workspaces, command outbox replay, park reports, and recovered workflow resumption identity mismatch.

Out of scope: implementing other decomposition ranks, changing public daemon/control APIs, changing ledger record meanings, changing projection fold semantics, changing retry/backoff policy, changing provider-live behavior, changing cache behavior, migrating docs/helpers or workflow helper scripts, adding new operator commands, or introducing a new OTP/process boundary. If implementation must touch provider-live, cache, docs/helper, workflow-helper, public-protocol, or schema paths to make Rank 2 work, it should preserve any useful characterization tests, stop, and update the scope before merging behavior changes.

## Milestones

Milestone 1 establishes behavior characterization before code movement. At the end, `test/state_recovery_test.gleam` still passes, `test/orchestrator_startup_recovery_test.gleam` exists, and daemon startup tests explicitly name the required scenarios: interrupted run recovery, recovered retry timer generation and follow-up behavior, cleanup workspace effects, command outbox replay, startup park reports, and recovered workflow resumption identity mismatch. This milestone is complete only when the tests describe current behavior strongly enough that moving the code would break them if parity is lost.

Milestone 2 extracts the startup recovery planner. At the end, `src/scherzo/orchestrator/startup_recovery.gleam` owns the startup recovery result type, ledger replay/projection planning, tracker issue-state fetch chunking, recovery observation mapping, startup park report shaping, `recovery_by_issue` shaping, warnings, and returned startup actions. The new module does not import `src/scherzo/orchestrator/daemon.gleam`; `daemon.start` still returns the same startup errors, starts infrastructure in the same order, and applies the same recovery effects through the compatibility shell.

Milestone 3 extracts scheduled recovery reconstruction and recovered workflow resumption planning. At the end, scheduled status replay and workflow-resumption decisions are made outside the daemon, while the daemon remains responsible for mailbox ownership, dependency callbacks, logging context, timers, process registration, and EventHub publication. The recovered workflow identity-mismatch test must prove that drifted workflow recovery remains rejected or fail-closed.

Milestone 4 trims the daemon shell and resolves the runner split. At the end, recovered workflow launch helpers either stay as small daemon shell callbacks or move to `src/scherzo/orchestrator/recovered_workflow_runner.gleam` if they remain process-heavy; the decision is recorded. Daemon-local startup recovery helpers are removed or reduced to callbacks, no public daemon message or control behavior has changed, and the targeted startup-recovery/daemon tests pass.

Milestone 5 completes validation and scope audit. At the end, the implementation evidence includes passing output for targeted startup-recovery and daemon startup tests, `direnv exec . gleam format --check src test`, `direnv exec . gleam test`, `direnv exec . gleam run -m glinter`, and `direnv exec . gleam run -m scherzo_lint`. The owner also records that provider-live, cache, docs/helper, public daemon/control protocol, Linear command syntax, EventHub shape, ledger/projection semantics, workflow YAML semantics, retry/backoff policy, and OTP/process architecture stayed unchanged. No browser check is applicable; no pre-publish dogfood restart is required unless implementation intentionally changes operator-visible behavior, and otherwise any manual daemon restart check is a deferred human/operator check after handoff.

## Rollout, Recovery, and Idempotence

The follow-up change is an internal refactor with no data migration, feature flag, provider-live change, cache invalidation, docs/helper migration, or operator retraining. Rollout should be additive: add characterization tests, add the new module boundary, route the daemon through it, then remove daemon-local helpers after parity is proven. Recovery is to revert the extraction commit(s), or revert the optional `recovered_workflow_runner.gleam` split independently if the implementation is divided; because ledger records and public APIs must remain unchanged, no runtime cleanup or cache invalidation should be required. Re-running the tests and validation gates is idempotent, and startup recovery itself must remain idempotent by appending only the same recovery records current behavior would append. If implementation starts touching out-of-scope provider-live, cache, docs/helper, public-protocol, or schema surfaces, the safe recovery is to keep useful characterization tests, stop the extraction, and rescope before merging behavior changes.
