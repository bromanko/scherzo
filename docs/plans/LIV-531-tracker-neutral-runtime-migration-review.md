# LIV-531 Tracker-Neutral Runtime Migration ExecPlan Review

## Purpose / Big Picture

Scherzo's product direction is tracker-neutral rather than Linear-only: a daemon should be able to run the same workflow orchestration against Linear today or another production tracker later without pretending every task is a Linear issue. This does not mean one daemon runs multiple trackers at once. The supported runtime model for this migration is exactly one configured tracker backend per daemon process, with backend-neutral types allowing different daemon deployments to choose different adapters. The migration plan should move core runtime ownership to backend-neutral `Task` and `TaskRef` values, keep durable identity as `(backend_kind, remote_id)`, and leave Linear names only where they are explicit compatibility aliases or Linear-only adapter internals. Review feedback sharpened the planning outcome: follow-up implementation tickets must carry concrete acceptance evidence, tests, lint, docs/helper migration checks, and clearly classified manual or dogfood validation rather than relying on directional architecture text alone.

## Problem Framing and Constraints

The current tree already has `src/scherzo/task.gleam` and `src/scherzo/tracker/adapter.gleam`, but core runtime still crosses a legacy Linear-shaped bridge. The coupling map is: daemon startup builds `adapter_legacy.legacy_client` and stores both `tracker_client` and `tracker_adapter`; orchestrator state, transition messages, effects, once-mode service dispatch, worker identity, retry, parking, and recovery still carry `tracker_issue.Issue`; `task.from_legacy_issue` hardcodes `backend_kind: "linear"` and `task.to_legacy_issue` rejects non-Linear tasks; handoff still emits legacy handoff variants to the Linear handoff client; remote command transport still uses `LinearCommandConfig`, `linear_transport`, `linear_parser`, and `pending_linear_command_acks`; durable records have generic `TaskRefFields` but many active records, projections, and recovery lookups are keyed by `issue_id` or synthesize Linear task refs; templates, workflow environment variables, workflow policies, doctor, smoke, scheduled failure reporting, examples, and many tests still use issue or Linear vocabulary.

The constraints are deliberate. This planning ticket must not implement the migration, add a production tracker, support multiple configured tracker backends inside one daemon, or remove compatibility aliases without a separate migration decision. Existing Linear deployments, old ledgers, `issue.*` prompt variables, `SCHERZO_ISSUE_*` environment variables, and Linear CLI/config aliases must continue to work during the migration.

Review feedback adds three planning constraints for all derivative work. First, every implementation slice must state exactly what acceptance evidence proves success, including targeted tests and the required full validation/lint commands. Second, docs and helper migration are part of the runtime migration boundary: repository docs, `.scherzo` operator docs, and workflow helper scripts that still fetch or mutate Linear issues must either move behind tracker-neutral wording/capabilities or be named as Linear-only compatibility surfaces. Third, provider-live/cache behavior belongs to Scherzo's structured-output and review-lane workflow infrastructure, not the tracker runtime; if a migration slice touches workflow helper scripts, provider-facing schemas, or review-lane preflight code, it must preserve offline validation, optional live-provider canaries, and cache semantics unless a separate workflow ticket explicitly changes them.

## Strategy Overview

The target architecture has a single tracker-neutral runtime spine and one active tracker adapter per daemon. `src/scherzo/task.gleam` should own `Task`, `TaskRef`, and a small identity helper for `(backend_kind, remote_id)`. `src/scherzo/tracker/adapter.gleam` should remain the adapter capability boundary: `task_source` is required, while comments, remote commands, state transitions, routing metadata, links, handoff, scheduled failures, readiness, smoke, and attachments stay optional capabilities validated against the one configured adapter. `src/scherzo/orchestrator/*` should dispatch, refresh, retry, park, recover, and record work using `Task` and `TaskRef`, not `tracker_issue.Issue`. Linear conversion should live inside the Linear adapter and explicit compatibility modules only. No slice should add fan-out across adapters, cross-tracker scheduling, or configuration that makes one daemon serve multiple tracker backends.

The first implementation slice should replace daemon candidate fetch, refresh, and dispatch validation with `TrackerAdapter.task_source` and introduce task-ref identity keys in runtime state before touching handoff or command transport. Later slices can promote generic handoff events, add `remote_commands` config while preserving `linear_commands` as an alias, normalize ledger/projection recovery, and make doctor/conformance prove a full non-Linear fake can dispatch through the daemon.

Implementation sequencing should be evidence-first. Each derivative ticket should name the files it intends to touch, the red tests that fail before the slice, the compatibility aliases that must remain green, the manual/operator checks that are pre-publish for that slice, and the deferred dogfood checks that require credentials, live providers, or a future production adapter. This keeps the migration reviewable as a series of reversible proofs rather than a broad rename.

## Alternatives Considered

One alternative is to keep the runtime issue-shaped and require every future tracker adapter to manufacture Linear-like issues. That is rejected because it preserves the collision-prone `issue_id` identity model and makes a non-Linear tracker conform to Linear semantics rather than Scherzo's task model. A second alternative is a big-bang rename of every `issue` and `linear` name. That is rejected because it would risk old ledgers, operator workflows, and docs all at once. A third alternative is to update docs and helper wording first while leaving runtime identity unchanged. That is rejected as a standalone solution because it would make the product sound tracker-neutral before the daemon can prove non-Linear dispatch, recovery, handoff, and remote-command behavior. A fourth alternative is to let one daemon configure multiple tracker backends and route among them. That is rejected for this migration because it adds scheduler, isolation, credential, and operator semantics that are not needed to let a deployment choose Linear or a future tracker. The selected approach is staged: move runtime behavior to neutral types for one configured adapter, then retire or relabel compatibility paths only where tests prove parity.

## Risks and Countermeasures

The largest risk is losing Linear parity while changing internal types. Countermeasure: keep Linear adapter tests, handoff tests, doctor checks, and old-ledger decode/recovery tests green at every slice, and keep aliases active until explicitly retired. A second risk is false confidence from adapter-unit tests alone. Countermeasure: add a non-Linear fake that runs through full daemon dispatch, recovery, handoff, and remote-command paths before any production non-Linear adapter is attempted. A third risk is accidentally expanding scope into a multi-adapter daemon. Countermeasure: keep configuration, daemon state, dispatch loops, and tests centered on one active `TrackerAdapter`; add validation that rejects or clearly reports attempts to configure more than one tracker backend for one daemon. A fourth risk is durable identity collision when old records, migrated projections, or different deployments contain the same remote id for different backend kinds. Countermeasure: use `(backend_kind, remote_id)` for maps, ledgers, outbox replay, command receipts, workstream task refs, and recovery fetches, while treating `issue_id` as a Linear compatibility alias only.

A fifth risk is documentation or helper drift: examples could advertise tracker-neutral behavior while `.scherzo/workflows/scripts/scherzo-execplan`, `.scherzo/workflows/scripts/scherzo-implementation`, Linear attachment helpers, or `.scherzo/README.md` still require Linear issue operations. Countermeasure: include docs/helper migration in the milestone that normalizes operator surfaces, keep Linear-only helpers explicitly labeled until replaced, and run doc/contract tests when those surfaces change. A sixth risk is accidentally changing provider-live or cached review-lane preflight behavior while editing workflow helpers. Countermeasure: treat provider-live/cache behavior as out of scope for tracker runtime work; if touched by helper edits, require review-lane offline contract evidence and either a skipped or passing optional live-provider report with cache behavior unchanged.

## Scope Boundaries

In scope for the migration plan are daemon/orchestrator dispatch for one configured tracker backend, `adapter_legacy`, task conversion, handoff events, remote command config and transport names, durable state task references, workflow/template/env compatibility, doctor/smoke/contract checks, conformance tests, examples, docs, and helper scripts whose operator-facing behavior depends on Linear issue identity. The docs/helper set includes `README.md`, `.scherzo/README.md`, `docs/GETTING_STARTED.md`, `docs/runbooks/tracker-adapters.md`, `docs/specs/TRACKER_ADAPTER_SPEC.md`, workflow examples, and Linear-only helper options such as `--linear-attach-comment-file`.

Out of scope are implementing the migration in this ticket, adding a new production adapter, configuring multiple active tracker backends in one daemon, adding cross-tracker routing or scheduling, deleting Linear compatibility aliases, changing operator-visible Linear behavior without parity evidence, rewriting unrelated workflow-driver and pi-agent internals, or changing review-lane provider-live/cache policy. If a derivative implementation must edit structured-output workflow schemas, review-lane preflight, or cache files, that change should be split or explicitly validated as workflow infrastructure rather than hidden inside tracker-neutral runtime work.

Temporary compatibility aliases that must remain are `linear_commands`, `linear_contract`, `linear-smoke`, `linear-contract`, `--linear-smoke`, `--linear-contract-check`, nested `tracker.linear.*` plus older flat Linear tracker fields, `issue.*` template variables, `SCHERZO_ISSUE_ID`, `SCHERZO_ISSUE_IDENTIFIER`, legacy ledger fields `issue_id` and `issue_identifier`, decodable `linear_command_*` ledger records, and Linear-only helper scripts/options such as `--linear-attach-comment-file` until separately migrated.

## Milestones

Milestone 1 freezes the neutral identity contract, the one-tracker-per-daemon constraint, and compatibility guardrails. The outcome is a small `TaskRef` identity helper in `src/scherzo/task.gleam`, tests in `test/task_test.gleam` proving Linear conversion remains compatibility-only code, startup/config validation that treats exactly one tracker adapter as active for the daemon, and structural tests or targeted greps proving new runtime maps cannot key durable or in-memory state by bare remote id. Acceptance evidence for this milestone is the targeted task tests, the config/startup validation evidence, the structural check output, and the full validation/lint commands listed in Validation and Acceptance.

Milestone 2 is the recommended first implementation slice: replace daemon and once-mode candidate fetch, retry refresh, recovery refresh, and dispatch validation with `TrackerAdapter.task_source` while preserving Linear behavior through the Linear adapter. The outcome is that `src/scherzo/orchestrator/daemon.gleam` and once-mode service paths no longer need `adapter_legacy.legacy_client` for core fetch paths, while legacy conversion remains available only for compatibility callers. Required tests must cover Linear candidate dispatch parity, a non-Linear fake task reaching dispatch validation without conversion to `tracker_issue.Issue`, retry refresh by `TaskRef`, and failure diagnostics when a task source returns the wrong backend kind.

Milestone 3 moves orchestrator state, transition messages, effect runner requests, worker identity, retry, parking, workflow selection, and workstream references to `Task` and `TaskRef`. The outcome is that `tracker_issue.Issue` is confined to Linear compatibility and template/env aliases, while daemon state still contains only one active tracker adapter. Required tests must cover worker identity, parking/unparking, retry timers, recovery clearing, workflow routing, and task-ref identity fixtures with duplicate remote ids across two backend kinds so `(backend_kind, remote_id)` is the durable collision domain without implying two active trackers in one daemon.

Milestone 4 promotes generic handoff and remote commands. The outcome is that effect runner emits generic `HandoffClaim`, `HandoffSuccess`, `HandoffFailure`, and `HandoffPark` events, remote commands use a `remote_commands` config section, and `linear_commands` remains a tested alias. Required tests must prove alias parsing, clear startup validation when an adapter lacks `remote_commands` or `comments`, command receipt/outbox replay by `TaskRef`, and Linear acknowledgement parity. Manual Linear comment-command dogfood is deferred until after automated alias and replay tests pass, because it requires operator credentials and a live Linear task.

Milestone 5 normalizes durable recovery, operator surfaces, docs, and helpers. The outcome is that ledger records, projection snapshots, recovery refreshes, outbox replay, workstream references, doctor, smoke, contract/readiness checks, docs, examples, and helper scripts all use backend-neutral task refs or clearly labeled Linear compatibility aliases while old Linear records still decode. Required tests must include old-ledger decode/recovery, projection snapshot migration, docs/spec/runbook assertions, helper fixture tests, and doctor aliases for both tracker-neutral and Linear names. If this milestone touches workflow helper scripts or structured-output workflow schemas, review-lane offline contract validation is a pre-publish requirement; optional live-provider canaries may remain skipped when credentials are absent, and cached preflight behavior must not be changed without a separate workflow decision.

Milestone 6 closes conformance gaps before another production tracker. The outcome is a non-Linear fake adapter that exercises full daemon dispatch plus conformance packs for remote commands, handoff, scheduled failures, readiness/smoke, and durable recovery behavior. Required evidence includes the fake daemon-dispatch test, tracker conformance reports for required and optional packs, full validation/lint commands, and a Linear operator check of `scherzo doctor --check tracker-contract --check tracker-smoke` before enabling any production non-Linear backend. Production dogfood with a real non-Linear tracker is explicitly deferred to a future production-adapter ticket.

Derivative backlog should be split into separate implementation tickets for task-source dispatch, generic handoff, remote command config aliasing, durable task-ref recovery, non-Linear daemon fake and conformance packs, doctor/docs/helper cleanup, review-lane/helper validation if workflow scripts are touched, and eventual Linear alias retirement decisions.

## Rollout, Recovery, and Idempotence

Rollout should be additive and reversible. Each slice should keep the Linear adapter as the production backend, keep exactly one active tracker adapter per daemon, keep old ledger decoding intact, and prefer dual-read or alias parsing before removing names. Re-running recovery must be safe because it should refresh tasks by `(backend_kind, remote_id)` and ignore duplicate outbox or command receipts by their durable event ids. If a slice regresses Linear behavior or accidentally introduces multi-adapter daemon semantics, recovery is to revert that slice while leaving old ledgers and aliases readable. No production non-Linear backend should be enabled until the non-Linear fake daemon test and the expanded conformance suite pass.

Docs and helper rollout should follow the same additive pattern: introduce backend-neutral language and helper paths first, leave Linear-only helpers clearly labeled, and remove or rename aliases only after a separate compatibility decision. If a helper or workflow change accidentally alters review-lane provider-live or cache behavior, roll it back independently from tracker runtime changes and restore the documented offline-required, live-optional, cache-reusable semantics before continuing.

## Open Questions and Clarifications Needed

The migration plan no longer treats daemon tracker cardinality as open: Scherzo should support exactly one configured tracker backend per daemon for this migration. The remaining open questions are the final generic config names for tracker contract/readiness and scheduled failure reporting, and whether `issue.*` and `SCHERZO_ISSUE_*` remain permanent aliases or receive a dated retirement plan. Generic handoff payloads may need richer fields than the current placeholder success/failure summaries to preserve Linear comment parity. A future workflow-infrastructure ticket, not this runtime migration, should decide whether provider-live cache policy needs additional operator controls beyond the current documented TTL and deletion behavior.
