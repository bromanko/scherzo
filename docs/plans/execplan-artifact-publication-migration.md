# Migrate ExecPlan workflows to artifact publication

This review document frames the ExecPlan for moving Scherzo's ExecPlan authoring and revision workflows from workspace-driver `publish-change` to workflow artifact publication. Mechanical implementation details are supplied through the structured implementation pack for LIV-742.

## Purpose / Big Picture

After this migration, an ExecPlan run still produces a human-reviewable Markdown plan, an implementation pack, an ExecPlan bundle, and a GitHub pull request for the review document, but the pull request is created by Scherzo artifact publication from retained canonical artifacts rather than by publishing the step workspace diff. Operators should observe the same practical review loop: the review doc appears in the configured GitHub repository, reruns update the stable PR instead of creating PR spam, and the retained bundle remains the handoff source for implementation.

## Problem Framing and Constraints

`docs/specs/ARTIFACT_PUBLICATION_PRD.md` makes Scherzo's internal artifact store canonical and treats GitHub as a derived publication target. The current `execplan` and `execplan-revision` workflows still require `publish-change` and run an explicit `publish_review_doc` command before bundle materialization. That creates the wrong ownership boundary and also forces bundle metadata to know PR details before canonical outputs are recorded. The migration must keep legacy `publish-change` available for implementation, conflict-resolution, and other workspace-change workflows, must preserve the prepared review-doc target path, must keep revision runs on a stable review branch as much as the existing GitHub adapter supports, and must build on the earlier artifact-publication config, planner, ledger/control, runtime/retry, and GitHub adapter plans.

## Strategy Overview

Use artifact publication as the finalization step for ExecPlan review docs and keep the workflow changes narrow. First make the canonical ExecPlan bundle carry enough publication metadata for the planner to publish the selected `plan` entry back to the exact prepared review-doc path, while marking the bundle's legacy `review_surface` fields as explicitly not applicable before artifact publication supplies external PR state. Then configure a dedicated GitHub artifact repository target and workflow-level `artifacts.publications` routes in both `execplan` and `execplan-revision`, remove only the obsolete `publish_review_doc` steps and `publish-change` requirements from those workflows, and rely on the existing publication runtime to record `published`, `unchanged`, or `failed` outcomes and support retry.

## Alternatives Considered

Keeping `publish_review_doc` and merely adding artifact publication was rejected because it would double-publish the same review surface and leave the workspace driver on the critical path. Replacing dynamic review-doc targets with a fixed `docs/plans/{{ work.identifier }}.md` route was rejected because current tasks can request exact Markdown paths such as `docs/plans/execplan-artifact-publication-migration.md`. Removing `publish-change` globally was rejected because implementation and code-change workflows still publish workspace diffs and are outside this migration.

## Risks and Countermeasures

The main correctness risk is publishing the wrong path or bytes. Counter it with tests that create a non-default review-doc target, materialize an ExecPlan bundle, and assert the publication planner reads the retained `plan` artifact bytes and renders that exact target path. The main compatibility risk is breaking revision or implementation handoff consumers that read `review_surface`; counter it by emitting explicit not-applicable publication metadata for newly materialized bundles before artifact publication, preserving legacy published/reused bundles, and keeping implementation prompts' canonical-plan behavior unchanged. The main operational risk is duplicate PRs after revision or retry; counter it by using the same publication id and stable branch template for `execplan` and `execplan-revision`, plus fake-GitHub tests for unchanged reruns, retry, and update-existing behavior. The main rollout risk is accidentally removing `publish-change` from remaining workflows; counter it with workflow parsing and portability tests that assert only ExecPlan authoring/revision dropped that requirement. A planning-process risk is letting review feedback live only in this Markdown file while the structured implementation pack omits acceptance evidence, test obligations, milestone specificity, manual dogfood timing, docs/helper inventory, provider-live/cache boundaries, full validation, or lint gates; counter it by mirroring those obligations in the updated pack before Scherzo materializes implementation artifacts.

## Scope Boundaries

In scope are `workflows/dogfood/execplan.yaml`, `workflows/dogfood/execplan-revision.yaml`, their installed `.scherzo/workflows` copies, the installed/source ExecPlan helper and bundle schemas, the artifact-publication template/planner support needed for the prepared review-doc destination, root artifact repository configuration for the Scherzo GitHub docs target, PR body prompt/template updates, focused tests, portability tests, and operator documentation.

The docs/helper boundary is narrow. The implementation may change `workflows/dogfood/scripts/scherzo-execplan`, `.scherzo/workflows/scripts/scherzo-execplan`, `workflows/dogfood/schemas/exec-plan-bundle.v2.schema.json`, `.scherzo/workflows/schemas/exec-plan-bundle.v2.schema.json`, and small docs or prompt templates only to support ExecPlan bundle materialization and artifact-publication routing. It must not migrate unrelated workflow helpers, provider-facing structured-output helpers, review-lane contract files, provider-live behavior, or provider-cache behavior. If a helper/schema/prompt surface is touched, the implementation evidence must name it and run the relevant offline helper or contract tests; if provider-live or provider-cache surfaces are untouched, the evidence must explicitly record that those validations were not applicable.

Out of scope are removing the workspace-driver `publish-change` capability, migrating `execplan-implementation`, implementation, conflict-resolution, research, cleanup, or scheduled workflows, adding non-GitHub repositories, changing generalized review state, changing provider-live/cache semantics, or requiring live GitHub, browser, provider-live, or provider-cache evidence before this implementation ships.

## Milestones

Milestone 1 proves the metadata seam before any workflow is migrated. The ExecPlan bundle schema accepts a `metadata.publication.destination_path` string on the `plan` entry, `workflows/dogfood/scripts/scherzo-execplan` and its installed copy emit that metadata from the prepared review-doc target, and the artifact publication planner exposes it as `{{ artifact.metadata.publication.destination_path }}` for file paths. Focused tests must prove non-default prepared paths render correctly, canonical artifact-store bytes are read, missing metadata fails the required route, and absolute, parent-traversing, empty, or duplicate destinations are rejected.

Milestone 2 proves bundle materialization no longer depends on workspace publishing. `materialize-bundle` and `materialize-revision` can run without `--publish-context`, produce schema-valid bundles whose canonical plan and implementation-pack refs are unchanged, emit `review_surface.status: not_applicable` with null PR fields before publication, and continue to read legacy published or reused bundles for revisions. Revision preparation must seed the review document from the retained canonical plan artifact when the file is absent locally, with branch refresh retained only as a legacy fallback for older bundles.

Milestone 3 migrates workflow configuration. Both source and installed ExecPlan authoring/revision YAML files declare a required `execplan_review_doc` `artifacts.publications` route selecting `exec_plan_bundle` entry `plan`, using the dedicated `github.docs` repository target, the stable branch template, and a PR body template. The obsolete `publish_review_doc` command steps disappear, `materialize_bundle` and `materialize_revision` depend directly on pack validation/materialization, and only the obsolete `publish-change` workspace requirement is removed from `execplan` and `execplan-revision` while all workspace-change workflows keep it.

Milestone 4 proves GitHub behavior parity through deterministic fakes and local dogfood commands before publish. A configured authoring run publishes the review doc to the prepared path, a revision run updates the same stable branch/PR, unchanged selected bytes record `unchanged`, required publication failures block workflow success with retryable state, optional publication absence is not used for these required routes, and `scherzoctl artifact publication retry --run <run-id> --publication execplan_review_doc --json` replays retained artifacts without rerunning producing steps.

Milestone 5 closes release readiness. Focused helper, schema, planner, workflow, executor, CLI/retry, and documentation tests pass; full Gleam test, format, `glinter`, and `scherzo_lint` gates pass; review-doc validation passes; fake/local dogfood evidence is retained; and the implementation evidence records a docs/helper scope inventory plus explicit deferral of live GitHub PR, browser, provider-live, and provider-cache checks to a human/operator after implementation.

## Validation and Acceptance

Acceptance requires automated evidence that `execplan` and `execplan-revision` parse with publication routes, no longer contain a `publish_review_doc` step, and no longer require `publish-change`, while `execplan-implementation`, implementation, merge-conflict-resolution, research, cleanup, and scheduled workflows that still publish workspace diffs retain `publish-change` when they need it. Helper/schema evidence must show `materialize-bundle` and `materialize-revision` succeed without `--publish-context`, preserve canonical plan and implementation-pack refs, emit `metadata.publication.destination_path` on the `plan` entry, allow explicit not-applicable review-surface metadata, seed revisions from retained canonical plan bytes when needed, and still accept legacy published/reused bundles.

Artifact-publication behavior is accepted only when focused tests prove prepared-path publication through `{{ artifact.metadata.publication.destination_path }}`, canonical artifact-store byte reads, safe rendered-path validation, duplicate destination rejection, same-stable-branch authoring and revision behavior, unchanged no-op status, required failure blocking, no optional absence for these required routes, retry from retained manifests, and no producing-step rerun during retry or restart recovery. Tests must include a non-default review-doc target, a missing metadata failure, absolute and parent-traversal metadata failures, duplicate destination failure, fake GitHub update-existing behavior, fake GitHub unchanged behavior, required failure blocking, and `scherzoctl artifact publication retry` against retained artifacts.

Full validation must run from the repository root: focused helper/schema/planner/workflow/executor/CLI tests, `direnv exec . gleam test`, `direnv exec . gleam format --check src test`, `direnv exec . gleam run -m glinter`, `direnv exec . gleam run -m scherzo_lint`, and `workflows/dogfood/scripts/scherzo-execplan validate-review-doc --path docs/plans/execplan-artifact-publication-migration.md`. Lint warnings that preexist this change may remain as ratchet inventory, but the implementation must not add production `let assert`, `panic`, `todo`, or unlabeled public Boolean-parameter violations.

Pre-publish manual evidence is local and deterministic: collect seeded or fake-command `scherzoctl artifact publication list`, `show`, and `retry --run <run-id> --publication execplan_review_doc --json` transcripts that show `published`, `unchanged`, `failed`, and retry recovery for the migrated ExecPlan route without duplicate commits or PRs. Live GitHub PR evidence, browser evidence, provider-live checks, and provider-cache checks are deferred post-implementation human/operator evidence against a staging repository with credentials kept out of logs.

Docs/helper evidence must include a touched-surface inventory. If `workflows/dogfood/scripts/*`, `.scherzo/workflows/scripts/*`, workflow schemas, installed schemas, prompt templates, or operator docs are changed, run and retain the relevant offline helper, schema, portability, or contract tests. If provider-facing structured-output helpers, provider-live behavior, or provider-cache behavior are not changed, record that no provider-live or provider-cache validation was applicable.

## Rollout, Recovery, and Idempotence

Rollout is additive for non-ExecPlan workflows because the legacy workspace publish capability and helper command remain available. Pre-publish rollout evidence is limited to local fake/seeding checks and offline helper/schema/planner tests; live GitHub PR, browser, provider-live, and provider-cache checks are deferred human/operator checks after implementation. If the migrated required publication fails, canonical artifacts and the ExecPlan bundle remain retained, the workflow records retryable publication state, and an operator recovers with `scherzoctl artifact publication retry --run <run-id> --publication execplan_review_doc`. Repeating the same run, rerunning finalization after a crash, or retrying the same selected bytes and destination must record `unchanged` or an equivalent no-op rather than creating duplicate commits or PRs. Recovery from a bad rollout is to revert the workflow YAML, helper/schema, root repository config, prompt/docs changes, and any installed `.scherzo/workflows` copies changed by the migration; any already-created GitHub branch or PR can be left as audit evidence or manually closed by an operator.

## Open Questions and Clarifications Needed

No blocking open questions. The implementation should defer live GitHub and browser proof until a staging repository and credentials are explicitly chosen, and it should not deprecate `publish-change` beyond removing it from the two migrated ExecPlan authoring workflows.
