Handle context-window exhaustion in workflow agent steps

Plan artifact: docs/plans/LIV-210-handle-context-window-exhaustion.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Scherzo workflows currently treat a model provider context-window overflow as an ordinary fatal Pi or agent failure. In operator terms, a long-running workflow can make real progress in a retained workspace and then stop because the model rejected one oversized request. The operator is left with a partial workspace, a failed workflow, and no first-class signal that the next useful action is to retry with a smaller context rather than debug the plan or change models.

After this plan is implemented, Scherzo workflow agent steps will recognize context-window exhaustion as a named failure mode, retain redacted and bounded evidence about the overflow, and retry the affected agent step once through a bounded recovery action. When the Pi RPC session is still alive and Pi's documented noninteractive compact command is available, Scherzo will first compact that session with recovery-specific instructions and then send the compact recovery prompt in the same session. When RPC compaction is unavailable, fails, or cannot reduce the oversized rendered prompt, Scherzo will fall back to launching a fresh Pi session in the same workspace with the same compact recovery prompt. A normal agent step that does not overflow will continue to run exactly as it does today. A provider overflow that cannot be recovered will fail with a clear pi_context_window_exhausted diagnostic and artifacts that explain what Scherzo attempted. A provider overflow that is recovered must not be finalized or surfaced as an ordinary failed workflow step before the recovery action succeeds.

Problem Framing and Constraints

The concrete pain is recent dogfood workflow breakage. LIV-184 failed in apply_plan_completion_feedback after a failed plan-completion verdict. LIV-207 failed in implement_plan when a large HTML ExecPlan and substantial implementation context produced a provider context_length_exceeded error. These are not product failures in the code under implementation; they are orchestration failures caused by Scherzo sending too much context to Pi or to the model behind Pi.

A context window is the maximum amount of text a model can consider in one request. When Scherzo exceeds that limit, retrying the exact same prompt is not useful. The retry must be smaller, must preserve enough task state for the agent to continue safely, and must not silently hide repeated overflows. The design must be generic across workflow agent steps; it must not hand-edit individual plans, switch models, or redesign the workflow scheduler.

The plan is constrained by current workflow behavior. Workflow YAML files such as .scherzo/workflows/execplan.yaml and .scherzo/workflows/execplan-implementation.yaml contain kind: agent steps that call prompt files and then command steps that validate results. A recovery design must fit into that agent-step path and preserve existing on_failure and dependency semantics. It must also use repository-relative artifact paths and avoid leaking local absolute workspace paths into retained artifacts.

Strategy Overview

The chosen approach is to add context-exhaustion handling at the Scherzo agent/Pi boundary, then add one bounded recovery attempt inside the same workflow step attempt. Scherzo should classify Pi/provider errors conservatively, write redacted recovery artifacts through the existing artifact-store path, and choose a recovery method behind one Scherzo interface. The preferred method is Pi RPC compaction on the existing live RPC session: call compact with custom recovery instructions, observe compaction_start and compaction_end, and then send a short recovery prompt instead of resending the oversized original prompt. The fallback method is to launch a fresh Pi session in the same workspace with that same recovery prompt. The recovery prompt tells the agent that the prior attempt overflowed, names the workflow and step, names the artifact refs and workspace-relative paths to inspect, requires jj status --color=never before making changes, and instructs the agent to read large files in targeted chunks instead of asking Scherzo to preload them.

The recovery boundary is part of the design, not an implementation detail. In the current runner, src/scherzo/agent/run_attempt.gleam calls fail_pi for client.send_prompt failures and passes turn_loop.Context.cleanup_failure into src/scherzo/agent/turn_loop.gleam for read failures and stopReason=error records. That callback reaches cleanup_failure, which emits a turn failure update, terminates the Pi session, runs workspace.after_run, drops queued prompts, and returns WorkerFailure. Context-exhaustion recovery must happen before that cleanup path for the first overflow. A recovered first overflow may emit only recovery-specific events such as context_recovery_started and context_recovery_succeeded; it must not emit the ordinary final failure event, write a failed step artifact, trigger on_failure, or allow dependent-step scheduling to observe failure.

This is the right size because it fixes the generic failure mode without changing provider/model selection, without changing every workflow prompt, and without building a new scheduler. It uses Pi's documented noninteractive compaction support where it fits, but does not force all recovery through that path. Pi 0.70.2 documents RPC commands compact and set_auto_compaction, get_state fields isCompacting and autoCompactionEnabled, and compaction_start/compaction_end events with reasons manual, threshold, and overflow. No standalone CLI compaction flag was found in pi --help. Scherzo should therefore treat RPC compaction as the preferred backend when it is available and the session can continue, while retaining fresh-session recovery as the fallback when compaction is unavailable, fails, or the failing payload is the rendered prompt itself rather than accumulated session history.

Alternatives Considered

The simplest alternative is to shorten the failing workflow prompts by hand. That is insufficient because the next dogfood failure may occur in a different agent step or a different issue with a larger plan, review artifact, diff, or transcript. It also treats symptoms as prompt tuning instead of recognizing the provider failure mode.

A second alternative is to let the whole workflow retry from the failed step using the existing prompt. That is also insufficient because the same oversized prompt is likely to overflow again, and a generic retry can duplicate side effects without telling the agent how to resume from partial workspace state.

A third alternative is to change model selection or use a larger context model for implementation workflows. That is out of scope for this issue and would still leave Scherzo unable to classify and recover from provider context-limit errors on any model.

A fourth alternative is to make Scherzo summarize every workflow artifact before every agent step. That is too broad for the immediate problem. Preemptive summarization may become useful later, but this plan focuses on the observed failure mode: provider-reported overflow at request time.

A fifth alternative is to make Pi RPC compaction the only recovery path. That is too narrow because context exhaustion may be caused by the single rendered workflow prompt rather than accumulated Pi conversation history, or the Pi process may already be unable to continue. This plan uses Pi RPC compact first when possible, but keeps fresh-session recovery as a necessary fallback.

A sixth alternative is to store the entire rendered prompt verbatim in a workspace tmp/ directory and point recovery at that file. This is rejected for the first implementation because the retention and indexing semantics for tmp/ are not the authoritative artifact path, and the oversized prompt may contain private issue text, diffs, local paths, or accidental secrets. The safer first implementation stores redacted, bounded prompt evidence in the existing artifact store and records truncation explicitly.

Risks and Countermeasures

The main risk is that a recovery attempt repeats work in a workspace that already has partial edits. The countermeasure is to run recovery in the same workspace, require the recovery prompt to inspect jj status --color=never before editing, and instruct the agent to continue from the actual working tree rather than restart the task. The retry count is capped at one by default, so a bad recovery loop cannot run indefinitely.

A second risk is false-positive classification of non-context provider errors. The classifier must prefer structured provider error codes such as context_length_exceeded when available and only use message-pattern fallbacks that clearly describe context length, prompt length, input tokens, or maximum context. Tests must prove that rate limits, authentication failures, timeouts, malformed JSON, and operator aborts are not classified as context exhaustion.

A third risk is artifact leakage. The oversized rendered prompt may contain issue descriptions, diffs, review content, operator text, local paths, or accidental secrets. The implementation must redact with existing Scherzo redaction helpers before writing prompt evidence, must write only repository-relative or artifact-ref paths, must cap stored prompt evidence with an explicit truncated flag, and must keep the full prompt body out of the compact provider-error JSON. Tests must include a fake secret value and a placeholder local path such as <absolute-local-path>/workspace/file.gleam and prove that retained artifacts and recovery prompts do not expose them.

A fourth risk is that the compact recovery prompt is too small for the agent to know what to do. The prompt therefore includes the workflow id, step id, issue identifier when available, concise current workspace state, artifact refs for the redacted prompt evidence and provider error, and explicit instructions to inspect source files or plan artifacts in slices. The plan also includes an integration test where the fake second attempt asserts that it received those references.

A fifth risk is assuming Pi RPC compaction always fixes an overflow. Native compaction reduces retained conversation history, but it cannot make a too-large rendered workflow prompt safe if Scherzo resends that prompt unchanged. The countermeasure is to never resend the original oversized prompt after a context overflow; after native compaction, send the same compact recovery prompt used by the fresh-session path, and fall back to a fresh session if the compact command fails or the session cannot continue.

A sixth risk is that inner context recovery and existing outer retry policy multiply each other. The context recovery cap is per workflow step attempt: with the default agent.context_recovery_max_attempts = 1, one oversized first Pi attempt may be followed by one native-compaction recovery prompt or one compact fresh-session Pi invocation before the step attempt returns success or failure. If the broader workflow retry machinery later starts a new step attempt after an unrecovered failure, that new step attempt gets its own context-recovery budget but remains bounded by the existing outer retry limits. Tests must cover an unrecovered overflow with the existing retry policy so repeated recovery invocations cannot happen invisibly.

  • DecisionImplement context exhaustion as a first-class Pi/agent failure mode and a bounded per-agent-step recovery attempt, not as hand-tuned prompt edits.

    RationaleThe failures in LIV-184 and LIV-207 occurred in different workflow steps and were caused by request size, so a generic agent/Pi boundary fix is more reliable than changing individual prompts.

    Date2026-05-10

  • DecisionPrefer Pi RPC compaction when available; keep fresh-session compact recovery as fallback.

    RationalePi 0.70.2 documents noninteractive RPC compact, auto-compaction controls, and compaction events, so Scherzo should not ignore that primitive. Fresh-session recovery remains necessary when RPC compaction is unavailable, fails, the session cannot continue, or the oversized rendered prompt itself must be replaced by a compact recovery prompt. This keeps one Scherzo recovery interface and avoids depending on any unconfirmed standalone CLI compaction flag.

    Date2026-05-11

  • DecisionCap automatic recovery at one retry per workflow step attempt by default.

    RationaleOne retry handles the common case where a smaller context is enough while bounding cost, duplicate side effects, and operator surprise. Treating the cap as per step attempt keeps it clear how existing outer retry policy composes with this inner recovery.

    Date2026-05-10

  • DecisionPlace the first-overflow recovery branch before run_attempt.cleanup_failure and before workflow-step finalization.

    RationaleA recovered overflow must not first be published as an ordinary failed step. The implementation must intercept context-exhaustion failures from client.send_prompt, turn_loop.run_active_turn, and stopReason=error records before cleanup_failure emits turn failure updates, terminates the session through the final failure path, or returns WorkerFailure to the workflow scheduler.

    RationaleOperator diagnosis is part of the feature, so recovery evidence must use the same retained artifact store and indexing path as other workflow artifacts. A tmp/ directory may be ignored, omitted from artifact indexing, or hard to discover.

    Date2026-05-10

  • DecisionMake agent.context_recovery_max_attempts a required rollout knob for this implementation.

    RationaleAutomatic second agent invocation changes production workflow behavior. Operators need a configuration rollback path that does not require reverting code.

    Date2026-05-10

  • DecisionStore redacted, bounded prompt evidence rather than an unbounded verbatim rendered prompt.

    RationaleThe oversized prompt is exactly the riskiest payload to retain. Recovery needs enough evidence and pointers to continue, not unlimited private text. Redaction, size caps, and explicit truncation preserve operator value while reducing leakage and disk-risk.

Context and Orientation

Scherzo is a workflow orchestrator in this repository. A workflow YAML file describes steps. A kind: agent step runs Pi with a rendered prompt inside a workspace. A kind: command step runs a shell command. The workflow runner uses dependencies between steps to decide what runs next. If an agent step fails without an on_failure: continue policy, dependent steps do not proceed.

The dogfood workflow definition .scherzo/workflows/execplan.yaml turns a Linear ticket into an ExecPlan. It starts with draft_plan, an agent step using prompts/execplan-draft.md, then runs validation commands such as scripts/scherzo-execplan validate, and then uses additional agent steps such as repair_validation, review_plan, and incorporate_review.

The dogfood implementation workflow .scherzo/workflows/execplan-implementation.yaml includes multiple agent steps that can accumulate large context: implement_plan, verify_plan_completion, apply_plan_completion_feedback, review steps, feedback-application steps, and final verification steps. The reported failures in LIV-184 and LIV-207 happened in this family of workflow steps.

The source files relevant to the implementation are concentrated in these areas:

  • src/scherzo/error.gleam defines the error types and string codes surfaced by Scherzo.
  • src/scherzo/agent/types.gleam defines WorkerSuccess, WorkerFailure, Pi updates, and runner updates.
  • src/scherzo/agent/pi_rpc.gleam, src/scherzo/pi/client.gleam, and src/scherzo/pi/protocol.gleam are the Pi RPC and protocol modules that decode JSONL records from Pi.
  • src/scherzo/agent/runner.gleam, src/scherzo/agent/run_attempt.gleam, and src/scherzo/agent/turn_loop.gleam are the agent-side modules that launch Pi, send prompts, read turns, and currently convert Pi failures into WorkerFailure.
  • src/scherzo/agent/pi_event.gleam, src/scherzo/session/event.gleam, src/scherzo/session/json.gleam, and src/scherzo/terminal/render.gleam are the likely places to surface recovery attempts in live session events and operator output.
  • src/scherzo/step_artifact.gleam, src/scherzo/state/artifact_store.gleam, and src/scherzo/state/local_artifacts.gleam are the places to connect recovery evidence to retained workflow artifacts.
  • src/scherzo/session/redaction.gleam, src/scherzo/path.gleam, and src/scherzo/workflow_identity.gleam provide existing redaction, path-safety, and safe-component helpers that should be reused instead of adding ad hoc string manipulation.
  • src/scherzo/config/types.gleam and src/scherzo/config.gleam define and parse agent configuration, including existing agent limits.
  • src/scherzo/workflow_dag.gleam, src/scherzo/workflow_structured_retry.gleam, src/scherzo/workflow_checkpoint.gleam, and src/scherzo/orchestrator/yaml_step_session.gleam are relevant to workflow-level observability, checkpoint artifacts, and outer retry interactions. The first implementation should avoid changing DAG semantics unless tests show it is necessary.

A provider context-limit error is any structured Pi/provider failure that says the request exceeded the model's context window, prompt limit, input-token limit, or maximum context length. It is not a rate limit, quota error, network timeout, authentication failure, malformed JSON failure, operator abort, or ordinary nonzero process exit.

Scope Boundaries

In scopeclassify provider context-window exhaustion; preserve a clear error code and diagnostic; parse real Pi/provider error evidence from RpcRecord fields or raw_json; expose Pi RPC compact and set_auto_compaction in the Scherzo Pi client if missing; prefer same-session Pi RPC compaction for recoverable live sessions; write redacted and bounded recovery artifacts through the artifact store; retry an overflowing workflow agent step once before final failure cleanup; expose recovery attempts and compaction method in tests, retained artifacts, session events, terminal output, and step artifacts; add mandatory disable/config limits; and add fixtures that simulate provider context-limit errors and compaction success/failure.

Recovery should be generic for all kind: agent steps. Milestones

The first milestone locks down classification, real protocol evidence, and the Pi RPC compaction seam. At the end of this milestone, Scherzo can name context-window exhaustion without changing runtime behavior, tests cover false positives, the Pi client can encode and observe documented compaction commands/events, and the implementation has a redacted persisted Pi session fixture plus a source-confirmed expected message_end shape, while the raw Pi RPC stdout fixture remains explicitly replaceable if one is later captured.

The second milestone adds mandatory recovery configuration and safe artifact/prompt generation. At the end of this milestone, code can take a rendered prompt and a context-exhaustion error and produce redacted, size-bounded, repository-relative artifacts under .scherzo-state/artifacts/.../context-recovery/, plus a short recovery prompt suitable for either a compacted existing Pi session or a fresh fallback session. This milestone is independently testable without running real Pi.

The third milestone wires bounded recovery into the agent runner before final failure cleanup. At the end of this milestone, a fake Pi that overflows once, accepts compact, and succeeds on the compact recovery prompt produces a successful worker result with no intermediate ordinary failure. A fake Pi whose compaction command fails proves that Scherzo falls back to a fresh compact recovery session. A fake Pi that overflows twice produces a clear context-exhaustion failure. Normal success remains one Pi prompt call and no recovery action.

The fourth milestone surfaces the behavior through session events, step artifacts, terminal rendering, and workflow diagnostics. At the end of this milestone, operators can tell whether a step recovered, whether recovery used Pi RPC compaction or a fresh session, whether compaction started and ended, whether recovery failed after exhaustion, and where to find the retained evidence.

The fifth milestone adds workflow-level regression fixtures, covers outer retry interaction, and runs validation. At the end of this milestone, tests prove normal success paths, context-exhaustion recovery paths, non-context failures, and dogfood-style agent step ids that motivated the ticket.

Plan of Work

Create a new pure module src/scherzo/agent/context_exhaustion.gleam. It should expose a small typed classification result and functions that classify provider code/message pairs, protocol.RpcRecord values, and existing PiRpcError values. Keep provider code/message classification independent of process execution so tests can cover many provider strings cheaply. The RpcRecord classifier may depend on src/scherzo/pi/protocol.gleam and src/scherzo/json_value.gleam so it can inspect stop_reason, error_message, and selected fields from raw_json.

Extend src/scherzo/error.gleam with a new PiRpcError variant named PiContextWindowExhausted. Include provider, provider code, and a concise detail string. Update pi_rpc_code to return pi_context_window_exhausted, update pi_rpc_detail to produce an operator-readable message, and ensure agent_code(PiFailed(PiContextWindowExhausted(...))) returns a stable code that workflow artifacts can use. Rollout, Recovery, and Idempotence

The change is additive but changes production workflow behavior by allowing one automatic compact recovery action inside an agent step attempt. That recovery action may use Pi RPC compaction in the existing session or a fresh fallback session. Therefore the disable knob is mandatory. Existing workflows do not need YAML changes. Setting agent.context_recovery_max_attempts = 0 disables automatic recovery while preserving first-class context-exhaustion classification and diagnostic artifacts.

The one-retry cap is per workflow step attempt. A single step attempt may run the original Pi session and, after a classified first overflow, either compact that same session and send one recovery prompt or launch one compact recovery Pi session as fallback. If a broader workflow retry mechanism later schedules a new step attempt after unrecovered failure, that new attempt has its own inner recovery budget and remains bounded by the existing outer retry policy. Operator-facing diagnostics must distinguish inner context recovery from outer workflow retries and must name whether the inner recovery used pi_rpc_compact or fresh_session.

Recovery runs in the same workspace as the failed attempt. That makes it safe for partially completed work: a compacted existing Pi session or a fresh fallback Pi session sees the actual files on disk and is instructed to inspect jj status --color=never before editing. Recovery is not idempotent in the sense that an agent may still choose to edit files, so Scherzo must not perform unbounded automatic retries.

Rollback is straightforward. If recovery causes unexpected behavior, set agent.context_recovery_max_attempts = 0 and restart or reload Scherzo using the repository's normal configuration path. If deeper rollback is needed, revert the runner wiring while keeping the pure error classifier if desired. The artifact files live under .scherzo-state/artifacts/.../context-recovery/ and do not require a data migration. Existing retained workspaces remain readable even if later code stops generating these artifacts.

Operator observability is part of rollout. The terminal/session output should state when recovery starts, whether it is trying Pi RPC compaction or a fresh fallback session, when compaction starts and ends if Pi emits those events, whether recovery succeeds or fails, the recovery artifact refs, and whether recovery was disabled or exhausted. This prevents a recovered run from looking like a mysterious extra agent invocation.
