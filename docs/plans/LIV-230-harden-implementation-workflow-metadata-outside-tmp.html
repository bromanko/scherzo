Harden implementation workflow metadata outside tmp

Plan artifact: docs/plans/LIV-230-harden-implementation-workflow-metadata-outside-tmp.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

After this change, a Scherzo implementation workflow can lose its workspace-local tmp/scherzo-implementation.json cache and still continue safely, because the required cross-step metadata is stored in durable run state under $SCHERZO_RUN_ROOT/state/implementation/metadata.json. Operators should be able to see the workflow proceed from prepare through refresh-base, analyze, plan-completion gating, validation, and publish without depending on scratch files in tmp/. The observable success case is the LIV-216 failure mode no longer failing: after preparing metadata with $SCHERZO_RUN_ROOT set, deleting tmp/scherzo-implementation.json, and running a later step such as analyze, the helper restores the tmp cache from canonical run state and completes.

Problem Framing and Constraints

Scherzo implementation workflows currently use tmp/scherzo-implementation.json as required cross-step state. That file is intentionally untracked, which prevents accidental commits, but tmp/ is scratch space. Agents, tests, cleanup scripts, or manual recovery work may delete it. When this happened to run LIV-216-1778540605589-3, the implementation step had already succeeded, but analyze stopped with scherzo-implementation: missing tmp/scherzo-implementation.json; run prepare first. Rerunning prepare after implementation is not safe because it can record the wrong baseline for the already-written implementation patch.

This plan solves only the durability of required implementation workflow metadata. It leaves regenerable artifacts such as ticket briefs, ExecPlan briefs, indexes, analysis JSON, validation JSON, publish JSON, and refresh-base reports under repository-relative tmp/ paths unless a later plan explicitly moves them. It does not make workflow metadata tracked or commit-safe; the metadata remains untracked, but the canonical copy moves outside the worktree into the Scherzo run root.

The solution must preserve local and manual behavior. If $SCHERZO_RUN_ROOT is unset or blank, scripts/scherzo-implementation must continue to read and write tmp/scherzo-implementation.json exactly as it does today. When $SCHERZO_RUN_ROOT is available, the helper must treat $SCHERZO_RUN_ROOT/state/implementation/metadata.json as canonical and keep tmp/scherzo-implementation.json only as a compatibility cache for existing commands, diagnostics, and tests.

Strategy Overview

Centralize metadata path resolution in scripts/scherzo-implementation by adding dedicated metadata helpers rather than changing every call site independently. Keep the existing generic load_json and write_json helpers for ordinary JSON artifacts, but stop using them directly for implementation metadata. Add a small set of functions that know about the canonical run-state location, the tmp compatibility cache, repair behavior, and unrecoverable-state error message.

On writes, the new helper writes canonical metadata first when $SCHERZO_RUN_ROOT is set, then refreshes the tmp cache. If the canonical write fails, the command fails before refreshing the cache, so a workflow never appears to have durable metadata when it does not. When $SCHERZO_RUN_ROOT is unavailable, the helper writes only the tmp cache to preserve manual usage.

On reads, the new helper prefers canonical metadata whenever $SCHERZO_RUN_ROOT is set. If canonical metadata exists and the tmp cache is missing or stale, the helper rewrites the tmp cache and returns the canonical content. If canonical metadata is absent but the tmp cache exists, the helper backfills canonical state from the cache, emits an observable stderr diagnostic that names the backfill and both stable path fragments, and continues; this supports already-started workflows and local tests without silently turning stale tmp state into durable state. If both locations are missing, the helper fails with an explicit unrecoverable workflow-state-loss message that says not to rerun prepare after implementation.

This is the smallest proportionate change because the workflow already has a single Python helper that all relevant steps call. Moving metadata handling into that helper avoids workflow-template rewrites, new services, or tracking generated state in Git. It also preserves the current metadata JSON shape, so downstream commands keep reading the same keys.

Alternatives Considered

The simplest possible alternative is to keep using tmp/scherzo-implementation.json and teach failed workflows to rerun prepare. That is unsafe because prepare records the starting baseline; running it after implementation can capture the implementation itself as the baseline and make later analysis or publish steps diff the wrong range.

Another option is to track tmp/scherzo-implementation.json in Git. That would make state survive tmp cleanup, but it would commit run-specific Linear issue URLs, base change IDs, and transient paths into implementation branches. The ticket explicitly asks for untracked durable run state, not committed workflow state.

A broader option is to move every generated workflow artifact out of tmp/. That is larger than needed. Only implementation metadata is required cross-step state. Briefs, indexes, analysis artifacts, validation results, and publish results can be regenerated or are useful diagnostics rather than prepare-time baseline state. Keeping those under tmp/ avoids unnecessary migration risk.

Risks and Countermeasures

The largest risk is corrupting or changing the recorded baseline. The countermeasure is to preserve the existing metadata JSON keys and make write_implementation_metadata the only function that updates metadata. refresh-base --stage before-implementation must continue to preserve initial_base_change_id before updating base_change_id, and both canonical and tmp copies must receive the same JSON bytes.

A second risk is split-brain state where canonical metadata and the tmp cache disagree. The countermeasure is a deterministic rule: when $SCHERZO_RUN_ROOT is set and canonical metadata exists, canonical wins. The read helper rewrites the cache from canonical state. Write operations always write canonical first, then the cache. Tests must cover a stale or missing tmp cache so the behavior is observable.

A third risk is breaking manual developer usage. The countermeasure is to make $SCHERZO_RUN_ROOT optional. When it is unavailable, scripts/scherzo-implementation keeps using tmp/scherzo-implementation.json, and existing tests that do not set $SCHERZO_RUN_ROOT should continue to pass with minimal expectation updates.

A fourth risk is leaking absolute machine paths into diagnostics, tests, or plans. The countermeasure is to write tests using relative fixture directories and environment expressions such as SCHERZO_RUN_ROOT="$PWD/run-root" rather than committing literal local paths. The implementation may display the environment-derived canonical path in runtime diagnostics, but source files and docs must not contain literal machine-specific prefixes.

A fifth risk is silently backfilling the wrong canonical run root from a stale tmp cache. The countermeasure is to make tmp-to-canonical backfill visible and testable. When $SCHERZO_RUN_ROOT is set, canonical metadata is missing, and tmp/scherzo-implementation.json exists, load_implementation_metadata must write canonical metadata and print a stderr diagnostic containing stable fragments such as backfilled canonical implementation metadata, state/implementation/metadata.json, and tmp/scherzo-implementation.json. Operators can then recognize an unexpected repair and inspect the run before publish.

Outcomes & Retrospective

Context and Orientation

The repository is a Gleam project with Python helper scripts. The implementation workflow helper is scripts/scherzo-implementation, a Python script invoked by checked-in Scherzo workflows. It supports commands such as prepare, refresh-base, analyze, plan-completion-context, gate-plan-completion, validate, publish, plan-brief, extract-plan, languages, and ticket-brief.

In this plan, "implementation metadata" means the JSON object currently written to tmp/scherzo-implementation.json. For an ExecPlan implementation, it includes fields such as source_kind, issue_identifier, issue_title, issue_url, plan_path, base_change_id, and plan-brief fields. For a ticket implementation, it includes fields such as source_kind, issue_identifier, issue_title, issue_url, brief_path, and base_change_id. The field base_change_id is the baseline used to decide what changed during the workflow. The field initial_base_change_id, when present, records the original prepare-time baseline before a before-implementation base refresh updates base_change_id.

The scratch directory tmp/ is repository-relative and intentionally untracked. It remains appropriate for regenerable artifacts. The Scherzo run root is identified by the environment variable $SCHERZO_RUN_ROOT; it points to durable, untracked state for the current Scherzo run. The new canonical metadata file is $SCHERZO_RUN_ROOT/state/implementation/metadata.json. Source code and tests must build that path dynamically from the environment variable and must not commit literal machine-specific absolute paths.

The main test file for this script is test/execplan_implementation_helper_test.gleam. It runs the Python helper from isolated directories under test/tmp/, creates fake command-line tools under fixture bin/ directories, and asserts on stdout, stderr, exit codes, and JSON files. The project convention is to run commands through direnv exec . once .envrc has been allowed.

Preconditions and Verified Facts

The current scripts/scherzo-implementation defines TMP_DIR = Path("tmp") and METADATA_PATH = TMP_DIR / "scherzo-implementation.json" near the top of the file. The generic load_json(path) helper currently fails with scherzo-implementation: missing {path}; run prepare first when the requested path does not exist. The generic write_json(path, value) helper creates the parent directory and writes sorted, indented JSON plus a trailing newline.

The prepare_command function currently writes implementation metadata directly with write_json(METADATA_PATH, metadata) for both prepare --source execplan and prepare --source ticket. The ExecPlan path also runs generate_plan_brief(plan_path) and records plan-brief fields in the same metadata object before writing it.

The prepare_command function currently gets issue data through fetch_linear_issue or fetch_linear_issue_context; those functions call linear_graphql. A prepare-path test must therefore supply deterministic Linear issue data locally rather than using the network.

The update_start_refresh_metadata function currently runs only for refresh-base --stage before-implementation when the refresh status is fresh or rebased_clean. It loads metadata from METADATA_PATH, calculates the refreshed base, preserves the old value in initial_base_change_id if that field is absent, updates base_change_id, writes METADATA_PATH, and sets metadata_base_change_id_updated in the refresh result.

The commands that must load implementation metadata through the new centralized helper include plan-brief, analyze, plan-completion-context, gate-plan-completion, validate, and publish. Repository inspection found direct load_json(METADATA_PATH) calls in require_plan_brief_metadata, analyze_command, plan_completion_context_command, gate_plan_completion_command, and publish paths. Repository inspection also found direct write_json(METADATA_PATH, metadata) calls in prepare_command, update_start_refresh_metadata, and plan_brief_command.

The existing tests in test/execplan_implementation_helper_test.gleam already create and read tmp/scherzo-implementation.json directly in several fixtures. Those tests are still valuable for legacy behavior when $SCHERZO_RUN_ROOT is unavailable. New tests should add $SCHERZO_RUN_ROOT explicitly only for scenarios that exercise durable canonical metadata.

Milestones

The first milestone adds the centralized metadata helpers without changing workflow behavior for callers that do not set $SCHERZO_RUN_ROOT. At the end of this milestone, scripts/scherzo-implementation has named functions for canonical path resolution, metadata loading, metadata writing, metadata loss diagnostics, and visible tmp-to-canonical backfill diagnostics. Existing tests should still pass because legacy tmp behavior remains unchanged.

The second milestone switches all implementation metadata call sites to the new helpers. At the end of this milestone, prepare --source execplan, prepare --source ticket, refresh-base --stage before-implementation, plan-brief, analyze, plan-completion-context, gate-plan-completion, validate, and publish use the same load and write semantics. The tmp cache is restored automatically from canonical state when needed, and backfill from tmp to canonical is visible on stderr.

The third milestone adds regression tests for durable run state. At the end of this milestone, tests prove that both prepare source kinds write canonical metadata when $SCHERZO_RUN_ROOT is set, that deleting tmp/scherzo-implementation.json after prepare or refresh does not break a later read, that tmp-to-canonical backfill emits a diagnostic and creates canonical state, that refresh-base preserves initial_base_change_id while updating both copies, and that missing metadata in both places fails with a clear unrecoverable-state message.

The fourth milestone runs targeted and policy validation. At the end of this milestone, the helper tests pass, formatting is clean, and the production lint gates pass without introducing new production-policy violations.

Rollout, Recovery, and Idempotence

This change is internal to workflow helper behavior. It does not change metadata schema, command names, workflow step names, or tracked file layout. Rollout is safe because commands without $SCHERZO_RUN_ROOT keep the old tmp-only behavior, while Scherzo-managed runs gain canonical state in the run root.

The read helper is idempotent. Reading canonical metadata may rewrite the tmp cache, but doing so repeatedly produces the same JSON. If the tmp cache is deleted again, the next read restores it again. Writing metadata is also idempotent for the same input object: canonical state is written first and then the cache is refreshed with the same sorted JSON. Backfilling canonical metadata from an existing tmp cache is also idempotent for the same tmp content, but it is intentionally visible on stderr every time it has to repair missing canonical state.

If implementation fails halfway after adding helpers but before replacing all call sites, existing tmp behavior should still work because METADATA_PATH remains unchanged. If implementation fails after replacing some call sites, use the search command in the Concrete Steps section to find any remaining direct metadata accesses and normalize them. Backing out the change is straightforward because it is confined to scripts/scherzo-implementation and test/execplan_implementation_helper_test.gleam.

If a real workflow reports both metadata files missing, operators should not rerun prepare after implementation. They should restore state/implementation/metadata.json from retained run artifacts or abort and restart the workflow from a clean baseline. If a real workflow reports tmp-to-canonical backfill, operators should inspect the run root and issue identifier before continuing to publish, because the diagnostic means durable state was reconstructed from the compatibility cache.
