Design composable Scherzo workstreams without a mandatory giant workflow

Plan artifact: docs/plans/LIV-241-composable-workstreams-uberplan.html 33 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

This document is an umbrella plan, or UberPlan, for later implementation work. It does not implement workstreams, handoffs, human gates, playbooks, or dogfood workflow replacement by itself. Its purpose is to define the architecture and the smallest safe follow-up tickets that can implement the design incrementally. Each follow-up ticket must get its own implementation-grade ExecPlan with 2-5 minute steps, exact tests, expected red/green output, and a commit map before source code is changed. A later agent should treat this document as the architectural contract and ticket-splitting guide, not as a direct implementation script.

Purpose / Big Picture

Scherzo operators should be able to move an issue through several bounded workflows, such as drafting an ExecPlan, reviewing it, revising it, implementing it, collecting proof, and publishing, without keeping the transition state in memory or relying on Linear comments as the source of truth. After the future implementation work described here, an operator can inspect one durable workstream for an issue, see which typed artifacts were produced by each phase, see which human decisions were recorded against exact artifact hashes, and choose or accept a suggested next phase. The same system must also let an operator start in the middle when valid artifacts already exist.

The desired observable behavior is not a single enormous workflow run. The desired behavior is an artifact-first chain of small phase workflow runs. A phase workflow remains a normal Scherzo workflow, but its inputs, outputs, handoff, and next-action suggestions are recorded in durable local state so later phases can resume, audit, or intentionally deviate.

Problem Framing and Constraints

Today Scherzo can run small workflow units and can also run long workflow DAGs. The repository still has .scherzo/workflows/execplan.yaml, which turns a Linear ticket into a plan through drafting, validation, review, repair, publishing, and implementation-issue creation steps. It also has .scherzo/workflows/implementation.yaml, which prepares context, implements, runs native review lanes, applies feedback, validates, and publishes. The repository now also has v2 dogfood workflows such as .scherzo/workflows/execplan-v2.yaml, .scherzo/workflows/execplan-revision-v2.yaml, and .scherzo/workflows/execplan-implementation-v2.yaml with top-level contract blocks. Those contracts and their retained workflow contract manifests are useful run-local inputs and outputs, but they still do not by themselves create a durable cross-run delivery thread with gates, decisions, next-action options, and manual deviation history.

A single giant workflow DAG is not the right primary abstraction because it encodes one happy path as one long run. It makes entry from the middle awkward, makes extra review loops look like exceptional control flow, couples long-lived product delivery state to one run's workspace and recovery lifecycle, and makes partial progress harder to preserve when operators intentionally stop, skip, or branch. Giant DAGs are still useful for bounded automation inside one phase, but they should not be the only way to represent an issue's delivery journey.

The design must preserve manual entry, manual deviation, and optional automation. Typed artifacts and approvals are the durable source of truth. Linear comments, PR comments, and agent transcripts are projections or evidence, not the canonical state. Local retained artifacts and the Scherzo state ledger come first.

For the MVP, durable local state means one Scherzo daemon and one Scherzo state root, including .scherzo-state/ledger/ and the retained artifact store reachable by that daemon. The MVP is not a cross-operator database and does not promise that a different daemon, a cloned checkout, or a cleaned state root can continue a workstream from Linear comments alone. A second daemon that sees the same Linear issue must treat Linear comments as hints, not authority, and must either use the same state root, import an explicit workstream export, or manually import current artifacts and record new decisions. Export/import, shared remote storage, and backup automation are deferred follow-up work; the MVP must still make state-root loss visible by refusing to infer approvals from comments.

The generic structured-output validator foundation that was a prerequisite in the original draft has now landed in the inspected tree. src/scherzo/structured_output.gleam exposes a validator-runner boundary, src/scherzo/workflow_dag.gleam supports a list of structured-output validators, and JSON Schema plus command validator runners live in src/scherzo/structured_output_json_schema.gleam and src/scherzo/structured_output_command_validator.gleam. Workstream runtime code should reuse this existing validator machinery and add only a thin adapter for validating workstream artifact snapshots. If a future workstream artifact type has no configured schema or command validator, production code should fail closed with a stable unsupported-validator error rather than silently accepting the artifact.

Strategy Overview

Build a thin workstream layer above existing workflow runs. A workstream is a durable local record for one issue or delivery thread. It links workflow runs, typed artifacts, handoffs, human decisions, and next-action options. A phase workflow is still a checked-in .scherzo/workflows/*.yaml DAG and still uses the existing workflow runner. What changes is that phase workflows can be interpreted as phases when their existing contract outputs and optional future workstream_phase metadata are mapped into immutable workstream artifacts and events.

The MVP should start by adapting existing workflow contracts, contract manifests, retained artifacts, and structured-output validators to workstream artifact specs. Then add a minimal append-only workstream ledger and content-addressed artifact snapshot store, teach selected workflows to emit handoffs, add entry-from-handoff and manual-import tooling, add projection and read-only inspection, add human decisions, and only then add playbooks that can suggest or auto-enqueue the happy path. This order keeps the event foundation in place before any command records WorkstreamPhaseRunQueued or WorkstreamArtifactImported. A handoff artifact alone still gives useful shape to the data, but workstream-aware starts must not invent temporary state that later needs migration.

The approach is proportionate because it reuses existing workflow DAGs, top-level workflow contract blocks, local artifact storage, ledger patterns, structured-output capture and validators, operator controls, and Linear handoff mechanisms. It adds a new layer for cross-run state instead of replacing the workflow runner or forcing all dogfood work into a single DAG.

Alternatives Considered

The simplest alternative is to keep current workflows and improve Linear comments. That would be easy, but it would not make artifacts and decisions durable in Scherzo-owned state. A comment can be edited, deleted, truncated, or overlooked, and it does not give the runner a typed way to verify that a later phase consumed the exact artifact approved earlier.

Another alternative is to create one mandatory end-to-end dogfood workflow that drafts, reviews, revises, implements, proves, and merges every issue. That would reduce some handoff ambiguity for the happy path, but it would remove important operator flexibility. It would not naturally support starting from an already reviewed plan, running an extra review, rejecting one artifact while preserving another, or continuing after a partial run with a manually supplied proof bundle.

A third alternative is to make every workflow understand every other workflow's outputs directly. That creates tight coupling between phase implementations and spreads orchestration policy across prompts and scripts. The chosen design keeps phase workflows small and lets them communicate through typed artifacts and handoffs.

Risks and Countermeasures

The first risk is inventing a second schema, validator, and workflow-interface system inside the workstream feature. The countermeasure is to reuse the existing top-level workflow contract block for phase inputs and outputs, reuse workflow contract manifests where they already record run-local refs and hashes, and reuse the structured-output JSON Schema and command validator runners for artifact validation. Workstream code may add a narrow validation adapter for snapshot artifacts, but it must not hard-code a permanent validator enum for every domain artifact.

The second risk is making workstreams another hidden state system that operators cannot inspect. The countermeasure is to include read-only scherzoctl workstream inspection before any playbook auto-enqueue behavior. Every stored artifact, decision, and next action must have a JSON and human-readable view.

The third risk is repository-path drift. A human may approve a plan file and later the file changes, and if Scherzo recorded only the path then the approved bytes may be unrecoverable. The countermeasure is that any repository-path artifact must be snapshotted into a content-addressed workstream artifact store before a handoff, input bundle, or decision can target it. The original repository-relative path is retained only for human navigation. Decisions and downstream starts target the immutable snapshot ref plus SHA-256 hash and byte count.

The fourth risk is overstating local durability. If .scherzo-state/ is deleted or another daemon does not share the same state root, Linear comments alone cannot reconstruct approvals or exact bytes. The countermeasure is to state this MVP scope explicitly, surface missing-artifact and missing-ledger warnings in inspection commands, and require manual re-import plus new decisions after state-root loss. Backup, export/import, or shared storage is a separate follow-up, not an implicit property of this MVP.

The fifth risk is accidental loss of existing behavior. Existing workflows, workflow contracts, Linear routing labels, scheduled jobs, completion-state policy, and success/failure comments must keep working for workflows that do not opt into workstream-aware metadata. The current .scherzo/scherzo.yaml already uses handoff.completion_states so reviewable dogfood workflows complete into In Review while no-review maintenance can complete to Done. The first workstream-aware handoff emitter must prove it preserves or intentionally overrides that current policy; phase success must not mean whole-issue completion unless the phase is explicitly configured as final.

The sixth risk is over-automation. If playbooks auto-enqueue too early, operators will lose the ability to pause, inspect, or deviate. The countermeasure is to make playbooks suggest-only by default, require explicit per-playbook auto_enqueue policy, and require all referenced gates to be satisfied before any automatic transition.

The seventh risk is duplicate or conflicting starts. Two operators or two playbook evaluations might try to start the same next action from the same artifact set. The countermeasure is to route mutating commands through the daemon or an existing ledger lock and derive idempotency keys from workstream ID, action ID, input snapshot hashes, and gate decision IDs. Repeated attempts with the same key must coalesce to one queued phase run or return an explicit duplicate result; conflicting attempts with different inputs must be visibly rejected or recorded as a deliberate deviation.

Context and Orientation

Scherzo is a workflow runner for repository and issue work. In this repository, workflow definitions live under .scherzo/workflows/. A workflow DAG is a directed acyclic graph of steps. An agent step runs pi with a prompt, and a command step runs a shell command. The current parser and runtime live primarily in src/scherzo/workflow_dag.gleam, src/scherzo/workflow_run.gleam, and src/scherzo/workflow_scheduler.gleam.

A phase workflow is a bounded Scherzo workflow that does one phase of work. Examples include drafting an ExecPlan, reviewing an ExecPlan, implementing code, collecting proof, or publishing a PR. A phase workflow may have several internal steps, but it should produce a small number of durable outputs that another phase can understand.

A workstream is the durable state for one issue or delivery thread across many workflow runs. It records the issue identity, phase runs, typed artifact refs, handoffs, decisions, current gates, playbook assignment, and next-action options. A workstream is not a workflow DAG. It is a cross-run ledger and projection.

A workflow contract is the existing run-local interface declared by a top-level contract block in workflow YAML. It names inputs, context, and outputs with coarse contract types such as exec_plan_bundle, implementation_pack, and code_change_bundle. src/scherzo/workflow_contract.gleam parses this block, and src/scherzo/workflow_contract_manifest.gleam renders retained input and output manifests for a run. Workstreams should build on this existing interface.

A typed artifact is a durable JSON or file artifact with an artifact type, schema version, producer metadata, content hash, and validation metadata. Examples are an ExecPlan bundle, an implementation pack, a handoff, a proof bundle, or an approval decision. Existing workflow contract output manifests can identify run-local artifacts; a workstream snapshot preserves exact bytes for cross-run decisions.

A human gate is a durable decision point. It asks a human or authorized operator to approve, request changes, reject, or deviate based on specific artifact refs and hashes. The decision itself is a typed artifact and a ledger event.

A handoff is a structured artifact emitted by a completed phase. It records completed outputs, source run metadata, open questions, validation summary, and recommended next actions. It is the smallest useful unit of cross-phase handoff.

A playbook is optional orchestration policy for a common path. It can suggest the next phase or, when explicitly configured and all gates are satisfied, auto-enqueue it. A playbook never owns the source of truth; it reads the workstream projection and writes normal queued-run and decision records. Playbooks are also the right layer for composition: a standard playbook can list common phases, and an extended playbook can include or repeat those phases plus extra checks.

The existing .scherzo/scherzo.yaml routes Linear issues to workflows by labels with the workflow: prefix. It configures local dogfood workspaces, the pi command, handoff comments, Linear contract states, scheduled jobs, completion-state policy, and control command behavior. The handoff section currently posts Linear updates and can attach result Markdown, but comments are not typed durable handoff state.

The current structured-output path is relevant because workstream artifacts should be validated JSON without embedding every domain validator in the runtime. src/scherzo/workflow_dag.gleam currently allows an agent step to declare structured_output with one or more validators. src/scherzo/structured_output.gleam validates final-response or pi tool-call JSON and calls a validator runner. src/scherzo/structured_output_json_schema.gleam and src/scherzo/structured_output_command_validator.gleam implement the current production validators. src/scherzo/state/artifact_store.gleam stores step artifacts and structured output artifacts and returns refs with SHA-256 hashes.

The current local state ledger is relevant because workstreams should build on the same event-sourced style. src/scherzo/state/ledger.gleam appends records and loads projections. src/scherzo/state/record.gleam defines record bodies for workflow runs, workflow contract manifests, step attempts, issue parking, Linear commands, scheduled jobs, and outbox events. src/scherzo/state/projection.gleam folds those records into current status. src/scherzo/state/local_artifacts.gleam classifies retained artifacts and cleanup decisions.

Design Answers to the Required Questions

Scherzo should represent a workstream as an event-sourced record keyed by a stable workstream_id. For Linear-backed issue work, the default ID should be linear:<issue_identifier> unless a future multi-issue delivery thread explicitly supplies another ID. The workstream projection should include the Linear issue ID and identifier, current status, assigned playbook when one exists, linked workflow run IDs, known artifacts, gates, decisions, next-action options, and audit history. The storage should build on the local .scherzo-state/ledger/ pattern and should keep artifact bytes in the local artifact store or a new workstream artifact store under the same state root.

A task can be assigned to a workflow, a workstream, or both. A workflow:<id> label remains the current concrete dispatch trigger: it says which workflow should run. A future workstream:<playbook-or-template> label should create or resume a durable workstream assignment and compute suggested next actions. If both are present, the workflow label chooses the immediate phase and the workstream assignment supplies durable context, input validation, gates, and audit history. The canonical assignment must be recorded in the workstream ledger, not inferred forever from the label; removing a label must not erase history.

The first durable implementation should add a minimal append-only workstream ledger and content-addressed artifact snapshot store before any start-from-handoff or manual-import command records events. That minimal foundation does not need the full operator projection yet, but it must be able to append WorkstreamCreated, WorkstreamAssigned, WorkstreamArtifactRecorded, WorkstreamHandoffRecorded, and WorkstreamPhaseRunQueued records with stable IDs.

The minimum viable handoff artifact should be a JSON typed artifact named scherzo.handoff.v1. It should include schema_version, artifact_type, artifact_id, workstream_id, issue identity, source workflow ID, source run ID, source step ID when applicable, source run root, completed phase name, outcome, output artifact snapshot refs, validation summary, open questions, recommended next actions, and a short human summary. A handoff is valid only if every listed output has an artifact type, immutable snapshot ref, optional original repository-relative path, SHA-256 hash, byte count, and producer metadata.

Phase workflows should declare run-local inputs and outputs with the existing top-level contract block in workflow YAML. Future implementation should not add a competing top-level phase contract for the same input and output facts. Workstream-specific phase metadata, if needed, should be an optional additive block such as workstream_phase that names the phase ID, display name, handoff output, gate names, next-action suggestions, and completion-state behavior. The existing workflow parser must continue to accept workflows that omit this metadata.

A workflow should be startable from either a previous handoff or manually supplied artifacts. Starting from a handoff means resolving the handoff artifact by immutable ref and SHA, reading its output snapshot refs, matching them against the target workflow's contract.inputs, and creating both a workstream input bundle artifact and the existing workflow contract input manifest for the new run. Starting manually means the operator supplies artifact refs or repository-relative paths with expected artifact types. Scherzo computes hashes, snapshots repository-path bytes into the workstream artifact store, validates the snapshot through the configured JSON Schema or command validator, records a manual import event, and then creates the same input bundle shape. The target workflow should receive prompt/template variables such as workstream_id, phase_inputs_json, phase_inputs_summary, and source_handoff_ref so the phase does not need to scrape comments.

Human decisions should be recorded as scherzo.decision.v1 artifacts and matching ledger records. Each decision must include the workstream ID, gate ID, decision kind, actor identity or operator source, timestamp, rationale, and a sorted list of target artifacts with artifact type, immutable snapshot ref, SHA-256 hash, byte count, and original path when one exists. Before accepting the decision, Scherzo must re-read each target snapshot and verify that the hash matches. If any hash mismatches or any snapshot is missing, the command fails and no decision is recorded.

An approve decision satisfies the named gate for exactly the artifact hashes listed in the decision. A request-changes decision leaves the gate unsatisfied, records requested changes, and should suggest a revision or rerun phase using the same target artifacts plus the change request. A reject decision records that the current candidate artifact set should not proceed and should suppress auto-enqueue for downstream actions until a replacement artifact or deviate decision exists. A deviate decision records an intentional departure from the recommended next action. It should name the chosen workflow or manual action, explain why, and preserve the rejected or skipped recommendation for audit.

Scherzo should suggest next actions by storing next-action options in the workstream projection. A next action is data, not control flow. It includes an action ID, label, workflow ID, reason, required input artifact snapshot refs, gate requirements, whether it is safe to auto-enqueue, and a confidence or priority. The operator can inspect these options and choose one. The workflow runner should not assume there is exactly one next action.

Playbooks should automate the happy path by reading the workstream projection and emitting the same next-action suggestions a human could choose. A standard implementation playbook can list a common five-phase path, while an extended implementation playbook can list those same phases plus additional security, performance, or proof phases. The MVP should prefer explicit playbook definitions even if they duplicate phase lists. Include or extends syntax can be a later enhancement once repeated playbooks prove the need. A playbook may auto-enqueue only when the playbook explicitly allows it, all required artifacts validate, all required human gates are approved for matching hashes, no reject decision blocks the action, no operator pause or workstream hold is active, and the idempotency key for that action is not already queued or running. Playbooks must not prevent manual entry or deviation; a deviate decision should override the playbook for that branch and remain visible in history.

Linear integration should remain an entry and notification layer. Existing workflow: labels can still start a first phase. Future workstream: labels or commands can assign an issue to a workstream or playbook without replacing workflow labels. Workstream-aware phases should include the workstream ID and important artifact refs in Linear comments or attachments, but the local workstream ledger and local artifact store are canonical only within the configured state root. Existing queueing should be extended with local phase-run enqueue records rather than requiring a new Linear issue for every phase. Linear comments may present suggested next actions, but choosing an action should write a workstream event and then enqueue a workflow run.

Retained artifacts and history should be inspectable with scherzoctl workstream commands. The minimum useful surface is list, show, history, artifacts, next-actions, and decision. Every command should support --json so operators and scripts can consume the same state. The human view should show workstream status, assigned playbook, linked runs, artifact types, refs, hashes, decision history, and recommended next actions.

This design should build on existing generic structured-output validators. Runtime code can already ask a JSON Schema or command validator to validate a structured-output payload and receive success or a structured validation error. Workstream code should wrap that runner for artifact snapshots instead of knowing that an ExecPlan review result has a particular domain field beyond artifact type, contract type, and validator declaration. If a future artifact type cannot be validated by a configured schema or command, production behavior should fail closed.

The smallest MVP phases are: align workstream validation and workflow-interface design with the existing validator runner and workflow contracts; define specs and fixtures; add the minimal append-only ledger and artifact snapshot store; emit handoffs from selected workflows; start a workflow from a handoff or manual artifact set; add a projection and inspection CLI; add human gate decisions; add playbook assignment, suggestions, and guarded auto-enqueue; then integrate the model into the dogfood plan, review, implementation, proof, and publish flow.

Artifact-First State Model

Every cross-phase object should be recorded as an artifact first and a comment second. A workstream ledger event may reference the artifact, but the artifact bytes and hash are what make the event auditable.

The base metadata for every typed artifact should be rendered and stored as structured JSON like this:

{
  "schema_version": 1,
  "artifact_type": "scherzo.handoff.v1",
  "artifact_id": "artifact_<stable-or-generated-id>",
  "workstream_id": "linear:LIV-241",
  "ref": "workstream-artifacts/sha256/<sha256>.json",
  "created_at_ms": 1770000000000,
  "producer": {
    "workflow_id": "execplan",
    "run_id": "run_<id>",
    "step_id": "draft_plan",
    "attempt_index": 1
  },
  "content": {
    "sha256": "<sha256>",
    "bytes": 12345
  },
  "validation": {
    "validator": "scherzo.handoff.v1",
    "status": "valid"
  }
}

The artifact hash should be computed over the stored artifact bytes. If canonical JSON becomes part of the generic structured-output validator contract, use canonical JSON for hash stability. Until then, store the exact bytes and hash those bytes.

A repository file can be imported as a typed artifact only by snapshotting its exact bytes into the content-addressed workstream artifact store. The workstream record should preserve original_path, hash, byte count, artifact type, validation status, and optional git commit or blob identity when available, but decisions, handoffs, and input bundles must reference the immutable snapshot ref. This is needed for plan files such as docs/plans/LIV-241-composable-workstreams-uberplan.html: the path helps a human navigate, while the snapshot answers what bytes were approved.

A workstream projection should be reconstructable from ledger events and artifact reads. It should answer: what issue is this for; which runs happened; which artifacts are current candidates; which gates are pending or satisfied; which decisions were made; which next actions are available; and which actions were intentionally skipped or deviated from.

The MVP handoff must be small enough to emit from existing workflows but rich enough to start the next phase. It should not contain all transcripts or all proof. It should contain immutable refs to those artifacts.

{

The handoff should be allowed to reference multiple outputs. It should not duplicate large outputs. When a handoff output came from the existing workflow contract, include the contract output name and coarse contract type next to the richer workstream artifact type.

Phase Workflow Contracts

A future phase-aware workflow YAML file should remain a valid normal workflow. The existing top-level contract block is the source of truth for run-local inputs and outputs. Workstream-specific metadata should be optional and additive, not a replacement for contract. A draft shape is:

contract:
  version: 1
  inputs:
    exec_plan_bundle:
      type: exec_plan_bundle
      required: true
      source: mapped_output
  outputs:
    code_change_bundle:
      type: code_change_bundle
      source:
        step: materialize_code_change_bundle
        path: tmp/execplan-v2-code-change-bundle.json
workstream_phase:
  phase_id: implement_execplan
  display_name: Implement ExecPlan
  handoff:
    output: code_change_bundle
    artifact_type: scherzo.code_change_bundle.v1
    snapshot: required
  next_actions:
    - action_id: review_implementation
      workflow_id: implementation
      inputs:
        - code_change_bundle
      auto_enqueue: false

The MVP can use existing contract input sources such as issue_context and mapped_output. Workstream start tooling should translate a handoff or manual artifact import into supplied contract values for the workflow runner, then record the normal workflow_contract_inputs manifest. Later work can add richer alternatives only after the exact artifact handoff path works.

Outputs should use source kinds already supported by src/scherzo/workflow_contract.gleam: step fields, step files, structured outputs, inline JSON, static URLs, and static git refs. Repository-path outputs and structured-output refs must be snapshotted into workstream artifact storage before a handoff or decision targets them. Workstream metadata can say which contract output becomes the handoff output and which next actions should be suggested.

Validation should reuse existing structured-output validators and any schema or command validators attached to the artifact type by the workstream validation adapter. The workflow runner should validate contracted outputs at the end of a phase run using existing contract-manifest behavior. If a required output is missing or invalid, the workflow run should fail or park according to existing failure policy. If a required handoff is valid, Scherzo records the handoff and its output snapshots in the workstream ledger and updates next-action options.

Starting From the Middle

The MVP must allow two entry paths after the minimal workstream ledger and artifact snapshot store exist. The first entry path is from a handoff. An operator runs a command shaped like:

scripts/scherzoctl workstream start-from-handoff   --handoff-ref <ref>   --handoff-sha256 <sha256>   --workflow execplan-revision-v2

The command resolves and verifies the handoff, matches its output snapshot refs to the target workflow's contract.inputs, derives an idempotency key from workstream ID, action ID, input hashes, and relevant decision IDs, records one WorkstreamPhaseRunQueued event, and enqueues the workflow with an input bundle. It should also provide supplied contract values to the workflow runner so the existing contract input manifest records the same handoff-derived inputs. Repeating the same command must return the already queued or running phase run rather than queueing a duplicate.

The second entry path is manual artifact import. An operator runs a command shaped like:

scripts/scherzoctl workstream start   --issue LIV-241   --workflow execplan-implementation-v2   --artifact exec_plan_bundle:scherzo.exec_plan_bundle.v1:tmp/execplan-v2-bundle.json

The command computes the SHA-256 hash of the repository file, copies the exact bytes into the content-addressed workstream artifact store, validates that snapshot through the schema or command validator configured for the artifact type, records a WorkstreamArtifactImported event, creates an input bundle, supplies matching contract values, and enqueues the workflow. This path is required because operators may already have valid artifacts before Scherzo knows about the workstream.

The input bundle should be a typed artifact, scherzo.input_bundle.v1, with the workstream ID, target workflow ID, artifact snapshot refs, hashes, contract input names, and source reason. Workflow prompts should receive the bundle through templating rather than through free-form prompt scraping.

Human Gates and Decision Behavior

A gate is pending when a phase or playbook declares that human confirmation is required before a downstream action. A gate should name the artifact set it covers. If the artifact set changes, the previous decision no longer satisfies the gate.

An approve decision permits downstream actions that require that gate and exactly those artifact hashes. It does not force a downstream action. It only changes eligibility.

A request-changes decision records feedback and should add or prioritize a next action that revises the relevant artifact. It should not delete the artifact or hide the rejected candidate from history. The workstream should show the candidate as superseded or changes-requested.

A reject decision records that the artifact set should not proceed. It should block auto-enqueue and remove downstream suggestions that depend on that artifact set, except for suggestions that explicitly recover from rejection such as redraft or import replacement.

A deviate decision records a deliberate operator override. It may choose a different workflow, skip a suggested workflow, import a manual artifact, or hold the workstream. It should be auditable, but it should not be treated as an error. Deviation is a core feature, not an exception.

All decision commands should require a rationale string. For automation, the rationale can be generated by a playbook, but it must still be recorded.

Next Actions and Playbooks

Next actions are derived options. They should be stored in the workstream projection so operators can inspect them, but they can be recomputed from the latest handoff, decisions, and playbook. A next action must include its required inputs and gate status so the operator sees why it is available or blocked.

A playbook definition should live in repository configuration near workflows, for example under .scherzo/playbooks/. A playbook should name phases and transitions, but it should not replace workflow YAML. A transition should say which workflow to run, what input artifact or contract types it requires, which gate must be approved, and whether auto-enqueue is allowed.

The first playbook should be suggest-only. It should express the dogfood path as suggestions: draft plan, review plan, revise if needed, implement, review, prove, publish. Auto-enqueue can be introduced later for low-risk transitions, such as enqueueing a validation command after a valid artifact is produced, but only when all gates are satisfied.

Playbooks should be composable at the policy layer. The MVP can define standard-implementation and extended-implementation explicitly, even if the extended playbook repeats the standard phases and adds security review, performance review, and rollout proof. A later ticket may add extends or include syntax after at least two real playbooks prove the duplication is painful. The workstream ledger should allow a WorkstreamPlaybookChanged or deviate decision so an issue can move from a standard path to an extended path without losing prior phase history.

Linear, Comments, and Queueing

Linear remains useful for issue discovery, labels, comments, and human communication. It should not become the workstream database. .scherzo/scherzo.yaml already routes issues with workflow: labels and posts handoff comments. Workstream integration should preserve that behavior.

For the first phase of a workstream, a Linear issue with workflow:execplan-v2 can still dispatch the existing workflow. A future workstream:<playbook> label can assign the issue to a workstream or playbook. The two labels are complementary: workflow: chooses an immediate executable workflow, while workstream: chooses durable delivery context and suggestion policy. A workstream-only assignment should create or resume local state and show suggested next actions without requiring immediate execution unless auto-enqueue is explicitly enabled.

Once a phase emits a handoff, Scherzo should record the workstream locally and optionally post a Linear comment that includes the workstream ID, source run ID, artifact refs, and suggested next actions. The comment should say that local Scherzo artifacts are authoritative only for the configured Scherzo state root and that another operator must import or share state before continuing from those refs.

Existing success-state behavior needs care, and the current repository already has a more nuanced completion-state policy than the original draft assumed. .scherzo/scherzo.yaml configures handoff.completion_states.default_completion_state: In Review, no_review_completion_state: Done, and per-workflow produces_reviewable_artifacts plus requires_review flags. Future implementation should either preserve this policy for workstream-aware phase completion or add an explicit per-workflow or per-playbook successor such as unchanged, configured completion state, or playbook-controlled. The first workflow that emits a workstream handoff must prove in tests or a dry run that phase completion does not mark the whole Linear issue Done unless the configured policy explicitly allows it. Existing workflows keep the current behavior unless they opt in.

Queueing should reuse the existing workflow runner. A local phase-run enqueue record should identify the workstream ID, target workflow ID, issue identity, input bundle ref, requested reason, supplied contract values, and idempotency key. The orchestrator can then prepare a normal workflow run with extra phase input context. This avoids creating a new Linear issue for every phase.

Operator Inspection and Retention

The MVP operator surface should be intentionally small. scripts/scherzoctl workstream list shows known workstreams and their current status. scripts/scherzoctl workstream show LIV-241 shows the current projection. scripts/scherzoctl workstream history LIV-241 shows chronological runs, artifacts, decisions, and next-action changes. scripts/scherzoctl workstream artifacts LIV-241 lists artifact refs, paths, hashes, byte counts, and validation status. scripts/scherzoctl workstream next-actions LIV-241 shows available and blocked actions. scripts/scherzoctl workstream decision ... records approve, request-changes, reject, or deviate decisions.

Every command should support --json. Human-readable output should be concise and should never require reading Linear comments to understand current state.

Retention should respect existing local artifact cleanup behavior. Workstream artifacts referenced by active or recently terminal workstreams should be retained. Cleanup should not delete an artifact still referenced by a live workstream gate, decision, handoff, or next action. If cleanup finds a missing referenced artifact, it should retain the workstream record and surface an inspection-needed warning rather than silently dropping history.

Milestones

Milestone 0 aligns the workstream design with existing validator and workflow contract foundations. At the end, the ticket-specific ExecPlan documents how workstream artifact validation calls the current JSON Schema or command validator runner, and how workstream input resolution supplies values to the existing workflow contract path. This milestone prevents domain-specific validator sprawl and avoids creating a second workflow-interface language.

Milestone 1 defines artifact specs and optional workstream metadata parsing without changing runtime behavior. At the end, the repository has documented JSON shapes, fixtures, decoding tests, and optional workstream_phase parsing if a phase needs handoff or next-action metadata in YAML. Existing workflows and existing contract blocks still run unchanged. This milestone proves that the model can be expressed without a giant workflow.

Milestone 2 adds the minimal durable workstream ledger and content-addressed artifact snapshot store. At the end, Scherzo can create a workstream, record an assignment, snapshot a repository-relative artifact into immutable local storage, append core workstream records, and retry the same append idempotently. This milestone exists before entry tooling so later commands do not invent temporary state.

Milestone 3 emits a typed handoff from one selected dogfood phase. At the end, a normal workflow run produces or is adapted into a scherzo.handoff.v1 artifact whose outputs point to immutable snapshot refs and whose recommended next actions are visible as data. This proves the handoff contract before start tooling consumes it.

Milestone 4 adds input resolution and start-from-middle tooling. At the end, operators can start a target workflow from a handoff or manually imported artifact, Scherzo creates a workstream input bundle, supplies matching workflow contract inputs, and duplicate attempts do not queue duplicate runs.

Milestone 5 adds the workstream projection and read-only inspection commands. At the end, operators can list, show, and audit workstreams across runs from local state in human-readable and JSON modes. This milestone makes history inspectable before gates or automation become relied upon.

Milestone 6 adds human decisions and gates. At the end, approvals, changes requested, rejects, and deviations are tied to exact snapshot hashes and change next-action eligibility in the projection.

Milestone 7 adds playbook assignment, suggestions, and guarded auto-enqueue. At the end, a suggest-only playbook can present the dogfood path, explicit auto-enqueue can run only safe transitions, and a workstream can move from a standard playbook to an extended playbook without losing history.

Milestone 8 integrates dogfood planning, review, implementation, proof, and publish phases. At the end, Scherzo's dogfood flow can use workstreams across existing phase workflows while preserving manual start, skip, extra review, recovery behavior, and safe Linear completion-state handling.

Testing and Falsifiability

The workstream feature is falsified if an operator cannot reconstruct why a workflow was started from local Scherzo state alone. Every implementation ticket must include tests that prove artifact refs, hashes, decisions, assignment, and next actions survive ledger replay. The feature is also falsified if a repository-path approval cannot recover the exact approved bytes from the local artifact snapshot, or if repeated starts from the same inputs queue duplicate phase runs.

The foundation-alignment ticket should test reuse of existing foundations. A valid JSON artifact with a configured JSON Schema validator should return success. An invalid fixture should return a structured validation error with a stable kind. A fixture whose workstream artifact type has no configured validator should fail closed with a stable unsupported-validator error. A start-tooling fixture should prove that handoff-derived inputs can be represented as existing workflow contract supplied values and then appear in a workflow_contract_inputs manifest.

The artifact-spec ticket should add decoder tests for valid handoff, decision, input bundle, next-action, assignment, and optional workstream_phase fixtures. It should add negative tests for missing artifact_type, missing schema_version, missing snapshot ref, non-repository-relative original_path, unknown decision kind, and an output that has a path but no snapshot ref. Existing workflow YAML fixtures must still parse when they omit workstream_phase and when they keep only the existing contract block.

Validation and Acceptance

This UberPlan is accepted when the checked-in HTML artifact exists under docs/plans/, can be extracted with scripts/scherzo-execplan-html extract-md, and can produce a bounded brief with scripts/scherzo-execplan-html brief. The legacy scripts/scherzo-execplan validate command currently validates Markdown plan artifacts and rejects this HTML artifact path, so it is not the acceptance command for this file. The later implementation sequence is accepted only when each phase produces operator-visible behavior.

For the complete future MVP, an operator should be able to run commands shaped like:

scripts/scherzoctl workstream show LIV-241 --json
scripts/scherzoctl workstream artifacts LIV-241
scripts/scherzoctl workstream next-actions LIV-241

The expected output should show a workstream ID, linked Linear issue, assigned playbook when one exists, linked workflow runs, typed artifacts with immutable snapshot refs and hashes, decisions tied to those hashes, next actions with blocked or available status, and warnings for missing local state or retained artifacts.

The middle-entry acceptance scenario is: provide a valid ExecPlan bundle or code-change bundle artifact path and start an implementation or review phase without a previous Scherzo workstream run. Scherzo computes the artifact hash, snapshots the exact bytes, records a manual import, creates an input bundle, supplies matching workflow contract inputs, and starts the phase. If the repository file is edited after import, the old snapshot remains recoverable and any new start from the path must create a new snapshot requiring its own approval or explicit deviate decision.

The human-gate acceptance scenario is: approve a specific artifact snapshot hash, then start a downstream phase that requires approval. The phase is eligible only for that snapshot and hash. Editing the repository file should not mutate the approved snapshot; importing the edited file should produce a different hash and make the previous approval insufficient for that new snapshot.

The duplicate-start acceptance scenario is: run the same workstream start-from-handoff or playbook auto-enqueue twice for the same workstream, action ID, input hashes, and gate decisions. Scherzo should produce one queued phase run and report the existing run or an explicit duplicate result for the second attempt. It must not enqueue two indistinguishable implementations from one approval.

The Linear completion-state acceptance scenario is: the first phase workflow that emits a workstream handoff completes successfully while preserving the repository's current reviewable-workflow behavior, or while using an explicit successor policy that is visibly not final. A test or dry-run transcript must show the chosen behavior, such as current handoff.completion_states resolving the phase to In Review, or a future playbook-controlled policy refusing to mark the issue Done until a final publish phase.

The assignment acceptance scenario is: a task with only a workflow: label behaves as it does today; a task assigned to a workstream records durable assignment state and suggestions without relying on Linear comments as authority; a task with both labels runs the selected workflow inside the assigned workstream context. Removing the label does not erase the ledger history.

The playbook acceptance scenario is: a suggest-only playbook presents the next dogfood action but does not enqueue it. A standard and extended fixture playbook can point at the same phase workflows, with the extended playbook adding extra phases. After enabling auto-enqueue for a safe transition and satisfying all gates, Scherzo enqueues the next phase. If a reject or hold decision exists, auto-enqueue is refused and the reason is visible.

Rollout, Recovery, and Idempotence

Rollout should be opt-in. Workflows without workstream-aware metadata continue exactly as before. Existing top-level workflow contract blocks continue to be workflow-run interfaces whether or not the workflow participates in a workstream. Workstream-aware comments, assignment labels, and state transitions should be enabled per workflow or playbook, not globally.

The first production use should be a low-risk dogfood path that emits handoffs and suggestions but does not auto-enqueue. Operators should compare the workstream projection with current Linear comments, workflow contract manifests, and retained artifacts. Only after operators trust the projection should decision gates and playbook automation be enabled.

Workstream-aware phase completion must not imply whole-issue completion. The first dogfood workflow that emits handoffs should preserve current reviewable completion-state behavior or set an explicit non-final successor policy until a final publish phase marks the issue complete.

Recovery should favor preserving evidence. If a phase run crashes before emitting a handoff, the workstream should show the linked run as interrupted and should not invent outputs. If a handoff exists but a later ledger append fails, the handoff artifact remains recoverable and can be re-imported idempotently. If a repository file changes, the old snapshot remains the approved artifact; a new import creates a new snapshot and requires a new decision. If a snapshot ref is missing, Scherzo should block the action and surface a missing-artifact warning rather than proceeding from a Linear comment.

The MVP recovery model after state-root loss is intentionally manual. Restore .scherzo-state/ from backup if available. If it is not available, create a new workstream by manually importing current repository artifacts, then record fresh decisions. Do not infer approvals from old Linear or PR comments. A second daemon without the same state root follows the same manual import rule unless a future export/import feature is implemented.

Ledger writes should be idempotent where possible. Records should include stable IDs derived from workstream ID, assignment ID where relevant, run ID, artifact snapshot ref, action ID, input snapshot hashes, and decision ID so retrying a command does not create contradictory duplicate state. If exact idempotence is not possible in a first implementation, duplicate records must fold to the same projection or be visibly rejected.

Rollback is simple while the feature is opt-in: disable workstream metadata, workstream labels, or playbooks for affected workflows and continue using existing workflow labels and handoff comments. Local workstream artifacts can remain retained for audit even if the feature is disabled.

Backwards Compatibility

Existing .scherzo/workflows/*.yaml files must remain valid. Existing top-level contract blocks must remain valid and should not be replaced by a parallel input/output contract. Optional workstream metadata such as workstream_phase must not be required. Existing workflow: Linear labels must still route to current workflows. Existing scripts/scherzoctl commands must keep their current behavior.

Existing handoff comments should remain available. Workstream-aware comments can add refs and summaries, but they must not break current Linear contract behavior. Any change to completion-state transition must be opt-in per workflow or playbook to avoid marking phase completion as whole-issue completion accidentally. Existing retained artifacts, workflow contract manifests, and run ledgers should not need migration. A future import command can create a workstream from old runs or manual artifacts, but the MVP should not require backfilling all history before new workstreams can work. Old repository files become approval targets only after they are snapshotted into the workstream artifact store; prior paths and comments alone are historical hints.
