Design composable Scherzo workstreams without a mandatory giant workflow

Plan artifact: docs/plans/LIV-241-composable-workstreams-uberplan.html 33 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

This document is an umbrella plan, or UberPlan, for later implementation work. It does not implement workstreams, handoffs, human gates, playbooks, or dogfood workflow replacement by itself. Its purpose is to define the architecture and the smallest safe follow-up tickets that can implement the design incrementally. Each follow-up ticket must get its own implementation-grade ExecPlan with 2-5 minute steps, exact tests, expected red/green output, and a commit map before source code is changed. A later agent should treat this document as the architectural contract and ticket-splitting guide, not as a direct implementation script.

Purpose / Big Picture

Scherzo operators should be able to move an issue through several bounded workflows, such as drafting an ExecPlan, reviewing it, revising it, implementing it, collecting proof, and publishing, without keeping the transition state in memory or relying on Linear comments as the source of truth. After the future implementation work described here, an operator can inspect one durable workstream for an issue, see which typed artifacts were produced by each phase, see which human decisions were recorded against exact artifact hashes, and choose or accept a suggested next phase. The same system must also let an operator start in the middle when valid artifacts already exist.

The desired observable behavior is not a single enormous workflow run. The desired behavior is an artifact-first chain of small phase workflow runs. A phase workflow remains a normal Scherzo workflow, but its inputs, outputs, handoff, and next-action suggestions are recorded in durable local state so later phases can resume, audit, or intentionally deviate.

Problem Framing and Constraints

Today Scherzo can run small workflow units and can also run long workflow DAGs. The repository already has .scherzo/workflows/execplan.yaml, which turns a Linear ticket into a plan through drafting, validation, review, repair, publishing, and implementation-issue creation steps. It also has .scherzo/workflows/implementation.yaml, which prepares context, implements, runs review lanes, applies feedback, validates, and publishes. These workflows are useful, but when an operator wants to compose them across multiple runs, the durable link between one completed run and the next intended run is weak. The link usually lives in a human's memory, a free-form Linear comment, a convention about labels, or a checked-in artifact path that Scherzo does not understand as part of a larger delivery thread.

A single giant workflow DAG is not the right primary abstraction because it encodes one happy path as one long run. It makes entry from the middle awkward, makes extra review loops look like exceptional control flow, couples long-lived product delivery state to one run's workspace and recovery lifecycle, and makes partial progress harder to preserve when operators intentionally stop, skip, or branch. Giant DAGs are still useful for bounded automation inside one phase, but they should not be the only way to represent an issue's delivery journey.

The design must preserve manual entry, manual deviation, and optional automation. Typed artifacts and approvals are the durable source of truth. Linear comments, PR comments, and agent transcripts are projections or evidence, not the canonical state. Local retained artifacts and the Scherzo state ledger come first.

For the MVP, durable local state means one Scherzo daemon and one Scherzo state root, including .scherzo-state/ledger/ and the retained artifact store reachable by that daemon. The MVP is not a cross-operator database and does not promise that a different daemon, a cloned checkout, or a cleaned state root can continue a workstream from Linear comments alone. A second daemon that sees the same Linear issue must treat Linear comments as hints, not authority, and must either use the same state root, import an explicit workstream export, or manually import current artifacts and record new decisions. Export/import, shared remote storage, and backup automation are deferred follow-up work; the MVP must still make state-root loss visible by refusing to infer approvals from comments.

The generic structured-output validator runner is a prerequisite for production domain validation. A follow-up ticket may proceed before that foundation only for fixture-only specs, parsing, and adapters whose production behavior returns an explicit unsupported_validator error for unknown validators. Workstream runtime code must call a narrow named-validator interface and must not grow a permanent enum or bespoke validator layer for every domain artifact.

Strategy Overview

Build a thin workstream layer above existing workflow runs. A workstream is a durable local record for one issue or delivery thread. It links workflow runs, typed artifacts, handoffs, human decisions, and next-action options. A phase workflow is still a checked-in .scherzo/workflows/*.yaml DAG and still uses the existing workflow runner. What changes is that phase workflows declare what artifacts they require and what outputs they produce, and Scherzo records immutable artifact snapshots and workstream events in local state.

The MVP should start with artifact contracts and the generic-validator adapter, then add a minimal append-only workstream ledger and content-addressed artifact snapshot store, then teach selected workflows to emit handoffs, then add entry-from-handoff and manual-import tooling, then add projection and read-only inspection, then add human decisions, and only then add playbooks that can suggest or auto-enqueue the happy path. This order keeps the event foundation in place before any command records WorkstreamPhaseRunQueued or WorkstreamArtifactImported. A handoff artifact alone still gives useful shape to the data, but workstream-aware starts must not invent temporary state that later needs migration.

The approach is proportionate because it reuses existing workflow DAGs, local artifact storage, ledger patterns, structured-output capture, operator controls, and Linear handoff mechanisms. It adds a new layer for cross-run state instead of replacing the workflow runner or forcing all dogfood work into a single DAG.

Alternatives Considered

The simplest alternative is to keep current workflows and improve Linear comments. That would be easy, but it would not make artifacts and decisions durable in Scherzo-owned state. A comment can be edited, deleted, truncated, or overlooked, and it does not give the runner a typed way to verify that a later phase consumed the exact artifact approved earlier.

Another alternative is to create one mandatory end-to-end dogfood workflow that drafts, reviews, revises, implements, proves, and merges every issue. That would reduce some handoff ambiguity for the happy path, but it would remove important operator flexibility. It would not naturally support starting from an already reviewed plan, running an extra review, rejecting one artifact while preserving another, or continuing after a partial run with a manually supplied proof bundle.

A third alternative is to make every workflow understand every other workflow's outputs directly. That creates tight coupling between phase implementations and spreads orchestration policy across prompts and scripts. The chosen design keeps phase workflows small and lets them communicate through typed artifacts and handoffs.

Risks and Countermeasures

The first risk is inventing a bespoke schema and validator system inside the workstream feature. The countermeasure is to make the generic structured-output validator runner a hard dependency for production validation and to allow only a narrow temporary adapter for fixture-level work. That adapter may expose a named-validator call boundary, but production workstream code must return a structured unsupported-validator error instead of hard-coding long-lived domain validators in src/scherzo/workflow_dag.gleam or workstream modules.

The second risk is making workstreams another hidden state system that operators cannot inspect. The countermeasure is to include read-only scherzoctl workstream inspection before any playbook auto-enqueue behavior. Every stored artifact, decision, and next action must have a JSON and human-readable view.

The third risk is repository-path drift. A human may approve a plan file and later the file changes, and if Scherzo recorded only the path then the approved bytes may be unrecoverable. The countermeasure is that any repository-path artifact must be snapshotted into a content-addressed workstream artifact store before a handoff, input bundle, or decision can target it. The original repository-relative path is retained only for human navigation. Decisions and downstream starts target the immutable snapshot ref plus SHA-256 hash and byte count.

The fourth risk is overstating local durability. If .scherzo-state/ is deleted or another daemon does not share the same state root, Linear comments alone cannot reconstruct approvals or exact bytes. The countermeasure is to state this MVP scope explicitly, surface missing-artifact and missing-ledger warnings in inspection commands, and require manual re-import plus new decisions after state-root loss. Backup, export/import, or shared storage is a separate follow-up, not an implicit property of this MVP.

The fifth risk is accidental loss of existing behavior. Existing workflows, Linear routing labels, scheduled jobs, and success/failure comments must keep working for workflows that do not opt into a phase contract. Workstream adoption must be additive, with old workflows parsed and executed as they are today. The first workstream-aware phase that emits a handoff must prove that phase success does not move the whole Linear issue to Done unless its Linear success-state behavior is explicitly configured as unchanged, configured-success, or playbook-controlled.

The sixth risk is over-automation. If playbooks auto-enqueue too early, operators will lose the ability to pause, inspect, or deviate. The countermeasure is to make playbooks suggest-only by default, require explicit per-playbook auto_enqueue policy, and require all referenced gates to be satisfied before any automatic transition.

The seventh risk is duplicate or conflicting starts. Two operators or two playbook evaluations might try to start the same next action from the same artifact set. The countermeasure is to route mutating commands through the daemon or an existing ledger lock and derive idempotency keys from workstream ID, action ID, input snapshot hashes, and gate decision IDs. Repeated attempts with the same key must coalesce to one queued phase run or return an explicit duplicate result; conflicting attempts with different inputs must be visibly rejected or recorded as a deliberate deviation.

Context and Orientation

Scherzo is a workflow runner for repository and issue work. In this repository, workflow definitions live under .scherzo/workflows/. A workflow DAG is a directed acyclic graph of steps. An agent step runs pi with a prompt, and a command step runs a shell command. The current parser and runtime live primarily in src/scherzo/workflow_dag.gleam, src/scherzo/workflow_run.gleam, and src/scherzo/workflow_scheduler.gleam.

A phase workflow is a bounded Scherzo workflow that does one phase of work. Examples include drafting an ExecPlan, reviewing an ExecPlan, implementing code, collecting proof, or publishing a PR. A phase workflow may have several internal steps, but it should produce a small number of durable outputs that another phase can understand.

A workstream is the durable state for one issue or delivery thread across many workflow runs. It records the issue identity, phase runs, typed artifact refs, handoffs, decisions, current gates, and next-action options. A workstream is not a workflow DAG. It is a cross-run ledger and projection.

A typed artifact is a durable JSON or file artifact with an artifact type, schema version, producer metadata, content hash, and validation metadata. Examples are an ExecPlan draft, an ExecPlan review result, a handoff, a proof bundle, or an approval decision.

A human gate is a durable decision point. It asks a human or authorized operator to approve, request changes, reject, or deviate based on specific artifact refs and hashes. The decision itself is a typed artifact and a ledger event.

A handoff is a structured artifact emitted by a completed phase. It records completed outputs, source run metadata, open questions, validation summary, and recommended next actions. It is the smallest useful unit of cross-phase handoff.

A playbook is optional orchestration policy for a common path. It can suggest the next phase or, when explicitly configured and all gates are satisfied, auto-enqueue it. A playbook never owns the source of truth; it reads the workstream projection and writes normal queued-run and decision records.

The existing .scherzo/scherzo.yaml routes Linear issues to workflows by labels with the workflow: prefix. It configures local dogfood workspaces, the pi command, handoff comments, Linear contract states, scheduled jobs, and control command behavior. The handoff section currently posts Linear updates and can attach result Markdown, but comments are not typed durable handoff state.

The current structured-output path is relevant because workstream artifacts should be validated JSON without embedding every domain validator in the runtime. src/scherzo/workflow_dag.gleam currently allows an agent step to declare structured_output. src/scherzo/structured_output.gleam validates final-response or pi tool-call JSON and calls a validator runner. src/scherzo/state/artifact_store.gleam stores step artifacts and structured output artifacts and returns refs with SHA-256 hashes.

The current local state ledger is relevant because workstreams should build on the same event-sourced style. src/scherzo/state/ledger.gleam appends records and loads projections. src/scherzo/state/record.gleam defines record bodies for workflow runs, step attempts, issue parking, Linear commands, scheduled jobs, and outbox events. src/scherzo/state/projection.gleam folds those records into current status. src/scherzo/state/local_artifacts.gleam classifies retained artifacts and cleanup decisions.

Scope Boundaries

This UberPlan is in scope for architecture, artifact contracts, MVP sequencing, follow-up ticket candidates, proof expectations, rollout strategy, and recovery behavior.

This ticket is not in scope for implementing new workstream modules, editing workflow YAML, replacing current workflows, changing Linear state transitions, adding new CLI commands, or building UI. Those are future tickets.

This document is also not an implementation-grade plan for those future tickets. Each ticket must receive its own full ExecPlan with exact file edits, exact tests, expected command output, and a commit map. A future implementation workflow should not start from this UberPlan alone.

Future implementation should be additive. Existing workflows without a phase contract must continue parsing and running. Existing Linear label routing must remain a valid entry point. Existing handoff comments can continue to be posted, but they should become projections that include workstream IDs and artifact refs rather than being the source of truth.

The first implementation target should be local retained artifacts and local state. Linear comments and PR comments can summarize or link to artifacts, but the canonical payload, hash, decision, and workstream history must live in Scherzo-owned state.

The MVP's local-state boundary is one daemon and one state root. Shared remote workstream state, automatic backup, export/import between daemons, and continuity after cleanup of .scherzo-state/ are explicitly deferred. The MVP recovery story for state loss is manual: restore the state root from a backup if one exists, or manually import current repository artifacts into a new workstream and record fresh decisions against their new snapshots.

Design Answers to the Required Questions

Scherzo should represent a workstream as an event-sourced record keyed by a stable workstream_id. For Linear-backed issue work, the default ID should be linear:<issue_identifier> unless a future multi-issue delivery thread explicitly supplies another ID. The workstream projection should include the Linear issue ID and identifier, current status, linked workflow run IDs, known artifacts, gates, decisions, next-action options, and audit history. The storage should build on the local .scherzo-state/ledger/ pattern and should keep artifact bytes in the local artifact store or a new workstream artifact store under the same state root.

The first durable implementation should add a minimal append-only workstream ledger and content-addressed artifact snapshot store before any start-from-handoff or manual-import command records events. That minimal foundation does not need the full operator projection yet, but it must be able to append WorkstreamCreated, WorkstreamArtifactRecorded, WorkstreamHandoffRecorded, and WorkstreamPhaseRunQueued records with stable IDs.

The minimum viable handoff artifact should be a JSON typed artifact named scherzo.handoff.v1. It should include schema_version, artifact_type, artifact_id, workstream_id, issue identity, source workflow ID, source run ID, source step ID when applicable, source run root, completed phase name, outcome, output artifact snapshot refs, validation summary, open questions, recommended next actions, and a short human summary. A handoff is valid only if every listed output has an artifact type, immutable snapshot ref, optional original repository-relative path, SHA-256 hash, byte count, and producer metadata.

Phase workflows should declare required inputs and produced outputs with an optional top-level phase_contract block in workflow YAML. The workflow parser should treat the block as optional for backwards compatibility. The contract should name input requirements by logical name, artifact type, acceptable schema versions, required or optional status, and whether one of several alternatives is acceptable. It should name outputs by logical name, artifact type, source step, source artifact name or repository-relative path, required status, validator name, and whether a repository-path output must be snapshotted. The contract should not embed domain validation code; it should refer to generic structured-output validators by stable names or schema refs once the structured-output validator foundation is available.

A workflow should be startable from either a previous handoff or manually supplied artifacts. Starting from a handoff means resolving the handoff artifact by immutable ref and SHA, reading its output snapshot refs, matching them against the target phase's phase_contract.inputs, and creating an input bundle artifact for the new run. Starting manually means the operator supplies artifact refs or repository-relative paths with expected artifact types. Scherzo computes hashes, snapshots repository-path bytes into the workstream artifact store, validates the snapshot through the named validator, records a manual import event, and then creates the same input bundle shape. The target workflow should receive prompt/template variables such as workstream_id, phase_inputs_json, phase_inputs_summary, and source_handoff_ref so the phase does not need to scrape comments.

Human decisions should be recorded as scherzo.decision.v1 artifacts and matching ledger records. Each decision must include the workstream ID, gate ID, decision kind, actor identity or operator source, timestamp, rationale, and a sorted list of target artifacts with artifact type, immutable snapshot ref, SHA-256 hash, byte count, and original path when one exists. Before accepting the decision, Scherzo must re-read each target snapshot and verify that the hash matches. If any hash mismatches or any snapshot is missing, the command fails and no decision is recorded.

An approve decision satisfies the named gate for exactly the artifact hashes listed in the decision. A request-changes decision leaves the gate unsatisfied, records requested changes, and should suggest a revision or rerun phase using the same target artifacts plus the change request. A reject decision records that the current candidate artifact set should not proceed and should suppress auto-enqueue for downstream actions until a replacement artifact or deviate decision exists. A deviate decision records an intentional departure from the recommended next action. It should name the chosen workflow or manual action, explain why, and preserve the rejected or skipped recommendation for audit.

Scherzo should suggest next actions by storing next-action options in the workstream projection. A next action is data, not control flow. It includes an action ID, label, workflow ID, reason, required input artifact snapshot refs, gate requirements, whether it is safe to auto-enqueue, and a confidence or priority. The operator can inspect these options and choose one. The workflow runner should not assume there is exactly one next action.

Playbooks should automate the happy path by reading the workstream projection and emitting the same next-action suggestions a human could choose. A playbook may auto-enqueue only when the playbook explicitly allows it, all required artifacts validate, all required human gates are approved for matching hashes, no reject decision blocks the action, no operator pause or workstream hold is active, and the idempotency key for that action is not already queued or running. Playbooks must not prevent manual entry or deviation; a deviate decision should override the playbook for that branch and remain visible in history.

Linear integration should remain an entry and notification layer. Existing workflow: labels can still start a first phase. Workstream-aware phases should include the workstream ID and important artifact refs in Linear comments or attachments, but the local workstream ledger and local artifact store are canonical only within the configured state root. Existing queueing should be extended with local phase-run enqueue records rather than requiring a new Linear issue for every phase. Linear comments may present suggested next actions, but choosing an action should write a workstream event and then enqueue a workflow run.

Retained artifacts and history should be inspectable with scherzoctl workstream commands. The minimum useful surface is list, show, history, artifacts, next-actions, and decision. Every command should support --json so operators and scripts can consume the same state. The human view should show workstream status, linked runs, artifact types, refs, hashes, decision history, and recommended next actions.

This design should build on generic structured-output validators. The runtime should be able to ask a named validator to validate a JSON payload and receive success or a structured validation error. Runtime code should not know that an ExecPlan review result has a particular domain field beyond the generic artifact type and validator declaration. The existing narrow validator enum in src/scherzo/workflow_dag.gleam is a foundation to evolve, not the final domain-artifact validation mechanism. Before that evolution lands, workstream tickets may create fixtures and adapter boundaries but must not ship production behavior that silently accepts unvalidated domain artifacts.

The smallest MVP phases are: confirm or add the generic validator adapter contract; define specs and fixtures; add the minimal append-only ledger and artifact snapshot store; emit handoffs from selected workflows; start a workflow from a handoff or manual artifact set; add a projection and inspection CLI; add human gate decisions; add playbook suggestions and guarded auto-enqueue; then integrate the model into the dogfood plan, review, implementation, proof, and publish flow.

Artifact-First State Model

Every cross-phase object should be recorded as an artifact first and a comment second. A workstream ledger event may reference the artifact, but the artifact bytes and hash are what make the event auditable.

The base metadata for every typed artifact should be rendered and stored as structured JSON like this:

{
  "schema_version": 1,
  "artifact_type": "scherzo.handoff.v1",
  "artifact_id": "artifact_<stable-or-generated-id>",
  "workstream_id": "linear:LIV-241",
  "ref": "workstream-artifacts/sha256/<sha256>.json",
  "created_at_ms": 1770000000000,
  "producer": {
    "workflow_id": "execplan",
    "run_id": "run_<id>",
    "step_id": "draft_plan",
    "attempt_index": 1
  },
  "content": {
    "sha256": "<sha256>",
    "bytes": 12345
  },
  "validation": {
    "validator": "scherzo.handoff.v1",
    "status": "valid"
  }
}

The artifact hash should be computed over the stored artifact bytes. If canonical JSON becomes part of the generic structured-output validator contract, use canonical JSON for hash stability. Until then, store the exact bytes and hash those bytes.

A repository file can be imported as a typed artifact only by snapshotting its exact bytes into the content-addressed workstream artifact store. The workstream record should preserve original_path, hash, byte count, artifact type, validation status, and optional git commit or blob identity when available, but decisions, handoffs, and input bundles must reference the immutable snapshot ref. This is needed for plan files such as docs/plans/LIV-241-composable-workstreams-uberplan.html: the path helps a human navigate, while the snapshot answers what bytes were approved.

A workstream projection should be reconstructable from ledger events and artifact reads. It should answer: what issue is this for; which runs happened; which artifacts are current candidates; which gates are pending or satisfied; which decisions were made; which next actions are available; and which actions were intentionally skipped or deviated from.

Handoff Contract

The MVP handoff must be small enough to emit from existing workflows but rich enough to start the next phase. It should not contain all transcripts or all proof. It should contain immutable refs to those artifacts.

The proposed scherzo.handoff.v1 payload is:

{
  "schema_version": 1,
  "artifact_type": "scherzo.handoff.v1",
  "artifact_id": "handoff_<id>",
  "workstream_id": "linear:LIV-241",
  "issue": {
    "tracker": "linear",
    "id": "<linear-issue-id>",
    "identifier": "LIV-241",
    "url": "https://linear.app/living-systems/issue/LIV-241/write-uberplan-for-composable-scherzo-workstreams"
  },
  "completed_phase": {
    "workflow_id": "execplan",
    "phase_id": "draft_execplan",
    "run_id": "<run-id>",
    "outcome": "succeeded"
  },
  "outputs": [
    {
      "name": "execplan_html",
      "artifact_type": "scherzo.execplan.html.v1",
      "ref": "workstream-artifacts/sha256/<sha256>.html",
      "original_path": "docs/plans/LIV-241-composable-workstreams-uberplan.html",
      "sha256": "<sha256>",
      "bytes": 12345,
      "validation": {
        "status": "valid",
        "validator": "scherzo.execplan_html.v1"
      },
      "summary": "Umbrella plan for composable workstreams."
    }
  ],
  "validation": {
    "status": "passed",
    "commands": [
      "scripts/scherzo-execplan validate docs/plans/LIV-241-composable-workstreams-uberplan.html"
    ]
  },
  "recommended_next_actions": [
    {
      "action_id": "review_execplan",
      "label": "Review ExecPlan",
      "workflow_id": "execplan-revision",
      "reason": "A human or agent review should check the plan before implementation tickets are created.",
      "required_inputs": ["execplan_html"],
      "requires_gate": null,
      "auto_enqueue": false
    }
  ],
  "open_questions": [],
  "summary": "Phase completed and produced a reviewed artifact candidate."
}

The handoff should be allowed to reference multiple outputs. It should not duplicate large outputs. It should include enough summary text for a human to understand the handoff in scherzoctl workstream show, but all authoritative content should remain in referenced snapshots or structured artifacts.

Phase Workflow Contracts

A future phase-aware workflow YAML file should remain a valid normal workflow. The phase_contract block is optional and additive. A draft shape is:

phase_contract:
  phase_id: draft_execplan
  display_name: Draft ExecPlan
  inputs:
    - name: issue_brief
      artifact_type: scherzo.issue_brief.v1
      required: true
  outputs:
    - name: execplan_html
      artifact_type: scherzo.execplan.html.v1
      required: true
      source:
        kind: repo_path
        path: docs/plans/<issue>-<slug>.html
        snapshot: required
      validator: scherzo.execplan_html.v1
    - name: handoff
      artifact_type: scherzo.handoff.v1
      required: true
      source:
        kind: structured_output
        step_id: draft_plan
        artifact_name: handoff
      validator: scherzo.handoff.v1
  next_actions:
    - action_id: review_execplan
      workflow_id: execplan-review
      inputs:
        - execplan_html

Inputs may be required, optional, or alternatives. The first MVP can support only required inputs and exact artifact types. Alternatives can be added after the core path works.

Outputs should support two MVP source kinds. The first is structured_output, which points to an existing structured output artifact from an agent step. The second is repo_path, which points to a repository-relative file whose bytes Scherzo hashes and snapshots before it records the artifact. Later work can add command-produced run artifacts and artifact collections.

The workflow runner should validate phase outputs at the end of a phase run. If a required output is missing or invalid, the workflow run should fail or park according to existing failure policy. If a required handoff is valid, Scherzo records the handoff and its output snapshots in the workstream ledger and updates next-action options.

Starting From the Middle

The MVP must allow two entry paths after the minimal workstream ledger and artifact snapshot store exist. The first entry path is from a handoff. An operator runs a command shaped like:

scripts/scherzoctl workstream start-from-handoff \
  --handoff-ref <ref> \
  --handoff-sha256 <sha256> \
  --workflow execplan-revision

The command resolves and verifies the handoff, matches its output snapshot refs to the target workflow's phase_contract.inputs, derives an idempotency key from workstream ID, action ID, input hashes, and relevant decision IDs, records one WorkstreamPhaseRunQueued event, and enqueues the workflow with an input bundle. Repeating the same command must return the already queued or running phase run rather than queueing a duplicate.

The second entry path is manual artifact import. An operator runs a command shaped like:

scripts/scherzoctl workstream start \
  --issue LIV-241 \
  --workflow execplan-revision \
  --artifact execplan_html:scherzo.execplan.html.v1:docs/plans/LIV-241-composable-workstreams-uberplan.html

The command computes the SHA-256 hash of the repository file, copies the exact bytes into the content-addressed workstream artifact store, validates that snapshot through the generic validator named by the target input contract, records a WorkstreamArtifactImported event, creates an input bundle, and enqueues the workflow. This path is required because operators may already have valid artifacts before Scherzo knows about the workstream.

The input bundle should be a typed artifact, scherzo.input_bundle.v1, with the workstream ID, target workflow ID, artifact snapshot refs, hashes, and source reason. Workflow prompts should receive the bundle through templating rather than through free-form prompt scraping.

Human Gates and Decision Behavior

A gate is pending when a phase or playbook declares that human confirmation is required before a downstream action. A gate should name the artifact set it covers. If the artifact set changes, the previous decision no longer satisfies the gate.

An approve decision permits downstream actions that require that gate and exactly those artifact hashes. It does not force a downstream action. It only changes eligibility.

A request-changes decision records feedback and should add or prioritize a next action that revises the relevant artifact. It should not delete the artifact or hide the rejected candidate from history. The workstream should show the candidate as superseded or changes-requested.

A reject decision records that the artifact set should not proceed. It should block auto-enqueue and remove downstream suggestions that depend on that artifact set, except for suggestions that explicitly recover from rejection such as redraft or import replacement.

A deviate decision records a deliberate operator override. It may choose a different workflow, skip a suggested workflow, import a manual artifact, or hold the workstream. It should be auditable, but it should not be treated as an error. Deviation is a core feature, not an exception.

All decision commands should require a rationale string. For automation, the rationale can be generated by a playbook, but it must still be recorded.

Next Actions and Playbooks

Next actions are derived options. They should be stored in the workstream projection so operators can inspect them, but they can be recomputed from the latest handoff, decisions, and playbook. A next action must include its required inputs and gate status so the operator sees why it is available or blocked.

A playbook definition should live in repository configuration near workflows, for example under .scherzo/playbooks/. A playbook should name phases and transitions, but it should not replace workflow YAML. A transition should say which workflow to run, what input artifact types it requires, which gate must be approved, and whether auto-enqueue is allowed.

The first playbook should be suggest-only. It should express the dogfood path as suggestions: draft plan, review plan, revise if needed, implement, review, prove, publish. Auto-enqueue can be introduced later for low-risk transitions, such as enqueueing a validation command after a valid artifact is produced, but only when all gates are satisfied.

Linear, Comments, and Queueing

Linear remains useful for issue discovery, labels, comments, and human communication. It should not become the workstream database. .scherzo/scherzo.yaml already routes issues with workflow: labels and posts handoff comments. Workstream integration should preserve that behavior.

For the first phase of a workstream, a Linear issue with workflow:execplan can still dispatch the existing workflow. Once a phase emits a handoff, Scherzo should record the workstream locally and optionally post a Linear comment that includes the workstream ID, source run ID, artifact refs, and suggested next actions. The comment should say that local Scherzo artifacts are authoritative only for the configured Scherzo state root and that another operator must import or share state before continuing from those refs.

Existing success-state behavior needs care. Today .scherzo/scherzo.yaml maps success handoff to the Linear Done state. Phase workflows in a workstream may complete successfully without the whole issue being done. Future implementation should add per-workflow or per-phase handoff state behavior, such as linear_success_state: unchanged, linear_success_state: configured_success, or linear_success_state: playbook_controlled. The first workflow that emits a workstream handoff must prove in tests or a dry run that phase completion does not mark the whole Linear issue Done unless this setting explicitly allows it. Existing workflows keep the current behavior unless they opt in.

Queueing should reuse the existing workflow runner. A local phase-run enqueue record should identify the workstream ID, target workflow ID, issue identity, input bundle ref, requested reason, and idempotency key. The orchestrator can then prepare a normal workflow run with extra phase input context. This avoids creating a new Linear issue for every phase.

Operator Inspection and Retention

The MVP operator surface should be intentionally small. scripts/scherzoctl workstream list shows known workstreams and their current status. scripts/scherzoctl workstream show LIV-241 shows the current projection. scripts/scherzoctl workstream history LIV-241 shows chronological runs, artifacts, decisions, and next-action changes. scripts/scherzoctl workstream artifacts LIV-241 lists artifact refs, paths, hashes, byte counts, and validation status. scripts/scherzoctl workstream next-actions LIV-241 shows available and blocked actions. scripts/scherzoctl workstream decision ... records approve, request-changes, reject, or deviate decisions.

Every command should support --json. Human-readable output should be concise and should never require reading Linear comments to understand current state.

Retention should respect existing local artifact cleanup behavior. Workstream artifacts referenced by active or recently terminal workstreams should be retained. Cleanup should not delete an artifact still referenced by a live workstream gate, decision, handoff, or next action. If cleanup finds a missing referenced artifact, it should retain the workstream record and surface an inspection-needed warning rather than silently dropping history.

Interfaces and Dependencies

Future implementation should introduce a workstream namespace rather than placing all new types in existing large modules. Suggested files are:

src/scherzo/workstream/types.gleam for WorkstreamId, ArtifactType, ArtifactRef, HandoffArtifact, DecisionArtifact, NextAction, GateStatus, and InputBundle types.

src/scherzo/workstream/id.gleam for stable ID creation, including default linear:<issue_identifier> workstream IDs and validation for manually supplied IDs.

src/scherzo/workstream/contract.gleam for parsing and validating phase_contract blocks from workflow YAML.

src/scherzo/workstream/artifact_store.gleam for snapshotting repository-relative files and structured outputs into content-addressed workstream artifacts while preserving original paths for display.

src/scherzo/workstream/validation_adapter.gleam for the narrow named-validator boundary. The adapter should accept validator name, artifact type, and bytes or decoded JSON, then return success or a structured validation error. Before the generic validator runner lands, production callers should receive unsupported_validator for domain validators rather than silent success.

src/scherzo/workstream/handoff.gleam for handoff artifact encoding, decoding, and generic validation adapter calls.

src/scherzo/workstream/decision.gleam for decision artifact encoding, snapshot hash verification, and behavior rules for approve, request-changes, reject, and deviate.

src/scherzo/workstream/playbook.gleam for playbook parsing, suggestion generation, auto-enqueue eligibility checks, and idempotency-key derivation.

src/scherzo/workstream/render.gleam for human-readable scherzoctl workstream output.

Future implementation should extend src/scherzo/workflow_dag.gleam to include an optional phase contract on WorkflowDag without changing behavior for workflows that omit it.

Future implementation should extend src/scherzo/state/record.gleam with workstream record bodies. Candidate records are WorkstreamCreated, WorkstreamArtifactRecorded, WorkstreamHandoffRecorded, WorkstreamDecisionRecorded, WorkstreamNextActionsUpdated, WorkstreamPhaseRunQueued, WorkstreamPhaseRunStarted, WorkstreamPhaseRunFinished, and WorkstreamPhaseRunLinked. The minimal ledger ticket should introduce only the subset needed to snapshot artifacts and queue phase runs; projection and richer inspection can follow.

Future implementation should extend src/scherzo/state/projection.gleam with a workstreams dictionary keyed by workstream ID. The projection should fold records into current artifacts, gates, decisions, next actions, linked runs, duplicate-start status, and missing-artifact warnings.

Future implementation should extend src/scherzo/ctl.gleam and, where daemon-mediated mutation is needed, src/scherzo/control/command.gleam with workstream inspection and decision commands. Read-only inspection may read local state directly; mutating commands should go through the daemon or use the existing ledger lock so concurrent operators do not corrupt state.

Future implementation should extend prompt templating, likely in src/scherzo/template.gleam, so phase workflows can receive workstream_id, phase_inputs_json, phase_inputs_summary, and source_handoff_ref without scraping comments.

Future implementation should depend on the generic structured-output validator contract from the related structured-output tickets. The runtime dependency should be a generic validator runner interface, not an enum of every workstream artifact type.

Milestones

Milestone 0 verifies the generic validator prerequisite. At the end, either the generic structured-output validator runner exposes a named-validator contract that workstream code can call, or the future workstream branch contains only a temporary adapter with fixture-level tests and production unsupported_validator behavior. This milestone prevents domain-specific validator sprawl before any artifact becomes authoritative.

Milestone 1 defines artifact specs and contract parsing without changing runtime behavior. At the end, the repository has documented JSON shapes, fixtures, decoding tests, and optional phase_contract parsing. Existing workflows still run unchanged. This milestone proves that the model can be expressed without a giant workflow.

Milestone 2 adds the minimal durable workstream ledger and content-addressed artifact snapshot store. At the end, Scherzo can create a workstream, snapshot a repository-relative artifact into immutable local storage, append core workstream records, and retry the same append idempotently. This milestone exists before entry tooling so later commands do not invent temporary state.

Milestone 3 teaches one or two selected workflows to emit handoff artifacts and recommended next actions. At the end, a phase run can produce a scherzo.handoff.v1 artifact that references real output snapshots by immutable ref and hash. This milestone provides immediate operator value on top of the ledger foundation.

Milestone 4 adds start-from-handoff and manual artifact import tooling. At the end, an operator can start a target workflow from a handoff or from a manually supplied repository-relative artifact path, and repeated starts from the same action and hashes coalesce or are rejected as duplicates. This milestone proves middle entry.

Milestone 5 adds the workstream projection and read-only inspection commands. At the end, operators can list, show, and audit workstreams across runs from local state in human-readable and JSON modes. This milestone makes history inspectable before gates or automation become relied upon.

Milestone 6 adds human gate decisions. At the end, approve, request-changes, reject, and deviate decisions are recorded as typed artifacts and ledger events tied to exact artifact snapshot refs and hashes. This milestone proves auditability and safe branching.

Milestone 7 adds playbook suggestions and guarded auto-enqueue. At the end, a suggest-only dogfood playbook can derive next actions, and carefully configured transitions can auto-enqueue only after gates pass and the idempotency key is clear. This milestone proves automation without forcing one path.

Milestone 8 integrates dogfood planning, review, implementation, proof, and publish phases. At the end, Scherzo's dogfood flow can use workstreams across existing phase workflows while preserving manual start, skip, extra review, recovery behavior, and safe Linear success-state handling.

Testing and Falsifiability

The workstream feature is falsified if an operator cannot reconstruct why a workflow was started from local Scherzo state alone. Every implementation ticket must include tests that prove artifact refs, hashes, decisions, and next actions survive ledger replay. The feature is also falsified if a repository-path approval cannot recover the exact approved bytes from the local artifact snapshot, or if repeated starts from the same inputs queue duplicate phase runs.

The validator-prerequisite ticket should test fail-closed behavior. With the generic runner absent, a production validation call for scherzo.handoff.v1 should return an error kind named unsupported_validator. With the runner present, a valid fixture should return success and an invalid fixture should return a structured validation error with a stable kind.

The artifact-spec ticket should add decoder tests for valid handoff, decision, input bundle, next-action, and phase-contract fixtures. It should add negative tests for missing artifact_type, missing schema_version, missing snapshot ref, non-repository-relative original_path, unknown decision kind, and an output that has a path but no snapshot ref. Existing workflow YAML fixtures must still parse when they omit phase_contract.

The minimum valid handoff fixture should contain these fields so later ticket-specific ExecPlans can use it as a contract:

{
  "schema_version": 1,
  "artifact_type": "scherzo.handoff.v1",
  "artifact_id": "handoff_fixture_valid",
  "workstream_id": "linear:LIV-241",
  "outputs": [
    {
      "name": "execplan_html",
      "artifact_type": "scherzo.execplan.html.v1",
      "ref": "workstream-artifacts/sha256/<sha256>.html",
      "original_path": "docs/plans/LIV-241-composable-workstreams-uberplan.html",
      "sha256": "<sha256>",
      "bytes": 12345
    }
  ],
  "recommended_next_actions": []
}

Invalid fixtures should fail with stable error kinds such as missing_field, invalid_repository_relative_path, missing_snapshot_ref, unknown_decision_kind, or hash_mismatch. Ticket-specific ExecPlans may choose exact Gleam type names, but the CLI and JSON-facing error kind strings should remain stable.

The minimal-ledger ticket should test record replay and idempotency. Given two identical artifact imports, projection replay should show one current artifact snapshot and one duplicate/coalesced result. Given two imports from the same original path with different bytes, replay should show two distinct snapshot refs and should not transfer approvals from the old hash to the new hash.

The handoff-emission ticket should test that a handoff references existing snapshot refs by hash and that a missing required output prevents a successful handoff. It should include a fixture where the output file changes after hash computation and prove a new import creates a new snapshot instead of mutating the old one.

The start-from-handoff ticket should test both entry modes. One test should provide a valid handoff and assert that an input bundle contains the expected snapshot ref. Another should provide a manual repository-relative path and assert that the import records type, original path, snapshot ref, hash, and bytes. Negative tests should cover missing files, unsupported artifact types, invalid refs, hash mismatch, and repeated start attempts. Missing artifacts should exit non-zero with an error kind missing_artifact; stale hashes should exit non-zero with an error kind hash_mismatch; duplicate starts should either exit successfully with the existing queued run ID or return a non-zero duplicate error without enqueueing a second run.

The projection and inspection ticket should test stable CLI JSON. scherzoctl workstream show LIV-241 --json should include at least these top-level keys:

{
  "workstream_id": "linear:LIV-241",
  "issue": { "identifier": "LIV-241" },
  "status": "active",
  "runs": [],
  "artifacts": [],
  "gates": [],
  "decisions": [],
  "next_actions": [],
  "warnings": []
}

The decision-gates ticket should test approve, request-changes, reject, and deviate. Approve should satisfy a gate only for exact snapshot hashes. Request-changes should leave the gate unsatisfied and add revision guidance. Reject should block downstream auto-enqueue. Deviate should record the chosen alternate action and preserve the skipped recommendation.

The playbook ticket should test suggest-only and auto-enqueue behavior separately. Suggest-only must never enqueue. Auto-enqueue must refuse when a gate is missing, an artifact hash is stale, the workstream is held, a reject decision applies, or the same idempotency key is already queued or running. Auto-enqueue may proceed only when all required conditions are true.

Every production implementation ticket should run, from the repository root:

direnv exec . gleam test
direnv exec . gleam format --check src test
direnv exec . gleam run -m glinter
direnv exec . gleam run -m scherzo_lint

Expected success is that all tests pass, formatting reports no changes needed, and lint commands report no new errors. If warnings already exist, do not expand the warning set.

Validation and Acceptance

This UberPlan is accepted when the checked-in HTML artifact exists under docs/plans/, validates with the ExecPlan validation script, and answers the required design questions. The later implementation sequence is accepted only when each phase produces operator-visible behavior.

For the complete future MVP, an operator should be able to run commands shaped like:

scripts/scherzoctl workstream show LIV-241 --json
scripts/scherzoctl workstream artifacts LIV-241
scripts/scherzoctl workstream next-actions LIV-241

The expected output should show a workstream ID, linked Linear issue, linked workflow runs, typed artifacts with immutable snapshot refs and hashes, decisions tied to those hashes, next actions with blocked or available status, and warnings for missing local state or retained artifacts.

The middle-entry acceptance scenario is: provide a valid ExecPlan artifact path and start an implementation or review phase without a previous Scherzo run. Scherzo computes the artifact hash, snapshots the exact bytes, records a manual import, creates an input bundle, and starts the phase. If the repository file is edited after import, the old snapshot remains recoverable and any new start from the path must create a new snapshot requiring its own approval or explicit deviate decision.

The human-gate acceptance scenario is: approve a specific artifact snapshot hash, then start a downstream phase that requires approval. The phase is eligible only for that snapshot and hash. Editing the repository file should not mutate the approved snapshot; importing the edited file should produce a different hash and make the previous approval insufficient for that new snapshot.

The duplicate-start acceptance scenario is: run the same workstream start-from-handoff or playbook auto-enqueue twice for the same workstream, action ID, input hashes, and gate decisions. Scherzo should produce one queued phase run and report the existing run or an explicit duplicate result for the second attempt. It must not enqueue two indistinguishable implementations from one approval.

The Linear success-state acceptance scenario is: the first phase workflow that emits a workstream handoff completes successfully while the issue remains not Done unless its configuration explicitly chooses a final success transition. A test or dry-run transcript must show the chosen behavior, such as linear_success_state: unchanged or linear_success_state: playbook_controlled.

The playbook acceptance scenario is: a suggest-only playbook presents the next dogfood action but does not enqueue it. After enabling auto-enqueue for a safe transition and satisfying all gates, Scherzo enqueues the next phase. If a reject or hold decision exists, auto-enqueue is refused and the reason is visible.

Rollout, Recovery, and Idempotence

Rollout should be opt-in. Workflows without phase_contract continue exactly as before. Workstream-aware comments and state transitions should be enabled per workflow or playbook, not globally.

The first production use should be a low-risk dogfood path that emits handoffs and suggestions but does not auto-enqueue. Operators should compare the workstream projection with current Linear comments and retained artifacts. Only after operators trust the projection should decision gates and playbook automation be enabled.

Workstream-aware phase completion must not imply whole-issue completion. The first dogfood workflow that emits handoffs should set or prove a success-state behavior equivalent to unchanged or playbook-controlled until a final publish phase explicitly marks the issue complete.

Recovery should favor preserving evidence. If a phase run crashes before emitting a handoff, the workstream should show the linked run as interrupted and should not invent outputs. If a handoff exists but a later ledger append fails, the handoff artifact remains recoverable and can be re-imported idempotently. If a repository file changes, the old snapshot remains the approved artifact; a new import creates a new snapshot and requires a new decision. If a snapshot ref is missing, Scherzo should block the action and surface a missing-artifact warning rather than proceeding from a Linear comment.

The MVP recovery model after state-root loss is intentionally manual. Restore .scherzo-state/ from backup if available. If it is not available, create a new workstream by manually importing current repository artifacts, then record fresh decisions. Do not infer approvals from old Linear or PR comments. A second daemon without the same state root follows the same manual import rule unless a future export/import feature is implemented.

Ledger writes should be idempotent where possible. Records should include stable IDs derived from workstream ID, run ID, artifact snapshot ref, action ID, input snapshot hashes, and decision ID so retrying a command does not create contradictory duplicate state. If exact idempotence is not possible in a first implementation, duplicate records must fold to the same projection or be visibly rejected.

Rollback is simple while the feature is opt-in: disable phase contracts or playbooks for affected workflows and continue using existing workflow labels and handoff comments. Local workstream artifacts can remain retained for audit even if the feature is disabled.

Proof-of-Work Expectations for Later Implementation Phases

Every follow-up ticket should include a short proof section in its PR description or implementation ExecPlan. The proof must name the exact commands run, the artifact refs or fixture files produced, and the operator-visible output.

For the validator prerequisite, proof is a transcript or test output showing the named-validator boundary succeeds for a valid fixture and fails closed with unsupported_validator when no production validator exists.

For artifact specs, proof is decoder and validator tests with valid and invalid fixtures, including stable error kinds.

For the minimal ledger and snapshot store, proof is a replayed workstream with immutable snapshot refs and an idempotent duplicate-import or duplicate-queue test.

For handoff emission, proof is a handoff artifact whose listed output snapshot hash matches the actual stored snapshot bytes and whose original path points to the repository file that produced it.

For start-from-handoff, proof is a transcript showing successful start from a valid handoff, failure from a stale hash or missing snapshot, and duplicate start folding to one queued run or a visible duplicate result.

For projection and inspection, proof is a replayed workstream projection and scherzoctl workstream show --json output for a fixture or dry run.

For gates, proof is four decision transcripts: approve, request-changes, reject, and deviate. The approve proof must include a missing-snapshot or hash-mismatch negative case.

For playbooks, proof is a suggest-only transcript, an auto-enqueue refusal transcript when a required gate is absent, and a duplicate auto-enqueue test for the same idempotency key.

For dogfood integration, proof is an end-to-end retained workstream history across at least three phase runs, including one human decision and evidence that a phase handoff did not mark the Linear issue Done unless explicitly configured.

Backwards Compatibility

Existing .scherzo/workflows/*.yaml files must remain valid. The optional phase_contract field must not be required. Existing workflow: Linear labels must still route to current workflows. Existing scripts/scherzoctl commands must keep their current behavior.

Existing handoff comments should remain available. Workstream-aware comments can add refs and summaries, but they must not break current Linear contract behavior. Any change to success-state transition must be opt-in per workflow or playbook to avoid marking phase completion as whole-issue completion accidentally. The first workstream-aware handoff emitter must set or prove a non-final success-state behavior unless it is truly the final publish phase.

Existing retained artifacts and run ledgers should not need migration. A future import command can create a workstream from old runs or manual artifacts, but the MVP should not require backfilling all history before new workstreams can work. Old repository files become approval targets only after they are snapshotted into the workstream artifact store; prior paths and comments alone are historical hints.
