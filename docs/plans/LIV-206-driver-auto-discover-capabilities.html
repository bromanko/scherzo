Make workspace drivers self-describe capabilities

Plan artifact: docs/plans/LIV-206-driver-auto-discover-capabilities.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

After this change, a Scherzo operator no longer has to copy a workspace driver's supported capability list into every workspace profile by hand. The operator will configure the trusted driver command and lifecycle operations, while Scherzo will ask the driver what capability commands it supports before workflows are validated or dispatched. The visible result is that .scherzo/scherzo.yaml and examples/scherzo.yaml no longer contain workspace.profiles.<name>.driver.capabilities, yet workflows with workspace_capabilities still fail early when the selected driver does not support a required operation.

The plan deliberately preserves workflow-level workspace_capabilities. Those are workflow requirements, not driver-provided metadata. A workflow may still say it requires status, diff, changed-files, assert-only, baseline, refresh-base, or publish-change; the difference is that the selected profile's provided list comes from <driver> describe --json instead of YAML.

Problem Framing and Constraints

The current config shape duplicates driver knowledge in operator-authored YAML. A profile repeats capability metadata even though the driver script already determines which operations are implemented. That duplication is noisy and fragile: a profile can advertise a capability that the command does not implement, or fail to advertise one that the command does implement. The current list is metadata only; it is not an authorization boundary. Once a command or agent step receives SCHERZO_WORKSPACE_DRIVER, the trusted driver command itself decides what operations it accepts.

This plan solves the duplication problem for driver capabilities only. It does not remove workflow-level capability requirements. It does not introduce a new authorization model, a policy allowlist, a sandbox, or a restricted wrapper. It also does not auto-discover lifecycle operations; driver.lifecycle remains explicit operator config because lifecycle commands can create or remove directories and are a different safety surface from read-only or publish-oriented capabilities.

A key product constraint is that old configs with driver.capabilities do not need backwards compatibility. They should fail with a clear error that names the removed key and points to a runbook. This is a breaking config change, so the implementation must include migration documentation and actionable diagnostics.

Strategy Overview

Add one side-effect-free metadata command to workspace drivers:

<driver> describe --json

The command must print one JSON object on stdout and exit 0. The initial response contract is:

{"version":1,"capabilities":["status","diff","changed-files","assert-only"]}

The version field is an integer protocol version. Version 1 is the only accepted version in this plan. The capabilities field is a list of capability names from the existing fixed vocabulary. The list may be in any order, but Scherzo canonicalizes it before storing it, comparing it, exposing it to prompts, or fingerprinting it. A duplicate name, unknown name, malformed JSON document, missing capabilities field, nonzero exit, or timeout is a configuration/load error.

The implementation keeps the current internal idea that a resolved profile has a driver capability list. The external YAML schema changes: config parsing rejects driver.capabilities, and a new discovery phase fills the internal list by invoking the configured trusted driver. Put that discovery phase in a small src/scherzo/workspace_driver_discovery.gleam module, call it during runtime bundle loading before profile capability validation, and update direct execution tests so they either use an already-enriched in-memory profile or explicitly call the discovery helper. Keep workspace_profile.resolve pure; it should compare required capabilities with the capabilities already present on the selected profile and should not spawn a driver process.

This approach is the right size because it adds one metadata command and one enrichment path instead of inventing a capability registry, probing operational commands, or moving authorization policy into YAML. Probing commands such as status, diff, or publish-change is intentionally rejected: those commands can fail because a workspace is missing, a VCS is not initialized, credentials are absent, a network call failed, or ordinary runtime state is invalid. A dedicated metadata command avoids confusing runtime failures with driver support metadata.

Alternatives Considered

The smallest possible change would be to keep driver.capabilities and improve documentation saying it is metadata only. That reduces confusion but does not remove the duplicate source of truth, so profiles can still drift from drivers and workflows still validate against stale YAML.

Another option is to infer support by running each operational capability command and treating exit code 2 as unsupported. This is rejected because operational commands have real preconditions and side effects. publish-change can touch remotes and PRs, refresh-base can rebase work, diff and status require a valid workspace, and assert-only requires a target path. A metadata command is simpler and safer.

A broader option is to discover both lifecycle operations and capabilities from the driver. That is out of scope for this ticket. Lifecycle operations are destructive or workspace-shaping and should remain explicit operator policy for now. Removing driver.capabilities already solves the duplicated support metadata problem without changing lifecycle safety.

A compatibility option is to accept old driver.capabilities and ignore it with a warning. That is rejected because the product decision is to make the breaking change clear. A warning would let stale config survive and would make it harder for operators to know which source of truth is active.

Risks and Countermeasures

Discovery could become an unexpected side effect if drivers do too much work in describe. Countermeasure: the contract says describe --json must not require SCHERZO_WORKSPACE_PATH, must not inspect or mutate a workflow workspace, and must be implemented in the checked-in drivers as pure static output. Contract tests run both checked-in drivers with no workspace path and assert stable JSON.

Runtime validation could accidentally run before discovery and reject valid workflows because every driver appears to provide no capabilities. Countermeasure: add runtime bundle tests that remove YAML capability metadata, use fake drivers with describe --json, and assert that workflows requiring discovered capabilities load successfully while workflows requiring absent capabilities fail with workspace_capabilities_unavailable. Add direct workflow execution tests that use enriched profiles for command-step environment and prompt locals.

Old configs could silently keep working if the parser ignores unknown keys. Countermeasure: add an explicit rejection for workspace.profiles.<name>.driver.capabilities in src/scherzo/config.gleam, with tests that assert the error names the removed key and the migration runbook.

Fingerprints could become unstable if driver output order changes. Countermeasure: canonicalize discovered capabilities through the existing fixed ordering in src/scherzo/config/types.gleam before fingerprints are computed, and add tests that two fake drivers returning the same capabilities in different orders produce the same workflow/execution fingerprint.

Driver discovery failures could be hard to diagnose. Countermeasure: define a narrow discovery error shape that includes the profile name, resolved command, failure code such as workspace_driver_discovery_failed, and bounded diagnostics. Map it to runtime bundle errors and doctor/workflow-config diagnostics without leaking local absolute paths from adapter-authored messages.

This breaking config change could strand operators on old examples or docs. Countermeasure: update the dogfood config, public example config, driver contract runbook, driver migration runbook, portable research runbook, README, and .scherzo/README.md references that tell operators to configure driver.capabilities. The new runbook must explain the three-step fix: remove the key, ensure the driver implements describe --json, and rerun workflow-config validation or the test suite.

Decision Log

  • DecisionUse a dedicated describe --json metadata command instead of probing operational capability commands.

    RationaleProbing mixes support metadata with ordinary runtime failures such as missing workspaces, VCS state, credentials, network calls, or command side effects. A metadata command is deterministic, bounded, and easy to test.

    Date2026-05-11

  • DecisionKeep workflow-level workspace_capabilities unchanged and remove only profile-local driver.capabilities from YAML.

    RationaleWorkflows still need to declare requirements so Scherzo can reject incompatible selected drivers before dispatch. The duplicated piece is the profile's provided capability metadata.

    Date2026-05-11

  • DecisionKeep workspace_profile.resolve pure and put driver process invocation in a workspace_driver_discovery enrichment step before profile validation.

    RationaleProfile resolution and fingerprinting should remain deterministic over already-loaded data. A single load-time discovery step is easier to test and avoids hidden process spawning in pure comparison helpers.

    Date2026-05-11

  • DecisionTreat old driver.capabilities YAML as a hard config error, not a warning or ignored field.

    RationaleThe issue explicitly chooses a breaking change with clear guidance over backwards compatibility. Ignoring the old field would leave a misleading source of truth in operator config.

    Date2026-05-11

  • DecisionResolve discovery-time $SCHERZO_REPO_ROOT from the loaded config directory and run driver metadata commands with an isolated environment containing only PATH, SCHERZO_CONFIG_DIR, SCHERZO_REPO_ROOT, and SCHERZO_WORKSPACE_DRIVER.

    RationaleIn an active Scherzo worker, ambient process variables can point at the outer repository or current prepared workspace rather than the config being loaded. Discovery should describe the driver configured by the loaded profile, should not depend on a prepared workspace, and should not leak discovered capabilities or unrelated workflow secrets into the metadata command.

    Date2026-05-11

Context and Orientation

Scherzo is a Gleam application that loads an operator config file, loads workflow DAG YAML files, selects Linear issues, prepares workspaces for each workflow run, and executes command or agent steps. A workflow DAG is a YAML file with fields such as id, workspace_profile, workspace_capabilities, and steps. A workspace profile is operator configuration under workspace.profiles.<name> that says how Scherzo prepares and manages a workflow workspace. A workspace driver is one trusted local command configured by the operator inside a workspace profile. A workspace capability is a named driver operation that workflow code may require or call, such as status, diff, changed-files, assert-only, baseline, refresh-base, or publish-change.

The current config model is mostly in src/scherzo/config/types.gleam and src/scherzo/config.gleam. src/scherzo/config/types.gleam defines WorkspaceCapability, conversion functions such as workspace_capability_from_string, canonicalization through canonical_workspace_capabilities, and WorkspaceDriverConfig(command, lifecycle, capabilities, timeout_ms). src/scherzo/config.gleam currently reads workspace.profiles.<name>.driver.command, driver.lifecycle, driver.capabilities, and driver.timeout_ms in read_workspace_driver.

Workflow parsing lives in src/scherzo/workflow_dag.gleam. It parses top-level workspace_capabilities and stores them on WorkflowDag. Those requirements must stay.

Profile selection and compatibility live in src/scherzo/workspace_profile.gleam. resolve chooses the selected profile by explicit dag.workspace_profile or orchestrator.workspace_profiles.default_profile. validate_capabilities compares dag.workspace_capabilities with provided_capabilities(profile), which currently returns driver.capabilities when a driver is present.

Runtime bundle loading lives in src/scherzo/runtime_bundle.gleam. It loads config and workflows, then validate_workspace_profiles calls workspace_profile.resolve for each workflow. This is the primary pre-dispatch validation path and should discover driver capabilities before those calls.

Workspace driver context exposure lives in src/scherzo/workspace_driver_context.gleam. It builds environment variables SCHERZO_WORKSPACE_PROFILE, SCHERZO_WORKSPACE_DRIVER, and SCHERZO_WORKSPACE_CAPABILITIES, plus prompt locals workspace.profile, workspace.driver, and workspace.capabilities. These values should keep existing names, but the capabilities should come from discovery.

Driver lifecycle invocation lives in src/scherzo/workspace_driver_lifecycle.gleam. It resolves the driver command, invokes lifecycle operations, and currently includes SCHERZO_WORKSPACE_CAPABILITIES in the lifecycle environment. This environment should also receive discovered capabilities.

Fingerprints live in src/scherzo/workflow_fingerprint.gleam. They include workflow workspace_capabilities and selected workspace_driver metadata, including capability names. After this change, that selected driver capability list should still be present, but it should be the discovered canonical list.

The checked-in drivers are shell wrappers around Python scripts: scripts/scherzo-workspace-jj and scripts/scherzo-workspace-noop. docs/runbooks/workspace-driver-contract.md documents their current lifecycle and capability command forms. Both scripts need to add describe --json, and the runbook needs to define that command.

Milestones

Milestone 1 adds and tests the driver metadata command without changing Scherzo config loading. At the end, both checked-in driver scripts accept describe --json, print valid version 1 JSON, require no workspace path, and have contract tests proving their capability sets.

Milestone 2 changes the config schema and migration guidance. At the end, driver.capabilities is no longer accepted in YAML, old configs fail with a runbook link, dogfood and example configs no longer contain the field, and docs tell operators to rely on describe --json.

Milestone 3 adds runtime discovery and enrichment. At the end, runtime bundle loading invokes describe --json for configured drivers, stores the canonical discovered capability set on the resolved profile data, and validates workflow workspace_capabilities against that discovered list before dispatch.

Milestone 4 threads discovered capabilities through existing runtime surfaces. At the end, SCHERZO_WORKSPACE_CAPABILITIES, workspace.capabilities, lifecycle environment, command-step context, agent prompt locals, and execution fingerprints all use the discovered canonical capability set. Reordering driver output does not change fingerprints.

Milestone 5 completes documentation, full validation, and rollout notes. At the end, all tests and lint gates pass, every checked-in reference to configured driver.capabilities has either been removed or explicitly describes the old breaking-change error, and this plan's living sections record the implementation outcome.

Testing and Falsifiability

The core claim is falsified if Scherzo can load a workflow requiring a capability that the selected driver's describe --json does not report, or if it rejects a workflow whose selected driver reports the required capability. The runtime bundle tests must cover both outcomes using fake driver scripts, not YAML capability lists.

Driver contract tests must execute scripts/scherzo-workspace-noop describe --json and scripts/scherzo-workspace-jj describe --json with no SCHERZO_WORKSPACE_PATH. The no-op driver test asserts exactly status, changed-files, and assert-only. The jj driver test asserts exactly status, diff, changed-files, assert-only, baseline, refresh-base, and publish-change. These tests fail before implementation because the command is unsupported.

Config parser tests in test/orchestrator_config_test.gleam must prove that YAML driver profiles without capabilities parse, and YAML driver profiles with capabilities fail with the removed-key runbook message. The negative test should not merely assert any parse failure; it must assert the message names workspace.profiles.noop.driver.capabilities, describe --json, and the runbook path.

Discovery tests in test/workspace_driver_discovery_test.gleam must cover valid output, noncanonical order canonicalization, empty capabilities, malformed JSON, missing version, unsupported version, missing capabilities field, non-list capabilities, non-string entries, unknown capability names, duplicate names, nonzero exit, and timeout. A valid noncanonical output such as {"version":1,"capabilities":["assert-only","changed-files"]} should enrich the internal list to changed-files followed by assert-only, because the fixed canonical order places changed-files before assert-only.

Runtime bundle tests in test/runtime_bundle_test.gleam must load a workflow YAML with workspace_capabilities: [assert-only] and an orchestrator config whose selected driver omits YAML capabilities. With a fake driver returning assert-only, bundle load must succeed. With a fake driver returning only status, bundle load must fail with workspace_capabilities_unavailable and a message naming the workflow id, selected profile, and missing capability. With a fake driver returning malformed JSON, bundle load must fail with workspace_driver_discovery_failed before dispatch.

Environment and prompt tests in test/workflow_run_test.gleam and test/workspace_driver_context_test.gleam must prove that SCHERZO_WORKSPACE_CAPABILITIES and workspace.capabilities use discovered values. At least one test must start with an internal driver list empty, enrich it from a fake describe command, run or render a step, and assert the exposed values contain the discovered capabilities.

Fingerprint tests in test/workflow_fingerprint_test.gleam must prove three cases: workflow-level workspace_capabilities still affect the workflow fingerprint; selected driver discovered capabilities affect the execution fingerprint; and reordering the driver's describe response does not change the execution fingerprint.

Documentation tests or source guardrail tests should be updated if they check examples or runbook content. The public example config and dogfood config should no longer contain profile-local driver.capabilities. Historical files under docs/plans/ may mention the old field as historical context and should not be edited solely for this change.

Validation and Acceptance

A reviewer can open .scherzo/scherzo.yaml and see workspace.profiles.dogfood-jj.driver.command, driver.lifecycle, and driver.timeout_ms, but no driver.capabilities. A reviewer can open examples/scherzo.yaml and see the same removal for the public example profile.

A reviewer can run:

scripts/scherzo-workspace-jj describe --json scripts/scherzo-workspace-noop describe --json

Each command prints one JSON object with version: 1 and the expected capability list, without needing a workflow workspace.

A reviewer can create or inspect a test fixture where a workflow requires workspace_capabilities: [assert-only] and the selected fake driver reports assert-only; direnv exec . gleam test should show that bundle loading succeeds. Changing the fake driver output to omit assert-only should make the targeted runtime bundle test fail with workspace_capabilities_unavailable.

A reviewer can add the old YAML key back to a config fixture:

workspace: profiles: noop: driver: command: scripts/scherzo-workspace-noop capabilities: [assert-only]

The parser must reject it with a message that says the key was removed, tells the operator to implement or verify describe --json, and points to the checked-in runbook.

The full acceptance gate is:

direnv exec . gleam test direnv exec . gleam format --check src test direnv exec . gleam run -m glinter direnv exec . gleam run -m scherzo_lint

All commands must pass. glinter warnings that are already in the repository warning inventory may remain, but there must be zero errors and no new production safety violations.

Rollout, Recovery, and Idempotence

This is a breaking config change. Rollout is safe because configs that still use driver.capabilities fail early during config load with a runbook link; they do not dispatch a workflow with ambiguous metadata. The recovery path for an operator is to remove the driver.capabilities key, update or replace the driver so it supports describe --json, then rerun workflow-config validation or the test suite.

If discovery itself fails after config parsing, Scherzo should fail runtime bundle loading or workflow-config checks before claiming or dispatching new issues. The error should be actionable enough to tell the operator which profile and command failed. For a checked-in driver regression, rollback is to revert the implementation commit or restore the previous release and its config shape together. Because this plan intentionally removes backwards compatibility, do not mix a new config without driver.capabilities with an older Scherzo binary that still requires the field.

The implementation is mostly idempotent. Running describe --json repeatedly should produce the same output and no side effects. Runtime bundle loading may invoke describe multiple times across process starts; drivers must tolerate that. The docs and config edits are normal source changes and can be reapplied by version control if a branch is rebased.

If implementation stops halfway after drivers gain describe --json but before config parsing removes driver.capabilities, the system remains compatible with old configs. If implementation stops after config parsing rejects driver.capabilities but before runtime discovery lands, workflows requiring capabilities will likely fail validation because drivers provide an empty internal list; do not merge that intermediate state. The commit map keeps that parser change and discovery change adjacent, and tests should prevent a half-migrated merge.

Do not include absolute local paths in new diagnostics or docs. Interfaces and Dependencies

The driver metadata command interface is:

<driver> describe --json

It requires no positional arguments other than describe --json. It should use exit code 0 for a valid metadata response, exit code 1 for a valid request that failed internally, and exit code 2 for unsupported command usage. The response schema for version 1 is:

{ "version": 1, "capabilities": ["status", "changed-files", "assert-only"] }

The discovery module interface should be:

pub fn enrich_orchestrator(orchestrator: config_types.OrchestratorConfig) -> Result(config_types.OrchestratorConfig, DiscoveryError) pub fn enrich_profile(profile: config_types.WorkspaceHookProfile, orchestrator: config_types.OrchestratorConfig) -> Result(config_types.WorkspaceHookProfile, DiscoveryError) pub fn error_code(error: DiscoveryError) -> String pub fn error_message(error: DiscoveryError) -> String

The config parser interface remains config.read through existing public functions, but read_workspace_driver no longer accepts the capabilities YAML key. Internal WorkspaceDriverConfig.capabilities remains a List(WorkspaceCapability) populated after discovery unless the implementer chooses a small type rename for clarity.

Runtime bundle loading should call discovery before profile validation and return a bundle whose orchestrator contains discovered driver capability lists. workspace_profile.resolve, workspace_driver_context.from_profile_for_orchestrator, workspace_driver_lifecycle.lifecycle_env, and workflow_fingerprint.for_execution should consume that enriched data rather than spawning driver processes.

No new external package dependency is required. Use existing Gleam modules, scherzo/port.gleam for argv process execution, existing JSON decoding utilities already used in the repository, and existing capability conversion functions in src/scherzo/config/types.gleam.
