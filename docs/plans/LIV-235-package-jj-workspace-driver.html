Package the jj workspace driver for reusable Scherzo installs

Plan artifact: docs/plans/LIV-235-package-jj-workspace-driver.html 22 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

External Scherzo operators should be able to install Scherzo, put command: scherzo-workspace-jj in their workspace profile, and run workflows in jj-backed repositories without copying this repository's local driver scripts. After this work, a packaged deployment can discover the jj driver with scherzo-workspace-jj describe --json, create root and derived jj workspaces through Scherzo lifecycle calls, use workflow-facing capabilities such as changed-files, assert-only, refresh-base, and publish-change, and configure common non-dogfood base policies with environment variables.

The visible outcome is an installed scherzo-workspace-jj executable in the Scherzo package bin/ directory. Source-tree development remains possible through scripts/scherzo-workspace-jj, while packaged examples and docs use the stable command name. The package and tests prove that the installed command can be discovered by Scherzo, can create, inspect, and remove a local jj workspace offline through lifecycle calls, that the base selection policy is configurable for local/offline, trunk, and alternate-remote repositories, and that the driver still conforms to docs/specs/WORKSPACE_DRIVER_SPEC.md. Publication validation does not claim that tests create a real GitHub pull request; it proves that the packaged command carries the gh dependency and that source-tree or runtime authentication and network failures are surfaced through the versioned JSON failure shape.

Problem Framing and Constraints

Today the reusable jj candidate is scripts/scherzo-workspace-jj. It implements the workspace-driver command contract, but reusable deployments still have to know about a repository-local script path such as ../scripts/scherzo-workspace-jj or copy the script into their own repository. Its root-workspace base defaults are also dogfood-shaped: when no explicit base is set, it fetches ${SCHERZO_PR_BASE:-main} from ${SCHERZO_PR_REMOTE:-origin} before creating a root workspace. That default is useful for Scherzo's PR-oriented dogfood workflow, but it is surprising for local-only installs, repositories whose trunk branch is named trunk, repositories whose main remote is upstream, and operators who do not want a workspace create operation to contact the network.

This plan does not build a generic standalone jj workspace manager. It packages and documents a generic Scherzo workspace driver for jj-backed repositories. The workspace driver command remains the trusted extension boundary: an operator configures one executable, Scherzo calls that executable with argv-style lifecycle and capability commands, and workflow YAML cannot inject arbitrary shell to run after workspace creation. The bundled driver may remain opinionated, but its opinions must be explicit, tested, and escapable through wrapper executables, forks, or custom drivers rather than through workflow-authored post-create command strings.

A prerequisite is that LIV-234 has made scripts/scherzo-workspace-jj self-contained by folding in the legacy scripts/scherzo-jj-workspace lifecycle helper. If an implementer starts this plan on a branch where scripts/scherzo-workspace-jj still shells out to scripts/scherzo-jj-workspace, stop and complete or rebase over the LIV-234 work first. The target baseline is the self-contained driver; the deprecated helper wrapper is not the package surface.

Strategy Overview

Keep the current Python-in-shell driver shape for this packaging step. The existing scripts/scherzo-workspace-jj file is a single executable shell script that runs embedded Python, already implements the v1 command vocabulary, and is already covered by driver tests. Extracting it into a normal source module or rewriting it in Gleam or standalone Python would add migration risk without solving the operator problem. The proportionate change is to install the same trusted driver as a stable package command, wrap it with the runtime tools it needs, and add focused policy and conformance tests around the driver behavior that external users will rely on.

Add a small, explicit base-policy layer inside the driver. SCHERZO_JJ_WORKSPACE_BASE remains the strongest override for new root workspaces and skips fetch. Add jj-specific aliases SCHERZO_JJ_WORKSPACE_REMOTE and SCHERZO_JJ_WORKSPACE_BASE_BRANCH, while keeping SCHERZO_PR_REMOTE and SCHERZO_PR_BASE as compatibility names. Add SCHERZO_JJ_WORKSPACE_FETCH_BASE=true|false, defaulting to true, so local/offline installs can prevent driver-initiated fetches without forking the driver. The base resolver feeds lifecycle root-workspace creation and the default refresh-base target only. Publication must use a separate publication-remote helper: SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE, then legacy SCHERZO_PR_REMOTE, then origin. It must not implicitly reuse SCHERZO_JJ_WORKSPACE_REMOTE, so a repository can fetch bases from upstream/trunk while publishing feature branches to origin. SCHERZO_PR_REPO remains the explicit hosted-review repository override.

Keep one full jj driver and keep advertising publish-change. Package the GitHub CLI as part of the Nix/release wrapper so the advertised publication capability is honest for packaged installs. In source-tree or non-Nix usage, a missing gh must fail only when publish-change reaches the publication path, and it must fail with the existing versioned JSON failure shape rather than making describe --json dynamic or side-effectful. Documentation should say jj and python3 are required for normal jj driver use, gh and GitHub credentials are required only for publish-change, and direnv matters only for repositories that contain .envrc and accept the bundled driver's current environment-preparation opinion.

Alternatives Considered

The simplest alternative is to document copying scripts/scherzo-workspace-jj into every external repository. That does not solve distribution: users would keep stale copies, examples would remain source-tree-specific, and package-installed Scherzo could not offer command: scherzo-workspace-jj as a stable profile command.

A larger alternative is to extract the embedded Python into a normal source module or rewrite the driver in Gleam. That could be worthwhile if the driver grows a broad library API, but it is not necessary for packaging. The current file already has a stable executable contract, and the package can install and wrap it directly. Rewriting while also changing base policy and publication packaging would combine unrelated risks.

Another alternative is to split publication into a second driver or make describe --json advertise publish-change only when gh is found. That would make discovery depend on the operator's current PATH, credentials, or package variant, which conflicts with the spec requirement that describe --json be side-effect-free and stable. Keeping one driver with a packaged gh dependency and command-time JSON failures is simpler and keeps workflows compatible.

A final alternative is to add generic "run these commands after create" support inside the packaged driver. This is intentionally rejected. It would recreate hook-based workspace configuration inside the driver and make the model hooks all the way down. Operators whose jj workspace setup differs from the bundled driver's opinions should configure a wrapper executable, maintain a forked driver, or write their own driver that implements docs/specs/WORKSPACE_DRIVER_SPEC.md. Workflow YAML must not gain a way to inject post-create shell commands.

Risks and Countermeasures

The most likely functional risk is a base-precedence regression. If the new aliases are layered incorrectly, dogfood profiles using SCHERZO_PR_REMOTE and SCHERZO_PR_BASE could change behavior, or external profiles using SCHERZO_JJ_WORKSPACE_REMOTE could silently fall back to origin/main. Counter this with fake-jj tests that assert the exact fetch and workspace add --revision argv for explicit base, jj-specific aliases, legacy aliases, defaults, and offline mode.

A related compatibility risk is the intentional change that explicit base or remote configuration disables silent fallback to main@origin, main, or @ when the configured candidates do not resolve. This is safer for reusable installs because a stale SCHERZO_PR_REMOTE, SCHERZO_PR_BASE, SCHERZO_JJ_WORKSPACE_REMOTE, or SCHERZO_JJ_WORKSPACE_BASE_BRANCH should fail loudly rather than create a workspace from the wrong base. Counter this with a test that sets a stale explicit legacy base, proves no fallback workspace add occurs, and checks that the bounded diagnostic names the configured remote and branch plus the corrective environment variables.

Another functional risk is conflating base-selection remotes with publication remotes. Many repositories fetch trunk from upstream and publish feature branches to origin or a fork. Counter this by adding SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE as the publication-specific override, by making publish-change ignore SCHERZO_JJ_WORKSPACE_REMOTE unless the operator also sets the publication override, and by adding tests and docs for the upstream base / origin publication setup.

A publication risk is making describe --json dishonest. If publication is advertised but the packaged command cannot reach gh, then workflows can require a capability that fails before doing useful work. Counter this by including gh in the package wrapper's runtime path, documenting that credentials and network access are still runtime prerequisites for publish-change, and keeping missing-gh failures scoped to the publish-change command for non-packaged source-tree usage. Acceptance must say this proves dependency availability and failure shape, not an end-to-end GitHub pull request.

A path-safety risk is leaking local absolute workspace paths in machine-readable output or driver-authored diagnostics while improving failure messages. Counter this by keeping JSON paths workspace-root-relative, truncating backend output as the current driver does, and adding tests that failed default fetch diagnostics mention the configuration knobs without echoing local workspace roots. When a backend tool prints an absolute path, bound the relayed excerpt and prefer a driver-authored summary.

A safety-model risk is expanding the driver into an unsafe command runner. Counter this by not adding any generic post-create command feature, by documenting the existing environment-preparation behavior as an opinion rather than an extension point, and by adding tests or docs assertions that no workflow YAML field can inject arbitrary post-create shell through this driver.

A release risk is that Nix install checks become flaky by requiring network or credentials. Counter this by limiting install checks to discovery, usage errors, and local jj lifecycle operations in temporary repositories. Publication behavior involving GitHub should be tested with fake commands or unit-level command failures, not by contacting GitHub.

Context and Orientation

Scherzo runs workflow steps in workspaces. A workspace driver is a trusted operator-configured executable that Scherzo invokes for workspace lifecycle operations and workflow-facing capabilities. Lifecycle operations are create, before-step, after-step, and remove. Capabilities are commands such as status --human, changed-files --json, assert-only --path <relative-file>, refresh-base --stage <stage> --json, and publish-change ... --json. The normative command forms, JSON schemas, exit codes, and safety invariants live in docs/specs/WORKSPACE_DRIVER_SPEC.md.

The current jj driver lives in scripts/scherzo-workspace-jj. It is a shell script that resolves its own path, exports SCHERZO_DRIVER_SCRIPT, and execs embedded Python through python3 -. Its describe --json returns version 1 and capabilities status, diff, changed-files, assert-only, baseline, refresh-base, and publish-change. Lifecycle create infers the source repository root, verifies it is a jj repository, creates root workspaces from a base revision with jj workspace add, creates derived workspaces from SCHERZO_SOURCE_WORKSPACE_PATH at source @, verifies the resulting workspace with jj root and jj status, and runs its current environment-preparation behavior after create. Lifecycle remove forgets jj workspaces under the run root when safe to do so.

The deprecated compatibility path scripts/scherzo-jj-workspace is not the package target. It exists for older hook snippets and maps historical verbs to scripts/scherzo-workspace-jj lifecycle <operation>.

Package assembly is in nix/scherzo.nix. The file builds the Gleam Erlang shipment, installs scherzo, scherzoctl, scherzo-start, and the no-op workspace driver, and runs install checks. flake.nix exposes the package and checks across supported systems. Package work for the jj driver should follow the no-op driver's pattern but use a jj-specific runtime path.

Public source-tree examples currently include examples/scherzo.yaml, where workspace.profiles.isolated.driver.command is ../scripts/scherzo-workspace-jj. A packaged no-op example exists at examples/scherzo-packaged-noop.yaml; this plan adds the jj counterpart rather than changing the source-tree example to a package-only command.

Driver tests live mainly in test/jj_workspace_driver_test.gleam for the jj script and test/workspace_driver_contract_test.gleam for the no-op contract shape. Documentation assertions live in test/workspace_driver_docs_test.gleam. Workflow driver discovery, context exposure, and lifecycle invocation are covered by test/workspace_driver_discovery_test.gleam, test/workspace_driver_context_test.gleam, and test/workflow_run_test.gleam.

Rollout, Recovery, and Idempotence

This change is additive. Existing source-tree configs that use $SCHERZO_REPO_ROOT/scripts/scherzo-workspace-jj, scripts/scherzo-workspace-jj, or ../scripts/scherzo-workspace-jj continue to work. New packaged configs can use scherzo-workspace-jj. The old scripts/scherzo-jj-workspace compatibility wrapper remains in place for legacy hook snippets and is not part of the packaged public surface.

The base-policy change is designed for compatibility, but it intentionally fails faster for stale explicit configuration. Existing SCHERZO_JJ_WORKSPACE_BASE behavior remains strongest and still skips fetch. Existing SCHERZO_PR_REMOTE and SCHERZO_PR_BASE continue to work as base-policy fallbacks when the new jj-specific base variables are absent. New jj-specific names take precedence only when set. SCHERZO_JJ_WORKSPACE_FETCH_BASE defaults to true, preserving the current dogfood network fetch unless an operator opts out. If any jj-specific or legacy base/remote variable is explicitly set and the configured candidates do not resolve, the driver must fail with guidance instead of silently falling back to another base; this prevents accidentally creating workspaces from the wrong branch.

Publication remote rollout is separate from base remote rollout. Existing publication users that set SCHERZO_PR_REMOTE continue to use it for publication when SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE is absent. New reusable installs that fetch bases from upstream and publish to origin should set SCHERZO_JJ_WORKSPACE_REMOTE=upstream and SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE=origin, or rely on the publication default origin when no legacy publication remote is set. This avoids a hidden change where base-remote configuration redirects publication.

Rollback is straightforward because there is no data migration. If packaged command installation causes release problems, revert the nix/scherzo.nix installation and install-check changes while leaving source-tree driver fixes if they are already safe. If base-policy or publication-remote changes cause workflow regressions, revert the scripts/scherzo-workspace-jj resolver changes and their tests, then restore the previous PR-shaped resolver and publication remote selection. Workspaces created before rollback are normal jj workspaces; they do not need conversion.

Repeated lifecycle create calls should remain idempotent for an already-created workspace: the driver verifies the existing workspace and returns success. Repeated package builds should be deterministic aside from normal Nix build output. Re-running docs and tests is safe. Failed local jj workspace creation may leave a partially created directory; the implementer should clean only test directories under test/tmp/, tmp/, or temporary install-check directories, not real workflow workspaces.

The installed public command is scherzo-workspace-jj. It must support these invocations exactly as a driver command:

scherzo-workspace-jj assert-only --path <relative-file>

The base-policy environment interface is:

  • SCHERZO_JJ_WORKSPACE_BASE: explicit revision for new root workspaces. It wins over every remote/base-branch setting and skips fetch. The driver must fail if it does not resolve.
  • SCHERZO_JJ_WORKSPACE_REMOTE: jj-specific base remote alias. It wins over SCHERZO_PR_REMOTE for lifecycle root-workspace base selection and default refresh-base. It must not affect publication.
  • SCHERZO_JJ_WORKSPACE_BASE_BRANCH: jj-specific base branch alias. It wins over SCHERZO_PR_BASE.
  • SCHERZO_PR_REMOTE: legacy compatibility remote name. It is used for base selection only when SCHERZO_JJ_WORKSPACE_REMOTE is absent, and it remains the legacy publication remote fallback when SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE is absent.
  • SCHERZO_PR_BASE: legacy compatibility base branch name. It is used only when SCHERZO_JJ_WORKSPACE_BASE_BRANCH is absent.
  • SCHERZO_JJ_WORKSPACE_FETCH_BASE: true or false; absent means true. false disables driver-initiated base fetches in lifecycle create and refresh-base. It does not disable publication.
  • SCHERZO_JJ_WORKSPACE_PUBLISH_REMOTE: jj-specific publication remote. It is used by publish-change for publication branch transfer and default hosted-review repository inference. It wins over SCHERZO_PR_REMOTE for publication only. It must not affect root-workspace base selection.
  • SCHERZO_PR_REPO: existing publication override for GitHub owner/repository inference. Keep this name for compatibility.

Package dependencies are python3 for the embedded Python driver, jujutsu for jj, gh for publish-change, direnv for repositories where the driver sees .envrc and runs its existing environment-preparation behavior, and coreutils for shell/runtime basics. In nix/scherzo.nix, these dependencies are added as function arguments and wired into jjDriverRuntimePath; source-tree users must provide equivalent commands on PATH unless they use the Nix package wrapper.
