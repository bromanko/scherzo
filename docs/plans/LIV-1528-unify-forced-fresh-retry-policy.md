# Unify safe-point and forced-fresh retry policy

This ExecPlan review is the concise human-facing companion to the structured implementation pack. Together they are the living plan; Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must remain current during implementation.

## Purpose / Big Picture

An operator recovering an idle, nonterminal task should be able to choose either the deepest provably safe retry or an intentional fresh run without first removing an automatic failure park. After this change, `retry`, `retry all`, `--from-scratch`, dispatch-time recovery, and exact expert retry commands evaluate the same typed guards and retained-run model. A forced-fresh retry of a `failed_after_recovery` run parked for `worker_failure` will durably queue one replacement, release the automatic park only at a safe execution boundary, record which run it supersedes, and report the operation and run identifiers.

The behavior is observable through `scripts/scherzoctl`: accepted responses and operation-status reads name the selected action, any released park, preserved or discarded evidence, the superseded run, and the replacement run. Rejections use the exact guard, such as `operator_hold`, `terminal_issue_state`, `dispatch_paused`, `dispatch_disabled`, or `active_duplicate_work`, rather than `start_fresh_not_allowed`.

## Problem Framing and Constraints

The current safe-point lattice in `src/scherzo/workflow_retry_planner.gleam` is not the whole retry policy. Its production caller supplies every guard as false, ordinary task retry and forced-fresh retry have separate transition branches, and `src/scherzo/orchestrator/operator_retry_policy.gleam` authorizes fresh retry by inspecting park-reason string prefixes before it inspects the retained run. Consequently, the automatic `worker_failure` park created for the LIV-1495 `failed_after_recovery` run masked the terminal failure that a fresh retry was intended to supersede.

Park meaning is also split between runtime `ParkReason`, `ParkReleasePolicy`, persisted free-text reasons, projection strings, retry-step exceptions, and startup reconstruction. The implementation must preserve explicit manual and safety holds, terminal tracker states, dispatch pause or disablement, and duplicate-work coordination. It must fail closed on unavailable ledger evidence, keep exact salvage commands, avoid silently reopening terminal tasks, and make accepted retries crash-safe across validation, capacity waits, tracker claims, ledger failures, and daemon restart.

A “park” is a durable local suppression of dispatch. Its existing release policy controls issue-change auto-release; the new operator-retry disposition separately states whether an explicit Retry action may release it. A “replacement intent” is a durable queued control operation that already names the planned replacement run, even when capacity or an external tracker claim delays execution.

## Strategy Overview

Extend the retry planner into the single pure decision source. It will accept a retry mode—best safe point, force fresh, or exact expert step—plus origin, typed guards, park disposition, retained-run state, and recovery evidence. It will return one of four semantic outcomes: a precise block, an existing operation or replacement for idempotency, a retained-run action such as resume/rewind/publication recovery, or a fresh action that either starts normally or supersedes the latest failed or interrupted run. Force-fresh mode never requires recovery proof; missing or corrupt evidence changes what is discarded, not whether fresh retry is authorized.

Introduce a typed park class and a durably persisted operator-retry disposition independent of issue-change release policy. Worker failure, attempt limit, session limit, drift, failed repair, and recovery-blocked classes are releasable by an explicit operator retry. Manual operator holds, abort/stop holds, infrastructure safety holds, abandoned claims, and unknown legacy parks require explicit unpark. Max-attempt and max-session release is deliberate: the Retry command is the operator’s acknowledgement to reset those automatic budgets. Ordinary dispatch does not release them.

Accepted operator retries become durable control operations. Admission records the selected plan and, for a fresh action, a replacement run id without yet clearing the park, resetting counters, or superseding the old run. Capacity exhaustion leaves that operation queued; pause or dispatch disablement rejects admission. Validation failure leaves old state untouched. Immediately before reservation and again before starting a worker, execution re-reads the authoritative projection and tracker state. Capacity exhaustion, pause, or disablement introduced after admission defers the accepted operation. Before reservation its park and counters remain unchanged; after reservation the already atomic replacement/repair intent remains durable, but no tracker claim or worker start proceeds until the gate clears. A new terminal tracker state, manual or safety hold, or unrelated active/pending work fails the operation with the exact guard. Before reservation that failure changes only operation status; after reservation it compensates counters and reinstates a recovery-blocked park unless a stronger manual/safety hold already exists. It never reopens a terminal task, clears a new hold, or disturbs conflicting work.

The execution boundary atomically records the replacement/repair intent with any unpark, reset, and supersession records; fresh claims use the durable outbox. If an append or claim fails, the operation remains retryable or fails with a compensating/re-parked state, never with only part of the policy applied. A terminally failed retry operation is not a permanent idempotency target. A later explicit Retry re-evaluates current guards and, when only its matching `RecoveryBlockedPark` remains, creates one durable successor operation linked by `predecessor_operation_id`. If the planned fresh replacement never reached `WorkflowRunStarted`, the successor reuses that reserved replacement run id and existing supersession provenance; if a replacement run did start and later failed, ordinary latest-run planning supersedes that run with a new replacement id. Repeats return the queued/running successor, and startup reconstructs the same lineage from projection.

New parks use a typed v3 record. Legacy v1/v2 records are classified once at replay by a closed compatibility parser for known historical reason codes; unknown values become explicit-unpark-required holds. Runtime entries are rebuilt from the resulting typed projection, so restart cannot change the decision. Existing issue-change auto-release remains separate.

## Alternatives Considered

Adding `worker_failure` to the current prefix allowlist is the smallest patch, but it leaves two decision trees, interrupted-run gaps, counter and supersession partial failures, and restart divergence. Making Retry release every park is also simple, but it would bypass manual aborts and safety holds. Requiring explicit unpark for every automatic failure is safe but contradicts the operator meaning of Retry and leaves the original recovery failure intact.

Always starting fresh would remove recovery ambiguity but discard verified work and undo the safe-point lattice. Adding workflow-specific confirmations or recipes was rejected because generic retry policy cannot reliably identify non-idempotent side effects from a workflow name. `retry all` and `--from-scratch` are the explicit acknowledgement for rerunning the whole workflow; the runbook must warn operators to inspect workflows with external side effects.

Rejecting when capacity is exhausted was rejected because capacity is temporary and an accepted durable intent is safer and more useful. Queuing while dispatch is already paused or disabled was rejected because those are explicit global operator guards; pause or disablement that begins after admission merely keeps the already accepted operation queued.

Requiring explicit unpark after every terminal retry-operation failure was rejected because it would make an automatic recovery blockage permanently defeat the force-fresh guarantee. Treating the failed operation as the forever-idempotent answer was rejected for the same reason. A linked successor that reuses an unstarted reserved replacement identity preserves both operator intent and duplicate safety without erasing failure history.

## Risks and Countermeasures

The largest correctness risk is superseding a run or clearing a park before a replacement is durable. The countermeasure is a queued operation that names its replacement and atomic ledger batches at execution boundaries; supersession is never appended in a separate pre-claim write. Ledger append and outbox failure tests must prove that no partial unpark, reset, or supersession survives.

A second risk is weakening holds during migration. New constructors must choose typed classes explicitly, legacy classification must be closed and fail unknown values to `explicit_unpark_required`, and matrix tests must cover manual hold, abort/stop, infrastructure failure, abandoned claim, automatic failures, drift, and recovery blockage before and after restart.

A third risk is duplicate work under repeated commands, delayed callbacks, or restart. Durable operation metadata and source/replacement links provide the idempotency key. A repeat returns the queued/running operation or durable replacement when it belongs to the same retry; unrelated active or pending work returns `active_duplicate_work`. Stale callbacks must be ignored by operation and run identity.

A fourth risk is turning a terminally failed operation into a permanent deduplication tombstone. Recovery-blocked compensation records the failed operation and reserved replacement identities. A later Retry may create exactly one linked successor after guard revalidation; tests before and after restart prove that repeated requests neither return only the failed predecessor nor allocate competing replacements.

A fifth risk is admitting work under one guard state and executing it under another. The runner revalidates before reservation and worker start. Later pause/disablement defers; later terminal state, manual/safety hold, or unrelated work fails and preserves the stronger state. Barrier-driven tests cover each transition on both sides of reservation and across restart.

A sixth risk is broad orchestration churn. The work is staged: establish typed parks and the pure matrix first, add durable retry operations second, migrate each caller third, then remove the old forced-fresh policy. Exact retry-step, output recollection, finalization, and publication commands remain available and keep fail-closed evidence validation.

## Scope Boundaries

In scope are retry modes and guards; typed durable park classification; legacy park replay; common, fresh, dispatch-time, and exact-step planner integration; durable retry operation metadata and failed-operation successor lineage; capacity, pause, and disablement deferral; execution-time terminal/hold/conflict revalidation; atomic park/counter/supersession/claim handling; startup resumption; a decoder-retaining v3 rollback floor; command and operation-status result contracts; CLI rendering; recovery runbook updates; and deterministic unit, daemon, restart, protocol, and failure-injection tests.

The existing issue-change park release policy remains, but no longer determines operator-retry authorization. Tracker terminal states are never reopened or cloned. Reopen/clone operations, workflow-specific retry recipes, semantic merging, a database redesign, cross-daemon coordination, and a Scherzo UI redesign are out of scope. Browser and provider-live/cache behavior do not change; only optional backend/CLI contract fields needed to display retry outcomes are added.

## Milestones

Milestone 1 makes park policy explicit and durable. At its end every new park has a typed class and operator-retry disposition, v3 records and snapshots round-trip, known legacy records classify deterministically, unknown legacy records fail closed, and startup rebuilds the same runtime decision as projection.

Milestone 2 makes the pure planner authoritative. It introduces explicit retry modes and origin, removes hard-coded false guards, models no run, failed run, interrupted run, already-superseded run, and publication/repair evidence, and proves the required property-style matrix. Force fresh selects supersession for failed and interrupted runs and a normal fresh start when no retained run exists.

Milestone 3 adds crash-safe retry operations. Admission durably records plan and replacement identity while retaining old park/counters; capacity and later pause/disablement can defer execution. Reservation and worker start revalidate terminal state, new holds, and conflicts. Repair or fresh reservation uses atomic ledger/outbox boundaries, failures remain retryable or restore a blocking park, and startup resumes queued work. A Retry after terminal operation failure creates one linked successor, reusing an unstarted reserved replacement identity; repeated requests return the live successor or replacement rather than getting trapped on its failed predecessor.

Milestone 4 migrates all entry points and removes the independent policy. Ordinary Retry uses best-safe-point mode, `retry all` and `--from-scratch` use force-fresh mode, dispatch recovery uses the same planner with dispatch origin, and exact expert retry-step uses exact mode. The old prefix authorization and `start_fresh_not_allowed` result disappear.

Milestone 5 completes operator contracts, documentation, and validation. Command and operation-status output expose action, park release, safe point, source/superseded/replacement ids, and exact blocks; the recovery runbook documents limit release, capacity queuing, side-effect acknowledgement, and manual holds; deterministic unit and contract suites plus formatting and both lint gates pass.

## Surprises & Discoveries

The safe-point planner already names `operator_hold`, `terminal_issue_state`, `dispatch_paused`, and `active_duplicate_work`, but `src/scherzo/workflow_repair.gleam` passes all four as false. The apparent unified guard model is therefore not an admission boundary in production.

Forced-fresh policy checks runtime/projection park strings before retained terminal failure, recognizes only drift/recovery prefixes, and treats an interrupted latest run as a normal dispatch rather than a superseded run. Its policy helper also reloads the ledger internally, so one command may not use one projection observation.

The repository already has durable queued control operations and a durable claim outbox, which are the right primitives for crash-safe retry admission. Current fresh supersession is nevertheless appended before claim intent in a separate write, while ordinary retry clears runtime state and emits unpark/reset writes with `ContinueRegardless` before accepted side effects finish.

Adversarial review found three lifecycle boundaries that the first draft left implicit: a failed operation could remain the deduplication winner forever, post-admission guards other than pause had no defined result, and emitting v3 records makes a pre-v3 binary an invalid rollback target. These are specification gaps rather than confirmed current-code behaviors; the revised strategy, acceptance, and rollout sections close them.

## Validation and Acceptance

The defining regression starts with a retained `failed_after_recovery` run and a durable automatic `worker_failure` park. `retry all` must return a queued/applied result naming the released park, superseded run, replacement run, and operation; projection must contain exactly one supersession and one durable replacement intent; the replacement must start when claim/capacity permits. Repeating before start, while active, after restart, and after supersession must return the existing operation or run without duplicate records.

A terminal failure after durable admission must not trap later Retry on the failed operation. When no replacement run started, compensation parks with the failed operation and reserved replacement identities; the next explicit Retry creates exactly one successor operation, links its predecessor, reuses that replacement id, and eventually starts it once. Repeat the successor request before and after daemon restart and assert one successor, one effective supersession, one replacement run, and stable operation metadata. When the replacement run did start and then failed, assert that a later force-fresh operation treats it as the retained source and allocates one new replacement.

A table/property-style suite must cover worker failure, max-attempt, max-session, drift, recovery-blocked and failed-repair parks, manual and safety holds, terminal tracker state, dispatch pause/disablement, capacity exhaustion, active and pending work, failed and interrupted runs, no retained run, already-superseded runs, ledger read/append failure, validation failure, tracker claim/outbox failure, stale callbacks, and daemon restart. Each case asserts mode, action, released park, source and replacement ids, predecessor operation where applicable, preserved/discarded evidence, operation status, exact block reason, and record counts. Runtime and projection decisions must be equal before and after restart.

Use deterministic barriers to change each guard after admission both before and after reservation. Before reservation, capacity, pause, and disablement leave the operation queued and old park/counters unchanged; after reservation they preserve the committed intent and defer tracker claim or worker start until the gate clears. A terminal tracker transition fails the operation without reopening the task; a new manual/safety hold fails it without clearing or replacing that hold; unrelated active/pending work fails it without starting or mutating the conflicting work. Post-reservation failures restore counters and add a recovery-blocked park only when no stronger hold exists. Restart at every deferred or failed state and assert the same outcome with no extra records or worker.

Publish-blocking validation is the deterministic unit suite, deterministic contract suite, `direnv exec . gleam format --check src test`, `direnv exec . gleam run -m glinter`, `direnv exec . gleam run -m scherzo_lint`, and review-document validation; all must exit zero with no new warning inventory. No browser or provider-live/cache validation is required. A real Linear dogfood retry is deferred to a human/operator after implementation because it mutates live tracker state; automated in-process tracker and daemon contract tests are required before publish.

## Rollout, Recovery, and Idempotence

Roll out in additive stages: first land and validate the additive v3 decoder, projection fold, snapshot reader, and legacy classifier while writers can still emit v2; this decoder-capable revision is the rollback floor. Next switch new park writes and compaction snapshots to v3, then add planner/operation metadata, migrate entry points, and delete the old forced-fresh policy. Legacy v1/v2 records remain readable and compaction snapshots their typed classification.

After the first v3 ledger record or snapshot is emitted, a pre-v3 binary cannot decode the state and is not a supported rollback target. There is no down-migration: rollback may revert writers, planner, or callers only on a build that retains the v3 record and snapshot decoders and projection fold. Decoder-only fixture, compaction, and daemon-restart tests must pass before enabling v3 writes and again on the release candidate. If an emergency requires a pre-v3 binary, the operator must stop the daemon and restore an independently captured complete pre-v3 state backup, knowingly discarding all later local activity; this destructive disaster-recovery option is not the normal rollback. Scherzo is pre-release, but ordinary rollout deliberately avoids requiring a local state reset.

If retry behavior is suspect, pause dispatch. Queued retry operations remain durable and must not execute while paused or disabled. Reverting caller migration above the decoder floor leaves retained runs, parks, control operations, and outbox intents inspectable; do not delete the ledger. A failed pre-reservation operation leaves the original park, counters, and run unchanged. A terminal post-reservation failure appends a typed recovery-blocked park and a failed operation result in one batch unless a newer manual/safety hold must remain authoritative. Terminal tracker state and unrelated work are never modified by compensation.

Admission and execution are idempotent by issue, mode, source run, operation, and replacement run identities. Repeated requests return matching queued/running operations or durable replacement runs; unrelated active work blocks. A failed operation remains immutable history but is excluded as the terminal deduplication winner after an explicit Retry: one linked successor is admitted, and concurrent repeats find that successor. An unstarted replacement id is reused across the predecessor/successor lineage; a started failed replacement becomes the next retained source. Duplicate appends use stable record ids, stale callbacks cannot advance another operation, and restart replays queued intent once. Supersession and claim intent are committed together or not at all.
