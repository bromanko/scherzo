# LIV-910: Migrate ExecPlan publication to workspace-driver commit stacks

This ExecPlan v2 review document is the human review surface for LIV-910. It plans the migration of ExecPlan publication to the same-repository, workspace-driver-backed commit-stack path while keeping the final plan document as retained Scherzo provenance.

## Purpose / Big Picture

After this change, an ExecPlan authoring or revision run publishes the actual repository change made in its workflow workspace: the final reviewed Markdown plan checked in under `docs/plans/` or another prepared target. Operators see a normal PR created by the selected workspace driver, and Scherzo still retains the final plan document as a separate file artifact for internal review and provenance.

The review feedback is part of the purpose of this revision: acceptance evidence, exact test obligations, milestone-specific proof, manual and dogfood timing, docs/helper migration boundaries, provider-live/cache non-scope, full validation, and production linting must be visible both here and in the structured implementation-pack submission that Scherzo materializes for follow-up implementation.

## Problem Framing and Constraints

The current ExecPlan publication route treats the plan as retained file bytes and copies it into a managed GitHub checkout under `.scherzo-state/artifact-repositories/github/<hash>`. That is the wrong same-repository boundary because the workflow workspace driver already owns the checkout, remotes, credentials, signing environment, branch policy, and publish operation. The migration must preserve the `exec_plan_bundle` and plan file artifact contract, must use workspace-driver publication for the checked-in repository change, must not create or fall back to the managed artifact-repository checkout, and must keep failed required publication recoverable from the retained workflow workspace.

The implementation must also respect Scherzo's review-doc workflow constraints. The human-reviewable document remains this single file, while mechanical commands and file-level implementation instructions live in the structured implementation pack. If the implementation changes workflow helper scripts, workflow schemas, provider-facing structured-output helpers, or operator runbooks, it must include focused helper/schema/docs validation evidence. It must not change provider-live probes, provider cache behavior, browser UI, or live GitHub credential handling unless this review document and the pack are revised again before code changes.

## Strategy Overview

Use the existing artifact-publication split between retained file artifacts and same-repo `commit_stack` publication. The reviewed plan remains a contracted `plan` file output and an `exec_plan_bundle` entry, while a new contracted `commit_stack` output describes the checked-in workspace change. The ExecPlan publication route switches from `files` mode to `commit_stack` mode, and runtime publication invokes `publish-commit-stack` when available or the current `publish-change` compatibility operation otherwise. This is proportionate because it reuses the workspace-driver-backed publication executor and only extends the missing initial-PR/stable-branch commit-stack path needed by ExecPlan authoring.

The implementation should keep helper migration narrow. `workflows/dogfood/scripts/scherzo-execplan` should materialize the reviewed document into the prepared repository target and emit a deterministic `scherzo.git_commit_stack.v1` manifest for the selected workspace change; it should not publish the review doc itself or create a hidden managed clone. The workflow YAML should then expose that manifest as a `commit_stack` output and let artifact publication own the driver call. Initial authoring uses a stable-branch target that creates a PR. Revision uses `target.kind: existing_pr_branch` when previous PR metadata is present; if previous PR metadata is missing, it creates a superseding stable branch rather than guessing a stale branch.

## Alternatives Considered

Keeping the managed GitHub artifact checkout was rejected because it violates same-repo publication ownership and can use different remotes, credentials, signing, or branch semantics from the workflow workspace. Calling the old ExecPlan `publish-review-doc` helper directly was rejected because it bypasses the workflow artifact-publication evidence model and does not expose a first-class `commit_stack` output. Reconstructing the repository change from retained file bytes or a hidden bundle import was rejected for this same-repo migration because it would make retained artifacts, not the workflow workspace, authoritative.

Making live GitHub or browser verification a mandatory pre-publish requirement was rejected because deterministic fake-driver and local dogfood evidence can prove the routing, retained artifacts, failure retention, and no-managed-clone behavior without credentials. A human/operator live GitHub or browser check remains a post-implementation rollout check unless the implementation deliberately changes live provider behavior, credential handling, provider-live checks, cache behavior, or browser surfaces.

## Risks and Countermeasures

The main risk is publishing a workspace state that does not exactly match the retained `commit_stack`; the countermeasure is to capture base and head metadata before publication, verify driver output head metadata against the selected stack, and fail closed on mismatch. Another risk is losing the internal plan artifact while switching publication modes; the countermeasure is to keep the `plan` file output and bundle entry unchanged and test both outputs. A third risk is breaking revision or retry behavior; the countermeasure is to cover initial stable-branch PR creation, existing-branch revision/update semantics, unchanged retries, required-failure retention, and explicit abandonment or retry diagnostics.

A fourth risk is review/pack drift: this document could require evidence that the structured implementation pack does not ask the follow-up implementer to collect. Counter this by mirroring the review feedback obligations in the pack's concrete steps and testing notes before Scherzo materializes downstream artifacts. A fifth risk is accidental scope expansion into provider-live, cache, browser, or unrelated helper behavior. Counter this with a changed-file inventory and a stop rule: if provider-live probes, provider cache files, browser UI, or unrelated workflow helpers must change, update this review document and the pack first or split that work.

## Scope Boundaries

In scope are the ExecPlan authoring and revision workflow contracts in `workflows/dogfood/execplan.yaml` and `workflows/dogfood/execplan-revision.yaml`; the `workflows/dogfood/scripts/scherzo-execplan` helper logic that materializes the reviewed plan into the prepared target and emits commit-stack evidence; workflow schema/config/parser support for stable-branch `commit_stack` publication; artifact-publication planner/executor/driver evidence needed for same-repo commit stacks; publication recording and retry/abandonment diagnostics; operator documentation for artifact publication and workspace-driver publication; and tests.

The docs/helper migration boundary is explicit. Updating `docs/runbooks/artifact-publication.md`, workspace-driver publication docs, workflow YAML, workflow schemas, and the ExecPlan helper is in scope only where needed for this migration. Unrelated helper rewrites, provider-facing structured-output schema changes beyond the existing implementation-pack submission contract, review-lane helper changes, provider-live behavior, provider cache behavior, browser UI, and changes to `workflows/dogfood/execplan-implementation.yaml` are out of scope unless this review document and the implementation pack are revised again. Generalized external/cross-repo publication, replacing the bundled jj driver's existing `publish-change` command, and inventing a new managed clone fallback are also out of scope.

## Rollout, Recovery, and Idempotence

Roll out by changing the checked-in ExecPlan workflow routes, helper behavior, targeted docs, and tests together, then dogfood one fake-driver or local ExecPlan authoring run before broader use. The rollout is additive from the operator perspective: retained plan artifacts continue to exist, while the repository-visible PR is published from the retained workflow workspace through the selected driver. Operators should verify the fake/local transcript before enabling live same-repo ExecPlan publication on normal work.

If required commit-stack publication fails, Scherzo must mark the workflow as failed, retain the workflow workspace, record the publication failure and recovery reason, and allow an operator to retry publication from the retained workspace or explicitly abandon it. Retrying an unchanged commit stack must record `unchanged` rather than creating duplicate remote state. Re-running helper materialization should overwrite ignored `tmp/` outputs but must not create extra checked-in files or mutate `.scherzo-state/artifact-repositories/github/<hash>`.

Recovery for a bad workflow/helper migration is to revert the workflow YAML, helper, schema, docs, source, and tests from this plan as one logical change; retained plan-file artifacts remain readable because their contract is preserved. Recovery for accidental provider-live, provider-cache, browser, or unrelated helper edits is to revert those edits and revise this review document plus the structured pack before attempting them again. No provider cache invalidation, browser state cleanup, or external managed-clone cleanup is part of the intended rollout because those surfaces are not changed.
