Replace native review lane JSON finals with terminating Pi tool submissions

Plan artifact: docs/plans/LIV-204-pi-tool-enforced-review-lane-drafts.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

After this change, Scherzo's native review lanes will submit their draft review artifacts by calling a Pi-enforced structured-output tool instead of printing free-form final assistant JSON. The operator-visible gain is earlier, clearer failure detection: a lane that omits required review-draft structure, mutates a forbidden field, or prints prose instead of submitting the draft will fail at the lane boundary with retained diagnostics and one bounded retry, not later after downstream evidence verification and normalization have already spent time on the run.

The desired working behavior is easy to observe. In a native review run, each specialist lane calls a single Pi tool named submit_review_lane_draft; Scherzo captures the tool arguments, validates them with the same deterministic review-lane rules used by scripts/scherzo-review, persists the accepted payload under the existing retained structured-artifact location, and then lets scripts/scherzo-review verify-evidence and scripts/scherzo-review normalize-lane-result consume that artifact unchanged. A lane that merely prints JSON in its final assistant response is treated as missing the required tool submission.

Problem Framing and Constraints

The current native review lane contract asks the model to return JSON only in the final assistant response. Scherzo currently validates that final response with a shallow top-level JSON schema gate. That catches malformed JSON and missing top-level keys, but it can accept a payload that later fails the richer review-lane domain validation in scripts/scherzo-review. For example, a payload can contain the top-level draft_findings key while using malformed finding objects, duplicate finding ids, evidence requests that do not link to findings, unsafe paths, or remote_mutations values other than none. The operator problem is that these failures can surface only after the expensive native lane attempt has completed and downstream commands start processing retained artifacts.

This plan is constrained by the pre-cutover status of native review. No external production users depend on the current native review structured-output contract. The right rollout is therefore a direct replacement in the pre-cutover native review path, validated in branch and PR before merge. The plan intentionally avoids a long-lived compatibility path, canary mode, or productized dual runtime where both final-response JSON and Pi tool-call submission remain supported indefinitely. Rollback is reverting the implementation branch or PR before the broader LIV-115 native-review cutover.

The plan also keeps Scherzo's deterministic validators as the durable source of truth. Pi TypeBox validation is used to make the model's tool-call interface explicit and provider-independent, but it is not the final authority for domain invariants. Scherzo must still validate accepted tool arguments with the repository's review-lane rules before marking a native lane submission valid.

Strategy Overview

Use a repo-local Pi project extension named submit_review_lane_draft for native review lane agent steps. The permanent extension entrypoint is .pi/extensions/scherzo-review-lane-draft/index.ts, because Pi auto-discovers project-local extensions at .pi/extensions/*.ts and .pi/extensions/*/index.ts. Do not use .pi/extensions/scherzo-review-lane-draft/extension.ts as the permanent entrypoint unless src/scherzo/pi/command.gleam explicitly passes that path with Pi's --extension flag and the Decision Log records why auto-discovery was not used.

The tool definition exposes a TypeBox argument schema for the review_lane_draft object. For string constants such as artifact_type and remote_mutations, use StringEnum from @mariozechner/pi-ai, not Type.Union or Type.Literal, so provider conversion stays compatible with Google-style enum requirements. The tool's execute function returns terminate: true; termination is a result property, and Pi only skips the automatic follow-up model turn when every finalized tool result in that same batch is terminating. Scherzo therefore accepts a native lane submission only when the final relevant tool-call batch contains exactly one successful submit_review_lane_draft call and no sibling tool calls.

Scherzo then reads the tool-call arguments from Pi session records, extracts the real object-valued arguments from raw JSON rather than display strings, and validates the exact canonical JSON before persistence. The deterministic validation interface is scripts/scherzo-review validate-lane-draft --lane <lane-id> --draft-json -, which reads the captured draft from stdin. src/scherzo/workflow_run.gleam must not write a retained structured artifact, even to an attempt-scoped temporary path, until that stdin validator exits successfully. Only after deterministic validation succeeds may Scherzo call workflow_checkpoint.write_structured_output_artifact with the existing artifact name and json format.

The first implementation milestone is still a spike, but the spike is now concrete. Add a temporary tool-contract workflow at .scherzo/workflows/review-native-tool-contract-spike.yml and run it through the same local Scherzo workflow runner command used by native lanes: direnv exec . gleam run -- workflow run .scherzo/workflows/review-native-tool-contract-spike.yml --run-root tmp/liv-204-review-tool-spike --run-id liv-204-review-tool-spike --native-review-scenario contract-spike. That command must prove extension loading, TypeBox rejection, object-argument capture, termination behavior, and final-text-only rejection before the native review prompts or workflow are replaced.

Provider differences stay contained at the Pi boundary. Workflow prompts tell lanes to call the tool; Scherzo parses Pi session records for tool calls; downstream review scripts consume the same retained draft JSON path they consume today. No downstream script should need to know which language model provider produced the tool call.

Alternatives Considered

The simplest plausible alternative is to make src/scherzo/structured_output.gleam validate the final assistant JSON more deeply while keeping the current prompt instruction to print JSON only. That would catch more bad drafts, but it would not solve the brittle contract where a model can mix prose, Markdown, or multiple JSON blobs into a final response. It would also keep Scherzo dependent on provider-specific final-message formatting rather than a Pi-enforced structured interaction.

A second alternative is a dual path where native review accepts either the new Pi tool call or the old final-response JSON for an extended period. That is not proportionate here because native review is still pre-cutover and has no external production users. A dual path would increase test matrix size and preserve the exact stale behavior this issue is meant to remove.

A third alternative is to trust TypeBox validation entirely and remove downstream domain validation. That is rejected because Pi tool schemas are an interface convenience, not Scherzo's durable business rule authority. Review-lane invariants such as linked evidence request ids, safe repository-relative paths, no remote mutations, and lane-specific semantics must remain enforced by deterministic repository code.

Risks and Countermeasures

The main feasibility risk is that Scherzo-managed Pi sessions may not load the project-local extension in the same way an interactive pi -e experiment does. The countermeasure is the first milestone: create the temporary project extension and run .scherzo/workflows/review-native-tool-contract-spike.yml through direnv exec . gleam run -- workflow run ..., not only through direct Pi. If that runner does not auto-discover .pi/extensions/scherzo-review-lane-draft/index.ts from the repository root, update src/scherzo/pi/command.gleam to pass --extension .pi/extensions/scherzo-review-lane-draft/index.ts, add a launcher test, and record that explicit mechanism in the Decision Log before changing native review.

A second risk is schema drift between the TypeBox tool arguments, docs/schemas/review-artifacts.v1.schema.json, and scripts/scherzo-review domain validation. The countermeasure is to make the schema module and validator fixtures part of the implementation. Tests must compare the TypeBox-derived JSON schema against the documented ReviewLaneDraft required keys and constants, must prove string constants are represented with provider-compatible StringEnum, and must run the same valid and invalid fixtures through the Python validator and the Scherzo lane-acceptance path.

A third risk is accidentally validating the wrong data before persistence. The captured Pi tool arguments are in memory, while retained structured artifacts are files. The countermeasure is the required stdin validation interface: src/scherzo/review_lane_draft_validator.gleam passes the exact canonical captured JSON to scripts/scherzo-review validate-lane-draft --lane <lane-id> --draft-json -, captures stdout and stderr, redacts secrets only for retained diagnostics, and returns review_lane_draft_domain_invalid if the subprocess exits non-zero. No retained draft file is written until that helper returns success.

A fourth risk is that Scherzo may capture the wrong Pi record. src/scherzo/pi/protocol.gleam already decodes tool names, tool input, tool output, tool status, and preserves each record's raw JSON, but current structured input decoding can replace non-string inputs with a display placeholder. The implementation must parse raw record JSON for the actual tool arguments or otherwise configure Pi to emit raw JSON records. Tests must include object-valued arguments to prove Scherzo persists the real submitted draft, not a placeholder.

A fifth risk is accidentally treating a final assistant JSON message as valid during the replacement. The countermeasure is a negative integration test: when a native review lane emits a perfect review_lane_draft JSON object as final assistant text but does not call submit_review_lane_draft, Scherzo must classify the attempt as review_lane_draft_tool_missing, retain diagnostics, and trigger only the bounded retry path.

A sixth risk is remote mutation during smoke validation. The concrete local no-remote gate is direnv exec . ./scripts/scherzo-review native-preflight --output-dir tmp/liv-204-native-preflight, followed by validation of tmp/liv-204-native-preflight/preflight-manifest.v1.json. The concrete curated legacy PR gate is direnv exec . ./scripts/scherzo-review legacy-pr-smoke --output-dir tmp/liv-204-legacy-pr-smoke --overwrite, whose curated default PR set is reported by legacy-pr-smoke --list-curated. Both manifests must report remote_mutations: "none", and the implementation must not post comments, push commits, update Linear, or use fixture or heuristic lane backends in those smoke gates.

Context and Orientation

Scherzo is a workflow runner that can execute command steps and agent steps. A native review workflow is a staged code-review workflow where multiple specialist agent lanes inspect a prepared diff, produce lane-specific draft findings, verify evidence, normalize lane results, synthesize the final review, and retain artifacts for operator inspection.

The current native review workflow is .scherzo/workflows/review-native.yml. It has a prepare_review command step, a clean-tree check, four parallel agent lane steps, another clean-tree check, evidence verification commands, normalization commands, and later synthesis and publishing steps. The four lane steps are lane_correctness, lane_test_quality, lane_idioms_maintainability, and lane_security_performance. Each lane currently has a structured_output block with format: json, an artifact name such as correctness_draft, and a list of required top-level keys.

The lane prompts live in .scherzo/workflows/prompts/review-native-correctness.md, .scherzo/workflows/prompts/review-native-test-quality.md, .scherzo/workflows/prompts/review-native-idioms-maintainability.md, and .scherzo/workflows/prompts/review-native-security-performance.md. They currently tell the model to return JSON only and to emit a review_lane_draft artifact. Those instructions must change to tell the model to call submit_review_lane_draft exactly once with the draft object as tool arguments and not to print final JSON.

The current final-response capture path starts in src/scherzo/result_artifact.gleam. It builds a ResultArtifact from completed assistant messages, using the last non-empty assistant message as both display text and untruncated structured response. src/scherzo/workflow_run.gleam receives an agent success, calls structured_output.validate_final_response, and writes a structured artifact if validation succeeds. The validator lives in src/scherzo/structured_output.gleam; it parses JSON, checks top-level object shape, verifies configured required keys, redacts secrets, and returns the payload string. It does not understand review-lane domain invariants.

The retained artifact writer is split across src/scherzo/workflow_checkpoint.gleam and src/scherzo/state/artifact_store.gleam. The checkpoint writer exposes write_structured_output_artifact, and the artifact store writes a wrapper containing run id, workflow id, step id, attempt index, artifact name, format, schema required keys, and parsed payload. The implementation should reuse this writer for accepted tool arguments so downstream artifact paths stay stable.

The bounded retry path is in src/scherzo/workflow_structured_retry.gleam and src/scherzo/workflow_run.gleam. src/scherzo/workflow_dag.gleam defaults structured_output.validation_retries to one and only permits zero or one. The retry prompt currently tells the model to return JSON only. For native review tool submission, the retry prompt must instead tell the model that the previous attempt failed the tool-submission contract and that the only valid completion is a submit_review_lane_draft tool call.

The deterministic review contract is in scripts/scherzo-review and docs/schemas/review-artifacts.v1.schema.json. The Python function validate_review_lane_draft checks schema_version, artifact_type, remote_mutations, producer and lane objects, repository-relative artifact references, unique draft finding ids, linked evidence request ids, safe locations, review notes, evidence request target paths, and the presence of self_check. verify_evidence_command loads and validates a lane draft before producing an evidence ledger. normalize_lane_result_command safely loads and validates the draft and emits a failed lane result if the draft is missing or invalid.

The Pi integration code currently inspected for this plan is under src/scherzo/pi/. src/scherzo/pi/command.gleam builds the Pi launch command, and src/scherzo/pi/protocol.gleam decodes JSON-RPC records from Pi. The protocol decoder already has fields for tool name, tool input, tool output, and tool status, which makes it the natural boundary for capturing submit_review_lane_draft calls once the spike confirms the exact record shape.

Scope Boundaries

In scopereplacing native review lane draft submission with a terminating Pi tool call; loading that tool for Scherzo-managed native review agent sessions; capturing the tool arguments from Pi records; validating captured arguments with TypeBox first and deterministic review-lane validation before persistence; persisting accepted payloads under the existing structured artifact layout; updating native review prompts and retry prompts; updating tests and native review smoke validation; and removing the stale final-response JSON contract from .scherzo/workflows/review-native.yml.

Also in scope: keeping scripts/scherzo-review verify-evidence and scripts/scherzo-review normalize-lane-result as downstream consumers of retained draft artifacts, while making them no longer be the first place a malformed review-lane draft is discovered.

Out of scopeimplementing the broader LIV-115 native review cutover; publishing remote review comments during smoke validation; designing long-lived compatibility with final-response JSON for native review; supporting both old and new native review submission paths indefinitely; or changing non-review workflows that still intentionally use generic final-response structured output.

The generic src/scherzo/structured_output.gleam module may remain if other workflows or tests still use it. The required removal is from the native review path: native review lane prompts and .scherzo/workflows/review-native.yml must no longer instruct or configure final assistant JSON as the accepted submission mechanism.

Milestones

Milestone 1 proves Pi tool feasibility before any broad replacement. At the end of this milestone, .scherzo/workflows/review-native-tool-contract-spike.yml and a temporary project-local extension demonstrate that a Scherzo-managed Pi session loads .pi/extensions/*/index.ts or the explicitly configured equivalent, that provider conversion accepts StringEnum constants, that a successful terminating call emits capturable object arguments, that invalid arguments produce deterministic diagnostics, that a final JSON message without the tool is detected as absence, and that a same-batch extra tool call is classified as invalid for native review submission.

Milestone 2 establishes the canonical review-lane draft contract. At the end of this milestone, the repository has a TypeBox schema module for submit_review_lane_draft, a deterministic validation entry point scripts/scherzo-review validate-lane-draft --lane <lane-id> --draft-json - for Scherzo to call before persistence, and fixtures that prove valid and invalid lane drafts receive the same accept or reject result across the TypeBox shape checks and the repository's Python domain validation.

Milestone 3 adds Scherzo's tool-submission capture path while preserving retained artifact layout. At the end of this milestone, workflow_dag can represent a native review tool submission requirement, the Pi launcher loads the review tool for those agent steps, tool_submission.gleam extracts exactly one accepted tool call from raw Pi records, review_lane_draft_validator.gleam validates captured JSON on stdin, and the accepted payload is written through the existing structured-artifact writer with metadata identifying the Pi tool source.

Milestone 4 updates prompts, retry semantics, and failure classification. At the end of this milestone, native lane prompts and retry prompts instruct the model to call the tool, invalid tool arguments and domain invariant failures have clear failure codes, missing tool calls trigger the same bounded retry budget as current structured-output failures, mixed tool-call batches are rejected, and cancellation or transient Pi failures retain actionable diagnostics.

Milestone 5 removes the stale review-native final-response JSON contract and validates downstream parity. At the end of this milestone, .scherzo/workflows/review-native.yml no longer uses final-response structured_output for native lanes, downstream verify-evidence and normalize-lane-result still consume the retained draft paths, and tests prove that final assistant JSON is rejected for native lanes even if the JSON object itself is otherwise valid.

Milestone 6 performs named smoke validation and prepares rollback evidence. At the end of this milestone, unit tests, integration tests, scripts/scherzo-review native-preflight --output-dir tmp/liv-204-native-preflight, and scripts/scherzo-review legacy-pr-smoke --output-dir tmp/liv-204-legacy-pr-smoke --overwrite all pass with remote_mutations: "none" and tool-submitted native lane drafts. The implementation branch can then be reviewed for merge before LIV-115. If the smoke fails, rollback is to revert the implementation branch or PR rather than enabling a dual runtime.

Rollout, Recovery, and Idempotence

Rollout is a direct replacement in the pre-cutover native review path. The implementation should be developed and validated in a branch or PR before merge. There is no canary mode and no long-lived dual runtime. Once the tool path is proven by tests and smoke validation, native review should require the tool call.

Rollback before LIV-115 is to revert the implementation branch or PR. Because native review has no external production users yet, rollback does not require data migration or compatibility shims. If validation fails before merge, do not merge the branch. If validation fails after merge but before LIV-115, revert the merge commit and restore the previous review-native workflow files.

The retained artifact layout should remain idempotent for retries. Each attempt writes under its own attempt directory. Re-running a failed native review smoke in a fresh run root should not depend on old artifacts. The tool handler itself should not perform remote mutations or write durable review artifacts; Scherzo's checkpoint writer owns persistence after deterministic validation.

No smoke validation should post comments, push commits, update Linear, or otherwise mutate remote services. The local native-preflight smoke uses local fixtures only. The curated legacy-pr-smoke gate may read historical GitHub PR metadata and diffs, but it must remain read-only and must retain remote_mutations: "none" in every manifest and final review artifact. The lane prompts, TypeBox schema, deterministic validators, and smoke acceptance all require remote_mutations: "none".

Interfaces and Dependencies

The Pi tool interface to expose is submit_review_lane_draft. It accepts the review_lane_draft object as its arguments, not a string containing JSON. Its TypeBox schema must require schema_version, artifact_type, generated_at_utc, producer, lane, input_refs, draft_findings, review_notes, evidence_requests, self_check, and remote_mutations. It must constrain artifact_type to review_lane_draft and remote_mutations to none with StringEnum. It must return terminate: true from execute on successful submissions.
