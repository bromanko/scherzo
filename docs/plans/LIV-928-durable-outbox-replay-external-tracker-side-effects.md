# LIV-928 durable outbox and replay for external tracker side effects

This is a focused ExecPlan review for LIV-928. It is documentation-only; the mechanical implementation details are supplied through the structured implementation pack for the follow-up implementation task.

## Purpose / Big Picture

Scherzo should be able to restart after a crash or forced shutdown and know which external tracker/report side effects still need attention. After implementation, external claim, park/report, worker success/failure, and invalid-workflow reporting should be driven from durable ledger-backed outbox records, replayed at least once, reconciled when they may already have applied externally, and surfaced when they need operator action instead of disappearing into logs.

## Problem Framing and Constraints

Today several externally visible operations are executed by `src/scherzo/orchestrator/effect_runner.gleam` after transitions enqueue effects from `src/scherzo/orchestrator/daemon.gleam`. `ClaimIssue` currently performs the Linear handoff before the workflow-start ledger batch is appended, and success/failure, park, and invalid-workflow reports can be killed after the daemon has decided to send them but before a durable replayable record exists. Startup recovery in `src/scherzo/state/recovery.gleam` already sees legacy outbox records, but `src/scherzo/state/outbox.gleam` treats all current replay kinds as unsupported and `src/scherzo/orchestrator/transition.gleam` ignores `_outbox_to_replay` on startup.

The plan must target at-least-once execution. Linear, the network, and BEAM processes cannot provide exactly-once behavior, so the implementation must make duplicate attempts safe with idempotency keys, external reconciliation, and bounded retry/failure states. Retry timer durability remains LIV-925; this plan may record an outbox retry state and compute whether a retry is due, but it must not depend on durable timer machinery to be correct. The targeted claim orphan mitigation in LIV-924 can land first; this plan should either preserve it or replace it with the broader outbox invariant once implemented.

## Strategy Overview

Use the existing ledger as the durable source of truth and the projection as the queryable outbox queue. Add an outbox lifecycle around `OutboxPendingV2WithTask` rather than introducing a second store: pending intent, attempted/in-flight, retryable failure, succeeded, and permanent failure/operator action required. Normal runtime code should append pending intent before starting the external operation. Startup recovery should treat pending, in-flight, and due retryable records as replayable, because an in-flight record at shutdown is only evidence that the daemon tried, not proof that Linear did or did not apply the operation.

Each outbox payload should include a stable kind, task reference, run or violation identity, redacted human summary, and an idempotency key that is also embedded into any created tracker comment. Linear comment/state replay should first reconcile by finding a comment with the marker or by observing the target state, then update or no-op if already applied, and only create/transition when reconciliation says it is still missing. Claim success must append the workflow-start ledger batch before or with `OutboxCompleted` so every durable prefix recovers either a pending/replayable claim or an active workflow run.

## Alternatives Considered

A separate SQLite or file queue was rejected because Scherzo already has append-only ledger replay, projection snapshots, schema guardrails, and startup recovery around `src/scherzo/state/record.gleam` and `src/scherzo/state/projection.gleam`; a second store would create a new consistency problem. Logging failed side effects and asking operators to inspect Linear was rejected because it still loses in-flight work on crash and does not satisfy at-least-once replay. Retrying direct effect-runner messages without durable intent was rejected because queued and in-flight BEAM messages die with the daemon. Exactly-once semantics were rejected as unrealistic across Linear/network/process crashes. Splitting the whole feature into unrelated long-running migrations was rejected for the core invariant, but nonessential migrations should be follow-up work.

## Risks and Countermeasures

The main risk is duplicate tracker comments. The countermeasure is a required idempotency marker in every Scherzo-owned comment body and a Linear adapter helper that finds or updates an existing marked comment before creating a new one. Another risk is considering a claim completed without a recoverable workflow run. The countermeasure is to order claim completion records so `WorkflowRunStartedWithTask`, `KnownWorkspace`, and counter updates are durable before `OutboxCompleted`, and to make startup recovery treat an active run as stronger evidence than a stale claim outbox.

Permanent failures can loop silently if every restart retries forever. The countermeasure is a bounded retry policy with `OutboxPermanentlyFailed`, warning logs, and control-query metrics for pending, retryable, in-flight, and permanent outbox counts. Reconciliation can be wrong if provider capabilities are too weak; the countermeasure is to add explicit Linear comment lookup/listing capability before enabling replay for comment-producing families. Graceful shutdown can still time out; the countermeasure is bounded drain for in-flight outbox effects and reliance on replay for forced shutdown.

## Scope Boundaries

Immediate implementation covers durable outbox intent, lifecycle projection, startup replay, reconciliation, graceful effect-runner drain, and tests for `ClaimIssue`, worker success/failure reports, park reports from `ReportPark` and `ReportParkEffect`, invalid workflow comments/state transitions, and the current `ReleaseClaim` behavior. `ReleaseClaim` is in scope as a side-effect family, but in the current tree it is local-only logging in `src/scherzo/orchestrator/daemon.gleam`; the immediate work should document and test that it creates no external outbox until a tracker release capability or configured release mutation exists.

Operator documentation is in scope only if the implementation adds or renames control-query metrics, log event names, or documented runbook behavior for outbox failures; in that case the implementer should update the relevant checked-in docs such as `docs/runbooks/artifact-publication.md` or another operator runbook in the same implementation. Migrating ExecPlan workflow helpers, artifact-publication helper scripts, or review-helper docs is not part of this durable-outbox ticket. The implementation must not touch `.scherzo/workflows/scripts/scherzo-execplan*`, `.scherzo/workflows/scripts/scherzo-review*`, provider-live state, or remote-provider cache behavior unless it explicitly broadens the ticket and adds matching acceptance evidence.

Deferred follow-up migrations include scheduled failure publication unification, remote command acknowledgement replay beyond existing failure/dedupe behavior, richer `scherzoctl` drill-down UI beyond metrics, historical ledger backfill for old non-outbox side effects, and any new provider-live/cache conformance packs. Worker spawn semantics, local cleanup side effects, session/event publishing, and durable retry timers remain outside this plan except where the outbox must avoid breaking their current behavior. The core durable-outbox implementation should be one implementation ticket with clear milestones; deferred migrations should be separate follow-up tickets so the base invariant can land without waiting for every side-effect family in the repository.

## Milestones

Milestone 1 establishes the durable storage model and proves it in isolation before any side-effect routing changes. At the end, `src/scherzo/state/record.gleam`, `src/scherzo/state/record/outbox.gleam`, `src/scherzo/state/projection.gleam`, `src/scherzo/state/projection/outbox.gleam`, `src/scherzo/state/outbox.gleam`, schema fixtures, `test/state_record_test.gleam`, `test/state_projection_test.gleam`, and `test/state_outbox_test.gleam` represent pending, in-flight/attempted, due retryable failed, succeeded, and permanently failed/operator-action-required outbox records. The projection tests must show chronological replay selection, completed/permanent records suppressing replay, legacy pending records remaining decodable, and retryable records replaying only when their recorded next-attempt time is due.

Milestone 2 routes normal runtime side effects through durable intent and proves that every covered family has an outbox record before external execution. At the end, claim, worker success/failure, park, and invalid-workflow transitions append outbox pending records before `src/scherzo/orchestrator/daemon.gleam` enqueues the external operation. Completion handlers append success, retryable failure, or permanent failure records instead of only logging. Claim completion must make `WorkflowRunStartedWithTask`, `KnownWorkspace`, counter updates, and `OutboxCompleted` durable in an order where every persisted prefix recovers either a replayable claim or an active workflow run. `ReleaseClaim` must have an explicit test proving that the current local-only log path does not emit an external outbox record.

At the end, `src/scherzo/tracker/adapter.gleam`, `src/scherzo/tracker/linear_adapter.gleam`, `src/scherzo/linear.gleam`, `src/scherzo/handoff_format.gleam`, and the invalid-workflow formatter in `src/scherzo/workflow_policy.gleam` can embed and find idempotency markers, avoid duplicate comments, no-op already-applied state transitions, and preserve deterministic success-result attachment behavior. `test/tracker_linear_adapter_test.gleam`, `test/linear_test.gleam`, and handoff-format or workflow-policy tests must cover create, update/no-op, state-already-applied, missing capability, and malformed-provider-response cases without requiring live Linear access.

Milestone 5 makes failures operator-visible and completes validation. At the end, query metrics and logs expose outbox pending, in-flight, retryable, and permanent-failure counts; `test/control_query_metrics_test.gleam` or the nearest query-service test verifies those counts; any changed operator-facing names are documented. ## Rollout, Recovery, and Idempotence

Roll out as an additive ledger/projection change with backward-compatible decoding for existing `OutboxPending`, `OutboxPendingV2`, `OutboxCompleted`, and `OutboxFailed` records. On rollback, revert the schema/projection, effect routing, startup replay, reconciliation, and metrics changes together; a partial rollback could leave durable intents that no code replays. Startup recovery must be idempotent: seeing the same pending or in-flight outbox record twice may cause another attempt, but reconciliation must make that attempt safe, and `OutboxCompleted` or `OutboxPermanentlyFailed` must suppress future execution.

Graceful shutdown should stop accepting new direct side-effect work, wait briefly for in-flight outbox effects to finish and record completion, and then stop. Forced shutdown may kill an effect at any point, but because the intent was durable before execution, the next startup can reconcile and replay it. Idempotency keys should be stable per side-effect family: `claim:<backend>:<task_remote_id>:<run_id>`, `report_success:<backend>:<task_remote_id>:<run_id>:<workflow_id>`, `report_failure:<backend>:<task_remote_id>:<run_id>:<workflow_id>`, `park:<backend>:<task_remote_id>:<source_run_or_park_fingerprint>`, `invalid_workflow:<backend>:<task_remote_id>:<violation_fingerprint>:<policy_fingerprint>`, and a reserved `release_claim:<backend>:<task_remote_id>:<run_or_reason>` for any future external release operation.

No rollout step should migrate ExecPlan helper scripts, review helper scripts, provider-live state, or remote-provider caches. If the implementation accidentally requires one of those surfaces, stop and split that work into a separately reviewed follow-up; do not publish a durable-outbox change whose acceptance depends on unreviewed helper/provider migrations. Re-running startup recovery, query metrics, and reconciliation after a failed deploy must be safe because replay is driven from durable records and external writes are guarded by the same stable idempotency markers.
