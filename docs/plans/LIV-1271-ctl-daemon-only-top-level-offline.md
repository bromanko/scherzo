# Make `scherzo ctl` daemon-only and move offline commands to top level

This ExecPlan review document is intentionally concise. Mechanical implementation detail is supplied in the structured implementation pack for LIV-1271, and review feedback is incorporated in both artifacts so the follow-up implementation can be driven from either the human-readable intent or the structured pack.

## Purpose / Big Picture

Operators currently use `scherzo ctl` for both live daemon control and local disk inspection, which blurs whether a command talks to a running process or edits retained state directly. After this change, `scherzo ctl` is the live-daemon control plane, while offline retained-state commands are top-level `scherzo` commands. The visible outcome is that `scherzo ctl ping`, `scherzo ctl ps`, and other daemon RPCs remain under `ctl`, while `scherzo cleanup`, `scherzo schedules status`, `scherzo artifact publication list`, `scherzo workstream list`, and `scherzo state status` work as top-level disk-backed commands.

## Problem Framing and Constraints

The current CLI shape makes destructive or state-mutating local commands look like daemon operations, and makes daemon verbs such as `ctl schedules run --now` look like offline schedule inspection. The repository is Gleam-based and already has parser, renderer, handler, wrapper, packaging, documentation, and dogfood-workflow coverage around these commands, so the plan should preserve existing behavior while changing the public command tree. The task explicitly allows breaking compatibility because Scherzo is the only user, but asks for one-release deprecated aliases for old `ctl` spellings with clear retirement hints. Review feedback adds a non-negotiable evidence constraint: acceptance evidence, test obligations, milestone proof points, docs/helper migration, manual or dogfood timing, full validation, and lint gates must be mirrored in the structured implementation pack. This work must not change provider-live behavior, remote-provider cache behavior, browser UI behavior, tracker semantics, workspace-driver semantics, cleanup policy, schedule projection semantics, workstream storage semantics, or artifact publication planning semantics.

## Strategy Overview

The right-sized approach is to split CLI routing and command registries at the boundary users see: `src/scherzo/main.gleam` recognizes top-level offline nouns, `src/scherzo/ctl/command_registry.gleam` exposes separate canonical daemon commands, canonical offline commands, and hidden deprecated `ctl` aliases, and old `ctl` offline paths call the same offline handlers with a warning instead of being advertised in happy-path help. The implementation should reuse the existing offline handler modules rather than rewrite cleanup, schedules, artifact publication, workstream, or state logic. `ctl schedules run <job> --now` becomes `ctl run-schedule <job> --now`, making `schedules` an offline inspection noun; top-level `scherzo schedules run` must remain invalid so schedule execution is still clearly daemon control.

## Alternatives Considered

One alternative is to leave every command under `ctl` and only update help text. That does not solve the operator confusion because the command path would still imply daemon control. Another alternative is a full package-level refactor that moves every `src/scherzo/ctl/*` offline module into a new directory. That may be cleaner eventually, but it is larger than needed for the user-visible CLI split and would increase regression risk. The chosen plan changes the public routing first, then leaves internal module renames as optional future cleanup.

## Risks and Countermeasures

The main risk is silently changing command behavior while tests still cover only parser internals. The countermeasure is parser, routing, usage, wrapper, packaging, and handler tests that exercise both new top-level commands and deprecated aliases with observable outputs. A second risk is that `artifact publication retry` races a live daemon because it mutates retained state directly. The countermeasure is to require `--root`, hold the existing instance lock for the retry, refuse when the lock is already held, and prove no CLI path sends a daemon `RetryArtifactPublication` command. A third risk is stale docs and helper workflows continuing to teach `scherzoctl` for offline operations; the implementation must update checked-in runbooks, dogfood workflow commands, helper wording, package install checks, and affected tests. A fourth risk is letting review feedback live only in this prose document while the structured pack omits acceptance evidence, docs/helper boundaries, provider-live/cache non-scope, manual/dogfood timing, full validation, or lint gates. The countermeasure is to mirror those obligations in the implementation pack before Scherzo materializes follow-up artifacts. A fifth risk is making live dogfood a hidden pre-publish blocker when no safe daemon or retained run exists; the countermeasure is to require local/fake-root CLI evidence before publish and defer only real-daemon operator dogfood as a human follow-up check.

## Scope Boundaries

In scope: keep these daemon RPCs under `ctl`: `ping`, `ps`, `query status`, `query metrics`, `query operation-status`, `task list`, `task show`, `outbox`, `session`, `events`, `attach`, `pause`, `resume`, `reload`, `retry`, `retry-step`, `recollect-outputs`, `recovery cleanup-orphan-steps`, `park`, `unpark`, `abort`, `stop-after-turn`, `prompt`, `ui respond`, and `run-schedule`. Move these offline commands to top-level siblings: `cleanup`, `schedules status/history/logs/doctor`, `artifact publication list/show/retry/abandon`, `workstream ...`, and `state ...`. Keep deprecated `ctl` aliases for the moved offline commands and for `ctl schedules run` with retirement hints, but hide them from the main `ctl` help so they do not continue teaching the old command shape. Required docs/helper migration surfaces include `src/scherzo/main.gleam`, `src/scherzo/ctl/usage.gleam`, `src/scherzo/ctl/command_registry.gleam`, `scripts/scherzoctl`, `nix/scherzo.nix`, `README.md`, `docs/GETTING_STARTED.md`, `docs/runbooks/artifact-store.md`, `docs/runbooks/scheduled-jobs.md`, `docs/runbooks/workflow-recovery.md`, `workflows/dogfood/workspace-cleanup.yaml`, and `scripts/scherzo-workspace-cleanup` wherever they currently describe offline commands through `scherzoctl`. Out of scope: changing cleanup policy, schedule projection semantics, workstream storage, artifact publication planning, provider-live behavior, remote-provider cache behavior, browser UI behavior, tracker semantics, workspace-driver semantics, or the `workflow run` command beyond ensuring `workflow` and `workstream` are both top-level siblings.

## Milestones

Milestone 1 establishes the new command taxonomy in `src/scherzo/main.gleam`, `src/scherzo/ctl.gleam`, and `src/scherzo/ctl/command_registry.gleam`. At the end, top-level parsing routes offline nouns to an offline CLI path, `main.launcher_route` treats `cleanup`, `schedules status`, `artifact publication list`, `workstream list`, and `state status` as direct commands, `ctl run-schedule <job> --now` is the canonical daemon schedule trigger, and top-level `schedules run` is rejected. The proof is targeted coverage in `test/main_test.gleam`, `test/ctl_test.gleam`, and `test/ctl_command_spec_test.gleam` before broader docs work.

Milestone 2 preserves old operator muscle memory safely without advertising it. At the end, old `ctl cleanup`, `ctl schedules status`, `ctl artifact publication list`, `ctl workstream list`, `ctl state status`, and `ctl schedules run` still execute through the same handlers but emit deprecation hints that name the replacement command and the one-release retirement window. The proof is stderr or renderer-level tests for the hint text, plus help-output tests showing canonical `ctl` help lists daemon commands and canonical top-level help lists offline commands.

Milestone 3 removes the daemon retry path for artifact publication and adds the live-daemon safety guard. At the end, `artifact publication retry` is top-level offline-only, requires `--root`, acquires and releases `src/scherzo/instance_lock.gleam` around retained-state mutation, refuses while the lock is held, and no CLI path sends `RetryArtifactPublication` to the daemon. The proof is negative parser/handler/protocol tests for missing `--root`, lock contention, JSON and text failures, and the absence of raw daemon retry requests.

Milestone 4 updates tests, docs, helpers, packaging checks, and dogfood command examples. At the end, repository tests, lint gates, runbooks, checked-in workflows, `scripts/scherzo-workspace-cleanup` wording, and `nix/scherzo.nix` install checks prove the new command shape and no longer teach offline operations as daemon control. Pre-publish manual evidence is limited to local or fake-root CLI transcripts that require no live daemon; live operator dogfood against a real daemon or retained run is explicitly deferred unless a safe target is available during implementation.

## Surprises & Discoveries

The current `artifact publication retry` path already has two execution modes: with `--root` it performs local retry logic, and without `--root` it sends a daemon operator command. Evidence: `src/scherzo/ctl.gleam` dispatches `ArtifactPublicationRetry` to a daemon `RetryArtifactPublication` command when `explicit_root` is absent and to `ctl_artifact_publication_retry.retry` when `--root` is present.

The docs/helper migration surface is broader than the parser. Evidence from repository search shows offline `scherzoctl` examples in `workflows/dogfood/workspace-cleanup.yaml`, `scripts/scherzo-workspace-cleanup`, `docs/GETTING_STARTED.md`, `docs/runbooks/artifact-store.md`, `docs/runbooks/scheduled-jobs.md`, and `docs/runbooks/workflow-recovery.md`; the implementation pack must keep those updates coupled to the CLI change.

## Rollout, Recovery, and Idempotence

This is a CLI-only restructuring with no stored-data migration, no provider-live/cache rollout, and no browser UI rollout. Rollout is a single code release: new top-level commands become canonical immediately, while deprecated `ctl` aliases remain for one release and print retirement hints. Recovery is straightforward: if a regression is found, revert the CLI routing, command-registry, help, and documentation/helper changes; retained state remains compatible because underlying handlers and ledgers are not being redesigned. Re-running offline read commands is idempotent. Re-running mutating commands keeps their existing safety checks, and `artifact publication retry` adds the instance-lock guard so repeated attempts either acquire the lock and run through existing retry idempotency or refuse safely while a daemon owns the workspace. If a deprecated alias warning is too disruptive, recovery may hide or soften the warning without reintroducing the alias in primary help, but the canonical top-level commands should remain the forward path.
