# LIV-891 typed lifecycle refactor review

This review defines a behavior-preserving plan for a follow-up implementation task. It is intentionally concise; detailed implementation steps, tests, interfaces, and dependencies are carried in the structured implementation pack for this issue.

## Purpose / Big Picture

Scherzo's daemon should make task lifecycle states explicit enough that invalid transitions are hard to write and easy to test. After the follow-up implementation, a maintainer should be able to inspect one typed lifecycle model for tracker-backed tasks and see when a task is idle, validating, claiming, starting, running, waiting for retry, parked, stopping, or completed, instead of reconstructing that state from several dictionaries. Operators should observe unchanged dispatch, retry, park, recovery, ledger, and worker behavior; the visible proof is stronger transition tests and unchanged daemon/read-model outcomes.

## Problem Framing and Constraints

The current lifecycle is implicit across `src/scherzo/runtime/state.gleam`, `src/scherzo/orchestrator/transition_types.gleam`, `src/scherzo/orchestrator/transition.gleam`, `src/scherzo/orchestrator/transitions/claims.gleam`, `src/scherzo/orchestrator/retry_scheduler.gleam`, `src/scherzo/orchestrator/worker_registry.gleam`, and `src/scherzo/state/recovery.gleam`. Runtime state stores separate `running`, `claimed`, `retry_attempts`, `parked`, and `completed` dictionaries. The transition state also stores `pending_claims`, `pending_dispatch_validations`, and a logical `WorkerDirectory`. Retry timers and refreshes in flight live in the retry scheduler, real PIDs and monitors live in the worker registry, and startup recovery rebuilds dictionaries from ledger projections. Those pieces are individually typed, but no single ADT states that one task cannot be both `Claiming` and `Parked` or both `Running` and `RetryWaiting`.

The refactor must preserve local ledger and recovery compatibility. It must not redesign tracker state policy, workflow YAML, control/query JSON, EventHub payloads, Linear behavior, scheduled-job semantics, retry backoff, or worker process supervision. It must separate mechanical representation changes from any later behavior changes and keep every accepted milestone green.

## Strategy Overview

Introduce a small lifecycle module first, then move ownership gradually. The planned boundary is `src/scherzo/orchestrator/task_lifecycle.gleam`, with a `TaskLifecycle` ADT whose core states are `Idle`, `Validating`, `Claiming`, `Starting`, `Running`, `RetryWaiting`, `RetryRefreshing`, `Stopping`, `Parked`, and `Completed`. `RetryRefreshing` and `Stopping` are included because the current daemon already has retry refreshes in flight and worker stop flows even though the operator-facing state family is still retry-waiting or running. The module should also expose a `TaskDirectory` keyed by `identity.TaskIdentity`, pure transition helpers, invariant checks, count/query helpers, and adapters to and from the current runtime and transition dictionaries.

The first implementation slice should be adapter-only and behavior-preserving: derive typed lifecycles from existing dictionaries, assert conflicts in tests, and use lifecycle query helpers for dispatch guards without changing stored shapes. Later slices should make lifecycle updates the source of truth inside the transition kernel while preserving projection adapters for `RuntimeState`, read-model counts, startup recovery, ledger append helpers, and shell effects. The worker registry remains shell-owned; lifecycle owns logical run/session/workspace facts. Scheduled jobs remain owned by `scheduled_runtime.gleam` and interact only through shared global capacity and worker-count inputs.

## Alternatives Considered

Leaving the dictionaries in place and adding comments or helper predicates was rejected because it would not prevent contradictory state from being constructed. Replacing the daemon runtime state in one big bang was rejected because dispatch, claims, retry timers, worker registry synchronization, and startup recovery are too intertwined for a safe single diff. Adding new durable lifecycle ledger records was rejected for this slice because the existing `WorkflowRun*`, `RetryScheduled`, `RetryCancelled`, `IssueParkedV2`, and recovery records already contain the information needed to reconstruct lifecycle state. Folding scheduled jobs into the same task lifecycle was rejected because scheduled runtime already has its own typed state and is not tracker-claim based.

## Risks and Countermeasures

The main risk is introducing two sources of truth during migration. The countermeasure is to start with derived adapters and invariant tests, then flip individual transition families only when both the typed lifecycle and legacy projection produce identical counts and effects. A second risk is breaking recovery from existing ledgers. The countermeasure is to keep ledger schemas unchanged and add recovery parity tests that replay existing retry, park, interrupted-run, terminal-run, and outbox scenarios into the new lifecycle. A third risk is worker-directory divergence. The countermeasure is to keep real process handles in `worker_registry.Registry`, keep logical run/session/route facts in lifecycle, and test start, command-ready, stop, finish, down, and YAML-step paths for consistent indexes. A fourth risk is accidental behavior change in dispatch and retry guards. The countermeasure is to add negative transition tests for duplicate claim, stale validation, stale retry generation, parked issue, blocked dependency, no slot, terminal issue, and non-retryable issue before removing legacy checks.

A fifth risk is letting review feedback live only in this prose document while the structured implementation pack omits acceptance evidence, test obligations, milestone proof points, manual/dogfood timing, docs/helper boundaries, provider-live/cache non-scope, full validation, or lint gates. The countermeasure is to mirror those obligations in the implementation pack's concrete steps and testing notes before Scherzo materializes the follow-up implementation artifacts.

## Milestones

Milestone 1 captures the current lifecycle as executable facts before any representation changes. It adds characterization coverage or an explicit inventory note for the existing dictionaries in `src/scherzo/runtime/state.gleam`, `src/scherzo/orchestrator/transition_types.gleam`, transition handlers, retry scheduler, worker registry, scheduled runtime, and startup recovery. Reviewers should see which states consume a dispatch slot, hold a tracker claim, have a live worker, have a retry timer, survive startup recovery, or intentionally stay outside tracker-task lifecycle, with `direnv exec . gleam test -- --suite unit` passing afterward.

Milestone 2 introduces the typed lifecycle boundary without changing behavior. It adds `src/scherzo/orchestrator/task_lifecycle.gleam`, conversion from the existing runtime/transition dictionaries to `TaskDirectory`, invariant-check helpers, and `test/orchestrator_task_lifecycle_test.gleam` or equivalent focused tests for valid states and impossible combinations such as running plus parked, claiming plus retry-waiting, duplicate worker entries, and completed plus active.

Milestone 3 moves read-only decisions to lifecycle queries while legacy dictionaries remain writable. Dispatch guards, duplicate checks, slot counts, retry eligibility, parked checks, and read-model counts should call lifecycle helpers. Reviewers should see parity tests proving lifecycle-derived counts match current read-model counts for running, queued claim, pending validation, claimed, retry, parked, completed, and scheduled-job-independent counts.

Milestone 4 migrates claim, worker-start, worker-running, worker-finish, stop, and park transitions to lifecycle-producing helpers. Legacy runtime and worker-directory views remain as projections until tests prove they match after claim success/failure, worker start success/failure, command-ready, normal finish, failed finish, worker-down, operator stop, park, unpark, and YAML-step orphan cleanup paths.

Milestone 5 migrates retry scheduling and refresh handling. `RetryWaiting` and `RetryRefreshing` should own generation matching, stale tick rejection, defer-on-capacity behavior, cancel-on-dispatch behavior, retry refresh failure rescheduling, release-on-terminal/non-retryable behavior, blocked-dependency behavior, and parked safety while preserving retry scheduler timer ownership. Reviewers should see existing retry behavior and new lifecycle invariants pass in the same unit-suite run.

Milestone 6 migrates startup recovery. Recovery should reconstruct lifecycle states from existing projection records and then project back to the runtime/read-model surfaces used by the daemon, with no ledger schema change. Reviewers should see parity tests for old retry, parked, completed, interrupted-run, outbox replay, cleanup, and scheduled-runtime scenarios.

Milestone 7 removes obsolete direct dictionary mutation from transitioned paths, leaves compatibility projection functions at daemon/read-model/ledger boundaries, records any deferred cleanup, and completes validation. The outcome is one typed lifecycle source for tracker-backed task state inside the transition kernel, with format, full unit tests, relevant contract tests if touched, glinter, and `scherzo_lint` evidence retained before publish.

## Decision Log

- Decision: Keep durable ledger records unchanged in the planned refactor. Rationale: existing records already restore retries, parks, completed runs, interrupted runs, counters, and cleanup requests; adding lifecycle records would expand migration risk without solving the implicit-state problem. Date: 2026-06-05.
- Decision: Add `RetryRefreshing` and `Stopping` to the implementation ADT even though the issue listed a shorter example state set. Rationale: current retry refresh and worker stop flows exist today, and modeling them explicitly avoids hiding those transient states in scheduler or worker-directory side channels. Date: 2026-06-05.
- Decision: Keep scheduled jobs outside the tracker-task lifecycle. Rationale: `scheduled_runtime.gleam` already has a typed scheduled state model, and scheduled jobs do not follow tracker validation/claim/retry/park semantics. Date: 2026-06-05.
- Decision: Use adapters before replacing dictionary ownership. Rationale: adapter-first migration lets tests prove parity and gives a safe fallback if lifecycle ownership needs to be rolled back. Date: 2026-06-05.
- Decision: Treat review feedback about evidence, tests, milestone specificity, manual/dogfood timing, docs/helper migration, provider-live/cache boundaries, full validation, and linting as structured implementation-pack obligations. Rationale: the follow-up implementation workflow materializes concrete instructions from the pack, so prose-only obligations would be easy to miss. Date: 2026-06-05.
