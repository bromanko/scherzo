# LIV-933 composable CLI command help review

This review defines a behavior-preserving-first plan for a follow-up implementation task. It is intentionally concise; detailed implementation steps, tests, interfaces, dependencies, and artifact notes are carried in the structured implementation pack for this issue.

## Purpose / Big Picture

Scherzo operators should be able to trust `scherzo ctl --help` and `scherzoctl --help` as an accurate map of the commands they can run, and maintainers should be able to add or change a `ctl` command without editing parsing rules and a separate giant help string by hand. After the follow-up implementation, the `ctl` command definitions will drive parsing, command-specific option validation, and generated help from one registry. Existing valid commands such as `ping`, `ps`, `task list`, `task show`, `attach`, `schedules`, `artifact publication`, `state`, and `workstream` should continue to parse to the same behavior, while irrelevant flags such as `ping --yes` or `task show LIV-1 --state ready` should fail with usage errors instead of being silently ignored.

## Problem Framing and Constraints

The current CLI surfaces are split across several files. `src/scherzo/main.gleam` parses the top-level `scherzo` command and contains a large hand-written top-level usage string. `src/scherzo/ctl.gleam` defines the `ctl.Command` ADT, delegates execution, and contains a large `command_from` dispatcher for command parsing. `src/scherzo/ctl/parser.gleam` parses a broad `Flags` record that includes every option any `ctl` command might need. `src/scherzo/ctl/usage.gleam` contains one large hand-written help string for the `ctl` surface. `test/ctl_test.gleam` already characterizes many parse results and help substrings, but it mostly proves that the current string mentions important words, not that help is generated from the same definitions that parse commands.

The real operator and developer problem is drift and weak validation. As nested `ctl` commands grow, help can advertise a command shape that the parser does not actually accept, and the parser can accept a global flag that the selected command silently ignores. The refactor must preserve user-visible command names and successful parse results for valid invocations. It should focus on `scherzo ctl`, where the largest hand-written usage and parser complexity live. The top-level `scherzo` parser and help should remain unchanged unless the implementation proves that reusing the new help renderer for the top-level command is tiny, low-risk, and covered by existing `test/main_test.gleam` assertions.

## Strategy Overview

Use a small internal command/option spec registry for `ctl` rather than immediately adopting an external CLI package. The planned production shape is `src/scherzo/ctl/command_spec.gleam` for reusable parser and renderer primitives plus `src/scherzo/ctl/command_registry.gleam` for Scherzo's registered command definitions. Each command spec names a nested command path, positionals, allowed options, help summary, and a handler key. The generic module tokenizes arguments, supports options before or after nested subcommand words, parses boolean flags, value flags, repeatable flags, and `--color=auto`-style equals values, validates that only the selected command's options were used, and renders the command table and option table for help. The registry must expose command usage lines or equivalent structured metadata so tests can compare the generated `ctl.usage()` output against the registered command definitions instead of only checking ad hoc substrings. `src/scherzo/ctl.gleam` will keep the current `Command` ADT and execution code, but replace the broad flag parse plus `command_from` dispatch with a builder that turns a parsed spec result into the same `Command` variants.

This is proportionate because Scherzo needs a constrained parser for an existing internal command surface, not a general CLI framework. The registry solves the drift and irrelevant-flag problems directly while avoiding a dependency and avoiding a broad top-level CLI rewrite. The implementation should still include an early, time-boxed spike for external libraries, especially `glint` and `clip`, before any dependency is added. If that spike demonstrates a better fit for Scherzo's nested commands, generated help, no-exit error handling, repeatable enum flags, and exact existing parse results, the implementer must update the Decision Log before changing the approach.

## Alternatives Considered

Keeping the hand-written `ctl` usage string and only cleaning up formatting was rejected because it leaves parsing, validation, and help as separate sources of truth. It might make the help easier to read today, but it would not stop future drift or catch ignored irrelevant flags.

Adopting an external Gleam CLI library remains a candidate only after a spike. Initial research found `glint`, which documents nested command paths, typed flags, grouped flags, constraints, and generated help, and `clip`, which documents applicative option, flag, argument, and help parsers. Those are promising, but this repository currently has no `glint` or `clip` dependency, and the implementation still has to prove that either library preserves Scherzo's current nested `ctl` behavior, command ADT outputs, `--color=auto` syntax, repeatable `--state`, and no-surprise error handling better than a small internal registry.

The selected default is a small internal registry. It minimizes dependency risk, keeps behavior builders near the existing `ctl.Command` execution boundary, and can be introduced with parity tests before deleting the old parser and help string.

## Risks and Countermeasures

The main risk is changing valid command behavior while replacing the parser. The countermeasure is to add explicit compatibility tests for representative existing commands before switching `ctl.parse` to the new registry, then compare old and new parse results during migration.

A second risk is generating help that is technically derived from specs but less useful than the current hand-written help. The countermeasure is to preserve the current command ordering and important descriptions, test that every registered command usage line appears in generated help, and keep focused substring tests for operational notes that are not tied to a single command.

A third risk is overfitting the internal parser and accidentally creating a general framework. The countermeasure is to implement only the option forms Scherzo already uses: nested paths, required/optional/rest positionals, boolean flags, single-value flags, repeatable value flags, enum/int validation, and explicit equals-form support for `--color=auto`.

A fourth risk is adopting a library because it looks attractive but then discovering it cannot preserve current behavior. The countermeasure is an early spike with pass/fail criteria and no production dependency unless the spike proves the library handles nested commands, generated help, repeatable flags, equals-form options, and no-exit error reporting cleanly.

A fifth risk is letting implementation obligations live only in this prose document. The countermeasure is to mirror the compatibility tests, negative flag-validation tests, generated-help tests, library-spike evidence, full validation commands, and non-scope boundaries in the structured implementation pack before Scherzo materializes the follow-up implementation artifacts.

A sixth risk is accepting a parser/help refactor with only unit-test evidence and no direct CLI check of the operator surfaces. The countermeasure is to make manual CLI dogfood a pre-publish requirement for the follow-up implementation: `direnv exec . gleam run -- ctl --help`, `./scripts/scherzoctl --help`, and an invalid-command check such as `direnv exec . gleam run -- ctl ping --yes` must demonstrate generated help and command-specific flag rejection. Browser checks, daemon-provider-live checks, provider cache checks, and workflow-helper or schema migrations remain out of scope unless implementation changes those files; if it does, acceptance must be expanded before publish rather than silently relying on the CLI test gates.

## Scope Boundaries

For this planning issue, the scope is exactly this Markdown review document under `docs/plans/` and one structured implementation-pack submission. No production parser, generated bundle, canonical implementation-pack JSON, helper migration, or test change should be written by this issue.

For the follow-up implementation, in scope are `src/scherzo/ctl.gleam`, `src/scherzo/ctl/parser.gleam`, `src/scherzo/ctl/usage.gleam`, `src/scherzo/ctl/command_spec.gleam`, `src/scherzo/ctl/command_registry.gleam`, and relevant tests in `test/ctl_test.gleam` or a focused new CLI spec test file. Existing command execution and rendering should stay in place except for small adjustments needed to consume parsed commands. `scripts/scherzoctl` is a validation surface because it wraps `gleam run -- ctl`, but it is not expected to need code changes. `src/scherzo/main.gleam` and `test/main_test.gleam` are in scope only for a low-risk top-level help reuse after `ctl` is complete; otherwise they should remain unchanged except for confirming `scherzo ctl <args>` still delegates to `ctl`.

Out of scope are user-visible command renames, semantic changes to successful valid commands, daemon control protocol changes, command execution redesign, renderer refactors, Linear or tracker behavior changes, workflow helper or schema migration under `.scherzo/workflows/`, browser/UI work, provider-live behavior, provider cache behavior, broad documentation migration, and adopting a CLI dependency without the spike evidence described above. If implementation unexpectedly needs helper, schema, provider-live, provider-cache, or broad docs changes, that work should be split out or the plan must be revised with explicit validation before those changes are made.

## Milestones

Milestone 1 captures the current CLI behavior and completes the external-library spike. The implementer should add or expand passing characterization tests in `test/ctl_test.gleam` for representative valid parse outputs: `ping`, `ps --json`, `task list --state ready --state active --limit 50 --cursor cursor:50 --json`, `task show LIV-770`, `attach --color=never ABC-1`, `schedules status/history/logs/doctor/run`, `artifact publication list/show/retry/abandon`, `state status/compact/repair-run-provenance`, and at least one `workstream` parse path. These compatibility tests must pass against the current parser before migration. The external-library spike must record whether `glint` or `clip` can satisfy nested command paths, generated help, no-exit error handling, repeatable enum flags, equals-form values, and exact current parse results without forcing behavior changes.

Milestone 2 introduces the internal command-spec parser and help renderer behind focused tests, without wiring it into `ctl.parse`. The outcome is `src/scherzo/ctl/command_spec.gleam` plus tests that exercise nested path selection, required and optional positionals, rest positionals, boolean flags, single-value flags, repeatable value flags, enum validation for task states and color modes, integer validation for limits and cursors, unknown-option errors, missing-value errors, and both `--color auto` and `--color=auto` forms.

Milestone 3 builds `src/scherzo/ctl/command_registry.gleam` and generated help while keeping existing command execution intact. The outcome is that `ctl.usage()` is rendered from registered command definitions instead of a separate giant string, every registered command usage line can be compared against `ctl.usage()` by a test, and operational notes from the old help remain present where still useful. This milestone must not rewrite `src/scherzo/main.gleam`; it may only confirm that `scherzo ctl <args>` still delegates to `ctl`.

Milestone 4 migrates `ctl.parse` from the old broad flag parser to the command registry. The outcome is that all representative valid commands still produce the same `ctl.Command` variants, nested commands remain composable, flags may still appear before or after subcommand words where current behavior allows it, and existing execution tests continue to pass. The implementation should keep the old parser available only long enough to compare behavior in tests or small local helpers, then remove it once parity is established.

Milestone 5 enforces command-specific option validation. The implementer should add red-then-green tests that currently fail because broad flags are ignored, including `ping --yes`, `task show LIV-1 --state ready`, `schedules logs nightly --now`, and `artifact publication list --run run-1 --publication extra`. The outcome is that unsupported or irrelevant options are rejected per command with usage errors, while command-required options and cross-option rules such as `--dry-run` versus `--yes`, `--last`, `--now`, `--run`, `--publication`, `--reason`, and `--root` remain explicitly tested.

Milestone 6 removes obsolete parser/help code and completes validation. The outcome is a smaller `ctl` parsing surface, no remaining giant `ctl` usage string, no unnecessary external dependency unless the spike changed the decision with evidence, and retained pre-publish evidence for `direnv exec . gleam test`, `direnv exec . gleam format --check src test`, `direnv exec . gleam run -m glinter`, `direnv exec . gleam run -m scherzo_lint`, `direnv exec . gleam run -- ctl --help`, `./scripts/scherzoctl --help`, and an invalid-flag CLI check such as `direnv exec . gleam run -- ctl ping --yes`. Before publish, the diff should also confirm that workflow helpers, workflow schemas, provider-live files, provider cache files, browser/UI files, and broad docs migrations were not touched; if they were touched, acceptance must be revised before continuing.

## Rollout, Recovery, and Idempotence

Rollout for this planning issue is to commit this review document and let Scherzo materialize the canonical ExecPlan bundle and follow-up implementation task from the structured submission. Recovery is to edit or revert this document and submit a corrected structured implementation pack; no generated bundle values should be invented here.

Rollout for the follow-up implementation should be incremental: commit the passing characterization tests and spike note; commit the command-spec module behind focused tests; commit generated help from the registry while the old parser still handles execution; commit the parser migration with parity tests green; commit command-specific irrelevant-flag rejection with red-then-green tests; then commit obsolete parser/help cleanup after full validation. Each commit should leave the tree green. Recovery is to revert the latest migration slice while keeping characterization tests that still describe current behavior. If the new parser is partially wired and causes a regression, restore `ctl.parse` to the old path and keep the command-spec module dormant until the failing parity case is fixed. The changes are idempotent because they are source-only parser/help changes with no data migration, no daemon protocol migration, no provider-live mutation, no cache invalidation, no browser state, and no external provider state.
