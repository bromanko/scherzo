# Artifact publication runtime integration and retry

This review document frames the ExecPlan for integrating artifact publication into workflow finalization and operator retry. Mechanical implementation detail, file-by-file edits, tests, interfaces, and artifact notes are supplied through the structured implementation-pack submission for LIV-741.

## Purpose / Big Picture

After this change, Scherzo will treat publication of retained workflow artifacts as part of workflow finalization instead of as a workspace-driver publishing step. Once a workflow records its canonical output manifest, Scherzo will publish configured artifacts, record whether each publication was `published`, `unchanged`, or `failed`, and let an operator retry failed publications with `scherzoctl artifact publication retry --run <run-id> [--publication <publication-id>]` without rerunning the workflow steps that produced the artifacts.

## Problem Framing and Constraints

The source PRD keeps Scherzo's artifact store canonical and treats GitHub or any later repository as a derived copy. The current tree already has publication configuration, a dry-run planner, retained publication manifests, ledger-backed list/show inspection, and workflow finalization that records dry-run `planned` or `failed` attempts after outputs are recorded. The missing behavior is the runtime publication executor: actual publication must run after the output manifest exists, required failures must block workflow success and move the task into the existing failure/triage path, optional failures must be warnings, retry must replay retained artifacts rather than workflow steps, and daemon restart recovery must not duplicate remote branches, pull requests, commits, or ledger attempts.

## Strategy Overview

The proportionate approach is to replace dry-run recording in workflow finalization with a publication runtime layer that reuses the existing planner as the deterministic input builder. The runtime will plan from the retained output manifest, call a repository publisher through a narrow interface, write a terminal publication manifest, append a ledger attempt record, and return required failures or optional warnings to `workflow_run`. Workflow success remains blocked until all required routes are terminally successful or unchanged. Retry uses the same runtime in an operator mode that selects latest failed retryable publications for a run and replays them from canonical artifact refs and route configuration, never from a step workspace.

## Alternatives Considered

Leaving publication as a dry-run ledger record was rejected because it does not satisfy the PRD's requirement to publish selected artifacts or retry transient backend failures. Calling `workspace-driver publish-change` was rejected because it publishes workspace diffs, while artifact publication must publish retained output bytes by artifact-store ref. Rerunning the producing workflow step on publication retry was rejected because it can produce different artifacts and defeats the canonical-store boundary. Automatically rewriting task success after every later retry was deferred for the MVP; this slice records recovered publication state and leaves task-state promotion to the existing handoff policy or a later explicit reconciliation task.

## Risks and Countermeasures

The largest correctness risk is publishing bytes from a workspace instead of from canonical refs. The countermeasure is to make the runtime consume the retained output manifest and planner-selected artifact refs only, with tests that count step executions and use fake artifact refs. The largest operational risk is duplicate external state after a retry or daemon crash. The countermeasure is deterministic `series_id` and `version_id`, backend no-op detection, terminal attempt checks before workflow recovery republish, and fake publisher tests that prove repeated retries do not create duplicate commits or PRs. The largest user-facing risk is optional failures being invisible. The countermeasure is to record optional failure attempts and append a workflow diagnostic that list/show and local evidence can inspect. A fourth risk is accidentally folding this runtime slice into a broader dogfood workflow/helper migration, provider-live/cache change, or legacy `publish-change` removal. The countermeasure is an explicit docs/helper scope inventory in the implementation evidence: if workflow helper scripts, workflow schemas, provider-facing structured-output helpers, review-lane contracts, operator docs, or installed `.scherzo/workflows` copies change, the relevant helper or offline contract tests must run; if they do not change, the evidence must state that no helper migration, provider-live validation, or cache validation was applicable. A review-process risk is letting acceptance evidence, test obligations, milestone proof, local dogfood timing, full validation, or linting live only in this prose while the structured implementation pack omits them. The countermeasure is to mirror those obligations in the updated implementation pack before Scherzo materializes follow-up artifacts.

## Scope Boundaries

In scope are workflow-finalization publication execution, terminal publication statuses, required-versus-optional failure handling, optional warning diagnostics, retry selection and execution for failed publications, the exact retry command shape, idempotency across retries, daemon restart recovery from crashes before, during, and after publication attempts, focused operator documentation for the retry command, and a pre-publish docs/helper scope inventory. Existing workflows without `artifacts.publications` must remain unchanged, and legacy `publish-change` behavior must continue until a separate migration moves specific workflows. If implementation touches `workflows/dogfood/scripts/*`, `workflows/dogfood/schemas/*`, `.scherzo/workflows/**`, provider-facing structured-output helpers, review-lane contract files, or operator docs helpers, the relevant helper or offline contract tests must be included as implementation evidence; if those surfaces stay untouched, the evidence must explicitly say no helper migration, provider-live validation, or cache validation was applicable. Out of scope are generalized review approval state, non-GitHub repository backends, selecting artifacts by metadata or media type, browser evidence, live GitHub dogfood before a staging target is chosen, provider-live/cache behavior changes, broad migration of checked-in dogfood workflows from legacy publishing, and automatic task-state promotion after a later successful retry.

## Milestones

Milestone 1 establishes the runtime seam and terminal status model. At the end, publication execution has a fakeable repository-publisher interface, manifests can represent `published`, `unchanged`, and `failed`, existing dry-run `planned` records remain readable for list/show compatibility, and focused runtime tests prove canonical artifact refs are the only byte source.

Milestone 2 integrates publication with workflow finalization. At the end, configured publications run only after workflow outputs are recorded, required publication failure prevents workflow success and goes through the normal failure/triage handoff path, optional publication failure records a warning and allows workflow success, workflows without publication routes behave exactly as before, and ledger/list/show evidence proves each terminal attempt is durable.

Milestone 3 delivers operator retry. At the end, `scherzoctl artifact publication retry --run <run-id> [--publication <publication-id>]` retries the selected latest failed retryable publication attempts from retained outputs, rejects missing runs, missing publications, and non-retryable latest statuses clearly, can retry all failed publications for a run when `--publication` is omitted, and returns JSON/human-readable summaries that name the retried publication ids and new attempt statuses.

Milestone 4 proves restart recovery and idempotency. At the end, daemon recovery after a crash with outputs already recorded does not rerun producing steps, incomplete or missing publication attempts are replayed, terminal failed required attempts finish the run in failure instead of silently auto-retrying, and repeated retry of the same selected version produces `unchanged` or an equivalent no-op rather than duplicate external state.

Milestone 5 closes release readiness. At the end, focused runtime, workflow, CLI, and restart-recovery tests pass; the docs/helper scope inventory is recorded; full Gleam validation, format, `glinter`, and `scherzo_lint` gates pass; pre-publish local fake-publisher or seeded CLI evidence shows success, unchanged/no-op, required failure, optional failure, retry, retry-all, restart recovery, and no duplicate external operations; and live GitHub, browser, provider-live, and provider-cache evidence are explicitly deferred to a human/operator after implementation.

## Rollout, Recovery, and Idempotence

Rollout is additive for workflows that do not declare `artifacts.publications`, and legacy workspace `publish-change` remains available for workflows that still use it. Pre-publish rollout evidence must include automated tests, full format/lint validation, review-doc validation, the docs/helper scope inventory, and local fake-publisher or seeded operator transcripts; live GitHub, browser, provider-live, and provider-cache checks are deferred human/operator checks after implementation. Required publication failure keeps canonical artifacts and the output manifest retained, records retryable publication state, and sends the task through the existing failure/triage path. Optional publication failure records a warning diagnostic and remains retryable after workflow success. Recovery is the retry command: the operator replays selected failed publications from retained output refs, and if the target already contains the selected version, the runtime records `unchanged` or the backend's equivalent successful no-op. Restart recovery uses the same idempotency: missing or incomplete publication state is replayed, terminal success is skipped, and terminal required failure finalizes as failure rather than silently auto-retrying. If implementation discovers it must migrate dogfood workflows, helper scripts, schemas, provider-facing contracts, provider-live behavior, or cache behavior, split that migration into a separate plan or add the relevant helper/offline-contract evidence before publishing this slice.
