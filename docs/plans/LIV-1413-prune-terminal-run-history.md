# Prune terminal workflow-run history during ledger compaction

This ExecPlan review is the concise human-facing companion to the structured implementation pack. The implementation pack carries the file-by-file mechanics. This is a living document; Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must stay current during implementation.

## Purpose / Big Picture

Scherzo operators should be able to leave scheduled and issue-driven workflows running without `snapshot.json` and the future resident projection growing forever. Each retention-enabled ledger compaction will fold new records, remove terminal run details that are outside policy and safe to forget from the online projection, and then write the snapshot. Raw JSONL records remain in archived ledger segments, so pruning reduces startup, compaction, and memory cost without deleting audit history. Existing installations do not prune until an operator explicitly enables the policy.

## Problem Framing and Constraints

A measured compacted snapshot was 44 MB: 29.2 MB was 30,545 step attempts and another 11.7 MB represented 10,701 workflow runs and their task/provenance data. Fifteen-minute scheduled jobs add about 200 runs per day, so compaction currently moves growth from `current.jsonl` into an ever-growing snapshot instead of bounding it. Pruning must be atomic with compaction and must never remove active, parked, recovering, retained-workspace, unsettled-publication, or queued/running-control state. It must preserve clear append and operator errors after a run disappears, remain compatible with old snapshots, and avoid any linear archive scan while the ledger writer lock is held.

The raw archive and a small derived archive index are allowed to grow because they are the durable audit tier; neither is decoded into the normal projection or resident read model. This is different from keeping tombstones in `snapshot.json`: an exact disk index can answer an exceptional missing-run query in logarithmic reads without restoring unbounded history to startup or steady-state memory. Corrupt or unavailable index/coverage metadata fails closed and never falls back to an unbounded archive scan.

## Strategy Overview

Add a pure retention pass to the projection and invoke it inside the ledger lock between folding `current.jsonl` and atomically writing `snapshot.json`. Issue-driven terminal runs become eligible after a 24-hour grace period. Scheduled terminal runs keep everything in grace, then keep only runs that are both no older than seven days and among the newest 25 for that job; safety holds override those ordinary caps. The policy is configurable under `state_ledger.projection_retention` and defaults to disabled. The daemon and `state compact` resolve the same workspace configuration, and preview prints the exact effective values and policy fingerprint that the next compaction would apply.

Pruning removes every run-owned family together, cleans settled control/outbox references and source-run lists, and rebuilds the latest-publication-by-series index from retained attempts. At the same transaction boundary, compaction atomically creates exact-id markers in a derived, hash-sharded `archive/pruned-runs/v1/` index. Each run id maps through SHA-256 to two fixed directory shards and one marker file containing the original id; a missing-run query computes that one path and compares the original id rather than scanning JSONL. A synthetic hash callback proves collisions are compared exactly. Lookup is bounded to a fixed number of filesystem operations and the collision marker, independent of archive bytes, segment count, and other indexed ids. An absent marker means genuinely unknown; a present but malformed or unreadable marker returns a stable ledger/index error rather than guessing. Tests with a large synthetic archive and repeated misses must show that known append traffic continues and that lookup work does not scale with archive bytes or segment count.

Before the first retention-enabled compaction, Scherzo proves that the raw archive can reconstruct the current unpruned projection by folding numbered segments and `current.jsonl` from an empty projection and comparing the encoded result. The successful compaction records segment names, sizes, and hashes in `archive/coverage.json`; later compactions extend that manifest with the newly archived current segment. Retention refuses to prune if initial coverage cannot be proved. Recovery verifies the manifest before folding. This makes full reconstruction an explicit, testable prerequisite rather than an assumption.

## Alternatives Considered

Keeping seven days of every run is simpler, but it retains far more issue history than operators use and does not exploit the agreed “drop after completion” policy. Keeping permanent run-id tombstones in the online projection makes late appends cheap to classify, but it recreates unbounded snapshot and resident-memory growth. Linear JSONL archive scans, even only after a miss, were rejected after review because repeated unknown ids could monopolize the ledger lock as archives grow. The selected derived disk index has unbounded audit-tier disk usage but bounded lookup and no projection or startup-memory cost.

Silently accepting records for pruned runs was rejected because those records could not safely update a projection whose parent and recovery context are gone. Targeted reconstruction of one run was also rejected for this change: safely merging one run's workflow, step, publication, outbox, control, and secondary-index families is almost the same consistency problem as pruning and can leave a mixed projection. Full retain-all reconstruction is slower but preserves projection-wide fold semantics and is reserved for stopped-daemon emergency recovery after resource and archive-coverage preflight.

## Risks and Countermeasures

The largest semantic risk is pruning a run that still supports recovery or publication. Eligibility therefore fails closed on retained-marker inspection errors and checks terminal age, parked issue state, started recoveries, queued/running control operations, latest publication statuses, and unsettled outbox entries before deleting anything. Cross-family dangling references are prevented by one run-id removal set and count-based tests for every affected family. Publication series dedupe can regress if its latest entry is deleted blindly, so the index is rebuilt from retained attempts.

The largest availability risk is historical classification blocking writers. The hash-sharded archive index replaces JSONL scans, malformed index data returns an error without fallback, and repeated-hit, repeated-miss, hash-collision, large-archive, and concurrent-writer tests enforce bounded behavior. New marker creation precedes snapshot replacement under the existing ledger lock; if a later snapshot/archive action fails, the old snapshot still makes a stale marker harmless because online presence wins. Atomic-write and restoration tests cover every failure boundary.

The largest rollout risk is surprise pruning from a new default or a preview that does not match runtime. Retention therefore defaults to disabled. Preview and compaction consume one resolved effective policy, report its values and fingerprint, and share candidate selection; a parity test requires identical candidate ids for the same projection and clock. Deployment requires an operator to stop the daemon, back up the ledger, explicitly configure the intended policy, and preview before enabling actual compaction.

Full reconstruction can exhaust disk or memory and is impossible if raw history is incomplete. The rebuild command first verifies `archive/coverage.json`, segment hashes and ordering, defines `estimated_output_bytes` as the larger of current snapshot bytes and total raw input bytes, estimates peak memory as four times raw input bytes plus `estimated_output_bytes`, and requires free disk of at least raw input bytes plus twice `estimated_output_bytes` plus a 1 GiB margin. It refuses before mutation when either bound is unmet. A copied pre-enable ledger is the primary immediate rollback; full reconstruction is the slower emergency path.

## Scope Boundaries

In scope are workflow-run projection retention, compaction reports and logs, configuration/schema support, a derived pruned-run archive index, archive-coverage metadata, distinct pruned-run handling for ledger appends and the `run retry-step`, `recollect-outputs`, `finalize`, and publication-retry paths, compaction dry-run/reconstruction support, deterministic tests, and the state-ledger runbook. Run-owned state includes workflow status, provenance, task references, input/interface/output manifests, repair data, step attempts and recoveries, settled publication history, terminal control operations, settled outbox entries, and secondary run-id references.

Raw archive deletion, legacy `runs`, command-receipt retention, workstream artifact/handoff retention, artifact-file deletion, provider-live state, UI/browser work, and replacing JSONL with a database are out of scope. The ledger append hot-path cache from LIV-1411 is not assumed to exist; if it lands first, this work must refresh its projection atomically and preserve the same indexed missing-run classification. Targeted reconstruction and automatic enablement are explicitly deferred.

## Surprises & Discoveries

The scheduled projection already limits `recent_run_ids` to 25, but the workflow-run, provenance, manifest, and step-attempt dictionaries retain those same scheduled runs indefinitely. Scheduled workflow checkpoints are identifiable because `workflow_run.execute_scheduled` creates a placeholder issue with an empty issue id and the job id as its identifier. Auto-compaction from LIV-1412 is already implemented through the effect runner and holds the ledger lock for fold, snapshot write, and archive rotation, so pruning can extend that transaction rather than invent another lifecycle.

Review exposed that “archive lookup only on exceptional paths” was not sufficient: a repeated unknown-id workload can make an exceptional linear scan a writer-availability problem. Exact historical classification therefore requires derived archive metadata even though projection tombstones remain forbidden. Review also exposed that archive preservation alone does not prove archives are complete enough to reconstruct; coverage must be established before the first prune.

## Decision Log

- Decision: Use a disabled default with 24-hour terminal grace, seven-day scheduled maximum age, and 25 post-grace scheduled runs per job once explicitly enabled. Rationale: the values implement the agreed policy, but disabled-by-default rollout prevents existing configurations from pruning before representative preview. Date: 2026-07-12.
- Decision: Reject post-prune run-scoped appends with `pruned_workflow_run`; do not accept and ignore them. Rationale: after grace, completed runs are closed, and silently losing new state would hide producer bugs. Date: 2026-07-12.
- Decision: Do not persist tombstones in `Projection`; persist an exact hash-sharded derived index in the archive tier. Rationale: projection tombstones recreate the growth being fixed, while one exact-path marker per pruned id makes repeated misses independent of archive volume, avoids rewriting the full index on every compaction, and is rebuildable from retained audit data. Date: 2026-07-12.
- Decision: Require archive reconstruction parity before first prune and persist hashed coverage metadata. Rationale: merely retaining segment files does not prove that they cover records already folded into a snapshot. Date: 2026-07-12.
- Decision: Rebuild `publication_latest_by_series` from retained attempts and delete a series entry when no retained attempt remains. Rationale: this prevents dangling run references while preserving ordering among still-online runs; archived records remain the offline source. Date: 2026-07-12.
- Decision: Prefer full retain-all emergency reconstruction over targeted run merging. Rationale: full replay preserves all projection family and secondary-index invariants; targeted merging is deferred until it can be designed and tested independently. Date: 2026-07-12.

## Validation and Acceptance

Acceptance requires deterministic tests showing issue runs disappear only after grace; scheduled runs retain grace plus the intersection of seven-day age and newest-25 policy; every safety condition prevents pruning; and all run-owned dictionaries and secondary references are cleaned together. Boundary tests use exactly grace, one millisecond beyond grace, exactly seven days, one millisecond older, rank 25, and rank 26. Preview and actual compaction, when given the same encoded projection, fixed clock, and effective-policy fingerprint, must report exactly the same candidate run-id set.

The plateau fixture contains two jobs completing one run every 15 minutes in half-open daily windows, three step attempts per run, ten initial days, and one appended day. For each job, ordinary retained runs must equal `G + min(25, E)`, where `G` is the number completed in `[now - 24h, now)` and `E` is the number outside grace but no older than seven days; active and safety-held runs are counted separately and are not charged to the 25-run cap. With the fixture's complete daily windows, `G` is exactly 96 and `E` exceeds 25, so each job retains exactly 121 ordinary terminal runs after each compaction. Every per-run fixture family must equal its declared multiplicity times retained runs, plus the explicit active/held fixtures, and no ordinary terminal run may be older than seven days. After appending the eleventh day, the second snapshot must be no larger than the first snapshot plus `max(4096 bytes, ceil(first_snapshot_bytes / 100))`. Exceeding any count or byte bound falsifies the plateau claim.

Tests must also prove old snapshots decode; retention-disabled compaction is projection-equivalent; a covered retain-all reconstruction restores history; incomplete, reordered, hash-mismatched, low-disk, and over-memory-budget rebuilds fail before mutation; and compaction/index/snapshot failures preserve recovery behavior. A synthetic archive fixture containing at least 100,000 unrelated records must prove exact indexed hits, misses, and injected hash-collision handling without opening JSONL on lookup, and 1,000 repeated misses concurrent with a known-run writer must complete with all writer records accepted and no lock starvation under deterministic barriers.

Live runs must never produce `unknown_workflow_run`. Terminal prune-versus-late-append must return either success-before-prune or `pruned_workflow_run`, and each named recovery command must distinguish pruned from never-known runs without side effects. The complete Gleam test suite, format check, `glinter`, `scherzo_lint`, and `jj diff --check` are publish-blocking and must pass.

## Rollout, Recovery, and Idempotence

Retention ships disabled. The automated implementation workflow ends after tests, format, lint, documentation, and diff validation; it does not enable retention on a real workspace. As a post-implementation operator gate before enablement, stop the daemon, copy `.scherzo-state/ledger`, set the intended `state_ledger.projection_retention` values including `enabled: true`, and run `state compact --dry-run`. The preview must report the resolved values and fingerprint, archive-coverage status, candidate and blocker counts, family counts, projected bytes, and reconstruction resource estimate. Unexpected candidates, coverage failure, or insufficient recovery resources stop enablement. Only after approving that exact preview may the operator run confirmed compaction or restart the daemon with the same configuration. Compare `projection_pruned` counts and projection bytes before/after. Real plateau dogfood over later compactions is deferred post-enablement evidence and is not a publish gate.

Repeating preview does not mutate files. Repeating compaction at the same clock, effective policy, and archive state is idempotent: already-pruned families and index ids remain single entries, retained runs remain unchanged, candidate counts become zero, and the coverage manifest does not duplicate segments. Disabling retention stops future pruning but does not recreate prior online history.

The copied ledger is the primary rollback. For retain-all recovery, stop the daemon, disable retention, and run `state compact --rebuild-from-archives --yes`. The command first verifies numeric segment ordering and every manifest hash, refuses incomplete coverage, prints raw input and `estimated_output_bytes`, compares the exact memory and disk formulas from Risks and Countermeasures with operating-system probes, and mutates nothing when either the probe or budget check fails. If preflight passes, it folds archives plus current from an empty projection, writes a replacement snapshot atomically, rotates a nonempty current segment once, and leaves archives and the derived index intact; online presence takes precedence over an old index entry. If coverage or resources do not pass, restore the copied ledger rather than forcing a partial reconstruction. Normal compaction never deletes archive segments.
