Make JSON Schema a first-class structured-output validator

Plan artifact: docs/plans/LIV-259-first-class-json-schema-structured-output-validation.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

Workflow authors should be able to say, in workflow YAML, that an agent step must produce JSON matching a repository-local JSON Schema. After this change is complete, a workflow author can declare validators: [{ type: json_schema, path: ..., draft: "2020-12" }] without writing or wiring a custom validator command for ordinary shape validation. Operators can then trust Scherzo to validate the model output locally, retain a structured artifact only after validation passes, and report concise retryable or non-retryable diagnostics when validation fails.

The visible outcome is a workflow whose agent step can use either a final JSON response or a Pi tool-call JSON payload as the structured-output source, then run Scherzo-owned JSON Schema validation and optional command validators in a deterministic local pipeline. The implementation is successful when tests, local workflow fixtures, and package install checks prove that JSON Schema payload mismatches retry the agent, missing or invalid schema files fail as configuration errors, schema paths cannot escape the repository even through symlinks, retained artifacts include enough metadata to audit exactly which schema accepted the payload, and an installed Scherzo can run the same validation without depending on a workflow repository copy of Scherzo's scripts/ directory.

Problem Framing and Constraints

Structured output is the boundary between probabilistic model text and later deterministic workflow steps. Today, Scherzo already contains generic structured-output infrastructure and JSON Schema-related code, but the project needs the feature to be treated as a baked-in platform capability rather than as a convention around user-provided validator commands. The operator pain is that common shape validation should not require each workflow to ship a validator binary, remember command exit-code contracts, or manually preserve schema metadata.

This plan intentionally keeps local Scherzo validation as the source of truth. Provider-native model contracts may later reduce invalid outputs before they reach Scherzo, but they are not authoritative for this work. Command validators remain in scope as semantic validators and escape hatches: JSON Schema should catch shape and field-level constraints, while command validators can check repository-specific invariants such as file existence, cross-artifact references, or policy rules.

The implementation must be additive and compatible with current structured-output declarations. It must not remove the legacy singular validator compatibility path until a separate migration issue chooses to do that. It must not require provider/model-native enforcement. It must not convert every existing workflow in this task.

Strategy Overview

Use the existing structured-output pipeline as the integration point, because it already has the right abstraction: source extraction, baseline JSON admission, ordered validators, retry classification, artifact persistence, metadata, and workflow fingerprinting. JSON Schema should be one validator variant in that pipeline, declared by type: json_schema and implemented by Scherzo-owned code. A workflow author supplies only schema metadata: a repository-relative schema path and an optional draft string. They do not supply an executable, working directory, timeout, or environment for shape validation.

The first implementation milestone should normalize the current state against the contract in this plan. If the current tree already contains a working JSON Schema runner, keep it and harden the gaps rather than rewriting it. The proportionate choice is to keep an internal helper process if that is the smallest reliable way to get draft 2020-12 validation, while making the helper clearly Scherzo-owned infrastructure instead of a workflow-declared command validator. The helper must be located as Scherzo runtime infrastructure, not under the workflow repository: source-checkout runs may fall back to scripts/scherzo-json-schema-validate, but installed Scherzo must use a packaged helper path supplied by its wrapper. The later milestones should then lock down packaging, diagnostics, metadata, tests, docs, and migration guidance.

Alternatives Considered

The simplest alternative is to tell workflow authors to keep using type: command validators that invoke a JSON Schema CLI. That is insufficient because it duplicates policy in every workflow, hides schema identity behind arbitrary command lines, makes migration and metadata harder, and exposes authors to command validator security and environment details for a common declarative case.

A second alternative is to wait for provider-native structured-output contracts and skip local validation. That is too risky because Scherzo still needs deterministic behavior across providers, must classify failures for retry and artifact retention, and must verify the exact schema file stored in the repository.

A third alternative is to implement a full JSON Schema validator directly in Gleam. That may be attractive long term, but it is larger than needed for the first-class API. Keeping a small Scherzo-owned helper around a well-known validator library is proportionate if the dependency is pinned, diagnostics are stable, and helper failures are reported as Scherzo configuration errors.

Risks and Countermeasures

The main risk is silently treating a broken validator setup as an agent-output problem. The countermeasure is a strict error split: payloads that do not satisfy a valid schema are retryable schema rejections, while missing helper dependencies, unreadable schema files, unsupported drafts, invalid schema documents, helper timeouts, and malformed helper diagnostics are non-retryable configuration errors.

A second risk is allowing schema paths to read files outside the trusted repository. The parser must reject empty paths, absolute paths such as <absolute-local-path>, and parent-directory traversal before any helper starts. The runtime must then resolve the repository root and candidate schema path to canonical paths and reject the schema when the resolved schema path is not inside the resolved repository root. Symlinks are allowed only when their resolved target remains inside the repository; symlink escapes are configuration errors, not agent-output failures. Tests must generate absolute paths and symlink targets dynamically instead of embedding machine-specific paths in source.

A third risk is leaking secrets or model payloads in diagnostics. JSON Schema validation may use the raw admitted JSON value because it is Scherzo-owned infrastructure, but diagnostics must never print the full payload. Failure messages and diagnostic summaries must be redacted with the same secret list used elsewhere and truncated to a small bounded size.

A fourth risk is creating false confidence by validating only final responses. The same validator pipeline must operate after both supported sources: source.type: final_response and source.type: pi_tool_call. Source extraction proves where the JSON came from; JSON Schema then validates the resulting admitted object.

A fifth risk is making existing workflows pass in development but fail when Scherzo is installed. The packaging milestone must keep devenv.nix as the source-checkout developer environment, add the JSON Schema helper and a Python interpreter with jsonschema to nix/scherzo.nix, and make the installed scherzo wrapper point the runtime at the packaged helper. The runtime must still produce a clear structured_output_json_schema_config_error if the helper is missing, cannot start, cannot import jsonschema, times out, or emits malformed diagnostics.

Context and Orientation

Scherzo workflows are YAML directed acyclic graphs parsed by src/scherzo/workflow_dag.gleam. Agent steps may declare structured_output, which tells Scherzo to extract a JSON value from the agent result, validate it, and retain it as a structured artifact. A structured-output source is the place where the candidate JSON comes from. Version 1 supports the final assistant response and a Pi tool call. A Pi tool call is a structured call emitted by the Pi agent runtime whose JSON arguments can be captured as the artifact payload.

The core files for this work are:

  • src/scherzo/workflow_dag.gleam, which defines the workflow AST, StructuredOutputSpec, StructuredOutputValidator, JsonSchemaValidator, and CommandValidator.
  • src/scherzo/workflow_dag_validator_parser.gleam, which parses structured_output.validator compatibility declarations and the generic structured_output.validators list.
  • src/scherzo/structured_output_source.gleam, which parses and represents source.type: final_response and source.type: pi_tool_call.
  • src/scherzo/structured_output.gleam, which extracts the structured output, performs baseline JSON admission, dispatches validators in order, and exposes retryability and diagnostic accessors.
  • src/scherzo/structured_output_json_schema.gleam, which implements the Scherzo-owned JSON Schema validator runner.
  • scripts/scherzo-json-schema-validate, which is the current Python helper used by the JSON Schema runner.
  • devenv.nix, which already supplies python3 with the Python jsonschema package in the source-checkout developer environment.
  • nix/scherzo.nix, which builds the installed Scherzo package, installs runtime helper scripts under libexec, wraps scherzo, and runs install checks with a sanitized PATH.
  • src/scherzo/structured_output_command_validator.gleam, which implements trusted workflow-declared command validators.
  • src/scherzo/structured_output_metadata.gleam, which records validation metadata such as schema path, schema hash, draft, command argv hash, and validator summaries.
  • src/scherzo/workflow_fingerprint.gleam, which converts workflow semantics to a canonical JSON string and hash for execution change detection.
  • src/scherzo/state/artifact_store.gleam, which writes retained step artifacts and structured-output artifacts under the run artifact store.
  • src/scherzo/step_artifact.gleam, which defines the JSON shape of step artifacts, structured-output success metadata, structured-output error details, and retry diagnostics.
  • src/scherzo/workflow_structured_retry.gleam, which builds concise retry prompts after retryable structured-output failures.
  • docs/specs/STRUCTURED_OUTPUT_VALIDATOR_SPEC.md, which describes the structured-output validator contract.
  • docs/GETTING_STARTED.md, which introduces structured-output workflow authoring.
  • test/workflow_dag_validator_parser_test.gleam, test/structured_output_json_schema_test.gleam, test/structured_output_test.gleam, and workflow fixtures under test/fixtures/workflows/, which are the starting point for conformance tests.

The term baseline admission means Scherzo-owned checks that run before validators: required or optional presence, truncation, JSON parsing, top-level object requirement, and configured top-level required keys. The term payload rejection means the agent produced JSON but it did not satisfy a valid validator. Payload rejections may retry the agent when the output is required and retry budget remains. The term configuration failure means Scherzo or the workflow cannot run validation correctly; configuration failures do not retry the agent.

Preconditions and Verified Facts

The authoring pass verified these facts against the current tree:

src/scherzo/workflow_dag.gleam has StructuredOutputValidator variants for JsonSchemaValidator(name, path, draft) and CommandValidator(name, argv, timeout_ms, working_directory, env). It lowers parser results into runtime validator variants, defaults validation_retries to 1, accepts only 0 or 1, rejects structured_output on command steps, and defaults the source to final response through structured_output_source.parse.

src/scherzo/workflow_dag_validator_parser.gleam accepts validators as a list, rejects ambiguous use of legacy validator with validators, assigns generated validator names such as validator_1, requires unique validator names, parses type: json_schema with a repository-relative path and optional draft, and parses type: command with argv, timeout_ms, working_directory, and env.

src/scherzo/structured_output.gleam dispatches JSON Schema validators to structured_output_json_schema.run_json_schema_validator and command validators to structured_output_command_validator.run_command_validator. The same dispatch is reached after final-response and Pi-tool-call source extraction.

src/scherzo/structured_output_json_schema.gleam treats an omitted draft as "2020-12", rejects unsupported drafts as structured_output_json_schema_config_error, rejects non-repository-relative schema paths, invokes python3 scripts/scherzo-json-schema-validate from the repository root, maps helper exit status 1 to retryable structured_output_json_schema_rejected, maps other helper errors to non-retryable structured_output_json_schema_config_error, redacts messages, and truncates diagnostic summaries.

scripts/scherzo-json-schema-validate uses Python's jsonschema.Draft202012Validator, checks the schema document before validating payload input from stdin, emits one compact JSON diagnostic line, exits 0 for accepted payloads, exits 1 for schema payload rejections, and exits 2 for configuration or helper errors.

src/scherzo/structured_output_metadata.gleam records JSON Schema validator metadata with name, status, schema path, schema SHA-256, and draft. It records command validator metadata separately with argv, argv hash, timeout, working directory, and environment keys.

src/scherzo/workflow_fingerprint.gleam includes structured-output validators in the canonical workflow JSON. For JSON Schema validators it includes name, type, path, effective draft, and, when the execution fingerprint has a schema root, a SHA-256 hash of the schema file contents.

src/scherzo/state/artifact_store.gleam writes structured-output artifacts with the payload, validation metadata, schema required keys, artifact name, format, workflow id, run id, step id, and attempt index. src/scherzo/step_artifact.gleam exposes structured-output success metadata and error details in retained step artifacts.

test/workflow_dag_validator_parser_test.gleam covers mixed JSON Schema and command validator parsing, default names, invalid declarations, and legacy review-validator lowering. test/structured_output_json_schema_test.gleam covers valid payload acceptance, invalid payload rejection with an instance path, missing schema file as non-retryable config error, invalid schema as non-retryable config error, and absolute or traversal schema paths. docs/GETTING_STARTED.md already includes workflow-author examples using type: json_schema.

devenv.nix already provides the source-checkout Python dependency as (pkgs.python3.withPackages (ps: [ ps.jsonschema ])). Do not replace that with an ad hoc requirements.txt; keep the repository-managed devenv path as the way source-checkout developers run helper checks.

nix/scherzo.nix is the release packaging surface that must change. It currently accepts a python3 package argument, defines the main runtimePath with erlang and coreutils, installs several scripts under $out/libexec/${pname}, wraps $out/bin/scherzo, and runs installCheckPhase with a sanitized PATH. It does not currently install scripts/scherzo-json-schema-validate, does not put a Python interpreter with jsonschema on the main scherzo runtime path, and does not run an install check that exercises JSON Schema validation.

Scope Boundaries

In scope

  • A stable YAML API for JSON Schema validators under structured_output.validators.
  • Built-in local validation using Scherzo-owned code, not a workflow-provided executable, for JSON Schema shape validation.
  • Draft 2020-12 support with an omitted draft defaulting to draft 2020-12.
  • Repository-relative schema path confinement at parse time and runtime, including rejection of symlink escapes after canonical path resolution.
  • Retry classification for schema payload rejection versus configuration/schema/helper failures.
  • Redacted and bounded diagnostics, retained structured-output artifacts, metadata, and workflow fingerprints.
  • Compatibility with source.type: final_response and source.type: pi_tool_call.
  • Command validators retained and documented for semantic checks.
  • Packaging and dependency hardening for the helper or replacement validator implementation in both devenv.nix and nix/scherzo.nix, including an installed-artifact validation path.
  • Documentation and examples for workflow authors.
  • A migration guide from command-based JSON Schema shape validation to built-in JSON Schema validators.

Out of scope

  • Converting every existing workflow to JSON Schema validators.
  • Removing command validators or removing the legacy singular validator compatibility path.
  • Making provider/model-native schema enforcement required.
  • Adding drafts beyond 2020-12 unless the implementation discovers that the current library requires a small compatibility adjustment.
  • Sandboxing command validators beyond the existing command-validator contract.

Milestones

Milestone 1 audits and normalizes the current contract. At the end, the parser, runtime types, and structured-output pipeline agree on the target YAML API, and any drift from this plan is documented in the Decision Log before deeper work proceeds. This milestone comes first because most of the feature already exists, and the safest implementation is to close specific gaps rather than duplicate working infrastructure.

Milestone 2 hardens the built-in JSON Schema runner and dependency story. At the end, Scherzo can run draft 2020-12 validation locally through a Scherzo-owned mechanism in both source-checkout and installed-package modes. devenv.nix remains the developer dependency source, nix/scherzo.nix installs the helper under $out/libexec/${pname}/, the installed wrapper points SCHERZO_JSON_SCHEMA_HELPER at that helper, and package install checks exercise JSON Schema validation with a sanitized PATH. This milestone retires the largest operational risk before metadata and documentation work proceeds.

Milestone 3 completes metadata, artifact, fingerprint, and retry behavior. At the end, retained artifacts and workflow fingerprints prove which schema and draft were used, JSON Schema rejection spends the structured-output retry budget when appropriate, and configuration failures do not retry. This milestone makes validation auditable and safe.

Milestone 4 extends conformance tests across parser, runtime, both sources, helper behavior, artifacts, and workflow fixtures. At the end, a later refactor cannot accidentally turn JSON Schema back into a user command hook or lose error classification. This milestone is intentionally broad because the value of first-class validation is mostly in integration behavior.

Milestone 5 updates documentation and migration guidance. At the end, workflow authors can copy a minimal JSON Schema declaration, understand when to keep command validators, know how to store schema files, and migrate command-based shape validators without changing semantic validators.

Plan of Work

In src/scherzo/workflow_dag.gleam, keep JsonSchemaValidator and CommandValidator as separate variants. Ensure structured_output_validator_type_to_string returns exactly "json_schema" and "command", because this string appears in diagnostics, metadata, retry prompts, and artifacts. Ensure read_structured_validators preserves validator order from YAML.

In src/scherzo/workflow_dag_validator_parser.gleam, make type: json_schema require path and accept optional draft. Keep path validation local: the path must be non-empty, must not be absolute, and must not contain parent-directory traversal. If the current parser accepts unsupported drafts and the runtime rejects them, either keep that behavior and document the runtime configuration failure, or tighten parsing to reject unsupported drafts during workflow load. The preferred final contract is that an unsupported draft never becomes a retryable agent failure.

In src/scherzo/structured_output.gleam, keep JSON Schema dispatch inside default_validator_runner. The runner signature should continue to receive the parsed raw json_value.JsonValue, a redacted JSON string, and validator context. JSON Schema may validate the raw value because Scherzo owns the implementation and diagnostics must not echo the payload. Command validators must receive the redacted JSON string on stdin.

In src/scherzo/structured_output_json_schema.gleam, make the validator runner the single production entry point for JSON Schema validation. It should compute the effective draft, reject unsupported drafts as structured_output_json_schema_config_error with retryable: False, reject string-level schema path escape attempts before starting any helper, then resolve the repository root and candidate schema path to canonical paths and reject any resolved schema path that is outside the resolved repository root. Invoke the helper as an executable path, not as python3 scripts/... under the workflow repository. Resolve that executable path by first reading SCHERZO_JSON_SCHEMA_HELPER; when the variable is absent, fall back only to the source-checkout helper scripts/scherzo-json-schema-validate for development runs. Keep the helper process working directory as context.repository_root so schema paths are interpreted relative to the workflow repository. Map results as follows: accepted payload returns ValidatorPass; schema mismatch returns ValidatorFailure with code structured_output_json_schema_rejected and retryable: True; missing schema, unreadable schema, invalid schema, symlink escape, helper import failure, helper start failure, helper timeout, helper malformed output, or unsupported draft returns ValidatorFailure with code structured_output_json_schema_config_error and retryable: False.

In scripts/scherzo-json-schema-validate, keep the helper small and deterministic if the project continues using a helper. It should be executable, read payload JSON from stdin, read the schema file from the repository-relative path supplied by Scherzo, support only draft 2020-12, run Draft202012Validator.check_schema before validating payloads, and emit exactly one compact JSON diagnostic line. Do not make workflow YAML point at this helper; Scherzo invokes it internally. If implementation replaces the helper with an in-process validator, keep the same external Scherzo semantics, preserve the installed-package validation requirement, and update this plan's Decision Log before deleting the helper.

In devenv.nix, keep the existing (pkgs.python3.withPackages (ps: [ ps.jsonschema ])) developer dependency and do not add a parallel Python dependency file. In nix/scherzo.nix, define a Python package value with jsonschema, include that package in the runtime available to the installed scherzo wrapper, install scripts/scherzo-json-schema-validate to $out/libexec/${pname}/scherzo-json-schema-validate, run patchShebangs on it, and add --set-default SCHERZO_JSON_SCHEMA_HELPER "$out/libexec/${pname}/scherzo-json-schema-validate" to the scherzo wrapper. Extend installCheckPhase so a package build fails if the installed binary cannot perform JSON Schema validation with a sanitized PATH.

In src/scherzo/structured_output_metadata.gleam, preserve JSON Schema metadata fields: validator name, type, status, schema path, schema SHA-256, and effective draft. Schema hash should be empty only when the schema cannot be read, which should also be a non-retryable validation configuration failure during execution. Command validator metadata must remain separate and should not be used for JSON Schema validators.

Testing and Falsifiability

Parser tests must prove that the target YAML API is accepted and unsafe declarations are rejected. The accepted test should parse a workflow with validators containing a JSON Schema validator followed by a command validator and assert the exact runtime variants in order. Negative tests should cover missing type, unknown type, missing JSON Schema path, blank path, traversal path, absolute path generated during the test, non-string draft, duplicate names, invalid command argv, invalid command env, and simultaneous legacy validator plus generic validators.

Runtime JSON Schema tests must prove the exact error split. A valid payload against test/fixtures/structured_output/review_lane_draft.schema.json must return ValidatorPass. An invalid payload must return structured_output_json_schema_rejected, set retryable to True, include the validator name and type, and include a concise instance path. A missing schema file, invalid schema document, unsupported draft, symlink escape, helper start failure, helper timeout, malformed helper diagnostic, and import failure must each return structured_output_json_schema_config_error with retryable set to False. Redaction tests should pass a known secret in a schema error context and assert that the secret does not appear in message or diagnostic_summary.

Helper failure tests must use a deterministic seam rather than ad hoc sleeps or environment accidents. The seam is SCHERZO_JSON_SCHEMA_HELPER. Each test that changes it must save the previous value, set it only for the test, and restore it during cleanup. Fixture helpers under test/fixtures/structured_output/ should simulate malformed output, timeout, and import failure; a generated nonexistent helper path should simulate helper start failure. The timeout test should use the shortest timeout value the runner accepts and should not rely on a long process sleep.

Path-confinement tests must prove both string-level and resolved-path policy. Parser tests reject blank, absolute, and traversal paths. Runtime tests reject a dynamically generated absolute path before helper execution and reject a repository-relative symlink whose target resolves outside the repository. A symlink whose target resolves inside the repository may be accepted if the schema is otherwise valid.

Source compatibility tests must prove that JSON Schema validation is source-independent. One test should validate a final response whose trimmed body is exactly a JSON object. Another should validate a pi_tool_call source whose successful tool-call arguments are the JSON object. Both should run the same JSON Schema validator after baseline admission. Negative Pi tool-call tests should continue to prove missing, wrong-name, failed, duplicate, malformed, non-object, and sibling calls fail before validators.

Retry tests must prove falsifiability of the claim that JSON Schema mismatch is an agent-correctable problem. With required: true and validation_retries: 1, a schema mismatch should produce retryable structured-output failure and a retry prompt that includes the failure code and validator identity but not the full payload. With a missing schema file, symlink escape, helper failure, or unsupported draft, no retry should be attempted. With required: false and absent output, validators should not run and no artifact should be persisted.

Artifact and metadata tests must prove auditability. A successful structured-output artifact should contain the structured payload, baseline required keys, validator summaries, source type, optional source tool name, schema path, schema SHA-256, and draft. A failed step artifact should contain stable structured-output error details but should not persist full invalid payload text in diagnostics. A fingerprint test should modify a fixture schema file and prove that the execution fingerprint changes.

Manual helper checks must prove source-checkout behavior. Running this command with valid payload on stdin must produce an accepted diagnostic:

direnv exec . scripts/scherzo-json-schema-validate --schema test/fixtures/structured_output/review_lane_draft.schema.json --draft 2020-12 < test/fixtures/structured_output/review_lane_payload_valid.json

Running the same helper with invalid payload must exit 1 and produce a rejected diagnostic. Running it with an unsupported draft must exit with a configuration-error diagnostic.

Package validation must prove installed behavior. The nix/scherzo.nix install check must run with PATH= or a non-path sentinel and must exercise JSON Schema validation through the installed scherzo artifact, not through the source checkout helper path. The package check is falsified if removing the installed SCHERZO_JSON_SCHEMA_HELPER wrapper default, omitting jsonschema from the packaged Python runtime, or failing to install the helper still lets the package build pass.

Rollout, Recovery, and Idempotence

This change should be additive. Existing command validators continue to work. Existing workflows that use the legacy singular validator field continue to parse through the compatibility path until a separate deprecation and migration issue removes it. Existing workflows that already use type: json_schema should keep the same declaration shape unless a test exposes a contract mismatch that must be fixed.

Rollback is straightforward if the change causes operational problems: keep command validators available, revert only the JSON Schema runner/parser/package/docs commits, and workflows can fall back to command validators for shape validation. The package changes are additive: removing the SCHERZO_JSON_SCHEMA_HELPER wrapper default and helper install returns installed Scherzo to its previous state, while command validators remain available. Do not delete existing command validator support. Do not migrate all workflows in this task, because that would make rollback harder and expand the blast radius.

The implementation steps are idempotent. Re-running parser tests, helper checks, Gleam tests, and lint gates should not mutate repository state except for intended test fixtures. Schema path checks must be deterministic and independent of the checkout location. Any test that needs an absolute path must generate it dynamically and must not write machine-specific absolute strings into tracked files.

Interfaces and Dependencies

Workflow YAML interface:

validators:
  - name: <stable_validator_name>
    type: json_schema
    path: <repository-relative-schema-path>
    draft: "2020-12"

The name field is optional and defaults to a stable generated name such as validator_1. The path field is required, must be repository-relative, must be non-empty, and must not traverse to a parent directory. At runtime, the resolved schema path must remain inside the resolved repository root; a symlink that resolves outside the repository is rejected as a configuration error. The draft field is optional and defaults to "2020-12"; version 1 supports only "2020-12".
