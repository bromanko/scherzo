Package the no-op workspace driver for reusable distribution

Plan artifact: docs/plans/LIV-232-package-noop-workspace-driver-for-reusable-distribution.html 21 sections

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.

Purpose / Big Picture

After this change, a Scherzo operator who installs a packaged Scherzo release can configure an artifact-only workspace profile with driver.command: scherzo-workspace-noop and run workflows without copying scripts/scherzo-workspace-noop into their own repository. The visible proof is that the installed package contains a stable bin/scherzo-workspace-noop executable, Scherzo can discover it with describe --json, lifecycle operations can create and remove artifact workspaces through that command, and workflow command steps can call the advertised capabilities through SCHERZO_WORKSPACE_DRIVER.

The operator problem is packaging, not a new workspace model. The current checked driver already implements the artifact/no-op behavior Scherzo needs: it creates an empty workspace, tracks regular files as produced artifacts, and supports status, changed-files, and assert-only. This plan turns that checked driver into a reusable package surface, tightens its conformance against docs/specs/WORKSPACE_DRIVER_SPEC.md, and updates documentation so source-tree development and packaged deployment are both clear.

Problem Framing and Constraints

Today, public examples and runbooks point at repository-relative commands such as ../scripts/scherzo-workspace-noop. That is acceptable for this repository's checked examples, because examples/scherzo.yaml lives under examples/, but it is awkward for external users consuming a Scherzo package. A packaged user should not have to vendor a repo-local script or guess where a release placed it. They should be able to put the Scherzo package on PATH and configure a stable command name.

The normative behavior is not whatever the current script happens to do. The source of truth is docs/specs/WORKSPACE_DRIVER_SPEC.md. The implementation must conform to that spec for discovery, lifecycle operations, capability outputs, path safety, unsupported command handling, diagnostics, and machine-readable output. The package work must not loosen Scherzo's driver-command safety rules: driver.command remains one trusted executable token invoked as argv, not shell.

The work must preserve source-tree development usage. Developers running checked examples directly from a checkout still need a configuration path that works before Scherzo is installed. The checked scripts/scherzo-workspace-noop script should remain executable and usable from the source tree. Packaged deployment documentation should prefer command: scherzo-workspace-noop, while source-tree examples may keep config-relative script paths when that is what makes them runnable in place.

Strategy Overview

Use the existing scripts/scherzo-workspace-noop script as the canonical driver implementation and install it into the Scherzo package as bin/scherzo-workspace-noop. Keep the Python-in-shell implementation for this plan. The current driver is small, already tested, and independent of the BEAM runtime. Rewriting it in Gleam would make a simple artifact driver depend on Scherzo's Erlang shipment and would create an unnecessary second CLI entrypoint. Extracting the embedded Python into a package module would add structure without solving the operator problem. The proportionate change is to package the existing executable with the runtime dependency it already uses, then add conformance and package-level tests.

In the Nix package, install the checked script under libexec/scherzo/ or the existing package libexec directory, patch its shebang, and wrap it as $out/bin/scherzo-workspace-noop with a PATH that contains python3 and any basic tools it needs. The existing package currently exposes scherzo, scherzoctl, and scherzo-start; this plan adds the workspace driver as a peer executable without changing meta.mainProgram. Scherzo users get the command automatically when they install the package, and Scherzo's existing discovery and lifecycle code can invoke it because it is just a PATH-resolved executable name.

The test strategy has three layers. First, direct driver contract tests exercise scripts/scherzo-workspace-noop against the spec. Second, package install checks prove the Nix output contains an executable scherzo-workspace-noop that can run with a minimal environment. Third, Scherzo integration tests use driver.command: scherzo-workspace-noop through a PATH shim to prove discovery, lifecycle invocation, and workflow-step capability invocation work the same way they will in an installed deployment.

Alternatives Considered

The simplest alternative is to update docs to tell users to copy scripts/scherzo-workspace-noop into their repository. That preserves current behavior but does not solve the packaging problem in the Linear issue. It also leaves every external user responsible for script placement and Python availability.

A second alternative is to rewrite the driver in Gleam and call it through scherzo subcommands. That would eliminate Python as a runtime dependency, but it expands the driver from a standalone trusted executable into a BEAM-backed command whose startup, argument routing, and release packaging need separate design. It is larger than the problem demands and increases the blast radius of a small artifact-only driver.

A third alternative is to extract the embedded Python into a reusable Python module. That might help if the driver grows substantially, but the current file is a compact executable wrapper. Packaging a module would require extra install layout, import-path handling, and tests while still requiring Python. Keeping one executable source is simpler and easier to validate.

The chosen approach is to keep the current script implementation, make Nix provide its runtime dependency, install a stable bin wrapper, and make conformance tests the gate for future changes.

Risks and Countermeasures

The first risk is shipping an executable that works in the source tree but fails from the package because python3 is not on PATH. The countermeasure is to add python3 explicitly to nix/scherzo.nix, wrap bin/scherzo-workspace-noop with a driver-specific runtime path, and extend installCheckPhase to run scherzo-workspace-noop describe --json, lifecycle operations, and assert-only with a deliberately minimal inherited environment.

The second risk is advertising capabilities that are not actually conformant. The countermeasure is a dedicated conformance pass against docs/specs/WORKSPACE_DRIVER_SPEC.md before packaging is treated as done. Tests must prove that describe --json emits exactly one version 1 JSON object, that the capability list contains only status, changed-files, and assert-only, and that unsupported commands such as diff, baseline, refresh-base, and publish-change exit 2 with bounded diagnostics.

The third risk is destructive cleanup deleting the wrong directory. The countermeasure is to preserve and test the driver's current safety model: lifecycle commands require explicit SCHERZO_WORKSPACE_PATH, remove refuses empty targets and filesystem roots, remove refuses targets outside SCHERZO_RUN_ROOT when that variable is set, and artifact/no-op workspaces must contain the private marker written by lifecycle create before removal.

The fourth risk is documentation drift. Source-tree examples need repository-relative paths, while packaged examples need a PATH command. The countermeasure is to label those two deployment modes explicitly, add docs tests in test/workspace_driver_docs_test.gleam that search for both forms, and add the packaged example examples/scherzo-packaged-noop.yaml with command: scherzo-workspace-noop while leaving examples/scherzo.yaml as the source-tree example.

The fifth risk is an undiscovered non-Nix release channel. This plan is based on the checked packaging surfaces flake.nix and nix/scherzo.nix. The implementation includes an early packaging inventory step with exact searches. If another checked release path installs scherzo, scherzoctl, or scherzo-start, apply the same stable-bin and runtime-dependency treatment there before declaring the plan complete, or record the surface in this plan's Decision Log as intentionally out of scope with a rationale.

Context and Orientation

Scherzo is a Gleam application that runs workflow steps in workspaces. A workspace driver is a trusted local executable configured by an operator under workspace.profiles.<name>.driver.command. Scherzo discovers the driver's capabilities by running <driver> describe --json. If a workflow asks for workspace_capabilities, Scherzo validates those requirements against the discovered capability list before dispatch. During workflow execution, Scherzo exposes the selected driver command in SCHERZO_WORKSPACE_DRIVER so command steps can invoke capabilities portably.

The no-op workspace driver is for artifact-only workflows. It does not create a version-control checkout and does not compute diffs against a baseline. Instead, it creates an empty workspace and treats every regular file under the workspace root as a produced artifact, except private driver markers and Scherzo scratch or diagnostic directories. It is useful for workflows such as research, where the agent should produce exactly one file and a command step should assert that no extra files were left behind.

The normative driver contract is docs/specs/WORKSPACE_DRIVER_SPEC.md. Important terms from that spec are: a lifecycle operation is a command such as lifecycle create or lifecycle remove that prepares or deletes a workspace; a capability is a workflow-facing command such as changed-files --json or assert-only --path <relative-file>; and a workspace root is the directory whose relative files the driver reports. Machine-readable output must use workspace-root-relative paths, not local absolute paths.

The current source-tree driver is scripts/scherzo-workspace-noop. It is a /bin/sh wrapper that executes embedded Python 3. It uses the private marker .scherzo-workspace-driver-noop, prints compact JSON for describe --json and changed-files --json, and implements bounded human output for status --human. It uses SCHERZO_WORKSPACE_PATH for lifecycle targets and may fall back to the current directory for read-only capability commands when that environment variable is absent.

Scherzo's Nix packaging is in flake.nix and nix/scherzo.nix. The package currently builds the Gleam Erlang shipment and installs command wrappers for scherzo, scherzoctl, and scherzo-start. installCheckPhase verifies those commands with help and version checks. This plan adds the no-op driver as a packaged supporting executable.

The checked public example config is examples/scherzo.yaml. Because it lives in the examples/ directory, it currently reaches checked scripts with ../scripts/scherzo-workspace-jj and ../scripts/scherzo-workspace-noop. The research workflow in examples/workflows/research.yaml selects workspace_profile: noop, requires workspace_capabilities: [assert-only], resolves relative driver commands against SCHERZO_CONFIG_DIR, and calls assert-only --path research-findings.md before streaming the findings file.

Preconditions and Verified Facts

The implementation starts from a repository where docs/specs/WORKSPACE_DRIVER_SPEC.md exists and is the source of truth for workspace driver behavior. It defines version 1 JSON schemas, lifecycle command forms, capability command forms, exit-code categories, and safety invariants.

The file scripts/scherzo-workspace-noop exists and is executable in the source tree. It reports {"version":1,"capabilities":["status","changed-files","assert-only"]} from describe --json. It implements lifecycle create, lifecycle before-step, lifecycle after-step, lifecycle remove, status --human, changed-files --json, and assert-only --path <relative-file>. It intentionally does not advertise diff, baseline, refresh-base, or publish-change.

The file test/workspace_driver_contract_test.gleam already contains direct tests for the no-op driver. Existing coverage includes static describe --json, lifecycle create/before/after/remove, remove safety for unset or unmarked targets, sorted changed-files --json, deterministic status --human, JSON escaping for special path names, successful assert-only, extra-file rejection, and several unsafe path rejections.

The file src/scherzo/workspace_driver_discovery.gleam discovers driver capabilities by starting env -i with PATH when available plus SCHERZO_CONFIG_DIR, SCHERZO_REPO_ROOT, and SCHERZO_WORKSPACE_DRIVER, then running the configured command with describe --json. It validates version 1 descriptions and canonicalizes known capabilities.

The file src/scherzo/workspace_driver_lifecycle.gleam invokes lifecycle operations as argv through the resolved driver command, with lifecycle arguments such as lifecycle create, from the inferred repository root. It adds SCHERZO_WORKSPACE_DRIVER, SCHERZO_WORKSPACE_CAPABILITIES, and SCHERZO_REPO_ROOT to the lifecycle environment.

The file src/scherzo/workspace_driver_context.gleam exposes the selected driver command and discovered capabilities to workflow steps through SCHERZO_WORKSPACE_DRIVER and SCHERZO_WORKSPACE_CAPABILITIES.

The file nix/scherzo.nix currently has no python3 input and does not install scripts/scherzo-workspace-noop. Any packaged driver based on the current script must add Python as a runtime dependency in the wrapper or the installed command can fail in minimal package environments.

Scope Boundaries

In scopepackage and expose the no-op/artifact driver as scherzo-workspace-noop; preserve the checked scripts/scherzo-workspace-noop source-tree command; add or strengthen conformance tests against docs/specs/WORKSPACE_DRIVER_SPEC.md; update Nix install checks; update public docs and examples to show packaged deployment with command: scherzo-workspace-noop; and validate Scherzo discovery, lifecycle, and workflow-step capability invocation with the packaged command name.

In scope if discovered during the early inventory: any checked release packaging surface that installs scherzo, scherzoctl, or scherzo-start must also install scherzo-workspace-noop with its runtime dependency. The known checked release surface is nix/scherzo.nix. A surface is complete only when package validation proves the installed driver command runs without relying on ambient python3.

Out of scopechanging the workspace driver specification, adding new capabilities, changing the jj driver, replacing Scherzo's driver-command validation rules, adding shell evaluation of driver commands, publishing a hosted review, or changing production workflow semantics beyond using the installed command in packaged examples.

Out of scope for this plan: rewriting the driver in Gleam, extracting a Python package module, or making artifact/no-op workspaces support diff, baseline, refresh-base, or publish-change. Those are not needed to solve reusable distribution for the current artifact driver.

Testing and Falsifiability

The direct driver tests in test/workspace_driver_contract_test.gleam are the primary spec-conformance gate. They must prove describe --json is side-effect-free, does not require a workspace, exits 0, writes no stderr, and prints exactly one version 1 JSON object followed by one newline. The expected object is {"version":1,"capabilities":["status","changed-files","assert-only"]}. The test must fail if the driver advertises an unimplemented capability or emits extra stdout records.

Lifecycle tests must prove that lifecycle create creates the workspace directory and private marker, before-step and after-step verify the workspace exists, and remove deletes only marked workspaces. Negative lifecycle tests must cover missing SCHERZO_WORKSPACE_PATH, an empty path, an unmarked directory, an outside-run-root target, and a filesystem-root-shaped target constructed at runtime. Each rejected destructive operation must exit 2 and leave the target directory in place when a target directory exists.

Capability tests must prove that status --human is bounded, deterministic, and human-only; that changed-files --json emits exactly one version 1 JSON object; and that changed-file records are sorted by path, deduplicated by path, use workspace-root-relative paths, use / as the JSON path separator for normal nested files, and report status: "modified" for present artifact files. The fixture must include the private marker and a .scherzo directory so the test proves those are ignored.

assert-only --path <relative-file> tests must cover the success case where exactly research-findings.md is present, the failure case where an extra file is present, the failure case where the expected file is absent, and usage-error cases for empty paths, ., absolute local paths constructed at runtime, Windows-drive absolute forms, and .. path segments. Usage errors must exit 2 before filesystem inspection. Assertion failures for valid but unmet conditions must exit 1 and name only workspace-root-relative paths.

Unsupported command tests must run examples such as diff --json, baseline --json, refresh-base --stage test --json, publish-change --json, status --json, changed-files --human, and unknown commands. Each unsupported command or flag must exit 2 and print bounded diagnostics. The test should assert diagnostics contain the command name or usage text, do not exceed a small fixed limit, and do not include the test workspace's local absolute path.

Package tests must falsify the claim that the installed driver has all runtime dependencies. nix build .#scherzo and nix flake check must fail if python3 is missing from the installed wrapper's runtime path. installCheckPhase must run the installed scherzo-workspace-noop with a minimal inherited environment and exercise describe --json, lifecycle, changed-files --json, assert-only, and unsupported command behavior.

Rollout, Recovery, and Idempotence

This is an additive packaging and documentation change. Existing source-tree configs that use scripts/scherzo-workspace-noop or ../scripts/scherzo-workspace-noop continue to work. Existing packaged Scherzo commands keep their names. The new scherzo-workspace-noop executable is an additional package surface.

Rollback is straightforward because there is no stored data migration. To roll back before release, remove the scherzo-workspace-noop installation and install checks from nix/scherzo.nix, remove package-name integration tests and docs/example changes, and keep the existing source-tree script and tests. To roll back after release, operators can change driver.command back to a trusted source-tree or vendored script path while pinning to a package version that matches their config.

Lifecycle operations are designed to be idempotent for safe retries. lifecycle create may be repeated for the same workspace and should leave the marker in place. before-step and after-step are read-only checks. remove is intentionally conservative and may fail with exit 2 if the workspace is already gone or no marker is present; Scherzo cleanup should treat best-effort remove failures as diagnostics rather than permission to delete arbitrary directories.

During implementation, if package build fails because the wrapped driver cannot find Python, do not weaken the script by relying on ambient shell state. Fix the wrapper runtime path. If integration tests fail because PATH is not propagated to discovery or workflow steps, inspect Scherzo's existing environment construction and adjust the test setup or runtime environment deliberately; do not change driver.command to allow shell snippets.
