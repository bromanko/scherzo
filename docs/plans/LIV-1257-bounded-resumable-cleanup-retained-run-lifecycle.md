# LIV-1257 bounded resumable cleanup and retained-run lifecycle policy

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries, Decision Log, and Outcomes & Retrospective must be kept up to date as implementation proceeds.

## Purpose / Big Picture

Scherzo operators need cleanup that makes bounded progress by default without risking the recovery state kept in retained workspaces. After this plan is implemented, an operator or scheduled workflow can run `scripts/scherzoctl cleanup --root .scherzo/workspaces --json`, observe a default page of at most 100 cleanup items with `truncated`, `next_cursor`, `summary.scanned`, and `summary.applied`, and resume with `--cursor <next_cursor>` until cleanup is complete. An operator may pass `--limit <n>` to choose a different page size, but this plan does not add a `--max-runtime-ms` option. Retained `.scherzo-keep-workspace` runs will age out only when durable run and publication facts say they are safe, and jj workspaces will still be removed through workspace driver lifecycle hooks rather than raw directory deletion.

## Problem Framing and Constraints

The current provider-backed cleanup in `src/scherzo/cleanup.gleam`, `src/scherzo/cleanup/local_state.gleam`, and `src/scherzo/cleanup/workspaces.gleam` is safe but effectively all-or-nothing for a large workspace root. `scripts/scherzoctl cleanup --yes --json` can scan and apply every discovered item in one process, and `.scherzo/workflows/workspace-cleanup.yaml` runs that path inside a five-minute scheduled step. This can exceed operator and workflow budgets.

The design must remain conservative because cleanup can delete the only workspace evidence needed for retry, publication recovery, or manual salvage. It must keep dry-run as the default and require `--yes` for deletion, but it does not need to preserve today's unbounded no-option behavior or exact output shape. It must never mutate remote task or artifact stores from generic cleanup, and it must never bypass jj workspace remove hooks. Existing plain-text `.scherzo-keep-workspace` markers must continue to retain by default unless newer machine-readable marker and ledger facts prove release is safe.

## Strategy Overview

Add a default-bounded cleanup request model with a page size of 100, optional `--limit <n>` to override that page size, and optional `--cursor <cursor>` to resume. Direct `scherzoctl cleanup`, `scherzoctl cleanup --dry-run`, and `scherzoctl cleanup --yes` all use bounded execution, and scheduled cleanup uses the same default while persisting the returned cursor between runs. In `src/scherzo/cleanup.gleam`, introduce a request type that carries the mode, root, `now_ms`, page limit, and cursor. The current `inventory(workspace_root, now_ms)` and `apply(workspace_root, now_ms)` wrappers should either call the bounded default request or be replaced by the request API where tests and CLI call sites need explicit control; do not keep an unbounded compatibility path. Do not introduce `--max-runtime-ms` or a runtime-budget clock.

Cleanup uses a fixed provider order of `local_state`, `workspaces`, `artifact_store`, `task_store`, `provider_live`, `remote_provider_cache`, and `browser`. Only `local_state` and `workspaces` page destructive candidates in this plan. The other providers stay as unavailable boundary reports so generic cleanup cannot mutate remote task stores, artifact stores, provider-live state, remote-provider caches, or browser/UI state. Stable item keys are provider-local strings sorted lexicographically before pagination; workspace keys use the normalized run root, and local-state keys use the existing local artifact id followed by the display path. The opaque cursor format is `v1|<root-sha256>|<provider-id>|<escaped-last-item-key>`, where the root hash is derived from the normalized workspace root and the last item key uses simple percent escaping for `%`, `|`, and newlines. Consumers must treat this as opaque; wrong-root, malformed, unknown-provider, or unknown-version cursors fail closed.

The JSON contract is page-oriented. Core fields such as `mode`, `dry_run`, `providers`, item `status`, and summary counts should remain because they are useful to operators, but the no-option shape may change to include page metadata. Top-level fields include `truncated: Bool`, `next_cursor: String | null`, `cursor: String | null`, and `limit: Int`; summary fields include `scanned`, `applied`, and `truncated_reason`. `summary.truncated_reason` is `"limit"` when another page remains and `null` when cleanup reached the end. `summary.scanned` counts classified items emitted on the page. In apply mode, `summary.applied` counts items that passed the pre-item checkpoint and were revalidated for apply, including items that became retained during revalidation or failed during delegated removal; in dry-run mode it is zero. Text output keeps the provider sections and always includes a small page summary because every cleanup invocation is bounded.

Apply is always a fresh classification, not an authorization token from a prior dry run. If a candidate is deleted before a later page, it is absent and not an error. If a candidate becomes active, parked, publication-protected, or manually held before apply reaches it, apply reports it as retained. If a new item appears before the cursor key, it may be skipped by that resumed pass and will be found by a later cleanup started without a cursor; this is acceptable because cursors are progress markers, not snapshots. Cleanup stops before starting the next provider item once the configured page limit has been reached. Once a tombstone write, local delete, or workspace driver `lifecycle remove` begins, that item is allowed to finish under the existing operation and driver behavior, and the report explains the partial page.

Retained workspace lifecycle is evaluated before a marker blocks deletion. Active and scheduled-active runs are hard holds. Parked runs and publication-pending or required failed publication runs are hard holds until unparked, published, retried successfully, or abandoned. Interrupted or drifted runs are retained unless an explicit newer marker review state says `safe_to_delete` or `abandoned` and all hard holds are gone. Published, abandoned, or superseded obsolete runs with a newer publication-retention marker are eligible only after a conservative stale-marker age window, defaulting to thirty days; legacy markers without a recognized schema remain manual holds indefinitely. The dogfood helper keeps writing a plain text `.scherzo-keep-workspace` marker, but adds these exact schema lines before the human-readable source lines: `Schema: scherzo.retained-workspace.v1`, `Review state: publication_guard`, `Created at ms: <millis>`, `Source kind: <source-kind>`, and `Source: <source-ref>`. Older cleanup still sees a marker and retains, while the new parser can distinguish schema-backed publication guards from legacy human holds.

## Alternatives Considered

A simple `--limit` applied after collecting the full inventory was rejected because it would not bound scanning work on large roots. A `--max-runtime-ms` option was rejected as overrotating on the timeout concern; default item-count pagination and cursor resumption solve the large-cleanup problem without adding wall-clock heuristics or test-only clock injection. A persistent daemon cleanup job table was rejected as too large for this task; an opaque CLI cursor and scheduled cursor file solve resumption without a new service. Raw deletion of run roots was rejected because jj workspaces must be forgotten through their driver lifecycle before directories are removed. Immediate age-out of all `.scherzo-keep-workspace` markers was rejected because existing markers are human recovery holds with no machine-readable release intent.

## Risks and Countermeasures

The main risk is deleting useful recovery state. The countermeasure is a fail-closed lifecycle policy: active, parked, interrupted, drifted, pending-publication, retryable-failed-publication, and legacy/manual-review states retain unless durable facts and explicit review state release them. The second risk is cursor bugs that skip or duplicate destructive work. The countermeasure is stable ordering tests, root-fingerprint validation, idempotent apply tests, and apply-time revalidation. The third risk is that operators assume the first bounded page means cleanup is finished. The countermeasure is clear `truncated` and `next_cursor` reporting, text page summaries, scheduled cursor persistence, and runbook instructions to continue until `truncated` is false. The fourth risk is one slow destructive item inside a page. The countermeasure is to stop only before starting an item, keep the existing workspace driver timeout behavior, and report the item failure or partial page rather than adding a separate cleanup runtime budget.

## Scope Boundaries

In scope are default-bounded cleanup, `--limit`, and cursor handling in `src/scherzo/ctl.gleam` and `src/scherzo/ctl/command_registry.gleam`; cleanup request, cursor, report, and JSON changes in `src/scherzo/cleanup.gleam`; a small cursor helper such as `src/scherzo/cleanup/cursor.gleam`; provider pagination and counts in `src/scherzo/cleanup/local_state.gleam`, `src/scherzo/state/local_artifacts.gleam`, and `src/scherzo/cleanup/workspaces.gleam`; retained-marker parsing and policy for `.scherzo-keep-workspace` in `src/scherzo/cleanup/retention_marker.gleam`; dogfood marker-writing updates in `workflows/dogfood/scripts/scherzo-execplan`; scheduled cleanup cursor persistence in `.scherzo/workflows/workspace-cleanup.yaml`; tests under `test/`; and operator documentation in `docs/runbooks/workflow-recovery.md`.

Out of scope are remote artifact or tracker cleanup, browser or UI cleanup, provider-live mutation, remote-provider cache deletion, a wall-clock cleanup budget such as `--max-runtime-ms`, a new daemon background cleanup service, a new operator command for editing review markers, and changing workspace driver contracts beyond using the existing `lifecycle remove` path. The conservative defaults are dry-run by default, bounded direct and scheduled cleanup with default page size 100, thirty-day stale-marker age-out for recognized publication markers, and indefinite retention for legacy or manual-hold markers. The provider-live and remote-provider-cache rows must remain visible as unavailable providers so operators can see that these surfaces were intentionally not cleaned rather than silently ignored.

## Surprises & Discoveries

Current cleanup is already provider-shaped and safety-oriented, not a raw filesystem sweeper. Evidence: `src/scherzo/cleanup.gleam` coordinates `local_state`, `workspaces`, and explicit unavailable providers, while `src/scherzo/cleanup/workspaces.gleam` delegates eligible workspace deletion through `workspace_run.cleanup_run`.

The dogfood scheduled cleanup still invokes one all-or-nothing apply command. Evidence: `.scherzo/workflows/workspace-cleanup.yaml` currently ends with `run_scherzoctl cleanup --root "$workspace_root" --json --yes` under a `5m` step timeout.

The execplan dogfood helper writes plain-text `.scherzo-keep-workspace` markers before publication. Evidence: `workflows/dogfood/scripts/scherzo-execplan` writes `Source kind:` and `Source:` lines without a marker schema, so legacy marker handling must remain fail-closed.

The existing command registry already has shared `--limit` and `--cursor` option helpers, but their help text is task-list-specific. Evidence: `src/scherzo/ctl/command_registry.gleam` defines `limit_option()` as "Maximum task list items (daemon clamps to 100)." and `cursor_option()` as "Opaque cursor returned by task list.", so cleanup support must either generalize those helpers or introduce cleanup-specific option specs.

## Decision Log

- Decision: Direct cleanup remains dry-run by default, but no-option direct CLI cleanup is bounded to a default page size of 100. Rationale: PR review clarified that preserving the current unbounded behavior is unnecessary, and making bounded cleanup the default directly solves the large-root failure mode. Date: 2026-06-28.
- Decision: Do not add `--max-runtime-ms` or a cleanup runtime budget. Rationale: PR review identified that option as overrotating on the original failure; item-count pagination and cursor resumption are the proportionate fix. Date: 2026-06-28.
- Decision: Cursors are opaque, versioned, root-bound progress markers rather than inventory snapshots. Rationale: cleanup must revalidate mutable state and cannot safely promise snapshot isolation over filesystem and ledger changes. Date: 2026-06-27.
- Decision: Legacy `.scherzo-keep-workspace` markers are indefinite human holds. Rationale: current markers lack machine-readable release intent and may represent valuable recovery state. Date: 2026-06-27.
- Decision: jj workspace cleanup remains delegated through `workspace_run.cleanup_run` and workspace driver `lifecycle remove`. Rationale: the jj driver forgets workspaces before directory removal, while raw deletion can leave jj metadata behind. Date: 2026-06-27.
- Decision: Provider-live and remote-provider cache cleanup stay unavailable boundary providers in this plan. Rationale: these surfaces need explicit owning-provider semantics and live/cache-specific safety rules, while LIV-1257 is about local retained run lifecycle and bounded progress. Date: 2026-06-27.
- Decision: Pre-publish dogfood evidence is a deterministic temporary-root cleanup transcript, while a real live-daemon scheduled-cleanup observation is deferred to a human/operator post-implementation check. ## Rollout, Recovery, and Idempotence

Roll out additively. First land the default-bounded request parsing and report fields, then provider pagination, then retained-marker policy and helper marker-writing, then the scheduled workflow change. If a cursor is invalid after rollback or upgrade, cleanup must fail closed for direct operator commands and scheduled cleanup must clear its saved cursor and restart from the beginning on the next run rather than deleting from an untrusted position.

Partial cleanup is expected and safe. Every apply page reclassifies items, writes local tombstones before local-state deletion, delegates workspace removal, and reports failures without continuing inside a failed item. Repeating the same page after a crash may see missing files or directories; those outcomes must be reported idempotently and must not delete outside the configured workspace root. Provider-live and remote-provider-cache data are not touched, so rollback does not need to reconstruct external provider state.

Scheduled cleanup stores only the latest cursor at `$workspace_root/.scherzo-state/cleanup/scheduled/workspace-cleanup.cursor`. Removing that cursor is a safe recovery action that restarts the next scheduled run from the beginning. Rollback is safe because new marker lines are additive text and legacy cleanup treats the marker file as a hold. If the marker parser rejects a schema-backed marker, it must retain the workspace and emit a warning rather than guessing deletion eligibility.
