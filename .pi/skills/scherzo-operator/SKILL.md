# Scherzo Operator

Use this skill when the user wants pi to inspect or operate a running Scherzo daemon from this repository. Scherzo control is local to the daemon host and all real daemon actions must go through `scripts/scherzoctl` with machine-readable `--json` output whenever possible. When Linear needs to be read or updated, use the repository `linear` wrapper through `direnv exec .` before considering raw GraphQL.

See [the command reference](references/commands.md) for exact command shapes, response status meanings, artifact paths, and Linear CLI examples.

## Operating policy

Start read-only. Inspect the daemon with `scripts/scherzoctl ps --json`, then use `scripts/scherzoctl session <session-id> --json` and `scripts/scherzoctl events <session-id> --json` for detail. Prefer `events --json` for summaries instead of `attach` because `attach` follows live output by default and can keep a tool call open. Use `scripts/scherzoctl attach --json --no-follow <session-id>` only for bounded replay, or live `attach` only when the user explicitly asks to watch a stream.

Find the control file safely. If the user gives a path, pass it after the subcommand with `--control-file <path>`. Relative control-file paths are resolved from the directory where `scripts/scherzoctl` was invoked, even through a symlinked `scripts` directory. Otherwise honor `SCHERZO_CONTROL_FILE`. If neither is available and the repository default `.scherzo/workspaces/.scherzo-state/control.json` exists in the caller repository, use that path. Do not scan broad filesystem locations for control files. If the control file is missing, ask the user for the `control_server_started` log line or an explicit control file path.

Use command-first forms. The Scherzo subcommand comes immediately after `scripts/scherzoctl`, and options such as `--json`, `--control-file <path>`, and `--root <workspace-root>` come after that subcommand, for example `scripts/scherzoctl ps --json --control-file .scherzo/workspaces/.scherzo-state/control.json`. Inspect JSON `target.control_file_path` and `target.workspace_root` before mutating a daemon; never reveal the token.

Choose the right session. Top-level issue sessions are workflow run ids such as `ABC-123-1700000000000-1`; workflow step sessions start with `workflow-step-...` and include the step id and attempt. For `prompt`, `stop-after-turn`, `ui respond`, and `abort`, inspect `ps --json`/`session --json` and disambiguate whether the user means the top-level issue run or a concrete step session. A top-level prompt or stop can route to the active step only when Scherzo has exactly one active step command subject; a top-level abort stops the whole run and its step sessions.

Prefer step-level recovery before whole-task retry. When a workflow failed or was interrupted after producing retained upstream artifacts, inspect the top-level session, step-session events, and run artifacts to identify the failed/interrupted `run_id` and `step_id`. Use `scripts/scherzoctl retry-step <target> --json` to retry the selected step and its descendants while preserving completed upstream work. Target by issue identifier for the latest repairable run, by `id:<issue-id>` for a Linear issue id, or by `run:<run-id>` when multiple failed runs could match; add `--step <step-id>` when multiple failed/interrupted step boundaries exist or the user names a step. If `retry-step` is rejected because there is no repairable failed/interrupted run, the issue is active or parked, workflow/issue drift is detected, the selected step is not repairable, or upstream artifacts/workspace recovery fail, report that reason and only then consider whole-task `retry`.

Use inspected identifiers for operator controls such as `pause`, `resume`, `reload`, `retry`, `retry-step`, `park`, `unpark`, `abort`, `stop-after-turn`, `prompt`, and `ui respond`. Prefer salvaging retained workflow work with `retry-step` when only a failed or interrupted workflow DAG step needs repair; reserve whole-task `retry` for cases where step repair is unavailable, rejected, unsafe, or explicitly requested.

Never reveal secrets. The control file contains a `token`; never reveal token values or paste the raw control file. Never print `LINEAR_API_KEY`, `SCHERZO_AGENT_LINEAR_API_KEY`, or other API keys. Summarize raw JSON, event payloads, command artifacts, and Linear comments by default; redact sensitive issue or repository content; quote raw excerpts only when the user explicitly asks for them.

Inspect retained runs and artifacts conservatively. A `.scherzo-keep-workspace` marker means a workflow run directory is retained for operator recovery, usually until publish succeeds or a human decides what to do with unpushed work. Command-step failures appear in step-session events and may write `.scherzo/command-step-diagnostics/<step>.txt` plus durable artifacts under `.scherzo/workspaces/.scherzo-state/artifacts/runs/`. Treat all retained prompts, stdout/stderr, tool payloads, and Linear excerpts as sensitive. Use bounded reads and prefer `scripts/scherzoctl cleanup --json --dry-run` and `scripts/scherzoctl state status --root .scherzo/workspaces --json` before any local maintenance. For dangling jj workspaces, do not delete first; run the configured remove hook/forget path before removing retained run roots.

Use Linear CLI before raw GraphQL. The devenv provides the `linear` wrapper, which uses `LINEAR_API_KEY`, falls back to `SCHERZO_AGENT_LINEAR_API_KEY`, and applies `LINEAR_DEFAULT_PROJECT` as the default `--project` for `linear issue create` when omitted. Prefer commands such as `direnv exec . linear issue view <issue> --json`, `direnv exec . linear issue comment list <issue> --json`, `direnv exec . linear issue comment add <issue> --body-file <file>`, and `direnv exec . linear issue update <issue> --state <state>`. Do not add `--json` to `linear issue create` or `linear issue update`; current `linear-cli` v2 does not support it. Use `direnv exec . linear api ...` or direct `curl https://api.linear.app/graphql` only when the CLI lacks the needed operation, and keep tokens out of command output and logs.

Report outcomes clearly. For read-only commands, summarize active sessions, top-level versus step sessions, issues, workflow steps, current status, recovery status, last event age, blocking UI requests, and relevant artifact paths. For daemon controls, run the JSON command once, then report whether the protocol response had `ok: true` or `ok: false` and include the command result status such as `applied`, `queued`, `rejected`, `not_found`, or `not_allowed` without exposing secrets. For local cleanup/state or Linear mutations, summarize their command output without inventing a protocol status.
