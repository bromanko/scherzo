# Scherzo Operator

Use this skill when the user wants pi to inspect or operate Scherzo from this repository. Live daemon actions go through `scripts/scherzoctl` with `--json` whenever possible. Offline retained-state maintenance uses the top-level Scherzo CLI (`direnv exec . gleam run -- <offline-command>` in this development checkout, or packaged `scherzo <offline-command>` when available). When Linear needs to be read or updated, use the repository `linear` wrapper through `direnv exec .` before considering raw GraphQL. For creating or editing checked-in workflow definitions, workflow prompts, schemas, routes, or schedules, use `scherzo-workflow-author` instead.

See [the command reference](references/commands.md) for exact command shapes, response status meanings, artifact paths, and Linear CLI examples.

## Operating policy

Start read-only. Inspect the daemon with `scripts/scherzoctl ping --json`, `scripts/scherzoctl ps --json`, `scripts/scherzoctl query status --json`, and `scripts/scherzoctl query metrics --json` as appropriate, then use `scripts/scherzoctl session <session-id> --json` and `scripts/scherzoctl events <session-id> --json` for detail. Prefer `events --json` for summaries because `attach` follows live output by default. Use `scripts/scherzoctl attach --json --no-follow <session-id>` only for bounded replay, or live `attach` only when the user explicitly asks to watch a stream.

Find the control file safely. If the user gives a path, pass it after the subcommand with `--control-file <path>`. Relative control-file paths are resolved from the directory where `scripts/scherzoctl` was invoked, even through the wrapper. Otherwise honor `SCHERZO_CONTROL_FILE`. If neither is available and the repository default `.scherzo/workspaces/.scherzo-state/control.json` exists in the caller repository, use that path. Do not scan broad filesystem locations for control files. If the control file is missing, ask the user for the `control_server_started` log line or an explicit control file path.

Use command-first forms. The Scherzo subcommand comes immediately after `scripts/scherzoctl`; options such as `--json` and `--control-file <path>` come after that subcommand, for example `scripts/scherzoctl ps --json --control-file .scherzo/workspaces/.scherzo-state/control.json`. Inspect JSON `target.control_file_path` and `target.workspace_root` before mutating a daemon; never reveal the token.

Choose the right resource. Top-level issue sessions are workflow run ids such as `ABC-123-1700000000000-1`; workflow step sessions start with `workflow-step-...`. Recovery commands are now resource-first: task-level restart is `task retry`, retained-run repair is `run retry-step`, output recollection is `run recollect-outputs`, manual completion is `run finalize`, and publication replay is `publication retry`. Do not use legacy top-level `retry`, `retry-step`, or `recollect-outputs` spellings except when intentionally diagnosing compatibility.

Prefer retained-run recovery before fresh task restart. When a workflow failed or was interrupted after producing useful upstream artifacts, inspect the session, step events, `query operation-status` if an operation was queued, and retained artifacts to identify the failed/interrupted `run_id` and `step_id`. Use `scripts/scherzoctl run retry-step <run-id> --step <step-id> --json` to retry that step and downstream descendants while preserving completed upstream work. Use `scripts/scherzoctl run recollect-outputs <run-id> --json` when outputs need to be reconstructed without rerunning steps, `scripts/scherzoctl publication retry <run-id> --json` when already-materialized outputs need publication replay, and `scripts/scherzoctl run finalize ... --dry-run` before any manual finalization. Use `scripts/scherzoctl task retry <issue> --json` for a whole-task retry, and add `--start-fresh --reason <text>` only when intentionally starting a fresh run from the current task payload and workflow definition, such as workflow/issue drift recovery.

Use inspected identifiers for operator controls such as `pause`, `resume`, `reload`, `task retry`, `run retry-step`, `run recollect-outputs`, `run finalize`, `publication retry`, `park`, `unpark`, `abort`, `stop-after-turn`, `prompt`, `ui respond`, and `run-schedule`. For queued recovery commands, capture `operation_id` from the JSON response and poll `scripts/scherzoctl query operation-status <operation-id> --json` before declaring recovery complete.

Never reveal secrets. The control file contains a `token`; never reveal token values or paste the raw control file. Never print `LINEAR_API_KEY`, `SCHERZO_AGENT_LINEAR_API_KEY`, or other API keys. Summarize raw JSON, event payloads, command artifacts, and Linear comments by default; redact sensitive issue or repository content; quote raw excerpts only when the user explicitly asks for them.

Inspect retained runs and artifacts conservatively. A `.scherzo-keep-workspace` marker means a workflow run directory is retained for operator recovery, usually until publish succeeds or a human decides what to do with unpushed work. Command-step failures appear in step-session events and may write `.scherzo/command-step-diagnostics/<step>.txt` plus durable artifacts under `.scherzo/workspaces/.scherzo-state/artifacts/runs/`. Treat all retained prompts, stdout/stderr, tool payloads, and Linear excerpts as sensitive. For local maintenance, start with top-level offline dry runs such as `direnv exec . gleam run -- cleanup --root .scherzo/workspaces --json --dry-run` and `direnv exec . gleam run -- state status --root .scherzo/workspaces --json`. For dangling jj workspaces, do not delete first; run the configured remove hook/forget path before removing retained run roots.

Use Linear CLI before raw GraphQL. The devenv provides the `linear` wrapper, which uses `LINEAR_API_KEY`, falls back to `SCHERZO_AGENT_LINEAR_API_KEY`, and applies `LINEAR_DEFAULT_PROJECT` as the default `--project` for `linear issue create` when omitted. Prefer commands such as `direnv exec . linear issue view <issue> --json --no-download`, `direnv exec . linear issue comment list <issue> --json`, `direnv exec . linear issue comment add <issue> --body-file <file>`, and `direnv exec . linear issue update <issue> --state <state>`. Do not add `--json` to `linear issue create` or `linear issue update`; current `linear-cli` v2 does not support it. Use `direnv exec . linear api ...` or direct `curl https://api.linear.app/graphql` only when the CLI lacks the needed operation, and keep tokens out of command output and logs.

Report outcomes clearly. For read-only commands, summarize active sessions, top-level versus step sessions, issues, workflow steps, current status, recovery status, last event age, queued operation status, blocking UI requests, and relevant artifact paths. For daemon controls, run the JSON command once, then report whether the protocol response had `ok: true` or `ok: false` and include command result status such as `applied`, `queued`, `rejected`, `not_found`, or `not_allowed` without exposing secrets. For local cleanup/state or Linear mutations, summarize their command output without inventing a daemon protocol status.
